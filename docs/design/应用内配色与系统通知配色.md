# 应用内配色与系统通知的权威划分

本文说明「应用里白字、通知栏黑字」（或反过来）为什么会出现、这次把权威收敛到了哪里、
哪些东西是刻意不做的，以及真机上怎么快速判定。对应的实测输入见
[`docs/measurements/`](../measurements/) 里的现场记录与用户提交的
`DSH_THEME_COLOR_ISSUE_2026.txt`。

## 一、四层颜色，原本各由谁决定

| 层 | 决定因素 | 实现位置 |
| --- | --- | --- |
| 应用内文字 | `body[data-ds-dark-theme]` 在不在 | 官方 `dsh-client-ui-theme`，两套 `body{...}` |
| 应用底色 | 外壳注入的 `--dsh-theme-surface/background` | `harness-web/android.css` |
| 状态栏/系统栏 | 原生 `setAppearanceLightStatusBars` + `html.style.colorScheme` | `HarnessThemeBridge` / `AppThemePreference` |
| 系统通知卡片 | SystemUI 自绘（`?attr/textColorPrimary`） | Android 框架 |

错位的直接原因：**底色跟外壳、文字跟页面**，而页面那侧的开关有两个写入者
（页面自己的 `ThemePresenter` 与外壳的注入脚本），谁最后写谁算数。外壳只重绑了
`--dsw-alias-bg-*` 这类底色令牌，`--dsw-alias-label-*` 一次都没碰过，于是
「壳深色 + 页面浅色」就是黑字压深底。

第二个原因：页面在 `system` 偏好下用 `prefers-color-scheme` 解析深浅，而这个媒体查询
跟的是**宿主 Activity 的 `uiMode`**；SystemUI 跟的是手机的深色模式，两者本来就可以不同
（本应用允许外观与系统不同）。拿它当判据，「应用白字 / 通知黑字」是结构性结果。

## 二、修法：文字与底色同源

判据只有一个：**外壳实际铺在页面上的那块 surface**。

- `HarnessThemeBridge.pagePalette(surface)` 取 surface 的 WCAG 相对亮度，`> 0.179`
  用官方浅色调色板（黑字），否则用深色调色板（白字）。0.179 与 `src/theme.ts` 里
  `--on-blue` 的黑白判定同一口径（黑字/白字在这一点上对比度相等）。
- 注入脚本写 `html[data-dsh-theme-resolved='dark|light']`，并把三档文字色写进
  `--dsh-theme-label-primary|secondary|tertiary`。
- `android.css` 用 `html[data-dsh-theme-source='shell'][data-dsh-theme-resolved] body`
  （权重 0,2,2）把官方 `--dsw-alias-label-*` 重绑到那三个变量上，压过
  `body[data-ds-dark-theme]`（0,1,1）。页面再 apply 也翻不动这三档文字。
- `color-scheme` 同理，但它压在 html 的**内联样式**上：页面写的是
  `documentElement.style.colorScheme`，样式表规则永远输给内联样式。`android.css` 里的
  两条规则只管首帧（页面还没写内联值的时候），运行期由注入脚本对齐内联值——不用
  `!important`：`android.css` 的强制声明必须留在窄屏/粗指针查询里，桌面与平板要保持官方度量。
- `data-ds-dark-theme` 仍由外壳对齐（`MutationObserver`），但只在对不上时回写：
  官方其余上百个令牌（边框、代码块、提示气泡、滚动条）都挂在那个属性上，不把它拉齐，
  文字虽然可读、界面仍然是半深半浅。回写发生在页面写入之后的微任务里，绘制之前。

`system` 模式在这里**不查系统**：同步过来的 surface 是外壳在它自己解析出的明暗下算好的，
页面跟随它才不会与底色分家；手机之后切换深色也不该让页面文字单方面翻面。

## 三、注入时机与自愈

1. **document-start**（`androidx.webkit` 的 `addDocumentStartJavaScript`）：在页面任何脚本
   之前落地，首帧就是对的。provider 不支持时静默跳过，由 `onPageFinished` 的
   `apply()` 兜底。
2. **body 尚未解析**：脚本短轮询（50ms，最多 200 次）+ `DOMContentLoaded` / `load`
   + `documentElement` 的 `childList` observer；body 被重建（React 重挂、重载中途）
   也会补上，用户不必刷新。
3. **可重入**：同一文档再注入一次会先 `stop()` 上一份实例（断掉两处 observer 与监听器），
   不会留下两套逻辑互相对写。`data-dsh-theme-applied` 是给现场判定用的幂等标记。
4. **取消同步**：`clearHarnessTheme` 之后跑 `RESET_SCRIPT` 并撤掉 document-start 注册，
   否则下一次加载还会被旧脚本按旧主题重写。在**从没同步过**的页面上这段脚本零副作用
   ——它不会抹掉页面自己的内联 `color-scheme`。

## 四、刻意不做的

- **不给通知写死文字色**。通知卡片由 SystemUI 按它自己的深色模式绘制，应用写死
  `#FFF`/`#000` 必然在另一半系统主题下不可读。能对齐的只有强调色：前台服务通知用
  `setColor(用户强调色) + setColorized(false)`，文字继续交给系统。用强调色而不是面板
  底色，是因为面板常是近黑色，深色系统主题下那块底色等于看不见。
- **不改官方 `--dsw-alias-label-*` 的根值**。那是官方调色板，改了外置浏览器（没有外壳
  同步）里的页面会跟着错乱。外壳只在 `[data-dsh-theme-source='shell']` 下覆盖。
- **不动页面自己的主题插件**。同步期间由外壳覆盖是预期行为：底色本来就来自外壳，
  页面单独换一套只会得到半深半浅。取消同步后页面重新对自己的外观负责。
- **不打开 WebView 的算法加深**。页面自带两套完整调色板，再反相一次等于画蛇添足；
  而且它的判定发生在加载时、重载后重新判定，恰好会被看成「刷新前后方向相反」。

## 五、兼容矩阵

`android.css` 随运行时（rootfs）发布，`HarnessThemeBridge` 随 APK 发布，两侧可以不同步：

| 桥 / CSS | 行为 |
| --- | --- |
| 新 / 新 | 完整修复：文字、底色、`color-scheme` 同源，属性由外壳对齐 |
| 新 / 旧 | 与修复前一致（旧 CSS 不消费 `data-dsh-theme-resolved`），不引入新退化 |
| 旧 / 新 | 显式 light/dark 由 `:not([data-dsh-theme-resolved])` 的兜底规则接住；`system` 仍按页面自身解析——升级 APK 后收敛 |

`scripts/android-theme-contract.test.mjs` 会在两侧名字或色值对不上时先失败，并检查
`harness-web/dist/dsh-android.css` 是否已经重新构建（否则修复不会随运行时进设备）。

## 六、真机判定（30 秒）

在 WebView 里执行：

```js
const r = document.documentElement, b = document.body
console.table({
  'theme-source': r.getAttribute('data-dsh-theme-source'),
  'resolved': r.dataset.dshThemeResolved,
  'mode': r.dataset.dshTheme,
  'body 深色属性': b.hasAttribute('data-ds-dark-theme'),
  '文字令牌': getComputedStyle(b).getPropertyValue('--dsw-alias-label-primary').trim(),
  '底色令牌': getComputedStyle(b).getPropertyValue('--dsw-alias-bg-base').trim(),
})
```

判读：

- `resolved` 为空 → 桥没升级或注入没跑；`body 深色属性` 应与 `resolved` 同向
  （`dark` ⇔ 有属性），不同向说明有第三个写入者；
- `文字令牌` 应等于 `--dsh-theme-label-primary` 的取值（深色 `#f9fafb` / 浅色 `#0f1115`）；
  若等于官方两套根值里的另一套，说明 `android.css` 还是旧的；
- 通知卡片的深浅**不属于**回归项：它跟手机深色模式走，与外壳选择不同是预期。
