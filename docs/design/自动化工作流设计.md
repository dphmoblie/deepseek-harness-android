# 自动化工作流：录制、编译与回放设计

> **状态**：设计稿（2026-11-08），**未实现**。本文定义模型、接口、状态机、边界与测试计划，不含实现代码。
> **与旧设计的关系**：本文**替代/合并**当前的 `AutomationRule`、`AutomationTaskLedger`、`AccessibilityAppConfigStore` 设计，不是并列新增模块；迁移映射见 §3.3，迁移步骤见 §11.4。
> **范围**：用户在主屏示范一次操作 → 本地编译成工作流 → 可选 AI 编导 → 用户确认 → 原生确定性回放；AI 只在录制后审阅与卡住时（由用户交出、限步限时）补救。

## 0. 一句话

**工作流是自动化参数的唯一模型：用户示范一遍，系统编译成一份可读、可编辑、可校验的工作流；执行时由原生无障碍服务按同一份工作流确定性回放，正常路径不调用 AI。AI 只在两处出现：录制后的一次性编导建议，以及卡住时由用户交出、限步限时的补救。**

**这不是在现有规则旁边加一个模块，而是对现有自动化参数设计的替代与合并：**

| 现有 | 去向 |
| --- | --- |
| `AutomationRule`（单步事件规则） | 变成「带 `event` 触发器的单动作工作流」；字段逐一映射（§3.3） |
| `AutomationRuleStore` | 迁移源；迁移后由 `AutomationWorkflowStore` 接管（§11.4） |
| `AutomationRuleMatcher` / `AutomationRuleExecutor` | 触发匹配与四层节流抽成 `AutomationTriggerEngine`；动作执行并入工作流运行器 |
| `AutomationTaskLedger` | 变成「AI 计划式临时工作流」；逐步执行语义保留，台账文件与工具退役（§7.7） |
| `AccessibilityAppConfigStore` | 变成应用级自动化设置（暂停 + 新工作流默认值），文件复用、字段扩展 |
| `AccessibilityAutomationStore`（白名单/密码） | 不动，仍是授权边界 |
| `AutomationControl`（总开关） | 不动，仍是运行闸门 |
| 规则列表/规则表单 | 变成工作流列表 + 触发器面板；旧规则迁移后以工作流形式显示 |

> 迁移完成后**只保留一套执行路径**：事件触发器启动工作流运行，手动运行也走同一个运行器；规则执行器与任务台账不再有独立的动作执行链路。

## 1. 问题与目标

### 1.1 现状

- 现有自动化参数（`AutomationRule`、`AccessibilityAppConfigStore`）是**单步规则**模型：选择器 + 一个动作 + 次数/冷却/重置。用户能在界面上改规则参数，但**没有「录一遍」的入口**，也没有「一串有序动作」的模型。
- `AutomationTaskLedger` 有步骤状态、重试、目标过期等语义，但它是 **AI 下发计划、逐步提交** 的台账；动作仍由 AI 逐步发命令，不是本地回放。
- 因此当前闭环是「AI 观察 → AI 写参数/发动作 → AI 验证」，用户既难记录自己的操作，执行也依赖 AI。
- 本文因此不是「再加一个工作流模块」，而是把上述三块**合并成一套**：规则变成事件触发工作流，台账变成临时工作流，应用配置变成工作流默认值；旧执行路径迁移后退役。

### 1.2 目标

1. **可记录**：用户在主屏操作一遍，系统录下动作、目标、时序与前后界面，形成可读轨迹。
2. **可控制**：编译出的每个参数都可见、可改、可回退；AI 不能静默改参数。
3. **可独立运行**：AI 完全不在线时，录制 → 编译 → 回放仍能跑通。
4. **可验证**：每步有目标与期望；失败就暂停并给现场单，不猜、不盲目重试。
5. **AI 只做增强**：录制后一次性编导（可选）、卡住时补救（优先直接处置，其次改参数，最后中止）。
6. **为前后台留缝**：V1 只做主屏；模型与执行器留 `surface`，以后接副屏/虚拟显示。
7. **单套执行路径**：迁移后规则/台账/配置都走工作流模型，不再有并行的第二套动作执行链路。

### 1.3 非目标（V1）

- 不做循环（「滚动直到找到」）、并行、定时触发、应用启动触发。
- 不做副屏/后台 surface；只留字段与接口。
- 不做应用内自动调用模型；AI 交互走 Harness 对话 + 工具。**没有会话/消息 API 时，AI 接手必须由用户点一下启动**；启动后 AI 先试，预算耗尽再转人工（§8.6）。零点击自动接手不在 V1。
- 不自动开通自动化总开关；不放开白名单/敏感页/频率。
- 不保存密码、验证码、支付信息；输入内容默认不存字面量。
- 迁移完成后不再保留旧规则/旧台账的第二套执行路径；兼容别名只保留一个发布周期。

## 2. 术语

| 术语 | 含义 |
| --- | --- |
| 轨迹（trace） | 录制产生的事件序列与每步的节点/屏幕快照；只在本机。 |
| 工作流（workflow） | 节点 + 边的有向无环图；可执行、可编辑、可校验。 |
| 草稿（draft） | 本地编译器从轨迹生成的第一版工作流；不需要 AI。 |
| 编导计划（plan） | AI 对草稿提出的剪辑/标注/参数/guard 变更；不直接生效。 |
| 提案（proposal） | 计划编译后的候选 revision + diff；等待用户接受。 |
| revision | 工作流的一次冻结版本；运行只认一个 revision。 |
| 现场单（incident） | 运行暂停时的结构化事实：节点、失败码、路径、耗时、当前界面指纹。 |
| surface | 操作面：V1 只有 `main`（主屏前台）；以后可有 `display:<id>`。 |
| guard | 条件节点：按观察到的界面事实选择分支，不新增动作。 |

## 3. 总体架构

```text
用户操作（主屏）
  │  TYPE_VIEW_CLICKED / LONG_CLICKED / TEXT_CHANGED / SCROLLED / WINDOW_STATE_CHANGED
  ▼
录制器（服务内，纯状态机） ──► 轨迹 trace（本机）
                                  │
                                  ▼
                         本地编译器（纯逻辑）
                                  │
                                  ▼
                         草稿 workflow（可运行）
                                  │
                    ┌─────────────┴─────────────┐
                    │                           │
                    ▼                           ▼
             用户直接编辑                   AI 编导（可选）
                    │                    读轨迹 + 草稿 → 计划
                    │                           │
                    │                    编译成候选 revision + diff
                    │                           │
                    └─────────────┬─────────────┘
                                  ▼
                         用户确认 / 拒绝 / 回退
                                  ▼
                         冻结 revision（唯一可执行版本）
                                  ▼
                    原生运行器（无 AI）按图执行
                                  ▼
                     成功 / 暂停 + 现场单 / 中止
                                  │
                                  ▼
                    用户或 AI 决定：重试 / 跳过 / 改参数 / 中止
```

### 3.2 复用的现有能力

- 选择器字段与严格 JSON 解析：复用 `AutomationRule.kt` 的 `Selector` 与 `AutomationRuleLimits` 口径【码】。
- 选择器匹配：把 `AutomationRuleMatcher` 里私有的 `matches(selector, node)` 抽成共享的 `AutomationSelectorMatcher`，触发匹配与工作流共用【推】。抽取时保持逐字段语义不变。
- 动作后端：复用 `AutomationNodeBackend`（click / clickCenter / longClick / back / swipe / key / launch）与 `BackendOutcome`【码】`AutomationRuleExecutor.kt:509-567`；工作流动作类型覆盖现有规则动作的全部取值，迁移不丢动作。
- 文本写入：复用服务侧 `writeTextOnDisplay` / `injectTextOnDisplay` 的既定闸门与失败码【码】`DeepSeekAccessibilityService.kt:641-957`。
- 窗口指纹：复用 `AutomationWindowDigest`（不含文本、对结构敏感）【码】。
- 运行记录：复用 `AutomationRunHistory` 的环形缓冲思路，统一记录「触发器命中 + 工作流运行」；不把界面文本写进记录【码】`AutomationRunLog.kt`。
- 安全闸门：白名单 `AccessibilityAutomationStore.packageAllowed`、锁屏 `isLockedOrScreenOff`、敏感窗口 `containsSensitiveWindow`、频率 `ACTION_INTERVAL_MS`【码】。
- 总开关：沿用 `AutomationControlPolicy`（`off` / `running` / `paused`）【码】。录制不需要打开总开关；**触发器求值与运行都需要 `running`**。

### 3.3 与现有自动化参数设计的合并

**原则**：一套模型（工作流）、一套执行路径（运行器）、一次数据迁移。迁移后旧规则不再有独立的执行器；旧字段在迁移期只作为只读来源。

#### 3.3.1 规则 → 事件触发的工作流

| 旧字段 | 新位置 | 说明 |
| --- | --- | --- |
| `id` | 工作流 `id` / 节点 `id` | 迁移时生成 `wf-rule-<id>`；保留原 id 到 `legacyId` 便于排查 |
| `packageName` | 工作流 `packageName` | 必须过白名单 |
| `enabled` | 工作流 `enabled` | |
| `selectors` | `triggers[event].selectors` + 首个动作节点 `selectors` | 触发器用同一组选择器；动作节点也保留一份，`targetRef="trigger"` 时优先用触发节点 |
| `allowActivities` / `denyActivities` | `triggers[event].allowActivities` / `denyActivities` | 正则语义不变 |
| `matchDelayMs` | `triggers[event].matchDelayMs` | 0..5000 |
| `maxActions` | `triggers[event].maxRuns` | **语义变化见下** |
| `actionCoolDownMs` | `triggers[event].cooldownMs` | 两次运行之间的间隔 |
| `resetOn` | `triggers[event].resetOn` | `activity` / `screen` |
| `action` | 一个动作节点 | click/clickCenter/longClick/back/swipe/key/wait/launch 全部保留；launch 的 component/uri 约束不变 |

**语义变化（必须写进迁移说明）**：旧 `maxActions` 数的是「动作次数」，新 `maxRuns` 数的是「运行次数」。对迁移来的单动作工作流，两者等价；只有用户后来给事件触发工作流加了多步，才会出现「一次命中执行多步」的差异。V1 因此限制：**事件触发器只允许单动作工作流**（迁移规则天然满足；多步工作流只能手动运行）。这条限制消除了「一次事件触发一串动作」的意外风险，后续再评估放开。

#### 3.3.2 任务台账 → 临时工作流

| 旧 `AutomationTaskLedger` | 新 |
| --- | --- |
| `plan(taskId, packageName, digest, steps)` | 生成一个内存中的 `EphemeralWorkflow`（`source=ai`，不落盘），每个 step 一个动作/断言节点，`runMode=step` |
| `gate(stepId)` | `workflow_step`：执行当前节点一次；返回 accepted/refused |
| `record(stepId, outcome)` | 由运行器自己记录，不再需要调用方回填；兼容层把旧 `record` 映射为 no-op/确认 |
| `resume(stepIds, digest)` | `workflow_resume`（带 runId/nodeId） |
| `cancel()` / `status()` | `workflow_abort` / `workflow_status` |
| `unknown` / 不自动重试 / `TARGET_STALE` | 运行器暂停 + 对应现场码；语义保留 |

旧的 `automationTask` 命令保留一个发布周期作为兼容 shim：内部构造临时工作流并映射回执；新工具一律用 `automationWorkflow`。台账文件与 `AutomationTaskLedger.kt` 在 shim 期后删除，单测迁移到运行器/兼容测试。

| 旧 | 新 |
| --- | --- |
| `AccessibilityAppConfigStore.paused` | 应用级 `paused`：挡触发器求值、手动运行、AI 临时运行；不挡录制 |
| `defaultMaxActions` | `defaultMaxRuns`（新触发器默认） |
| `defaultActionCoolDownMs` | `defaultCooldownMs` |
| `defaultMatchDelayMs` | `defaultMatchDelayMs` |

#### 3.3.4 工具与界面

- AI 工具：`mobile_automation_*` / `automationRules` / `automationTask` 逐步换成 `mobile_workflow_*` / `automationWorkflow`；旧名保留一个发布周期，映射到新命令并标注 deprecated。
- 界面：规则列表 → 工作流列表；规则表单 → 「触发器 + 节点」编辑器；迁移来的规则显示「来自旧规则」徽标，可像普通工作流一样编辑/运行/加分支。
- 运行记录：旧「规则运行记录」与新「工作流运行记录」合并为一份 `RunLog`，条目带 `source=trigger|manual|ai`。

#### 3.3.5 迁移策略（细节见 §11.4）

1. 首次升级启动时读取旧规则与应用配置，在内存中转换并校验。
2. 全部转换成功才原子写入新存储；任一包转换失败则整体不提交，保留旧数据并显示「迁移未完成」，避免半迁移。
3. 旧偏好文件不删，保留一个发布周期供回滚/取证；新代码不再读它（除迁移器）。
4. 迁移幂等：`workflow_migration_version` 标记；重复启动不会重复导入。
5. 转换失败的单条规则进入 `legacy` 列表，界面提供导出 JSON 与删除；**绝不静默丢弃**。

## 4. 工作流模型

一个工作流 = 元数据 + **触发器** + 节点图。触发器决定「什么时候开始一次运行」，节点图决定「运行做什么」。

- 触发器至少一个：`manual`（用户点运行）或 `event`（界面事件命中，迁移规则用）。
- 一份工作流可以被多个触发器共用；同一时刻只允许一个运行。
- V1 限制：`event` 触发器只允许单动作工作流（迁移规则天然满足），防止一次事件触发一串动作。

### 4.1 图

- 单入口 `start`，至少一个 `end`；`pause` 可选。
- 有向无环图（DAG）；允许多条边汇合到同一节点（单 token，先到先继续）。
- 节点 id：`n1`..`n40`（`^[a-z][a-z0-9-]{0,15}$`，可用 `end-ok` 这类短横线名）；`pause` 节点固定 id `pause`（V1 只有一个）。
- 边按来源节点的字段名区分，不用独立边数组：`next`、`onSuccess`、`onFailure`、`onTrue`、`onFalse`、`onSkip`。这样 JSON 更短，校验器按节点类型检查必填边。

### 4.2 节点类型

| 类型 | 必填字段 | 可选字段 | 出边 |
| --- | --- | --- | --- |
| `start` | `packageName` | `activityName`、`launch`（布尔） | `next` |
| `action` | `action`；`selectors`（click/longClick/setText 必填；scroll 可选） | `value`、`targetRef`、`waitBeforeMs`、`timeoutMs`、`settleMs`、`retries`、`optional`、`risk`、`expect` | `onSuccess`、`onFailure`、`onSkip`（`optional=true` 时必填） |
| `condition` | `predicate` | `settleMs` | `onTrue`、`onFalse` |
| `assert` | `predicate` | `timeoutMs`、`settleMs` | `onSuccess`、`onFailure` |
| `end` | `result`（`success` / `failure` / `cancelled`） | `message` | 无 |
| `pause` | — | `reason` | 无 |

### 4.3 动作

`action.type` 取值：

| 类型 | 附加字段 | 语义 |
| --- | --- | --- |
| `click` | — | 点节点；不可点击时按「最近可点击祖先 → 中心坐标」降级，与规则执行器一致 |
| `clickCenter` | — | 直接点目标节点 bounds 中心（节点不在屏内 → 失败，不猜） |
| `longClick` | — | 长按节点 |
| `scroll` | `direction`（up/down/left/right） | 滚动；有选择器时滚目标容器，没有时从屏幕中心做一次 swipe |
| `swipe` | `direction`、`durationMs`（100..2000） | 全局滑动；迁移规则用 |
| `setText` | `value` | 写入聚焦的可编辑节点；走既有文本写入链 |
| `back` | — | 全局返回 |
| `key` | `keyCode`（允许表） | 受控按键；允许表与 `AutomationRule` 一致【码】`AutomationRule.kt:329-350` |
| `launch` | `component` / `uri` | 启动组件或链接；约束与 `AutomationRule` 一致（白名单包、http/https/market），仅迁移规则/手动工作流使用 |
| `wait` | `delayMs`（1..10000） | 只等待，不碰界面 |

> 动作类型必须覆盖现有规则的全部取值，否则迁移会丢动作。`launch` 不开放给录制生成的工作流（录制不会产生它），但迁移规则可以保留；事件触发工作流里出现 `launch` 时标 `risk=true`，并要求用户确认迁移。
>
> `targetRef="trigger"` 只对事件触发运行有效：优先点触发器命中的那个节点；节点已消失/过期时回退到节点自己的 `selectors` 重新查找。手动运行不允许 `targetRef="trigger"`（校验期拒绝）。

### 4.4 选择器

- 字段与 `Selector` 完全一致【码】`AutomationRule.kt:101-188`。
- 需要目标节点的动作（click / longClick / setText）配 1..16 个选择器，按顺序尝试；任一命中即用。列表语义是 OR。UI 默认只显示 3 条，迁移来的规则可保留 16 条。`scroll` 可选选择器；`back`/`wait` 不需要选择器。
- 录制默认只生成 1 个；AI/用户可加候选。
- 选择器字段之间 AND；空选择器拒绝。
- `id` 仍只接受全写 `包名:id/名称` 或短写 `:id/名称`；短写在跨包场景有歧义，录制默认写全写。

### 4.5 条件与断言

`predicate` 取值（V1）：

| 类型 | 字段 | 判定 |
| --- | --- | --- |
| `nodeExists` | `selectors` | 当前窗口里存在任一命中节点 |
| `textVisible` | `text` | 非可编辑节点的可见文本里存在精确相等或包含（`contains` 布尔） |
| `activityIs` | `activityName` | 当前前台 Activity 精确相等 |
| `packageIs` | `packageName` | 当前前台包名精确相等 |

- `condition` 是**立即**求值：看当前快照，选择 `onTrue`/`onFalse`；不等。
- `assert` 是**等待**求值：在 `timeoutMs` 内反复轮询，直到成立；超时走 `onFailure`。
- 两者都带 `settleMs`（默认 300ms）：谓词必须连续成立 `settleMs` 才认为稳定，避免动画/加载中误判。`activityIs`/`packageIs` 不做 settle。
- 谓词只读，不执行动作；不读输入框内容；密码/敏感页在求值前已由服务闸门拒绝。

**动作后的 `expect`**（与 `condition` 的谓词分开，因为它带「动作前」基线）：

| `expect.kind` | 字段 | 判定 |
| --- | --- | --- |
| `none` | — | 不验证（界面标「未验证」） |
| `screenChanged` | — | 当前结构指纹与动作前不同 |
| `nodeGone` | `selectors` | 动作前命中的目标节点不再存在 |
| `textAppears` | `text`、`contains` | 动作前没有、动作后出现该文本（非可编辑节点） |
| `activityChanged` | `activityName` | 当前前台 Activity 变为指定值 |

- `expect` 在 `timeoutMs` 内等待，并同样要求连续成立 `settleMs`。
- `screenChanged` 用结构指纹，不读文本；`textAppears` 只读非可编辑节点，密码/输入框内容不参与。

### 4.6 控制流语义

- **动作节点**：等待目标出现（`timeoutMs`）→ 执行动作 → 若配置 `expect`，在 `timeoutMs` 内等待期望成立 → 走 `onSuccess`；任何一步失败走 `onFailure`。
- **可选动作**：目标在 `timeoutMs` 内没出现 → 走 `onSkip`，不记失败；动作已执行但期望未达成 → 仍是失败（不能把「点了没效果」当跳过）。
- **条件节点**：立即求值 → 真/假。
- **断言节点**：等待谓词成立 → 成功/超时。
- **汇合**：多条边指向同一节点时，先到先继续；不等待其它分支，不做同步。
- **失败边**：默认指向 `pause`；用户可改到某个 `end`（例如「失败也停止」）或另一个动作节点（有风险，需确认）。
- **无环**：运行器不处理回边；校验器直接拒绝环。

### 4.7 校验规则（V1）

1. `entry` 必须指向一个 `start` 节点；有且只有一个 `start`。
2. 所有节点从 `start` 可达；不存在孤立节点。
3. 无环（DFS 三色标记）。
4. 每个节点的必填出边存在且目标存在；`action.optional=true` 时 `onSkip` 必填；`condition` 必须有 `onTrue` 与 `onFalse`。
5. 至少一个 `end`；`pause` 可有可无，但失败边默认指它。
6. 所有路径最终能到 `end` 或 `pause`（不允许死胡同）。
7. 节点数 ≤40，边数 ≤80，最长路径 ≤30。
8. 需要目标节点的动作（click / longClick / setText）必须有 1..16 个选择器，每个选择器非空；`scroll` 可有 0..16 个；`back`/`wait` 不允许带选择器。
9. `setText` 必须带 `value`；其它动作不带 `value`。
10. `scroll` 必须带 `direction`；`wait` 必须带 `delayMs` 且 1..10000。
11. `risk=true` 的节点 `retries` 必须为 0。
12. `surface` 必须是 `main`（V1）；非 main 整体拒绝。
13. 未知字段、类型不符、越界一律整体拒绝，不截断、不取默认值。
14. `condition`/`assert` 的 `predicate` 字段必须与 `kind` 配套：`nodeExists` 的 `selectors` 1..3；`textVisible` 的 `text` 非空；`activityIs`/`packageIs` 的值合法且非空。
15. `end.result` 只能是 `success` / `failure` / `cancelled`。
16. `triggers` 1..8 个；`manual` 无字段；`event` 的 `selectors` 1..16、`maxRuns` 1..99、`cooldownMs` 0..600000、`matchDelayMs` 0..5000、`resetOn` 二选一。
17. `event` 触发器只允许单动作工作流：恰好 1 个 `action` 节点，其余只能是 `start`/`end`/`pause`。
18. `targetRef` 只能是 `"trigger"`，且工作流必须至少有一个 `event` 触发器；手动运行的工作流不允许。
19. 动作字段必须与类型配套：`swipe` 带 `direction`+`durationMs`；`key` 带允许表内的 `keyCode`；`launch` 带 `component` 或 `uri`；`wait` 带 `delayMs`；其它动作不带这些字段。
20. `launch` 的包名必须过白名单/合法包名，`uri` 只允许 `http`/`https`/`market`；与 `AutomationRule` 同口径【码】`AutomationRule.kt:299-317`。

错误码统一 `AUTOMATION_WORKFLOW_INVALID`，消息里指出具体节点/字段。

### 4.9 触发器

`triggers` 是数组，至少 1 个、最多 8 个。V1 只有两种：

| 类型 | 字段 | 作用 |
| --- | --- | --- |
| `manual` | — | 用户点「运行」；录制生成的工作流默认只有这一种 |
| `event` | `eventTypes`、`selectors`、`allowActivities`、`denyActivities`、`matchDelayMs`、`cooldownMs`、`maxRuns`、`resetOn` | 界面事件命中后启动一次运行；迁移规则用 |

**`event` 字段**：

| 字段 | 范围 | 默认 | 说明 |
| --- | --- | --- | --- |
| `eventTypes` | `windowStateChanged` / `windowContentChanged` / `viewScrolled` 的子集 | 三者全开 | 与旧规则一致 |
| `selectors` | 1..16 | 必填 | OR；选择器字段之间 AND；空选择器拒绝 |
| `allowActivities` / `denyActivities` | 每项 ≤200，正则 | `[]` | 与旧规则同一语义；拿不到 Activity 时按旧口径拒绝带 Activity 过滤的触发器 |
| `matchDelayMs` | 0..5000 | 0 | 命中后延迟再确认 |
| `cooldownMs` | 0..600000 | 3000 | 两次**运行**之间的最小间隔 |
| `maxRuns` | 1..99 | 1 | 每个重置周期内最多启动几次**运行** |
| `resetOn` | `activity` / `screen` | `activity` | 重置 `maxRuns` 的周期 |

**求值顺序（先拒绝者胜）**：

1. 服务已连接、总开关 `running`、应用未暂停、未锁屏、非敏感窗口。
2. 事件包名 == 工作流包名且在白名单；系统界面/本应用事件忽略。
3. `eventTypes` 命中；Activity 允许/拒绝。
4. 选择器命中（任一）；`matchDelayMs` 到期。
5. 冷却未到 / `maxRuns` 用尽 / 同一窗口指纹已执行 → 拒绝并记录原因。
6. 已有运行在跑 → 拒绝 `AUTOMATION_WORKFLOW_BUSY`（单槽位）。
7. 启动运行；把命中节点作为 `triggerNode` 绑定。

**自触发保护**：运行器每次动作后记 `lastActionAt`；触发器在动作后 1 秒内忽略同包事件，避免「点一下 → 界面变化 → 又触发」的循环。触发器命中的窗口指纹在同一重置周期内只启动一次（与旧规则的指纹去重同义）。

**连续失败自动停用**：同一触发器连续 3 次运行以 `end.result=failure` 结束（不含 `paused`）→ 工作流 `enabled=false`，记录原因并在列表里显示。暂停不算失败，必须由用户/AI 处理。

**V1 限制**：`event` 触发器只允许单动作工作流（`nodes` 里恰好一个 `action` 节点 + `start` + `end`/`pause`），迁移规则天然满足。多步工作流只能 `manual` 运行；以后评估放开时要单独做「一次事件触发多步」的风险评审。

**`targetRef`**：事件触发的动作节点可写 `"targetRef": "trigger"`，优先用触发命中的节点；节点失效则回退到节点自己的选择器。手动运行的工作流不允许这个值（校验期拒绝）。

## 5. 录制

### 5.1 事件与快照

录制依赖无障碍事件。现有订阅只有 `TYPE_WINDOW_STATE_CHANGED | TYPE_WINDOW_CONTENT_CHANGED | TYPE_VIEW_SCROLLED`【码】`res/xml/accessibility_service_config.xml`、`DeepSeekAccessibilityService.kt`。录制需要额外事件：

| 事件 | 用途 | 备注 |
| --- | --- | --- |
| `TYPE_VIEW_CLICKED` | 用户点击 | `event.source` 是点击的 view |
| `TYPE_VIEW_LONG_CLICKED` | 长按 | 部分 ROM 不派发【验】 |
| `TYPE_VIEW_TEXT_CHANGED` | 输入 | 每字符一次；按节点合并 |
| `TYPE_VIEW_SCROLLED` | 滚动 | `getScrollDelta()` 方向 |
| `TYPE_WINDOW_STATE_CHANGED` | 界面切换 | 不产生步骤，产生屏幕标记 |
| `TYPE_WINDOW_CONTENT_CHANGED` | 内容变化 | 只做屏幕摘要刷新，不产生步骤 |

**事件类型的开启方式**：优先在录制开始时通过 `AccessibilityServiceInfo` + `setServiceInfo` 临时加上四类事件，停止后恢复 XML 里的三类；避免常驻增加事件量。若运行时切换在某些 ROM 上不生效【验】，退回「XML 常驻全部类型 + 录制外早退」。V1 实现按临时切换，真机验证后再定。

**每步快照**：

- 动作：`click` / `longClick` / `scroll` / `setText`。
- 目标节点：`viewId`、`className`、`text`、`contentDescription`、`bounds`、`clickable`、`editable`、`scrollable`、`password`。
- 屏幕：`packageName`、`activityName`（能取到时）、`windowId`、结构指纹（`AutomationWindowDigest`）。
- 时间：`eventTime`、与上一步的间隔。
- 屏幕摘要：最多 20 个可见标签（去重、≤40 字符、排除可编辑/密码节点），供编译与 AI 审阅使用。
- `displayId`：API 30+ 读取；V1 只接受 `0`（主屏），其它 display 的事件直接忽略。

**自己产生的事件**：录制期间禁止运行工作流/AI 动作；若 500ms 内刚有自动化动作，丢弃该事件。事件包名必须等于目标包名；排除 `android`、`com.android.systemui` 与本应用包名。

**取不到 source 时**：`event.source` 可能为 null。回退顺序：
1. `rootInActiveWindow` 按事件时间猜最近的可点击节点并不可靠，V1 不猜。
2. 直接丢弃该事件，并计入 `missingSource` 计数；编译时如果 missingSource 超过 30%，提示「这个界面录不了」。
不做坐标猜测，避免录出无法回放的点。

### 5.2 录制状态机

```text
IDLE
  → ARMING（设置事件类型，1.5s 倒计时）
  → RECORDING（接收事件；上限 5 分钟 / 200 原始事件 / 40 步）
  → STOPPING（恢复事件类型，冻结轨迹）
  → COMPILING（本地编译）
  → DRAFT_READY（草稿）
  ↘ FAILED（服务断开 / 目标包不在白名单 / 存储失败 / 事件不足）
```

- 开始条件：无障碍服务已连接、目标包已白名单、没有运行中的工作流、没有正在录制。
- 停止条件：用户点通知/悬浮球、返回本应用、5 分钟超时、服务断开、步数上限。
- 录制过程中不写盘；停止后把轨迹与草稿**一次性**落盘（轨迹可单独删除）。原始轨迹按需保留（供 AI 审阅/重编译），默认保留到用户删除流程。
- 录制期间总开关可以不是 `running`（录制是只读的）；运行才要求 `running`。

### 5.4 隐私级别

| 级别 | 给 AI 的内容 | 默认 |
| --- | --- | --- |
| `none` | 只有 viewId/class/动作/时序/结构；无任何文字 |  |
| `labels` | 被点节点的文字 + Activity + 最多 10 个屏幕标签 | ✔ |
| `full` | 所有屏幕摘要标签 |  |

- 发送前展示将发送的 JSON 预览；用户可逐项取消。
- 密码/验证码/支付窗口不采集（服务侧已拒绝）；输入框内容永不进轨迹。
- AI 返回的计划只存在本机；不把计划正文写进日志。

### 5.5 录制 UX

- 入口：设置 → 自动化 → 目标应用 → 「录制工作流」。
- 点击后 3 秒倒计时，提示「现在切到目标应用，按你要自动化的步骤操作一遍」。
- 录制中：常驻通知「正在录制 · N 步」+「停止」动作；已有悬浮球时可在球菜单加「停止录制」。
- 返回本应用或点停止 → 立即编译 → 打开工作流预览，显示步数、可选步骤、低置信步骤。
- 事件不足/丢 source 过多 → 明确提示，不生成「看起来能跑」的流程。

### 5.6 已知限制

- WebView / Flutter / 游戏可能不派发可用的 `TYPE_VIEW_CLICKED`；录到的步骤会很少【验】。
- 系统返回手势、音量键、通知栏操作不可见；用户可手动加 `back`/`wait` 节点。
- 动态文案（数字、日期、昵称）会让 `text` 选择器不稳定；编译标记低置信，建议改用 viewId。
- 录制期间用户切到别的应用：只记录目标包名的事件，其它包忽略；切回继续。
- 屏幕旋转：`bounds` 变化；优先 viewId/text，不依赖坐标。

## 6. 编译

### 6.1 本地编译（不需要 AI）

输入：轨迹 + 目标包名。输出：草稿工作流 + 警告列表。

步骤：

1. **合并原始事件**
   - 同节点 300ms 内重复 `click` 合并为一次。
   - 连续 `textChanged`（同节点、间隔 ≤2s）合并为一个 `setText` 步骤。
   - 连续同方向 `scroll`（间隔 ≤1s）合并为一个 `scroll`，记录次数到 `note`（V1 不循环，只执行一次）。
   - `WINDOW_STATE_CHANGED` 转为屏幕标记，不生成步骤。
2. **生成动作节点**（线性链）
   - 每个合并后的事件一个 `action` 节点。
   - 选择器按 6.2 生成。
   - `waitBeforeMs`、`timeoutMs` 按 6.3。
   - `expect` 按 6.4。
   - `optional`、`risk` 按 6.5。
3. **连接**
   - `start.next` → 第一个动作。
   - 每个动作 `onSuccess` → 下一个；最后一个 `onSuccess` → `end-ok`。
   - `onFailure` → `pause`。
   - 可选节点 `onSkip` → 下一个。
4. **命名**
   - `<应用名> · <首个有意义的被点文字>`；没有文字时 `<应用名> · MM-dd HH:mm`。
   - 应用名从 `InstalledApplications` 取；取不到用包名。
5. **标记**
   - `needsReview`：没有稳定选择器、文本疑似动态、事件间隔异常、丢 source。
   - `lowConfidence`：只有 className+bounds、或文本长度 >40、或含 4 位以上数字。
6. **输出**
   - `triggers=[{"type":"manual"}]`：录制只生成手动触发；事件触发器由用户在工作流详情里加（或迁移器生成）。
   - `traceHash`：对规范化轨迹做 SHA-256 前 16 位；规范化 = 事件顺序 + 类型 + 节点属性 + 动作 + 时间量化到 100ms + 屏幕摘要标签。用于 AI 计划绑定。
   - 警告列表：给界面显示，不阻止保存。

### 6.2 选择器合成

优先级：

1. `viewId` 非空且符合全写/短写规则 → `{ "id": "包名:id/名称" }`。
2. `text` 非空且不像动态文本 → `{ "text": "...", "className": "..." }`。
3. `desc` 非空 → `{ "desc": "...", "className": "..." }`。
4. 只有 class + bounds → `{ "className": "...", "minWidth": ..., "minHeight": ... }`；标红，要求用户确认后才能运行。
5. 都没有 → 不生成步骤，记 `unrecordable`，提示重录。

「像动态文本」启发式：长度 >40、含 4 位以上连续数字、含日期/时间模式、含 `%` 或货币符号。命中时优先 `textContains`（取前 12 个字符）并标低置信；不自动用 `textStartsWith`/`textEndsWith`。

### 6.3 时序

- `waitBeforeMs = clamp(上一步事件到本步事件的间隔, 0, 3000)`，按 50ms 取整。
- `timeoutMs = clamp(max(1500, 3 × 观察到的「动作→下一屏幕」延迟), 1500, 15000)`。
- `settleMs = 300`。
- 如果观察到的延迟缺失，`timeoutMs = defaults.timeoutMs`（5000）。

### 6.4 期望

按「动作后 2 秒内发生了什么」：

| 观察 | `expect` |
| --- | --- |
| 出现新的 `WINDOW_STATE_CHANGED` | `screenChanged` |
| 目标节点消失且界面变化 | `nodeGone`（带目标选择器） |
| 出现新的高置信文本 | `textAppears`（带文本） |
| 什么都没观察到 | `none` |

`none` 不阻止运行，但会在界面上标「未验证」。最终成功建议用户/AI 加一个 `assert` 节点。

### 6.5 可选与风险

**可选**（满足任一，标 `optional=true`，`onSkip` → 下一步）：

- 文字属于 {跳过, 关闭, 以后再说, 取消, 知道了, 我知道了, 允许, 暂不}。
- bounds 在屏幕顶部 25% 或底部 25%，且文字属于上述集合。
- 该步骤之后界面回到与之前相同的 `activity + digest`（弹窗关闭）。

**风险**（`risk=true`，`retries=0`）：

- 文字含 {支付, 确认支付, 付款, 转账, 发送, 提交, 删除, 卸载, 退出, 注销, 授权, 允许}。
- 文字含货币符号/金额模式。
- 风险步骤在运行前需要一次显式确认；V1 可在流程详情里勾选「本次运行跳过确认」，但不持久化。

> 可选/风险都是启发式，编译只给建议；用户可改，AI 可改（见 §7）。

### 6.6 AI 编导（2B）

**定位**：AI 只对录制素材做剪辑、标注、参数化与 guard；**不写选择器、不新增动作**（新增动作由 2A 开关控制）。

**输入**：轨迹（按 `sharingLevel` 脱敏）+ 本地草稿 + 校验器约束。

**输出**：编导计划（JSON），只含操作，不含完整工作流。

```json
{
  "schema": 1,
  "workflowId": "wf-5f2c1a9e",
  "baseRevision": 1,
  "traceHash": "8a1c0f2d7e4b9a63",
  "intent": {
    "name": "每日签到",
    "description": "打开签到页并领取每日奖励",
    "success": { "kind": "textVisible", "text": "签到成功", "evidence": { "step": 4, "label": "签到成功" } }
  },
  "operations": [
    { "op": "annotate", "step": 0, "optional": true, "reason": "开屏广告不一定出现" },
    { "op": "set_param", "step": 3, "timeoutMs": 8000, "reason": "实测切换耗时 4.2 秒" },
    { "op": "drop", "step": 7, "reason": "点击后界面无变化，疑似误点" },
    { "op": "guard", "beforeStep": 3, "predicate": { "kind": "textVisible", "text": "已签到" }, "onTrue": "end-skip", "reason": "已签到则跳过" }
  ]
}
```

**允许的操作（2B）**：

| op | 作用 | 约束 |
| --- | --- | --- |
| `annotate` | 改 `optional`/`risk` | 引用已录制步骤 |
| `set_param` | 改 `timeoutMs`/`retries`/`waitBeforeMs`/`settleMs` | 在范围内 |
| `set_expect` | 改期望 | 引用轨迹里出现过的文字/节点 |
| `drop` | 删除录制步骤 | 给原因；用户逐条确认 |
| `merge` | 合并相邻同类步骤 | 只允许相邻、同动作 |
| `set_name` / `set_description` | 改元数据 | 长度限制 |
| `set_success` | 设最终断言 | 必须引用轨迹里出现过的文字/节点 |
| `guard` | 在某个录制步骤前插入条件节点 | 谓词必须引用轨迹里出现过的文字/节点；`onTrue` 必填且只能指向已有节点或 `end`/`pause`；`onFalse` 固定指向原步骤 |

**2A 开关（默认关闭，实验功能）**：

- 开关粒度：每个工作流 `allowAiAddNodes=false`；只有用户在设置里显式打开「实验：允许 AI 新增动作节点」后，AI 才能提 `add_action`。
- `add_action` 必须引用轨迹里观察到的节点（`evidence.step`），动作类型只能是 click/longClick/scroll/setText/back/wait；不能是 launch；不能写坐标；`setText` 文本必须是参数（不能是 AI 编造的字面量）。
- 新增动作节点在 diff 里标「AI 新增」，默认不勾选，用户必须显式接受。
- 即使打开，AI 仍不能改包名、不能放宽安全闸门、不能开启总开关。

**拒绝条件**：

- `baseRevision` 或 `traceHash` 不匹配 → `AUTOMATION_WORKFLOW_REVISION_STALE`。
- 引用不存在的步骤/节点/标签 → `AUTOMATION_WORKFLOW_INVALID`。
- 计划应用后图不合法（环、不可达、缺边）→ 整体拒绝。
- 未知 op/字段、越界 → 整体拒绝。
- **计划不能新增/修改 `triggers`**：事件触发器意味着「以后自动运行」，只能由用户在工作流详情里显式编辑；AI 最多建议「可以加一个事件触发器」，但不能提交。

### 6.7 计划应用与差异

- 计划不直接改活动 revision；应用后生成**候选 revision**。
- 差异按节点/边/字段展开：新增、删除、修改；每项带 `reason`、`source`、`riskLevel`。
- 用户逐条接受/拒绝；只有被接受的操作参与编译。拒绝全部即保持原 revision。
- 应用成功后 `revision+1`，`review` 记录 `planId`、`acceptedAt`、`acceptedOps`；原始轨迹不变。
- 「撤销 AI 修改」= 切回上一 revision，不删除轨迹。

### 6.8 确定性

- 同一轨迹 + 同一用户编辑 → 同一工作流 JSON（节点 id 按顺序分配，无随机、无当前时间参与）。
- `traceHash` 覆盖轨迹的全部语义字段（事件类型、节点属性、动作、顺序、时间量化到 100ms、屏幕摘要标签），不覆盖录制时间/展示用 id。轨迹一旦冻结就不可变，因此同一 hash 一定对应同一份可审阅素材；AI 计划绑定 hash，避免「审的是 A、应用到了 B」。
- AI 计划不参与运行时；只在编译期使用。

## 7. 执行

### 7.1 运行状态机

```text
IDLE
  → PREPARE（总开关 running、白名单、锁屏/敏感窗口、前台包/Activity）
  → NODE（当前节点）
      action:
        WAIT_TARGET（轮询目标，timeout）
        ACT（执行动作）
        VERIFY（等待 expect，timeout）
      condition: EVAL（立即）
      assert: WAIT（轮询谓词，timeout）
      end: DONE
      pause: INCIDENT
  → 下一个节点 …
  → DONE / PAUSED / CANCELLED
```

- 单槽位：同一时刻只允许一个运行；录制与运行互斥。
- 暂停后的恢复状态：`PAUSED` →（L0 自动）→ `AI_RECOVERY`（有租约时）→ `NEEDS_HUMAN`（预算耗尽/超时/无进展/安全例外）。`NEEDS_HUMAN` 下 AI 的恢复/动作/补丁一律拒绝，只能由用户处理或显式重开租约。
- `start.launch=true` 时，运行前先按既有 `mobile_device_app_launch` 口径启动目标包，再等前台包/Activity 匹配；`false` 时要求目标应用已经在前台。启动失败 → `AUTOMATION_WORKFLOW_TARGET_LEFT`（不猜别的入口）。
- 运行由服务主线程 + `Handler` 驱动；等待用轮询/事件唤醒，不阻塞主线程。
- 每步动作前重新取窗口、重跑白名单/锁屏/敏感窗口/频率判定；不缓存上一节点的节点句柄。
- 总超时 `totalTimeoutMs`（默认 90s，最大 10min）；超时 → 暂停 + `AUTOMATION_WORKFLOW_TIMEOUT`。
- 运行记录：只记节点 id、动作类型、结果码、耗时；不记文本、viewId、坐标、输入内容。

### 7.2 条件、断言与汇合

- `condition` 求值使用当前快照；如果当前没有可读窗口 → 暂停 `AUTOMATION_WORKFLOW_TARGET_LEFT`，不猜。
- `assert` 轮询间隔 200ms；`settleMs` 用「连续成立」判定。
- 汇合点不等待：先到的分支继续；另一分支不会被执行（单 token）。
- 条件分支如果指向 `pause`，该 `pause` 的现场单会记录来自哪个节点。

### 7.3 闸门

顺序（先拒绝者胜）：

1. 总开关 `AutomationControlPolicy.admits(runtime)`；不是 `running` → 拒绝运行/暂停。
2. 白名单 `AccessibilityAutomationStore.packageAllowed`。
3. 锁屏/熄屏 `isLockedOrScreenOff`。
4. 敏感窗口 `containsSensitiveWindow`（fail-closed）。
5. 前台包/Activity 与 `start` 一致；不一致 → `TARGET_LEFT`。
6. 动作频率 `ACTION_INTERVAL_MS = 350L`（所有动作共用）。
7. 节点级 `risk` 确认（如果开启）。

所有拒绝都写审计：`ACCESSIBILITY_ACTION` + 受控 detail；**不写包名、viewId、文本、输入内容**。

### 7.4 失败与现场单

| 场景 | 码 | 行为 |
| --- | --- | --- |
| 目标在 timeout 内没出现 | `AUTOMATION_WORKFLOW_TARGET_MISSING` | 可选 → 跳过；否则暂停 |
| 动作执行了但期望未达成 | `AUTOMATION_WORKFLOW_NOT_VERIFIED` | 暂停（风险节点不重试） |
| 断言超时 | `AUTOMATION_WORKFLOW_ASSERT_TIMEOUT` | 暂停 |
| 前台换了应用 | `AUTOMATION_WORKFLOW_TARGET_LEFT` | 暂停 |
| 锁屏/敏感页 | 复用 `ACCESSIBILITY_DEVICE_LOCKED` / `ACCESSIBILITY_SENSITIVE_WINDOW` | 暂停/中止，不交给 AI 绕 |
| 频率限制 | `ACCESSIBILITY_RATE_LIMITED` | 等待后重试该步一次；这次尝试计入节点 `retries` |
| 总超时 | `AUTOMATION_WORKFLOW_TIMEOUT` | 暂停 |
| 用户中止 | `AUTOMATION_WORKFLOW_CANCELLED` | 结束 |

现场单字段：

```json
{
  "runId": "run-...",
  "workflowId": "wf-...",
  "revision": 2,
  "nodeId": "n4",
  "code": "AUTOMATION_WORKFLOW_NOT_VERIFIED",
  "message": "第 4 步发出去了，但没有观察到「签到成功」",
  "elapsedMs": 8234,
  "attempts": 1,
  "path": ["n1", "n2", "n3", "n4"],
  "facts": {
    "packageName": "com.example.app",
    "activityName": "com.example.app/.CheckinActivity",
    "windowDigest": "…",
    "locked": false,
    "sensitive": false
  },
  "candidates": []
}
```

`candidates` 只在用户允许共享时附带最多 10 个可见节点摘要；默认空。

### 7.5 恢复 / 跳过 / 中止

- **重试**：从当前节点重新执行；重新取目标，不拿旧节点；受 `retries` 限制。
- **跳过**：仅对 `optional` 节点或用户显式选择「跳过这一步」可用；跳到 `onSkip` 目标。跳过会记 `skipped`，不记成功。
- **恢复**：用户/AI 处理完卡点后，从当前节点重新开始；必须重新校验前台包/Activity/指纹；不重放已成功节点。AI 发起的恢复必须持有有效租约，并扣 1 op；`needs_human` 下 AI 不能恢复。
- **中止**：结束运行，状态 `cancelled`；已执行的动作不回滚（自动化没有事务）。
- 恢复必须带 `runId` + `nodeId` + `revision`；不匹配 → `AUTOMATION_WORKFLOW_RESUME_INVALID`。

**运行模式**（不要把它们混成「试运行」一个词）：

| 模式 | 行为 | 能验证什么 |
| --- | --- | --- |
| `validate` | 纯静态：图校验 + 选择器对轨迹节点的接地检查；不连设备 | 模型/图/计划是否合法；不能证明真机可跑 |
| `dryRun` | 连设备但不执行动作：校验 `start` 前置 + 当前屏第一个动作的目标是否存在，然后停在「将执行」 | 第一屏是否就绪；不能验证后续步骤 |
| `step` | 真正执行，但每步后暂停等用户确认「继续/跳过/中止」 | 全流程；适合风险流程与首次验收 |
| `run` | 连续执行到结束/暂停 | 全流程；适合已验收流程 |

> `dryRun` 不会连续推进：不执行动作，界面就不会变，所以它**只能**回答「第一屏是否匹配」。不要在文案里说成「预演整个流程」。

### 7.6 Surface 抽象

```kotlin
internal interface WorkflowSurface {
    fun packageName(): String?
    fun activityName(): String?
    fun snapshot(): AutomationNode?
    fun digest(): String
    fun find(selector: Selector): WorkflowTarget?
    fun perform(node: WorkflowTarget?, action: AutomationAction, value: String?): BackendOutcome
}
```

- V1 实现 `MainScreenSurface`：`rootInActiveWindow` + `AndroidAutomationNodeBackend`。
- 以后 `DisplaySurface(displayId)`：复用 `displayRootFor(displayId)`、`displayWindowRoot`、文本写入链；流程级 `surface` 或节点级覆盖。
- V1 校验器拒绝 `surface != "main"`，但 schema/runner 已经按接口写，不把主屏假设散落到节点逻辑里。

### 7.7 AI 计划式临时工作流（合并 `AutomationTaskLedger`）

旧的台账让 AI「提交计划 → 逐步 gate → 回填 record」，动作仍由 AI 一条条发命令。合并后改成**临时工作流**，由同一个运行器执行：

- AI 提交 `plan`（taskId、package、steps：动作/目标/校验/超时/重试）。
- 原生把它编译成内存里的 `EphemeralWorkflow`：
  - `source=ai`、`manual` 触发器、`runMode=step`、不落盘、不可被事件触发。
  - 每个 step → 一个 `action`/`assert` 节点；`verify` 映射成 `expect`；`onFailure` → `pause`。
  - 单入口、线性、无分支；最多 20 步（与旧台账一致）。
- 运行器一次只执行一个节点，然后停在「已执行，等确认」；AI/界面用 `workflow_step` 推进。
- 旧台账的三条口径原样保留：
  1. **不确定就是不确定**：动作发了但没观察到预期 → 暂停 + `NOT_VERIFIED`/`TIMEOUT`，永不自动重试。
  2. **认不出的失败码按不安全处理**：只有明确可重试的码才允许再试，次数用尽即 `ATTEMPTS_EXHAUSTED`。
  3. **目标不是原来那个就不发**：前台换应用/窗口变化 → 暂停 + `TARGET_LEFT`/`TARGET_STALE`，恢复必须重新确认现场。
- 兼容层：`automationTask` 命令保留一个发布周期，内部构造临时工作流并映射旧回执：
  - `plan` → 创建临时工作流；
  - `gate` → `workflow_step`；
  - `record` → 运行器已自行记录，兼容层确认后返回当前快照；
  - `resume` / `cancel` / `status` → 对应运行器操作。
- 旧 `AutomationTaskLedger.kt` 在 shim 期后删除；其单测（`unknown` 分类、重试白名单、目标过期、迟到回执）迁移到运行器测试与兼容测试。
- 临时工作流不写 `accessibility_automation_workflows`，只存在内存 + 运行记录；进程重启即失效（与旧台账「进程内」一致）。

## 8. AI 交互

### 8.1 现状约束

壳页（Capacitor WebView）与 Harness 宿主之间只有 `MobileRuntime` 桥，**没有会话端点**；loopback 有动态端口、HttpOnly 令牌、混合内容、无 REST 四道门（见 `docs/measurements/壳页会话列表接线调研.md`）。因此：

- V1 **不能**由 App 自动创建/注入一条「工作流设计会话」。
- V1 能做：流程页生成设计简报 → 打开 Harness → 用户新建对话并粘贴 → AI 通过工具读流程、提计划。
- 以后要自动建会话，需要新增桥方法 + 宿主 API；那是独立工程，不在本设计内。

### 8.2 设计会话

**目的**：让 AI 在一个专门的对话里处理某个流程的参数，不污染主对话，也不让 AI 直接改盘面。

**流程**：

1. 用户在流程详情点「用 AI 优化」。
2. App 生成简报（`flowId`、`revision`、`traceHash`、共享级别、schema 摘要、可用工具、约束）。
3. App 打开 Harness；用户新建对话，粘贴简报。
4. AI 调 `mobile_workflow_get` 读轨迹/草稿/校验错误。
5. AI 调 `mobile_workflow_propose` 提交计划。
6. App 收到计划，编译候选 revision + diff，显示「有建议」。
7. 用户在工作流视图逐条接受/拒绝。
8. 用户可回到同一对话继续迭代；AI 再调 `get` 读新 revision。

**运行时会话**：流程暂停后，现场单可生成一段运行时简报；用户开对话让 AI 处理。AI 先直接处置（现有单步工具），不行再提参数补丁，最后才建议中止。

### 8.3 工具与命令

**App UI ↔ 原生**（`MobileRuntimePlugin`，供设置页调用）：

- `listAutomationWorkflows(packageName?)`
- `getAutomationWorkflow({ id })`
- `saveAutomationWorkflow({ workflow })`（用户编辑）
- `deleteAutomationWorkflow({ id })`
- `startAutomationRecording({ packageName })`
- `stopAutomationRecording()`
- `getAutomationRecordingState()`
- `runAutomationWorkflow({ id, mode })`（`mode: "validate" | "dryRun" | "step" | "run"`）
- `pauseAutomationWorkflow()`
- `resumeAutomationWorkflow({ nodeId })`

### 8.4 提案与审批

- 计划只进 `proposals` 区，不改活动 revision。
- App 编译计划 → 候选 revision + diff；校验失败直接拒绝并回错误码。
- 用户逐条接受；接受的操作集重新编译（不是把整份候选直接保存），保证拒绝某项后图仍合法。
- 操作应用时必须保持图合法：`drop` 把前驱重连到被删节点的 `onSuccess`；`merge` 合并相邻同类节点的边；`guard` 插入条件节点，`onFalse` 指向原步骤、`onTrue` 指向指定目标（默认 `end`）；任一重连产生歧义或环，整份计划拒绝。
- App 不轮询模型：提案落盘后，流程列表/详情在下次打开或手动刷新时显示「有建议」；AI 的工具回执里提示用户回 App 确认。
- 应用成功后写 `review` 元数据与审计（只记 `planId`、操作数、结果，不记界面文本）。
- 提案有 TTL（例如 24h）与 `baseRevision`；过期/过期 revision 拒绝。

### 8.5 兜底顺序：自动 → AI（限步/限时）→ 人

整体顺序：

1. **L0 原生自动恢复**：确定性的重试/等待/重启/返回，先做，不消耗 AI 预算。
2. **L1 AI 接手**：只在已有恢复租约时生效；步数、时间、补丁数都有硬上限，没有进展就转人工。
3. **L2 人工接手**：预算耗尽、租约过期、AI 主动升级，或安全例外（敏感页/锁屏/风险节点）时直接转人工。

**AI 内部优先级**：直接处置（单步工具清卡点）→ 改参数（补丁）→ 中止。这个顺序不因「AI 先接手」而改变。

L0 与 AI 的先后可由 `recovery.maxAutoRetries` 控制：设为 `0` 就是「暂停后直接让 AI 接手」，不再先做原生重试；默认 `1` 是先用一次低成本、确定性的恢复，仍有问题再交给 AI。

约束：

- AI 只能在已暂停的运行上接手；不能 `run`、不能录制、不能改盘面、不能开总开关。
- 所有 AI 动作走现有闸门与审计；不能写坐标、不能绕敏感页。
- AI 的 `resume` 必须引用当前暂停的 `runId`/`nodeId`；不能恢复已结束/已取消的运行。
- 预算按「租约」算，不按整个运行算；一次租约只服务一个现场单。

### 8.6 没有 API 通道时，兜底机制怎么落地

**先说实话**：壳页没有创建会话、注入消息、调用模型的通道（§8.1）。所以「暂停后系统自动叫 AI」在 V1 **不可能**；能落地的是「用户把运行交给 AI 后，AI 在硬预算内先试，失败再叫人」。如果要做零点击的自动 AI 接手，必须先补宿主会话/消息 API（§8.6 末尾）。

#### L0：原生确定性恢复（不依赖 AI，永远可用）

运行器在暂停前先跑一遍 `RecoveryPolicy`（纯函数，JVM 可测）：

```text
incident + workflow.recovery + 现场事实
        ↓
retry / retryAfter / skipOptional / relaunchAndRestart
/ backAndRetry / pause / abort
```

| 失败 | 默认恢复 | 上限 |
| --- | --- | --- |
| `TARGET_MISSING` | 延长超时重试一次 | 1 次，之后暂停 |
| `NOT_VERIFIED` | 风险节点不重试；非风险重试一次 | 1 次 |
| `RATE_LIMITED` | 等 500ms 重试 | 1 次，计入节点 retries |
| `TARGET_LEFT` / 应用崩溃 | `relaunchOnTargetLeft=true` 时重新启动并从头跑 | 1 次/运行 |
| `WINDOW_UNAVAILABLE` | 等 1s 重试 | 1 次 |
| `ASSERT_TIMEOUT` | 不猜；暂停 | 0 |
| `SENSITIVE_WINDOW` / `DEVICE_LOCKED` | 直接暂停/中止 | 0 |
| 未知码 | 暂停 | 0 |

工作流级恢复参数（用户可改）：

| 参数 | 范围 | 默认 | 说明 |
| --- | --- | --- | --- |
| `recovery.maxAutoRetries` | 0..3 | 1 | 自动重试总次数 |
| `recovery.retryBackoffMs` | 0..10000 | 1000 | 重试间隔 |
| `recovery.relaunchOnTargetLeft` | 布尔 | `true` | 前台离开/崩溃时是否重启应用并从头跑 |
| `recovery.backOnUnexpectedScreen` | 布尔 | `false` | 意外界面是否先按一次返回再重试 |
| `recovery.abortOnSensitive` | 布尔 | `true` | 敏感页一律不恢复；V1 固定 true，不开放 |

> L0 的关键是**只做参数化的确定性动作**，不发明新点击。它不能关掉一个录制里没出现过的弹窗；那属于 L1。

#### L1：AI 接手（限步、限时、限补丁）

**怎么开始**：

- 暂停后，App 的运行卡片与通知都有「让 AI 处理」。
- 用户点它 → App **立即创建恢复租约**（`RecoveryLease`），打开 Harness 并把运行时简报复制到剪贴板。
- 租约从点击那一刻开始计时；AI 还没回话也算在预算里。这样「AI 一直不响应」不会无限挂着。
- 以后有 API 时，App 可以在暂停时自动创建租约；V1 只能由用户点。

**租约参数**（工作流级，用户可改）：

| 参数 | 范围 | 默认 | 说明 |
| --- | --- | --- | --- |
| `recovery.aiMaxOps` | 1..10 | 3 | 本租约内允许的状态变更操作数（见计数口径） |
| `recovery.aiMaxPatches` | 0..2 | 1 | 本租约内允许提交的参数补丁数 |
| `recovery.aiTimeoutMs` | 30000..300000 | 90000 | 从点击「让 AI 处理」起算的硬超时 |
| `recovery.aiMaxIncidentsPerRun` | 1..3 | 2 | 一次运行最多让 AI 接手几个现场单；超过直接人工 |
| `recovery.humanWaitMs` | 60000..1800000 | 600000 | 转人工后等用户处理的时间；超时中止 |

**租约字段**（原生持有，工具可读）：

```text
leaseId, runId, incidentId, nodeId,
startedAtMs, expiresAtMs,
opsLeft, patchesLeft,
state: active | expired | escalated | closed,
progressAtMs, note
```

**计数口径**：

- 计入 `aiMaxOps`：通过设备桥发起的状态变更动作（`accessibilityAction` / `tap` / `inputText` / `back` / `scroll`），以及每次 `workflow_resume` 尝试。
- 不计数：读树、读状态、截图、`workflow_status`、`workflow_recovery_note`。
- 不计数：用户在 App 里手动操作、用户自己点重试/继续。
- 计入 `aiMaxPatches`：`workflow_propose` 提交一次算一次；被用户拒绝也计。

**什么算「有进展」**：

- 运行从 `paused` 恢复，并且至少前进一个节点；或运行以 `success` / `end` 收口。
- 只有「界面读到了 / 点了一下」但运行仍在同一个节点暂停，不算进展。
- 有进展 → 关闭当前租约；如果之后又暂停，开新租约（受 `aiMaxIncidentsPerRun` 限制）。
- 没进展 → 继续消耗 ops/时间；耗尽即转人工。

**AI 协议**：

1. 用户粘贴简报后，AI 调 `mobile_workflow_status` 读现场单与租约余额。
2. 需要确认租约时调 `mobile_workflow_recovery_begin`（App 已创建则返回现有租约，不重复计时）。
3. 用现有单步工具直接处置；每次状态变更扣 1 op。
4. 调 `mobile_workflow_resume`（扣 1 op）；运行器重新校验目标后继续。
5. 直接处置无效：调 `mobile_workflow_propose` 提补丁（扣 1 patch）；用户在 App 确认后，再 `resume`。
6. 无法安全继续：调 `mobile_workflow_recovery_escalate` 或 `mobile_workflow_abort`。
7. 结束时写一条 `mobile_workflow_recovery_note`（≤200 字，不含界面文本），供人工接手时看「AI 试过什么、卡在哪」。

**预算耗尽 / 超时 / 无进展**：

- 原生把租约置 `expired`，运行置 `needs_human`，发通知：
  - 「AI 未能恢复：<流程名> 第 N 步 <原因>（已用 3 步 / 90 秒）」
  - 附带 AI 的最后 note。
- 之后 AI 的任何状态变更/恢复/补丁都被拒绝：`AUTOMATION_WORKFLOW_RECOVERY_EXPIRED` 或 `AUTOMATION_WORKFLOW_RECOVERY_BUDGET_EXHAUSTED`。
- 用户可以：
  - 人工处理并「继续」；
  - 「重试」；
  - 「跳过」（仅可选节点）；
  - 「中止」；
  - 「再让 AI 试一次」：显式开新租约（计入 `aiMaxIncidentsPerRun`，不自动续期）。

**安全例外（直接转人工，不消耗 AI 预算）**：

- 敏感窗口、锁屏/熄屏：暂停/中止，AI 不能接手。
- `risk=true` 的节点失败：AI 可以读现场、提补丁，但不能替用户执行该风险动作；转人工确认。
- 白名单外、前台离开且用户未允许重启：转人工。

#### L2：人工接手（默认兜底）

- 暂停时现场单落盘（§7.4），通知/运行卡片显示失败码、节点、路径、AI 的最后 note。
- 动作：`重试` / `跳过`（仅可选）/ `中止` / `再让 AI 试一次`。
- 用户可手动把界面弄回预期状态，再点「继续」；运行器重新校验目标后从当前节点继续。
- 用户不处理：`humanWaitMs` 到期后按 `abort` 结束，避免暂停运行挂一整天。
- 这条路径不需要 AI，是 V1 的最终兜底。

#### 为什么「AI 先接手」在 V1 仍要用户点一下

- AI 不是常驻进程；它只在 Harness 对话里运行。没有会话/消息 API 时，App 无法在暂停瞬间把 AI 叫起来。
- 用户点「让 AI 处理」= 把 AI 拉进这个现场单；从这一刻起 AI 先试，预算用完再叫人。这已经是「AI 优先、人工兜底」，只是启动那一下需要人。
- 想要零点击：必须先做宿主侧会话/消息接口（创建会话、发消息、订阅事件）+ 一条桥方法；然后 App 才能在暂停时自动建租约。这是独立工程，V1 不依赖，也不假装有。

## 9. 用户界面

### 9.1 流程列表

位置：设置 → 自动化 → 目标应用 → 「工作流」。每行显示：

- 名称、触发器类型（手动/事件）、步数、最近一次运行结果（成功/暂停/中止）、最后更新时间、活动 revision。
- 状态徽标：`草稿` / `来自旧规则` / `AI 有建议` / `有分支` / `含风险步骤` / `需要确认的选择器`。
- 操作：运行、编辑、更多（复制、导出、删除、查看轨迹）。

列表上方是**应用级设置**：暂停开关、新工作流默认值（超时/重试/settle/冷却/匹配延迟）。它取代旧的「每应用自动化参数」页，但字段语义连续。

### 9.2 工作流视图

- 纵向节点卡片 + 连线；`condition` 用菱形/分叉卡片；`optional` 用虚线跳过边；失败边红色指向 `pause`。
- 当前运行节点高亮；已走路径打勾；暂停节点显示现场单入口。
- 节点卡片显示：动作、目标摘要（viewId/文字，不展开长文本）、期望、超时/重试徽标、`可选`/`风险`/`AI 新增` 徽标。
- 点节点 → 右侧/底部参数面板（9.3）。
- 图只读；编辑通过参数面板与「插入」菜单，不做自由拖拽连线（V1）。这样避免图编辑器的复杂手势与误连。

### 9.3 结构化编辑器

- 节点列表 + 图视图切换；同一份数据。
- 每个节点可改：动作、选择器（1..3，逐条编辑）、输入值模式、等待/超时/重试/`settleMs`、`optional`、`risk`、期望。
- 出边用下拉：`成功 →`、`失败 →`、`跳过 →`、`真 →`、`假 →`；下拉只列合法目标，实时校验。
- 「插入」菜单：条件、断言、等待、返回、结束、暂停。
- 「恢复录制值」：把该节点恢复为编译时的值（如果有 `provenance.traceStep`）。
- 校验错误就地显示；保存前必须通过校验。

### 9.4 运行视图

- 运行前确认：目标应用、步数、风险步骤数、是否 `dryRun`/`step`。
- 运行中：当前节点、已用时、已完成步数；「暂停」「中止」。
- 暂停：现场单卡片，展示失败码、节点、原因、路径；默认主按钮「让 AI 处理」（生成运行时简报并创建租约），人工「重试 / 跳过（仅可选）/ 中止」为次按钮。敏感页/风险节点不显示「让 AI 处理」。
- AI 接手：卡片显示「AI 处理中 · 剩余 N 步 / T 秒」、补丁余额、AI 最后一条 note；按钮「转人工」「中止」。预算耗尽/超时后自动切成「AI 未能恢复，已转人工」，并保留 note。
- 人工：可手动把界面弄回去点「继续」，或「再让 AI 试一次」（新租约，受 `aiMaxIncidentsPerRun` 限制）。
- 结束：成功/失败/取消；显示路径与耗时；「再跑一次」。

### 9.5 版本与差异

- revision 列表：原始录制、AI 建议、用户编辑；显示时间、来源、操作数。
- 差异：图视图上标绿（新增）/灰（删除）/黄（修改）；列表逐项显示原因。
- 接受/拒绝；接受后生成新 revision；可切回旧 revision（运行只认活动 revision）。
- 「删除原始轨迹」独立于 revision；删除后 AI 无法再基于轨迹提计划，但现有工作流仍可运行。

### 9.6 录制入口

- 应用选择器（复用现有 `ApplicationPicker`）→「开始录制」。
- 倒计时覆盖层/通知；录制中通知常驻；停止后自动打开预览。
- 浏览器预览（无设备）显示「浏览器预览不能录制」；不伪造流程。

### 9.7 触发器编辑与旧规则迁移

- 工作流详情顶部有「触发器」区块：`手动` 开/关；`事件` 可编辑选择器、Activity 白/黑名单、匹配延迟、冷却、次数上限、重置方式。
- 事件触发器只允许单动作工作流；多步工作流上开关置灰，并注明「多步工作流只能手动运行」。
- 迁移来的规则显示「来自旧规则」徽标；打开就是工作流编辑器，原来的 `maxActions`/`coolDown`/`resetOn` 在触发器区块里可改。
- 迁移失败/无法转换的规则进入「待处理旧规则」列表：显示原 JSON、允许导出、允许删除；不显示成「已迁移」。
- 旧规则列表/旧规则表单不再作为独立入口；同一份数据只在工作流列表里出现。

| `selectors` | 1..16（scroll 可 0..16；UI 默认显示 3 条） | 编译生成 | click / longClick / setText；scroll 可选 |
| `waitBeforeMs` | 0..5000 | 编译推导 | action |
| `timeoutMs` | 1000..30000 | 流程默认 | action/assert |
| `settleMs` | 0..2000 | 流程默认 | action.expect/assert/condition |
| `retries` | 0..3 | 流程默认 | action/assert |
| `optional` | 布尔 | 编译推导 | action |
| `risk` | 布尔 | 编译推导 | action |
| `expect` | `none`/`screenChanged`/`nodeGone`/`textAppears`/`activityChanged` | 编译推导 | action |
| `value.mode` | `literal`/`parameter`/`ask` | `ask` | setText |
| `value.text` | 0..200 | 空 | literal 时必填 |
| `value.name` | 1..40 | 空 | parameter/ask 时的提示名 |

### 10.3 用户控制点

- 录制后立即看到每一步与每个参数；不需要 AI 才能保存/运行。
- 任何 AI 建议都是 diff；不点接受不生效。
- 每个字段记录来源（录制/用户/AI）；可恢复录制值、可回退 revision。
- 输入内容默认 `ask`；要自动填，用户必须显式改成 `literal` 并输入值（本地保存，不共享给 AI，除非用户改 `sharingLevel`）。
- 风险步骤运行前确认；可选关闭「本次运行确认」，但不持久化。

## 11. 存储

### 11.1 文件与键

- 独立偏好文件 `accessibility_automation_workflows`（与白名单、密码隔离；迁移期只**读**旧规则文件）【推】。
- 键：
  - `index`：JSON 数组 `[{id, packageName, name, revision, enabled, triggerTypes, legacyId?, updatedAt}]`；不用 `\t`/`\n` 拼接。
  - `wf:<id>`：活动工作流 JSON。
  - `hist:<id>`：最近 5 个 revision 的 JSON 数组（或分键 `rev:<id>:<n>`）。
  - `trace:<id>`：轨迹 JSON；用户可删。
  - `prop:<id>`：未处理的提案 JSON（可多条，最多 3 条）。
  - `migration`：`{version, at, imported, skipped, legacyIds}` 迁移账本。
- 写入：先构造完整 JSON，再一次 `put` + `commit()`；不做「先删后写」。
- 读取：索引坏了 → 重建扫描 `wf:` 键；单条坏了 → 返回 `Corrupt`，**不自动删除**（用户数据，保留导出/删除入口）。

### 11.2 限额

| 项 | 上限 |
| --- | --- |
| 每个包工作流数 | 40（容纳旧规则的每包 40 条上限） |
| 全局工作流数 | 200 |
| 节点数 | 40 |
| 边数 | 80 |
| 单工作流 JSON | 256 KiB（UTF-8） |
| 全局工作流 JSON | 1 MiB |
| 单轨迹 JSON | 256 KiB |
| 轨迹总量 | 2 MiB；超过时按最旧优先提示用户删除，不静默删 |
| 每流程提案 | 3 |
| 每流程 revision | 5 |
| 节点选择器 | 16（UI 默认显示 3） |
| 事件触发器选择器 | 16 |
| 字符串字段 | 200 字符（沿用 `AutomationRuleLimits`） |
| 临时工作流步数 | 20（与旧台账一致） |

超限是**拒绝**，不截断；提示具体项。

### 11.3 损坏与版本

- `schema` 版本号；未知版本按「不支持」返回，不尝试猜测。
- 未知字段、类型不符、越界：整体拒绝（与 `AutomationRule` 一致）。
- 损坏的单条工作流：列表里显示「损坏」，提供导出/删除；不参与运行。
- 轨迹缺失但工作流存在：可运行；AI 审阅不可用。
- 未来字段升级：按现有严格口径**拒绝**；升级时做迁移或保留旧版本读取器。

### 11.4 从旧规则迁移

**执行时机**：应用启动、服务连接后、任何触发器求值前。迁移未完成时**不运行任何自动化**，界面显示「迁移未完成」，避免半套数据被当成完整盘面。

**步骤**：

1. 读 `migration` 账本；版本已是当前 → 跳过。
2. 读旧 `accessibility_automation_rules` 的每个包；逐条解析成 `AutomationRule`（旧严格解析器保留为迁移 DTO）。
3. 逐条转换成工作流（§3.3.1）：
   - 单动作节点；`trigger.event` 承载旧的选择器/Activity/延迟/冷却/次数/重置；
   - `maxActions` → `maxRuns`；`actionCoolDownMs` → `cooldownMs`；
   - `legacyId` 保留原规则 id。
4. 读旧 `accessibility_automation_app_config`：`paused`、三个默认值 → 应用级设置（字段重命名，见 §3.3.3）。
5. 对每个转换结果跑严格校验；任一包失败 → **整体不提交**，把该包标为 `legacy`，界面显示原因与原始 JSON。
6. 原子写新存储（所有 `wf:` 键 + `index` + `migration` 账本一次 `commit()`）。
7. 成功后旧文件保持只读，不再参与执行；一个发布周期后可由用户确认清理。

**幂等与回滚**：

- `migration.version` 是唯一判据；重复启动不会重复导入。
- 写入失败：不写账本，下次启动重试；旧数据仍在，不会丢。
- 回滚：旧文件未被删除；开发构建可用 `legacyEngine` 开关临时回到旧路径，生产不承诺。
- 迁移后用户改过的工作流以新存储为准；旧文件只作取证，不反向覆盖。

**边界**：

- 旧规则里的未知字段/越界值：旧解析器本来就拒绝；迁移把该包标 `legacy`，不猜测、不截断。
- 旧规则里的 `launch`：保留动作并标 `risk=true`，事件触发器仍只允许单动作。
- 旧规则 40 条/包：新存储每包上限 40，刚好容纳；超出说明旧数据本身已损坏，标 `legacy`。

### 11.5 与现有偏好的关系

- `accessibility_automation_control`（总开关）：不动，继续作为运行闸门。
- `accessibility_automation`（白名单）与 `accessibility_automation_guard`（密码）：不动。
- `accessibility_automation_app_config`：文件保留，字段扩展/重命名；迁移期由迁移器读，之后由应用级设置读写。
- `accessibility_automation_rules`：迁移后只读；不再有代码路径按它执行。
- 暂停语义：应用级 `paused` 挡触发器、手动运行、AI 临时运行；**不挡录制**。

### 13.3 真机【验】

- 事件覆盖：微信/浏览器/Flutter/WebView/系统设置；`TYPE_VIEW_CLICKED` 是否派发；`event.source` 是否为空。
- 录制 → 编译 → 回放 5 步流程，连续 3 次；广告弹窗出现/不出现两种路径。
- 条件分支：已签到/未签到两条路径。
- 触发器：旧规则迁移后事件命中 → 运行；冷却/次数/重置；自触发不循环；连续失败自动停用。
- 迁移：带旧规则的升级安装；迁移成功/失败/重试；旧规则可回滚取证。
- 恢复：L0 自动重试/重启；L1 AI 租约（3 步 / 90 秒 / 1 补丁，超时或未前进转人工）；L2 通知动作与 `再让 AI 试一次`。
- 选择器稳定性：应用升级后 viewId 是否变化；文本变化是否导致失败。
- 时序：慢网/动画下超时是否合理；`settleMs` 是否能避免误判。
- 安全：支付/验证码页强制拒绝；锁屏；非白名单；频率限制。
- 服务断开/重连：运行暂停、录制停止、恢复行为。
- 通知/悬浮球：录制中可见、停止可达；暂停通知动作可达。

### 13.4 安全回归

- AI 不能 `run`/`recordStart`/`save`/`delete`/`enable`；只能读、提计划、在租约内恢复已暂停的运行、中止。
- AI 租约的步数/时间/补丁数由原生强制；耗尽后所有恢复/动作/补丁调用都被拒，不能靠反复调用绕过。
- AI 计划不能改包名、不能写坐标、不能新增 `launch`、不能放宽闸门；迁移保留的 `launch` 不能被 AI 复制到新节点。
- 2A 关闭时新增动作节点被拒；打开后新增动作节点仍需用户勾选。
- 事件触发器只允许单动作工作流；迁移前后这条限制都成立。
- 迁移不允许静默丢规则：失败包必须显示、可导出、可重试。
- 所有拒绝/运行都写审计，detail 只有受控码，不含文本/viewId/包名。
- 现场单默认不带文本；共享级别为 `none` 时 `candidates=[]`。

## 15. 风险与开放问题

### 15.1 风险

1. **事件覆盖不足**：WebView/Flutter/游戏可能录不到点击；V1 只能提示「这个界面录不了」，不能假装成功。
2. **条件分支让用户更难理解**：默认只显示线性主链；只有存在分支时展开；图视图只读、编辑用结构化控件。
3. **无循环**：「滚动直到找到」「重复直到成功」V1 表达不了；如实说明，后续再加 `loop` 节点。
4. **AI 计划质量**：可能删错步骤、起错名字、设错成功判据；diff 评审是必需环节，不能自动应用结构变更。
5. **隐私**：轨迹含屏幕文字；默认 `labels`，发送前预览；输入内容不存；密码/敏感页不采集。
6. **时序常数**：1500/5000/15000ms 都是起点，需要真机调；不要把它们写死成「结论」。
7. **图编辑器复杂度**：V1 不做自由拖拽连线，避免误连；用结构化下拉 + 插入模板。
8. **迁移正确性**：替换旧规则是单向的；迁移失败/漏转会让用户「规则不见了」。必须整体失败不提交、保留旧文件、显示待处理项。
9. **事件触发器只允许单动作**：这是 V1 的安全限制；多步事件触发要单独评审，否则一次界面事件可能连点多次。
10. **AI 先接手的启动摩擦**：没有会话/消息 API，仍要用户点一下「让 AI 处理」；点完后 AI 在租约内先试，预算耗尽转人工。不要包装成零点击自动。
11. **AI 预算内也可能误点/耗时**：租约把「最多几步、最多多久、最多几次补丁」写死，但预算内的动作仍可能点错；敏感页/风险节点直接跳过 AI，是唯一硬保护。
12. **失败不可回滚**：已点击/已发送的动作不会因为后面失败而撤销；现场单与「不自动重试风险步骤」是唯一保护。
13. **旧数据清理**：旧规则文件保留一个发布周期；清理时机与回滚窗口要写进发布说明。
14. **进程被杀**：运行状态与录制状态都在服务内存；进程重建后暂停运行无法恢复，只能重新跑。现场单可落盘用于查看/取证，但不承诺跨进程恢复；要跨进程恢复必须把运行状态也落盘，V1 不做。

### 15.2 开放问题（需要用户拍板）

| # | 问题 | 建议 |
| --- | --- | --- |
| 1 | 输入内容是否允许存字面量？ | V1 默认不存；要自动填就让用户显式改 `literal`，本地保存、不共享给 AI。 |

## 16. 附录：关键交互示例

### 16.1 录制 → 草稿

轨迹（简化）：

```json
[
  { "type": "click", "node": { "text": "跳过", "viewId": "com.example.app:id/skip", "clickable": true }, "atMs": 800 },
  { "type": "click", "node": { "text": "我的", "viewId": "com.example.app:id/tab_me", "clickable": true }, "atMs": 4200 },
  { "type": "click", "node": { "text": "签到", "viewId": "com.example.app:id/checkin_entry", "clickable": true }, "atMs": 6100 },
  { "type": "click", "node": { "text": "签到", "viewId": "com.example.app:id/checkin_button", "clickable": true }, "atMs": 7600 },
  { "type": "window", "activity": "com.example.app/.CheckinActivity", "atMs": 7900 },
  { "type": "text", "text": "签到成功", "atMs": 8200 }
]
```

草稿：

```text
start
  → n1 点击「跳过」 [optional, skip→n2]  (id .../skip)
  → n2 点击「我的」                     (id .../tab_me)
  → n3 点击「签到」                     (id .../checkin_entry)
  → n4 点击「签到」  expect=screenChanged (id .../checkin_button)
  → n5 assert 文字「签到成功」           (来自屏幕摘要)
  → end-ok
失败 → pause
```

### 16.2 AI 编导（2B）

AI 计划：

```json
{
  "baseRevision": 1,
  "traceHash": "8a1c0f2d7e4b9a63",
  "intent": { "name": "每日签到", "success": { "kind": "textVisible", "text": "签到成功", "evidence": { "step": 5 } } },
  "operations": [
    { "op": "annotate", "step": 0, "optional": true, "reason": "开屏广告" },
    { "op": "set_param", "step": 3, "timeoutMs": 8000, "reason": "页面切换较慢" },
    { "op": "guard", "beforeStep": 2, "predicate": { "kind": "textVisible", "text": "已签到" }, "onTrue": "end-skip", "reason": "已签到则跳过" }
  ]
}
```

应用后：

```text
start
  → condition 「已签到」? ─是→ end-skip
  │否
  → n1 点击「跳过」 optional
  → n2 点击「我的」
  → n3 点击「签到」 timeout=8000
  → n4 点击「签到」
  → n5 assert「签到成功」
  → end-ok
失败 → pause
```

### 16.3 运行时兜底

1. 第 4 步 `NOT_VERIFIED`，L0 重试一次仍失败，流程暂停。
2. 用户点「让 AI 处理」；App 创建恢复租约（3 次状态变更 / 90 秒 / 1 次补丁），打开对话并复制运行时简报。
3. AI 读 `status`，发现是「签到成功」文案变了；先用 `mobile_accessibility_action` 读树确认新文案（读不扣步数）。
4. AI 用单步工具清掉卡点（扣 1 op），调 `resume`（扣 1 op）；运行前进一个节点 → 租约关闭，继续跑。
5. 如果 90 秒内没有前进，或 3 次操作/1 次补丁用完：租约过期，运行转 `needs_human`，通知里带 AI 的 note；之后 AI 的恢复调用被拒。
6. 如果页面是支付/验证码：不创建租约，直接转人工/中止，AI 不参与。

旧规则：

      "allowActivities": [],
      "denyActivities": [],
      "matchDelayMs": 300,
      "cooldownMs": 3000,
      "maxRuns": 1,
      "resetOn": "activity"
    }
  ],
  "entry": "n1",
  "nodes": [
    { "id": "n1", "type": "start", "packageName": "com.example.app", "next": "n2" },
    {
