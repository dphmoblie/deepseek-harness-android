首屏分块（5.6-A）。所有数字都是在仓库根目录真实跑出来的，命令与输出见第 3 节。

## 1. 任务 1（5.6-K）：握手窗口内只合并不丢弃

### 1.1 原来的语义

`TerminalPanel` 的挂载顺序是：注册输出/退出监听器 → `fit()` → `await bridge.createTerminal(...)` →
拿到 `sessionId`。**监听器注册在两个 await 之前**，而原生侧是在 `create` 里 spawn pty 并立刻开始读输出的
（`UbuntuTerminalManager.create()` 里 `ioExecutor.execute { readLoop(session) }`），所以「会话已经在吐字节、
JS 还没拿到 sessionId」是一段真实存在的窗口，起点是注册监听器，终点是 `createTerminal` 落定。

窗口内到达的事件原先被推进两个数组，并且带条数上限：

```ts
const pendingOutput: TerminalChunk[] = []
const pendingExit: TerminalExit[] = []
...
if (pendingOutput.length < MAX_PENDING_EVENTS) pendingOutput.push(event)   // MAX_PENDING_EVENTS = 32
if (pendingExit.length < MAX_PENDING_EVENTS) pendingExit.push(event)
```

超出的部分**直接丢弃，没有任何提示**。`sessionId` 就绪后按 `event.sessionId === sessionId` 过滤补写。

**丢弃是不是安全的？不是。** 原生侧的终端输出是一条一次性事件流：
`UbuntuTerminalManager.readLoop()` 每次 `NativePty.read` 最多读 16 KiB，Base64 之后交给
`PluginEventSink.onTerminalOutput()` → `notifyListeners("terminalOutput", …)`，**没有重放接口、没有落盘副本**；
`MobileRuntimePlugin` 里对这段的注释也是「不缓存、不落盘」。WebView 里丢掉一个事件，那一段字节就永久消失：
xterm 的回滚缓冲只保存已经写进去的内容，原生侧不会补发。所以 33 条以后（约 512 KiB 之后）的突发输出是真丢内容。

退出事件同理：它是终态事件，丢掉的后果不是「少一行提示」，而是 `disposeInput()` 永远不会执行 ——
会话其实已经结束，界面却仍把键盘输入写回一个不存在的会话，用户每敲一次键都会收到一次
`SESSION_NOT_FOUND` 报错。**（如实说明：`pendingExit` 的 32 条上限在真机上基本不可达
—— 一次握手窗口内要挤进 33 个会话的退出事件，而全应用同时最多两个终端面板；这一条的修复价值在于
把「结构上不可能」写死，而不是修一个已观测到的故障。）**

### 1.2 现在的做法

窗口内的事件改为按会话累积到一条字节缓冲（`Map<sessionId, PendingSessionOutput>`）：

- 同一会话的连续输出**按到达顺序拼进定长块**（`MAX_PENDING_BLOCK_BYTES = 64 KiB`），块写满就开新块；
- `sessionId` 就绪后同步交付：先按块顺序补写输出，再补发该会话的终态事件；
- 交付后立刻 `pending.clear()`；不属于本会话的残留（例如上一块面板正在收尾的会话）一并释放；
- 类型、体积校验（`base64ToBytes` 的 128 KiB / 字符集检查）两条路径共用，解码失败一律走 `onError` 上报，不静默吞。

顺序保证：交付点在 `sessionId = session.sessionId` 之后紧跟，**中间没有 await**，
事件回调不可能插队，所以「窗口内的字节」与「窗口后的字节」严格保持到达顺序。

### 1.3 为什么不会无界增长（量化上限）

1. **生命周期有界**：缓冲只在握手窗口存在 —— 成功路径在 `flushPending()` 里同步清空；
   失败路径在 `catch` 里 `handshakeFailed = true` + `pending.clear()`，之后**不再累积**
   （失败后本面板永远不会再有匹配的会话，继续攒就是纯占内存，这也是原来没有的一处真实的无界增长点）。
   面板卸载时再 `clear()` 一次。
2. **容器开销有界**：`MAX_PENDING_BLOCK_BYTES` 限制的是**单块容量**，不是「能收多少字节」。
   每 64 KiB 数据才占一个数组槽位（约 1/65536 的元数据开销），不会像「一条事件一个数组元素」那样
   在突发输出下膨胀出上万个条目。分配到一半的块最多浪费 64 KiB × 会话数（实际 ≤ 2）。
3. **唯一会继续增长的条件**是 pty 在窗口内持续产出，即缓冲量 ≈ 窗口时长 × 终端吞吐。
   窗口的时长由 PRoot spawn + 一次桥调用往返决定（百毫秒量级），缓冲量与同一组件已经持有的
   xterm 回滚缓冲（`scrollback: 5000` 行）同量级，不是新的数量级。
4. **残余风险（如实在此记录）**：如果 `createTerminal` 永远不 settle（原生侧卡死且不返回），
   窗口就一直开着，缓冲会随输出一直涨。这种情形下界面本身也已经卡在「正在连接」，
   属于既有问题，本次没有改变它的行为，也没有为它加超时 —— 加超时属于运行时策略，
   不在这两项优化的范围内。

**量化上限**：单块 65 536 B；稳态下缓冲字节数 = 握手窗口内的原生输出量（实测口径：原生每次
`read` 最多 16 KiB，窗口内的事件数决定了这个量），交付后立刻归零。

### 1.4 测试（`src/components/TerminalPanel.test.tsx`，6 条）

用例用 `vi.mock('@xterm/xterm')` 替身记录**每一次** `write` / `writeln` 的调用顺序与字节，
断言比对的是交付出去的**字节流**，不是任何内部数组的长度：

1. 窗口内推 100 条输出（旧实现只留前 32 条）→ 逐字节按序补齐，`onError` 未被调用；
2. 窗口内推 8 × 16 KiB = 128 KiB（跨过 64 KiB 块边界）→ 字节流逐字节一致，
   且交付形态为 `[65536, 65536]` 两次 write（证明上限只限制单块容量）；
3. 窗口内到达的退出事件 → 在输出之后补发「会话已结束，退出码 7」，且 `onData` 回调已注销
   （打字不再写回原生，证明终态处理真的生效，而不是只多了一行文字）；
4. 对照组：正常会话下输出直通、打字**会**写回原生（说明第 3 条的「不写回」来自终态处理本身），
   跨握手边界的输出仍保序；
5. 其它会话的输出与终态既不交付也不残留；
6. 握手失败后不再累积：失败后继续推 200 条，终端上仍然没有任何字节。

> 断言用逐字节比较而不是 `expect(uint8Array).toEqual(...)`：本仓库的 jsdom 环境里
> `TextEncoder` 与全局 `Uint8Array` 来自**不同 realm**，`toEqual` 会对内容完全相同的两个
> `Uint8Array` 报 "Compared values have no visual difference"（已实测确认）。逐字节比较既是
> 更强的断言，也避免踩这个坑。

## 2. 任务 2（5.6-A）：首屏分块

### 2.1 改动

`vite.config.ts` 增加：

```ts
const XPACKAGE = /[\\/]@xterm[\\/]/
const RUNTIME_PACKAGE = /[\\/]node_modules[\\/](react|react-dom|scheduler)[\\/]/

function manualChunks(id: string): string | undefined {
  const file = id.split('?')[0]
  if (file.endsWith('.css')) return undefined   // CSS 跟着引入它的块走
  if (XPACKAGE.test(id)) return 'xterm'
  if (RUNTIME_PACKAGE.test(id)) return 'react'
  return undefined
}
```

同时把 `@xterm/xterm/css/xterm.css` 的引入从 `src/main.tsx` 挪到 `TerminalPanel.tsx`。

### 2.2 踩到的坑（必须记下来）

**只加 `manualChunks`、不处理样式归属，首屏会显著变大。** `manualChunks` 只看模块 id，
`@xterm/xterm/css/xterm.css` 同样命中 `@xterm/`；而这条 CSS 由 `src/main.tsx` 静态引入，
于是整个 `xterm` 块（289.73 kB）变成了入口的静态依赖，Vite 直接给 `index.html` 加了一条
`modulepreload`：

```
<script type="module" crossorigin src="./assets/index-CyOS-rh0.js"></script>
<link rel="modulepreload" crossorigin href="./assets/react-B7Erz9g5.js">
<link rel="modulepreload" crossorigin href="./assets/xterm-mk2Bp_IF.js">   ← 首屏凭空多下 290 kB 终端代码
```

入口包开头也随之出现 `import"./xterm-mk2Bp_IF.js";`（实测抓下来的产物原文）。
修正办法就是现在的两条：**CSS 不参与手工分块**，并且**样式表跟着懒加载的组件走**。

复核时**不要只看文件名**，要看 `dist/index.html` 里 `<script type="module">` 与
`rel="modulepreload"` 到底指向了哪些文件。

> 口径提醒：Vite 打印的「原始大小」是**渲染后代码的字符数**，不是文件字节数。入口包里有大量中文文案，
> 两者会差出一大截（实测 `index-*.js` 打印 211.72 kB，磁盘上 253,043 字节）。上面的字符数表用于和
> Vite 输出对照，下表的**字节数**才是传输/存储的真实成本。

按磁盘字节 + gzip（`zlib.gzipSync(level 9)`）统计，并按 `index.html` 的首屏引用汇总：

| 产物 | 改动前 原始 B | 改动前 gzip B | 改动后 原始 B | 改动后 gzip B |
| --- | --- | --- | --- | --- |
| 入口/主包 `index-*.js` | 396,228 | 123,374 | **253,043** | **77,354** |
| `react-*.js` | —（含在入口里） | — | 142,324 | 45,590 |
| 首屏 `index-*.css` | 38,268 | 8,862 | 34,188 | 7,273 |
| `index.html` | 17,789 | 13,536 | 17,866 | 13,561 |
| **首屏 JS+CSS 合计** | **434,496** | **132,236** | **429,555** | **130,217** |
| 首屏（含 html） | 452,285 | 145,772 | 447,421 | 143,778 |
| 懒加载（打开终端才下） | 294,409 ／ 73,731 | | 298,521 ／ 75,647 | |

结论，逐条说清楚：

1. **主包（入口 chunk）确实变小了**：396,228 → 253,043 字节（−143,185 B，−36.1%）；
   gzip 123,374 → 77,354 字节（−46,020 B，−37.3%）。变小的部分是 React 运行时，
   它被拆成了独立的 `react-*.js`。
2. **首屏总量只小幅下降**：434,496 → 429,555 字节（−4,941 B，−1.14%）；
   gzip −2,019 B（−1.53%）。原因是 React 运行时首屏**仍然必须加载**，只是换了一个文件
   （并多了一条 modulepreload）；真正净减的是 CSS 那 4,080 字节。
3. **首屏 CSS 里的 xterm 规则整段搬走**：`index-*.css` 里现在只剩应用自己的
   `.terminal-canvas .xterm{height:100%}` 一条 `.xterm` 规则，xterm 自己的 60 条规则
   （含 `.xterm-viewport` / `.xterm-screen`）全部落在懒加载的 `TerminalPanel-*.css` 里。
4. **终端相关代码确认不在首屏**：`index.html` 只引用入口 JS、`react-*.js`（modulepreload）
   与 `index-*.css`；`xterm-*.js`、`TerminalPanel-*.js`、`TerminalPanel-*.css` 都不在其中。
   打开终端时多下的 4 KB，就是原来躺在首屏 CSS 里的那份样式表换了个位置。
5. **chunk 依赖图无环**（下面第 3 节给了复核脚本）。需要如实说明的是：产物里确实存在
   `index → (动态) TerminalPanel → (静态) index` 这条**改动前就存在**的环
   （懒加载块静态引用被 Rollup 提升到入口包的共享模块，例如 `i18n`），
   两个版本实测都报同一个环，不是 `manualChunks` 引入的；入口必然先于动态导入求值，
   运行顺序没有变化。

### 2.4 「648 KB 单块」的现状说明

登记册里「首屏单个 chunk 约 648 KB（gzip 184 KB）」对应的是**懒加载之前**的形态：
改动前的两个 chunk 按 Vite 打印口径相加正好是 354.90 + 294.09 ≈ 649 kB，与此吻合。
`src/App.tsx` 第 91 行在当前 HEAD 上**已经**是
`const TerminalPanel = lazy(() => import('./components/TerminalPanel')…)`，
所以本次实测的「改动前」首屏已经是 434,496 字节（JS+CSS），不是 648 KB。
本任务因此把重点放在「主包体积」与「把终端相关代码钉死在懒加载块里」，
并在 `manualChunks` 的注释里写明了那条 `modulepreload` 陷阱。

## 4. 只能真机验证的部分

- **握手窗口的真实吞吐**：本文给出的是「窗口内不丢字节」的**逻辑**保证与上限推导，
  真机上 PRoot spawn 期间到底会积压多少 KiB，需要在设备上打点实测（`TerminalPanel` 里
  加临时计数，或看原生侧 read 循环的节奏）。真机突发输出（例如 `cat` 一个大文件、
  `dsh` 打印长 banner）能否被完整交付，只能在设备上确认。
- **合并成大块后 xterm 的实际观感**：交付形态从「每条事件一次 write」变成「每 64 KiB 一次 write」，
  字节流不变，但在低端设备上的渲染节奏（是否出现整屏跳变）只能真机观察。
- **WebView 里 chunk 加载的真实耗时**：`index.html` 现在多了一条 modulepreload，
  在 Capacitor 的 WebView 里两个文件的加载是否真的比一个大文件更快，需要真机测。
- **懒加载样式表的注入时机**：xterm 样式现在随异步块注入，理论上 Vite 的 preload 会等 CSS 就绪后
  再执行模块，终端不应出现无样式闪一下；这条需要真机（或浏览器）确认。
- 本机没有 Playwright / 浏览器自动化可用，**没有做端到端运行验证**；
  产物侧只做了静态验证：chunk 依赖图无环、`index.html` 引用检查、四个 chunk 逐个
  `node --check` 语法通过、`react-*.js` 可在 Node 里独立求值。
