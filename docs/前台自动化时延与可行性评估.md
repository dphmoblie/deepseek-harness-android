# 前台自动化时延与可行性评估

评估问题（用户原话）：「评估在前台时遇到某些界面自动操作的延迟和可能性。」

- **评估对象**：`deepseek-harness-android`（应用 id `io.deepseekharness.mobile`），只评估本仓库**现有实现**，不评估「改造后能怎样」。
- **「在前台时」的口径**：目标界面正显示在最前面（`rootInActiveWindow` 就是它），本应用通过设备桥 / 无障碍服务 / Shizuku 设备 Shell 在它上面执行自动操作。
- **方法**：只读侦察（`glob` / `grep` / `read`）+ 官方文档 URL 引用。本轮**没有在真机上执行任何自动操作**，**没有跑 gradle / vitest / 构建**，**没有改编任何代码或文档**（本轮只新增本文件）。
- **仓库口径**：侦察时 HEAD = `42c4450`（2026-10-02）。工作区在本轮开始前已有未提交改动，与本评估无关、本轮未触碰。
- **未实测声明**：本文所有数字只有三类来源——①**代码常量**（能 grep 复现）；②**代码推算**（由常量与调用顺序推导出的量级，**不是实测**）；③**官方文档**（仅给 URL，本轮无法抓取正文）。凡是「实际多久」「实际能不能成」一律标 **未实测 / 待真机验证**。

## 1. 结论速览

### 1.1 可行性要点

1. **「自动操作」在本仓库是「按控件标识单步操作」，不是「按坐标手势操作」。** 设备桥把 `tap` 也实现为「先按坐标找到一个 **可点击且带 viewId 的节点**，再用 viewId 重新定位并 `ACTION_CLICK`」——纯坐标手势路径**不存在**（全仓无 `dispatchGesture`、无 `canPerformGestures`，`android/app/src/main/res/xml/accessibility_service_config.xml:1-8` 也没有该属性）【码】。
2. **一次动作有三道「能不能做」的硬门**：锁屏/息屏、前台包必须在白名单、窗口不能命中敏感词。系统设置、权限弹窗、SystemUI、安装器、支付/验证码/密码/生物识别窗口被代码**结构性排除**（`AccessibilityAutomationPolicy.kt:23-34` 的 `reservedPackages` + `sensitiveText`）【码】。
3. **「设备端一次性确认」当前不会出现**：`requestConfirmation()` 定义在 `DeepSeekAccessibilityService.kt:179`，**全仓无任何调用点**，`action()` 在第 175 行直接调用 `executeConfirmedAction()`。这与三处既有文档描述矛盾（见 §6）【码】。
4. **没有「等界面稳定」的原语**：`onAccessibilityEvent()` 是空实现（`DeepSeekAccessibilityService.kt:57`），服务不消费事件流；能用的等待只有 `mobile_device_wait`（100 ms–10 s，设备侧 `sleep`）。所以「动画没结束就点」在本实现里**不是低概率事件，而是默认行为**，只能靠模型多观察一次来规避【码】。
5. **观察与动作可能来自两份不同的结构来源**：`mobile_device_ui_dump` 在真机上已被记录为**静默空壳**（`docs/设备工具与PTY协议.md` §6.1），会自动回退到无障碍节点树；也就是说改走无障碍通道时，观察阶段返回的可能是 `uiautomator` 的 XML、也可能是无障碍 JSON，两者的坐标口径与标识一致性**未验证**【码】+【测】。

## 2. 一次自动操作的完整链路（含门禁与时序）

### 2.1 两条下发路径，三个执行后端

设备命令有**两条下发路径**，落在**三个执行后端**上，时延与门禁完全不同：

| 路径 | 入口 | 无障碍四命令 | 其余设备命令 |
|---|---|---|---|
| **A：模型工具**（主路径） | 插件 `mobile_device_*` / `mobile_accessibility_*` | 后端 ①：无障碍服务（不经过 Shizuku） | 后端 ②：Shizuku 设备 Shell |
| **B：前端终端面板** | `src/platform/native.ts:233` → `MobileRuntimePlugin.kt:1101` | **无此分支** | 后端 ③：同一个 Shizuku 设备 Shell，但复用已有 PTY 会话 |

- 前端 `src/**` 里**没有**任何 `mobile_device_*` / `mobile_accessibility_*` 工具名（grep 零命中）：这些工具由**容器内 Node 插件**定义，前端只负责设置界面（白名单选择器、Shizuku 状态、AI Shell 开关）【码】。
- **路径 B 没有 `uiDump → 无障碍节点树` 的回退**，只有路径 A 的 `mobile_device_ui_dump` 有【码】`lib/index.js:452-470`。
- **路径 B 的 `tap`/`inputText` 与路径 A 的 `tap`/`inputText` 不是同一份实现**：路径 B 的 `DeviceCommand.fromName("tap")` 命中 `DeviceCommand.TAP`（Shizuku 侧），路径 A 的 `tap` 被桥拦截后交给无障碍服务【码】`DeviceBridgeServer.kt:182-195`、`DeviceCommandRunner.kt:59-80`。

### 2.2 路径 A：模型工具 → 设备桥 → 无障碍服务（`tap` / `inputText` / `accessibilityAction` / `accessibilityTree`）

```
模型
 └─ 插件工具 mobile_device_tap / mobile_device_input_text / mobile_accessibility_action / mobile_accessibility_tree
     └─ ctx.on('tools/pre-execute')            ← 宿主审批钩子（见门禁 1）
         └─ callBridge(command, param)         ← fetch POST http://127.0.0.1:<port>/device-command，Bearer token
             └─ DeviceBridgeServer 工作线程
                 └─ commandName in {accessibilityTree, accessibilityAction, tap, inputText}
                     └─ DeepSeekAccessibilityService.current()?.execute(command, param)
                         ├─ executeChecked()：门禁 2–7
                         ├─ observedAction()（仅 tap / inputText）：门禁 8–9
                         ├─ action()：门禁 8–9 再走一遍
                         └─ executeConfirmedAction() → 主线程 performConfirmedAction()：门禁 3–9 第三次校验 + performAction
                     └─ PrivateAuditLog.record(...)（含 fsync）
             └─ HTTP 200 {"ok","exitCode","text","truncated","errorCode"}
```

关键 `file:line`：
- 桥的无障碍分支：`android/app/src/main/java/io/deepseekharness/mobile/DeviceBridgeServer.kt:182-195`（服务未开启 → `ok=false, exitCode=1, errorCode=ACCESSIBILITY_SERVICE_DISABLED`，「请先在系统设置中手动开启 Harness 无障碍服务」）。
- 服务入口：`android/app/src/main/java/io/deepseekharness/mobile/accessibility/DeepSeekAccessibilityService.kt:67-78`（`execute()` 是 `@Synchronized`，执行完写审计再返回）。
- 门禁主流程：同文件 `:80-100`；参数化动作：`:103-130`；按 viewId 的动作：`:164-176`；主线程执行：`:280-329`。

### 2.3 路径 A′：模型工具 → 设备桥 → Shizuku 设备 Shell（其余 19 项命令）

```
模型 → 插件工具 → callBridge → DeviceBridgeServer 工作线程
   └─ DeviceCommand.fromName(commandName)
       └─ SHELL / BACKGROUND_TASKS 需 shellEnabled()（AI Shell 开关）否则 SHIZUKU_SHELL_DISABLED
           └─ shizuku.create(80, 24, suppressPublicOutput = true, onSessionExit = ...)   ← 新建一次性会话
               └─ DeviceCommandRunner.execute(sessionId, command, param, 60_000)
                   └─ 把 /system/bin/sh -c '<固定模板>' 用 base64 写进 PTY，等双哨兵协议收口
               └─ finally { shizuku.close(sessionId) }                                   ← 关闭会话
```

- 会话创建：`android/app/src/main/java/io/deepseekharness/mobile/shizuku/ShizukuRuntime.kt:294-336`（每次 `requirePermission()` + `requireService()`，后者在 binder 存活时复用连接，`:489`）。
- 会话实体：`android/app/src/main/java/io/deepseekharness/mobile/shizuku/DeviceShellUserService.kt:38-101`（`NativePty.spawn("/system/bin/sh")` + 信号量 `MAX_SESSIONS = 4`，`:215`）+ `:188-204`（关闭 = 先 SIGTERM，2 s 后 SIGKILL——**`close()` 不是同步等进程退出**）。
- 命令模板与时间上限：`android/app/src/main/java/io/deepseekharness/mobile/shizuku/DeviceCommandRunner.kt:125-155`（超时 → `DEVICE_COMMAND_TIMEOUT`，退出码 -1，**无自动重试**）。
- 具体命令实现：`launchApp` → `monkey -p "$param" 1`（`:433`）；`foregroundPackage` → `dumpsys activity activities | grep -E "mResumedActivity|mFocusedApp|topResumedActivity" | head -n 4`（`:438-441`）；`backgroundTasks` → `ps` / `dumpsys`（各 `head -n 128`，`:469-476`）；`shell` → base64 解回后交给 `/system/bin/sh -s`（`:485`）；文件命令 → `readlink -f` 收敛 + `case` 前缀匹配 + 临时文件 `mv -f`（`:490-549`）。

### 2.4 路径 B：前端终端面板 → 原生插件

- `src/platform/native.ts:233` → `MobileRuntimePlugin.kt:1101-1121`：`DeviceCommand.fromName` → `SHELL`/`BACKGROUND_TASKS` 需 `DeviceShellAccess.enabled()` → `controller.hasDeviceSession(sessionId)`（否则 `SESSION_NOT_FOUND`）→ `RuntimeHost.deviceCommands().execute(sessionId, command, param, DEVICE_COMMAND_TIMEOUT_MS)`。
- 前端允许的命令集是 `src/platform/validation.ts:704-724` 的 19 项，**不含 `accessibilityTree` / `accessibilityAction`**；参数上限 180 000 字符（`:726`）【码】。
- 因为复用已有 PTY 会话，路径 B **没有**「每命令一次会话创建/关闭」的开销，但**必须先有一条活着的终端会话**【码】。

### 2.5 门禁清单（一次动作要过哪些门）

| # | 门禁 | 判定位置 | 失败码 / 结果 |
|---|---|---|---|
| 1 | 宿主审批（`tools/pre-execute`） | `lib/index.js:371-406` | **当前恒放行**：`schemaVersion === 3` 且 `allowlistedAutomation`/`directDeviceOperations` 为 true 就直接 `return decision`（`:381-382`）；这两个能力位由 `DeviceBridgeServer.kt:176` **硬编码为 true**。`{kind:'ask'}` 分支 `:387-404` 因此**不可达** |

| 4 | 速率限制 350 ms | 同文件 `:88`（`executeChecked`）、`:301`（`performConfirmedAction`） | `ACCESSIBILITY_RATE_LIMITED`「无障碍动作过于频繁，请稍后再试」 |
| 5 | 有没有活动窗口 | 同文件 `:87`、`:302` | `ACCESSIBILITY_WINDOW_UNAVAILABLE` |
| 6 | 前台包在白名单 | 同文件 `:89`、`:304` + `AccessibilityAutomationStore.kt:45-57`（**每次动作都重读 SharedPreferences 并整份校验**） | `ACCESSIBILITY_PACKAGE_DENIED`（`:305` 文案「确认后前台应用已变化」） |

| 9 | 目标节点 | `DeepSeekAccessibilityService.kt:168-172`、`:308-312` | `ACCESSIBILITY_NODE_NOT_FOUND`（未找到**唯一**节点）/ `ACCESSIBILITY_ACTION_REJECTED` |

| 11 | 改白名单要密码 | `AccessibilityAutomationStore.kt:19-31` + `AccessibilityPasswordPolicy.kt` | **不在单次动作路径上**，只在「谁能改白名单」时生效 |

补充两条容易忽略的门槛【码】：
- **`reservedPackages` 永不可选**：`android`、`com.android.settings`、`com.android.systemui`、`com.android.packageinstaller`、`com.google.android.packageinstaller`、`com.google.android.permissioncontroller`、`com.android.permissioncontroller`（`AccessibilityAutomationPolicy.kt:23-27`），并且应用内选择器把它们标成「系统安全组件，不支持无障碍自动化」（`src/components/ApplicationPicker.tsx:61`）。
- **本应用恒在白名单**：`withSelf()` 每次都会把 `io.deepseekharness.mobile` 补回（`AccessibilityAutomationPolicy.kt:63-64`），用户删不掉。

### 2.6 时序（以一次 `mobile_device_tap` 为例，路径 A）

```
t0  插件 callBridge：fetch → 127.0.0.1:<port>            （无重试；总超时 75 s）
t1  桥工作线程取任务                                     （线程池 2 + 队列 4，满则静默丢连接）
t2  无障碍服务 executeChecked：SharedPreferences 读白名单 + 取 root + 敏感 DFS
t3  observedAction：DFS ≤120 节点找「可见 + 可点击 + 有 viewId + 命中坐标」的最后一个节点
t4  action()：parseAction → findByViewId 要求**全树唯一** → 节点校验
t5  executeConfirmedAction：Handler.post 到主线程，latch.await(30 s)
t6  主线程 performConfirmedAction：锁屏 → 350 ms 节流 → root → 白名单 → 敏感 DFS → findByViewId → performAction
t7  审计：目录 chmod + （每天一次）目录扫描 + 文件 chmod + 写入 + force(true)
t8  HTTP 200 返回
```

注意 t2/t3/t4/t6 中「取 root、白名单、敏感扫描、按 viewId 查找」被**重复执行了 2–3 次**——这是本实现最主要的固定开销来源，而不是任何单个慢调用【推】。

| 保活前台服务 | Android 12+ 要求 `startForeground()` 5 s 内完成，否则进程被终结 | `docs/后台保持与恢复.md:84-89` |

### 3.2 代码推算的量级（【推】，非实测）

1. **无障碍动作的下限不是「一次 IPC」，而是「约 6–8 次系统/磁盘调用」**：2 次 `rootInActiveWindow`、2 次敏感 DFS（各最多 320 节点）、2 次 SharedPreferences 取集合、1–2 次 `findAccessibilityNodeInfosByViewId`、1 次 `performAction`、1 次 fsync。毫秒数取决于节点树大小与存储速度，**未实测**。
2. **重复调用的最短节奏是 350 ms 一格**，且因为 `lastActionAt` 只在成功时更新，**连续失败可以比 350 ms 更密**——想在动画里「连点」的实现不会被动刹车【码】。
3. **失败几乎都是「立刻失败」，不是「等超时才失败」**：门禁 3–9 都是同步判断，绝大多数拒绝在毫秒级返回；真正会等满 30 s 的只有「主线程 `performConfirmedAction` 卡住」，等满 60 s 的只有「Shizuku 命令的哨兵收不回来」【推】。
4. **`mobile_device_wait` 是唯一「可控延迟」**，但它是**设备侧 `sleep` + 一整套会话建立/拆除**。若把 wait 当节流手段，实际等待 = 参数 + 一次会话创建/关闭（含 `Semaphore.tryAcquire`、`NativePty.spawn`、binder 往返、SIGTERM 收尾）【推】。
5. **Shizuku 会话池是 4，且与前端终端共用**：桥的每条设备命令都新建会话，`close()` 先发 SIGTERM、2 s 后才 SIGKILL，而会话真正释放发生在 `readLoop` 的 `waitFor` 之后（`DeviceShellUserService.kt:188-204/137-186`）。因此**密集下发设备命令有可能在短窗口内撞上 `DEVICE_SESSION_LIMIT`（`ShizukuRuntime.kt:294-336`）**——这是要在真机上专门试的一条【推】+【测】。
6. **桥的并发是硬上限**：2 个线程 + 队列 4；第 7 条并发请求会被 `RejectedExecutionException` 后**静默关连接**（`DeviceBridgeServer.kt:97-100`），插件侧表现为 `DEVICE_BRIDGE_UNAVAILABLE`（`lib/index.js:62-107`）。它**不是超时，是立刻失败**。

## 4. 界面类型可行性矩阵

「能做」= 代码路径可达且没有结构性拒绝；「有条件能做」= 路径可达但依赖目标界面暴露特定特征；「做不到」= 代码里存在结构性拒绝；「不确定」= 代码不判定、只能实测。

| 界面类型 | 判定 | 靠什么特征判断 | 失效时会怎样 | 证据 |
|---|---|---|---|---|
| **原生 View（有 text / clickable / viewId）** | ✅ 能做 | `roots` 的 `viewIdResourceName` 形如 `pkg:id/name`；`accessibilityAction` 直接按 viewId 点击/输入/滚动 | `findAccessibilityNodeInfosByViewId` 返回 0 或 ≥2 个 → `ACCESSIBILITY_NODE_NOT_FOUND`（**要求全树唯一**，列表项重复 viewId 是典型翻车点） | 【码】`:168-169/331-334`、`AccessibilityAutomationPolicy.kt:20` |

| **输入法覆盖（IME 弹在目标上）** | ⚠️ 有条件能做 | 目标包仍是前台包（`root.packageName`）时可行；`inputText` 不依赖 IME | 若 IME 成为前台包 → 门禁 6 拒绝「动作目标不是当前前台应用」/「确认后前台应用已变化」 | 【码】`:167/304-305`、`:104-108` |

## 5. 延迟与失败来源清单

### 5.1 代码可判定的来源【码】

1. **门禁重复执行**：一次动作里「取 root / 读白名单 / 敏感扫描 / 按 viewId 查找」跑 2–3 遍（`:80-100` → `:164-176` → `:298-312`）。节点树越大，重复扫描越贵（每遍最多 320 节点）。
2. **敏感扫描的「宁可错杀」**：深度 > 24 或节点数 > 320 直接判敏感（`:347-355`），大列表页/复杂布局会被整页拒绝，表现为 `ACCESSIBILITY_SENSITIVE_WINDOW` 而**没有任何敏感控件**。
3. **viewId 唯一性要求**：`findAccessibilityNodeInfosByViewId(...).singleOrNull()`（`:331-334`）。RecyclerView 列表里同一个 item 布局有相同 id 时必然失败。
4. **`tap` 的两段式定位**：先用坐标找节点（要求 `isVisibleToUser && isClickable && viewId 非空 && bounds 含点`，取 DFS 最后一个匹配，`:119-122`），再用该节点的 viewId 重新定位。两段之间界面一变就失败。
5. **`inputText` 依赖焦点**：`findFocus(FOCUS_INPUT)`（`:108`），没有焦点节点或焦点节点无 viewId（`:124`）都失败；不接受非 ASCII（`lib/index.js:513-527`，插件侧 `ASCII_INPUT_PATTERN`，且禁止 `' " \ ; $ \``）。
6. **审计 fsync 在返回路径上**：`execute()` 写完审计才返回（`:67-78`），而 `PrivateAuditLog.append()` 每次 `force(true)`（`:115`）。存储慢的设备上这是**串行加在每次动作上的**成本。
7. **控制流门禁**：桥只有 2 个线程 + 队列 4，第 7 条并发命令被静默丢弃（`DeviceBridgeServer.kt:50/97-100`）。
8. **Shizuku 会话池 4 + 异步关闭**（`ShizukuRuntime.kt:625`、`DeviceShellUserService.kt:188-204`）→ 密集设备命令可能撞 `DEVICE_SESSION_LIMIT`。
9. **Shizuku 掉线重绑**：`bindUserService` 最长等 10 s（`ShizukuRuntime.kt:483-526`），binder 未就绪最长 8 s（`:540-559`）。
10. **`launchApp` 之后没有任何「等它起来」**：`monkey` 返回即结束（`DeviceCommandRunner.kt:433`），紧接着的观察多半看到的是启动前的界面。
11. **`uiDump` 回退到节点树**（`lib/index.js:452-470`）：真机上 `uiautomator` 不可用时，观察阶段返回的是**无障碍 JSON 而不是 XML**，格式与坐标系与模型预期可能不同。
12. **服务被系统回收**：`DeepSeekAccessibilityService.current()` 靠 `serviceRef` 静态引用（`:392/394`），服务断开后为 null → `ACCESSIBILITY_SERVICE_DISABLED`，需要用户重新开启后才恢复。

### 5.2 只能实测确认的来源【测】

- 目标应用**故意**不给 viewId、或给动态 viewId；WebView/Compose 的节点暴露程度。
- 系统对话框（数字键盘、日期选择器、Toast 不可点）、分屏/画中画时 `rootInActiveWindow` 指向谁。
- 动画时长与「提前点击」的具体失败形态。
- 厂商省电策略、后台限制、无障碍服务被回收后能否自动恢复。
- 同一动作重复 N 次的实际耗时分布（见下文「真机最小测量步骤」M1）。

## 代码能确定的

以下结论只依赖仓库代码，**不需要真机**即可成立（可 grep 复现）：

1. 设备工具与无障碍工具**不由前端定义**，前端 `src/**` 只做设置界面；`src/**` 里 grep `mobile_device_*` / `mobile_accessibility_*` 零命中。
2. 一次动作的**执行点在原生侧**：`tap`/`inputText`/`accessibilityAction` 由 `DeepSeekAccessibilityService.execute()` 执行（`DeviceBridgeServer.kt:182-195`），**不经过 Shizuku**；其余命令经过 Shizuku 且**每命令一次会话**（`:196-224`）。
3. 门禁的**顺序与失败码**如上表 §2.5；其中锁屏/息屏只读 `KeyguardManager.isKeyguardLocked` 与 `PowerManager.isInteractive` 两个信号（`:370-374`）——**它不检查设备是否 idle、不检查是否有密码锁**。
4. 速率限制是 **350 ms**，且**失败不刷新**时间戳（`:379`、`:326`）。
5. **设备端一次性确认（`requestConfirmation`）没有任何调用点**，当前实现不会弹出确认层；`pendingConfirmation`/`cancelPendingConfirmation` 只被 `onInterrupt()`/`onDestroy()` 使用（`:59/61-65`）。
6. 宿主审批门**当前恒放行**：`DeviceBridgeServer.kt:176` 硬编码 `allowlistedAutomation: true` / `directDeviceOperations: true` / `schemaVersion: 3`，插件在 `lib/index.js:381-382` 据此直接放行，`:387-404` 的 `ask` 分支不可达。
7. **系统设置页、权限控制器、安装器、SystemUI 永远进不了白名单**（`AccessibilityAutomationPolicy.kt:23-27`）；本应用自身永远在白名单里（`:63-64`）。
8. 白名单里任一非法条目会让**整份白名单失效为空**（`AccessibilityAutomationStore.kt:45-57`）——即「写坏一条 = 所有自动化立即停摆」。
9. 参数层已经挡掉：viewId 必须 `包名:id/名字` 且 ≤240 字符、前缀包名必须等于目标包、`setText` ≤512 且不含控制字符与敏感词、`scroll` 只允许 forward/backward、`param` 长度 2..2048（`AccessibilityAutomationPolicy.kt:69-90`）。
10. 返回的节点树最多 **120 节点 / 24 层**，`truncated` 标志在 `nodes.length() >= 120` 时为真（`:380-381`、`:137`）；**可编辑节点的 text/hint/contentDescription 一律置空**（`:143-145`），因此「输入框里已有内容」读不到。
11. 节点树里**不回传 packageName**（`appendNodes` 的字段集 `:147-156`），只有外层 `packageName`；模型无法从节点树判断某个节点属于哪个包。
12. 超时与上限：单条设备命令 60 s（`DeviceBridgeServer.kt:294`）、插件 HTTP 75 s（`lib/index.js:23`）、单次无障碍动作等待 30 s（`:289`）、Shizuku 绑定 10 s / binder 8 s / 授权 60 s（`ShizukuRuntime.kt:620-622`）。
13. **没有任何自动重试**：`DeviceCommandRunner.execute()` 超时即返回失败（`:125-155`），插件 `callBridge` 也不重试（`lib/index.js:62-107`）。
14. 悬浮球**不是自动化通道**：`OverlayBallService.kt:41` 明确不执行 Shell、不连接 Shizuku、不持有凭据；它只负责回到对话。
15. `mobile_device_wait` 的语义是**设备侧 `sleep`**，参数 100–10000 ms（`DeviceCommandRunner.kt:444-452/617-618`）。

## 只能实测/真机确认的

以下结论**本轮无法从代码得出**，必须在真机（或等效的 Shizuku 环境）上测：

1. 无障碍单次动作的**实际毫秒数**与重复 N 次的分布（代码只知道固定开销由哪些调用组成）。
2. **节点树滞后**：点击执行那一刻的 `bounds` / `isClickable` 与「模型看到的上一份节点树」差多少。
3. **WebView / Compose** 是否真的暴露 `viewIdResourceName`；暴露的话形态是否是 `包名:id/名字`。这条直接决定 §4 里两行「做不到」是否成立。
4. **`FLAG_SECURE` 窗口**下 `accessibilityTree` 是否可用、`screencap` 的失败形态。
5. **`uiautomator dump` 静默空壳**是否只在已记录的机型上出现，换 ROM 是否正常（对照 `docs/设备工具与PTY协议.md` §6.1）。
6. Shell uid（Shizuku）下 `input tap/swipe/keyevent` 是否可用、是否需要额外权限。
7. **坐标换算误差**：`(original/attached).toFixed(2)` 缩放后点击是否落在目标上（`lib/index.js:358-366`）。
8. **密集设备命令**下的会话池枯竭（`DEVICE_SESSION_LIMIT`）与桥队列丢弃（第 7 条并发）的真实触发概率。
9. **锁屏/息屏**下的真实拒绝行为，以及厂商 ROM 的额外限制。
10. 无障碍服务被系统或用户关闭后的恢复路径（是否必须手动重开）。
11. 一次完整「观察 → 动作 → 等待 → 再观察」循环在**真实应用**上的成功率与耗时（例如开屏广告、列表滚动、表单填写三类典型场景）。

### 真机最小测量步骤（只写步骤与要记录的数字，本轮不执行）

准备：一台已开启无障碍服务、已装并授权 Shizuku、已把目标应用加入白名单的设备；关闭「AI Shell」（先只测无障碍通道）。所有测量都记录 **设备型号 / Android 版本 / ROM / 目标应用版本**。

**M1 单次动作耗时分布**
1. 打开目标应用，停在同一个稳定界面（同一次会话内不切换界面）。
2. 用 `mobile_accessibility_tree` 取一份节点树，选一个 `clickable=true` 且 `viewId` 非空的节点。
3. 记录 `viewId`，连续执行 `mobile_accessibility_action(action=click)` **20 次**，每次之间用 `mobile_device_wait(400)` 保证不撞 350 ms 节流。
4. 记录：每次调用的**端到端耗时**、成功/失败、失败时的 `errorCode`。
5. 报告：中位数、P90、最大值、失败率、失败码分布。

**M2 节流边界**
1. 同一节点连续点击，**不加 wait**，间隔依次为 300 / 350 / 400 ms。
2. 记录：出现 `ACCESSIBILITY_RATE_LIMITED` 的比例。
3. 再加一组「前一次失败后立刻重试」，验证「失败不消耗 350 ms 配额」是否如代码所推。

**M3 动画中提前点击**
1. 触发一个已知有动画的跳转（列表项进入详情页）。
2. 在 `t = 0 / 100 / 200 / 500 ms`（尽量用 `mobile_device_wait` 逼近）分别点击**目标页面的**控件。
3. 记录：4 组各自的 `errorCode`（预期是 `ACCESSIBILITY_NODE_NOT_FOUND` / `ACCESSIBILITY_ACTION_REJECTED`，但也可能是**静默点到旧界面**——要重点记录这种「成功但错位」）。

**M4 观察与动作的一致性**
1. 取一次节点树 → 记录某控件的 `bounds` → `mobile_device_wait(1000)`（期间界面滚动或刷新）→ **用旧坐标** `mobile_device_tap`。
2. 记录：命中率、命中到了哪个节点（用命中后的节点树比对）。

**M5 `uiDump` 与节点树对比**
1. 同一界面分别调用 `mobile_device_ui_dump` 与 `mobile_accessibility_tree`。
2. 记录：耗时、返回的是 XML 还是 JSON、两者对同一控件的 `bounds` 是否一致、`UI_DUMP_EMPTY` 是否复现。

**M6 每类界面的「能不能做」**
对 §4 的 9 类各找一个代表界面（原生列表 / WebView 页面 / Compose 页面 / 自绘游戏 / 银行或密码页 / 权限弹窗 / 带 IME 的表单 / 加载动画页 / 需要滑动的手势页），每类记录：
`accessibilityTree` 是否可读、能否找到 `clickable && viewId` 节点、`accessibilityAction` 的结果 `errorCode`、`tap` 的结果 `errorCode`。

**M7 失败与恢复**
1. 关掉系统里的无障碍服务 → 调用一次 `mobile_device_tap` → 记录错误码（预期 `ACCESSIBILITY_SERVICE_DISABLED`）。
2. 锁屏 → 调用一次 → 记录错误码（预期 `ACCESSIBILITY_DEVICE_LOCKED`）。
3. 把前台切到 `com.android.settings`（白名单本来就选不上）→ 调用一次 → 记录错误码（预期 `ACCESSIBILITY_PACKAGE_DENIED`）。
4. 杀一次应用进程，重开 → 记录「从冷启动到第一次自动化成功」的总耗时（对照 `RuntimeSupervisor` 的 120 s 上限）。

**M8 设备 Shell 通道**
1. 开启 AI Shell。
2. 连续下发 8 条 `mobile_device_shell`（互相快速触发），记录：是否有请求**无响应**（桥队列丢弃）、是否出现 `DEVICE_SESSION_LIMIT`。
3. 记录每条命令的耗时，拆出「会话创建 + 执行 + 关闭」的比例。
4. `mobile_device_wait(1000)` 额外测 20 次：记录实际墙钟与 1000 ms 的差（即会话开销）。

### 未验证清单与风险

**未验证（本轮）**
- 所有耗时数字：**全部未实测**。
- 官方文档正文：本轮**没能抓取到任何一页正文**（见 §7），因此所有平台行为表述都只是「按官方文档口径」引用，**未经正文核对**。
- WebView / Compose / `FLAG_SECURE` 三类界面的实际可访问性表现。
- 真机上 `uiautomator dump` 是否仍为空壳（只在 `docs/设备工具与PTY协议.md` 里记录过一台机型）。
- 坐标换算误差、会话池枯竭、桥队列丢弃的真实触发概率。

**风险**
1. **「成功但点错」比「失败」危险**：`tap` 成功只代表「找到了一个含该坐标的可点节点并点击成功」，不代表点的是模型想点的那个。当前没有任何执行后校验（`:325-328`）。
2. **`ACCESSIBILITY_ACTION_REJECTED` 一码多义**：策略拒绝（`:172`）与 `performAction` 返回 false（`:328`）共用同一个错误码，排查时无法区分「不许点」和「点了没用」。
3. **敏感窗口误判**：深度或节点数越界即整页拒绝（`:347-355`），复杂界面会出现「明明没有敏感内容却被拒」。
4. **「失败不节流」可被放大**：失败路径不刷新 `lastActionAt`，配合模型的重试倾向会形成高频失败循环。
5. **不要把当前实现当作「有确认的自动化」**：宿主审批恒放行 + 设备端确认是死代码，实际只有「白名单 + 锁屏 + 敏感窗口 + 350 ms」四道**自动**门。这与本文档 §6 列出的既有描述冲突。
6. **不要把 Shizuku 当 root**：设备 Shell 是 shell uid（`docs/mobile-acceptance-checklist.md:327` 同口径），且本应用**不承诺**绝对保活、不承诺锁屏后仍可操作（`docs/后台保持与恢复.md:133-144`、`docs/应用自动化能力.md:65-74`）。
