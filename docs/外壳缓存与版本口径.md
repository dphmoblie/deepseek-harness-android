Android 侧 WebView 缓存策略 + 运行时静态缓存头补丁（登记册 5.6-H）

登记册 §5.6-H 的原文几乎每一句都与代码不符，按代码核实后重写口径，并把**真正的瓶颈**修掉。

## 一、按代码核实的更正

- **代码里根本没有 `?v=` 这个参数**（`git grep -n "?v="` 只命中登记册自己）。真正的缓存键是两个
  查询参数 `appVersion` + `runtimeVersion`，生成点唯一（`HarnessPageUrl.withVersions`），
  调用点唯一（`HarnessActivity`）；前端完全不读它们，服务端也只用 `pathname` 路由、忽略 query。
- 原文「`HarnessActivity.kt:114` 为 `LOAD_NO_CACHE`」**已过期**：HEAD 上 `LOAD_DEFAULT` 与
  `withVersions` 都已存在。
- 原文「控制台资源是内容哈希产物」只对 `dist/assets/*` 成立；`dist/index.html` **没有哈希**。

## 二、Android 侧（本次补齐的缺口）

- 新增 `HarnessPageCache.kt` + 11 条用例：未知/空运行时版本回退为固定占位值 `none`；
  加载策略由 URL 结构推导——两维皆为**真实取值**才 `LOAD_DEFAULT`，缺维或占位一律 `LOAD_NO_CACHE`。
  这样「漏传版本键」的代价从「命中旧前端（用户无从察觉）」降级为「不缓存（慢一次）」。
  未知态用固定值还排除了「清单版本恰好写成 `none` 与未知态撞键」。

## 三、运行时补丁（让收益真正成立的那一步）

**只改 Android 侧收益接近 0**：`@deepseek-ai/dsh-host-frontend-static` 对 index 与 `assets/*`
**不发任何缓存头**（`res.writeHead(200, { "content-type": type })`），既无新鲜度也无校验器，
按 HTTP 语义这样的响应无法被复用。

因此新增 `patches/@deepseek-ai__dsh-host-frontend-static@0.1.5-rc.2.patch`（走既有 pnpm 补丁通道），
在 `serveStatic` 里按**产物是否内容寻址**分岔：

| 路径 | `cache-control` | 理由 |
|---|---|---|
| dist 根 / `distIndex`（入口 HTML） | `no-cache` | 文件名固定、内容随 APK 与运行时版本变化：允许缓存但每次必须回源校验 |
| `assets/` 下的产物 | `public, max-age=31536000, immutable` | 带内容哈希（如 `index-Cr2OHXyD.js`），内容变则文件名变 |
| 其余（favicon、webmanifest…） | `no-cache` | **不敢假定带哈希**：宁可少缓存，也不要让用户拿到旧界面 |

与宿主侧的配合：入口 URL 带 `appVersion` 与 `runtimeVersion`，任一维变化即换 URL，
因此即使 `index.html` 被缓存也不会串版本。

补丁与「Android 侧做不到 HTML no-cache + 哈希资源 immutable」的关系：`cacheMode` 只决定本次加载
能否用 HTTP 缓存、改不了服务端响应头，所以那个目标**只能由运行时补丁达成**。
