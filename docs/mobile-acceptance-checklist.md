# 移动端真机验收清单（随版本滚动，不绑定某个历史版本号）

> 适用范围：荣耀 Android 16（arm64/16KB）及至少一台其他 arm64 真机。验收对象为
> **同一个 Release** 中的内嵌 APK、`runtime-manifest.json` 与 `rootfs.bundle`
> （正式版 tag 为 `v<versionName>`，预览版为 `v<versionName>-mobile-<run_number>`）。
> 各项验收请记录**实际执行的** `versionName` / `versionCode`；本文档里的版本数字只是示例，
> 当前值以 `android/app/build.gradle` 与 `.github/workflows/android-build.yml` 的 `APP_VERSION` 为准。
> 含修复的版本**不能**用旧回执抵账——凡是被某个缺陷影响过的条目，都要在装了修复版之后重跑。

## 0. 发布资产前置

- [ ] APK 的 `versionCode` / `versionName` 与 `android/app/build.gradle`、
      `.github/workflows/android-build.yml` 的 `APP_VERSION` **三者一致**（以仓库当前值为准），并通过团队签名校验。
- [ ] Release 同时包含 APK、`runtime-manifest.json`、`rootfs.bundle`，三者来自同一次 CI run。
- [ ] APK 内恰有一份 `assets/runtime/rootfs.bundle` 和运行时 manifest，没有 `.bak` 或其他 rootfs 副本。
- [ ] 内嵌 manifest 的 rootfs SHA-256 与 APK 内 bundle 一致；全新安装无需手工填写运行时来源。
- [ ] APK 包含 ARM64 PRoot runner/loader，二者通过 16KB 对齐检查。
- [ ] Shizuku 为可选项；未安装 Shizuku 不影响 Ubuntu 安装和 Harness 对话。

## 2. Harness 对话 GUI

在 360x800、390x844、480x960 及桌面宽度逐项验证：

- [ ] 启动时恢复最近未归档会话；没有会话时自动创建会话并进入聊天。
- [ ] 官方会话列表可打开、切换、新建、归档和关闭。
- [ ] 消息支持 Markdown、GFM 表格、代码块、工具调用与可展开工具结果；外部 HTML 不执行。
- [ ] Composer 可发送普通消息；运行中可选择排队或引导，队列数量同步显示。
- [ ] 模型和推理强度可选，选择结果会用于后续发送。
- [ ] 官方任务、文件、模型/Harness 设置及插件页面可进入并可返回聊天。
- [ ] 不再出现“移动对话/插件工作台”双前端切换；官方入口与插件资源正常加载。
- [ ] Android 软键盘弹出时输入框、发送按钮和最后一条消息均可见，无横向溢出或文字重叠。
- [ ] 应用切后台再恢复后事件流继续更新，不丢失增量，也不被迟到历史覆盖。

## 3. Ubuntu 下载、续传与状态

- [ ] 全新安装点“安装并进入对话”后先显示真实下载进度，未下载完成前不显示校验或安装完成。
- [ ] 下载中断后记录当前字节数；关闭并重开应用，再次安装从同一
  `rootfs-<sha256>.part` 偏移发出 Range 请求。
- [ ] 合法 HTTP 206 与精确 `Content-Range` 继续写入，不重新下载已有字节。
- [ ] 服务端返回 HTTP 200 或 416 时清理旧 partial 并从 0 开始；错误 206/Range 响应失效即关。
- [ ] 断网、DNS、TLS、超时及截断下载进入明确 `error`，保留合法 partial，不显示“正在安装”。
- [ ] 下载完成后校验 manifest 声明的大小和 SHA-256；摘要不符不得解压或启用。
- [ ] 解压完成后自动启动 Harness 并进入对话；重新启动应用仍识别已安装版本。
- [ ] 设置中的重置需要输入 `RESET_RUNTIME`，只清除应用私有 Ubuntu 环境并关闭相关会话。

## 4. 设置与终端

- [ ] Harness 服务启动/停止、Ubuntu 版本与状态、运行时来源、重置均位于设置或其二级页。
- [ ] Ubuntu 终端可创建、输入、调整尺寸、重新连接和关闭；字体设置立即用于新会话。
- [ ] 含权限修复的运行时中 `bash --version` 成功；Harness 的 `bash` 工具在 `workspace-write` 下执行 `pwd` 成功，`grep` / `glob` 可检索已知工作区文件（不能以终端成功替代工具验收）。
- [ ] 保持屏幕常亮开关生效，退出相关页面后不泄漏其他敏感状态。
- [ ] 设置页没有用户账号、密码、验证码或 Android 设备凭据认证入口。
- [ ] Harness HTTP 与 WebSocket 未认证请求均被拒绝；内部 WebView 无可见认证提示且可正常连接。

## 5. Shizuku 与设备 Shell

- [ ] 未安装：显示“打开 Shizuku”，Ubuntu 与 Harness 功能仍可用。
- [ ] 已安装但服务未运行：显示启动提示，打开 Shizuku 后可返回刷新状态。
- [ ] 服务运行但未授权：点击“请求授权”只触发系统 Shizuku 授权流程。
- [ ] 已授权但未连接：设备终端保持不可用，并显示“连接 Shizuku”按钮。
- [ ] 点击“连接 Shizuku”后仅在 UserService binder 存活时显示“已连接”并允许设备 Shell。
- [ ] 杀死 binder/UserService 后现有设备会话退出，状态回到未连接；再次连接可恢复。
- [ ] 设备 Shell 的 uid 为 Android shell 权限而非 root；固定 `/system/bin/sh`，无隐藏后台通用命令入口。
- [ ] screencap、uiautomator、tap、inputText 仅通过已有可见设备会话和固定白名单执行。

> 说明：`screencap / uiautomator / tap / inputText` 四项**必须真机验收后才能勾选**。
> JVM 单测（`DeviceCommandProtocolTest`、`DeviceCommandRunnerTest`）只固定「给定这样一段
> 字节流，解析必须得到什么结果」，无法覆盖 PTY 回显、mksh 行编辑器（它无视 `stty -echo`）
> 与 Shizuku UserService 的真实行为。协议、错误码分级与旧方案失败原因见
> `docs/设备工具与PTY协议.md`。验收要点：截图返回可解码的 PNG；`tap` 不再 60 秒超时；
> 1 个字符的 `inputText` 不再超时；`uiDump` 给出 `UI_DUMP_FAILED` / `UI_DUMP_EMPTY` /
> `UI_DUMP_NO_TOOL` 之类的**明确**错误码，而不是统一的 `DEVICE_COMMAND_FAILED`。

- [ ] 关闭/卸载 Shizuku 后「后台保持」相关状态显示“设备 Shell 辅助：不可用”，不影响 Harness 与后台保持。
- [ ] 设置页明确说明 Shizuku 不是 root，也不提供永久保活能力。

## 5.1 后台保持与恢复

前置：已在设置中配置模型凭据，运行时已安装。逐项记录 ROM 名称与版本，不同厂商结果可能不同。

| # | 操作 | 预期 |
|---|---|---|
| K1 | 全新安装后打开设置 | 「后台保持 Harness」默认关闭；前台服务显示“未运行” |
| K2 | 关闭开关时保存设置 | 不启动前台服务，不弹出通知权限对话框 |
| K3 | 打开开关 | Android 13+ 弹出通知权限对话框；拒绝后前台服务仍可用 |
| K4 | 打开开关并保存 | 通知权限已授予时出现常驻通知，文案不含 URL/凭据/终端内容 |
| K5 | 启动 Harness 后锁屏 5 分钟再解锁 | Harness 仍为运行中；前台服务仍为“运行中” |
| K6 | 按 Home 返回桌面，等待 5 分钟后回到应用 | 运行时未重启，会话凭据未重新生成 |
| K7 | 划掉最近任务，等待 1 分钟后重新打开应用 | 前台服务仍在运行时 Harness 继续可用；未出现“需要重新连接” |
| K8 | 未开启后台保持时划掉最近任务 | 运行时停止（与旧行为一致），重新打开后可重新启动 |
| K9 | 在系统设置中“强行停止”应用后重新打开 | 状态不显示“运行中”；出现“需要重新连接”，点击后启动全新会话 |
| K10 | 厂商后台清理（如一键清理）后重新打开 | 同上：只在确实无法复用时才提示重新连接 |
| K11 | 点击“停止” | 前台服务立即消失，通知被移除 |
| K12 | 执行“重置 Ubuntu 环境” | 前台服务消失，运行时覆盖层被清除 |
| K13 | 关闭后台保持并保存 | 前台服务被撤销，通知被移除，Harness 继续运行 |
| K14 | 查看设置页“最近状态” | 显示最近阶段与本地时间；从未运行时显示“从未记录” |
| K15 | 保活开启、Harness 运行中，点常驻通知 | 回到**对话界面**；不出现“对话闪一下就消失”，也不落在管理页回不去 |
| K16 | 紧接着 K15，回到管理界面操作设置 | 设置页能正常读取与保存（原生桥未失效，无“本机运行时操作失败”） |
| K17 | 重复“进入对话 → 返回管理 → 点通知”至少 5 次 | 每次都能回到对话；无累积异常，通知始终只有一条 |
| K18 | K15–K17 之后点“停止” | 前台服务与通知正常消失（说明设备桥与运行时生命周期一致，未泄漏） |

记录建议：对 K5–K10 同时记录 `adb shell dumpsys activity services io.deepseekharness.mobile`
的片段（确认前台服务是否存在）以及应用进程是否被重建（pid 是否变化）。
K15 若失败，请一并抓取 `adb logcat -b crash -d | tail -n 80`：插件注册失败会表现为
`PluginLoadException` / `RUNTIME_BUSY`，而 `ForegroundServiceDidNotStartInTimeException`
指向服务启动顺序问题。

| D15 | 主动制造一次启动失败（最省事：先用别的进程占住清单里的 Harness 端口 3080，再点「打开 Harness」） | 界面报错；导出日志里出现 `ERROR\|HARNESS_START\|result=failed\|code=HARNESS_PORT_IN_USE`，而不是只有成功时的 `INFO\|HARNESS_START\|result=ok` |
| D16 | 展开「诊断日志（最近 64 KB）」 | 列出受控字段行；内容与导出文件一致；有更早内容时显示「已按窗口截断」；切到 256 KB 后内容变多 |
| D17 | 展开「运行日志（最近 8 KB）」后在「读取窗口」切到 256 KB | 标题与窗口同步变化，能读到比 8 KB 更早的输出；折叠状态下不读取 |
| D18 | 在两个日志阅读器里输入关键字过滤 | 只显示匹配行并给出「匹配 N / M 行」；判读提示不受过滤影响；点「复制」得到的是**完整**文本而不是过滤结果 |
| D19 | 制造一次已确诊故障后展开任一阅读器 | 命中特征时出现判读提示（例如端口占用、缺凭据、插件加载失败）；没有命中时不显示任何结论 |
| D20 | 在「运行与后台」点「运行自检」 | 逐项列出 shell / node / 沙箱启动器 / 沙箱探针 / 真实 confine exec / 裸 PTY / 沙箱内 PTY / 数据目录 / 附件目录 / ripgrep，并显示可用空间；**不点不跑**（进页面不自动执行） |
| D21 | 在出现 `PTY shell exited during startup` 的设备上跑自检 | 能区分「沙箱探测通过但真实 exec 失败」与「PTY 层失败」：两组 PTY 都失败 = PTY 层，只有沙箱内那组失败 = 沙箱层，都成功 = 应在 dsh 配置/插件层排查；结论不得与自检数据矛盾 |
| D22 | 自检报出 `LAUNCHER_NOT_EXECUTABLE` / `RG_NOT_EXECUTABLE` / `ATTACHMENTS_MISSING` 时点「修复运行时权限」 | 显示「已修复 N 项（检查 M 项）」；重跑自检后对应项变为 ok；修复不改变运行时版本、不清数据 |
| D23 | 让运行环境空闲到自动停止后再打开对话 | 出现一次性提示「运行环境已自行停止（可能是空闲自动停止）…」；「运行与后台」的状态行显示「上次停止：自行停止」；用户自己点停止时该行显示「用户停止」且不弹提示 |

记录建议：D9 是隐私门禁，务必逐条核对；若发现任何疑似敏感内容，记录该行的字段名与来源

## 5.4 悬浮球

## 13. 运行时版本管理与切回（R-版本管理，五条）

前置口径见 `docs/项目状态.md` 2026-09-25 的「dsh/运行时版本管理」与 `docs/运行时更新与数据保留.md`
的「版本保留与一键切回」。**为什么单列一节**：这是本轮新加的能力，本机只验证了逻辑与桥接
（Kotlin 单测、前端测试），**真正的文件操作（改名、回填用户数据、旋转槽位）只能在设备上确认**；
而且它天然带「删掉用户数据」的风险面，所以第 3 条是本节的主判据。

| # | 操作 | 预期 |
|---|---|---|
| R-版本-1 | 打开 设置 → 运行与后台 的「运行时版本管理」 | 至少列出「当前使用」；若 APK 内置运行时，还有「随安装包内置」。每行显示版本号、`dsh <版本>`（读不到写「dsh 版本未读到」）、体积。**当前使用那行的 dsh 版本必须与运行时自检区块里的 dsh 版本一致**——两处不一致说明有一处读错了文件 |
| R-版本-2 | 装一个与当前 `rootfs.sha256` 不同的运行时（内置更新版或 manifest URL + SHA-256 各一份都试），装完回到本页 | 出现「上一版本」，其版本号与 dsh 版本**等于安装前「当前使用」的那一组**；「当前使用」变成刚装的那一组。若「上一版本」缺失，说明旋转失败——那时安装仍算成功，但回滚能力没建立，要记失败并附诊断日志 |
| R-版本-3 | 先停止运行环境与 Ubuntu 终端，点「切换到上一版本」 | 列表互换（可来回点两次验证 A/B）。**判据不是界面，而是数据**：切完打开 Harness，会话列表、`settings.yaml` 里的设置、`.credentials.yaml`（模型凭据）、附件、技能、`root/1` 工作区里的文件都还在。任何一项丢失即**阻断级失败**（这正是 `RuntimePreservePolicy` 存在的理由） |
| R-版本-4 | 切换后看设置页「运行时版本」行，并打开 Harness | 版本号变成切换后那一版；Harness 页面按新的版本加载（WebView 缓存键带运行时版本，切完不该继续用旧缓存）。若页面仍是旧版本的行为，记「缓存键没换」，附切换前后的版本号 |
| R-版本-5 | 点「删除上一版本」→「确认删除」 | 二次确认后才真删；删完本页显示「现在没有可切换的上一版本：安装一次新版本后才会保留」，**当前运行时不受影响**（Harness 能照常启动；若它当时正在运行，也不该被打断——删除只动保留副本）。另外对照系统「应用存储」占用，删除应回收约 778 MB（清单 `rootfs.extractedBytes`） |

- [ ] 第 2 条与第 3 条必须在**同一个**运行时组合上连做：只验「能安装」不验「能切回」等于没验本轮功能。
- [ ] 第 3 条要**先记下切换前的会话数与工作区文件清单**（例如 `ls /root/1` 与 Harness 里的会话条数），
      切完逐项对照；只写「数据还在」不算回执。
- [ ] 运行中切换按钮必须是**禁用**状态并给出「运行中不能切换版本：请先停止运行环境与 Ubuntu 终端。」；
      安装进行中要报「安装期间不能切换运行时版本」。这两条是**拒绝**路径，别只测成功路径。
- [ ] 记录本轮保留副本的实际占用（设置页显示的体积 vs 系统里的应用占用），用于判断「只保留一份」这个上限是否还合适。
- [ ] 真机若发现「上一版本」占了空间但用不上，先用第 5 条删除，再记「需要更省空间的方案」——
      不要为了省空间把旋转逻辑改回「安装成功即删旧版本」，那会回到没有回滚副本的状态。
