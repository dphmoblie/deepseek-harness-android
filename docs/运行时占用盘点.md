# 运行时占用盘点：7.46 GB 从哪里来，能回收多少

面向问题：真机 `dumpsys diskstats` 显示 App Size 307.51 MB、**App Data 6.96 GB**、Cache 213.83 MB
（合计约 7.46 GB），而 proot 容器内只看到约 3.1 GB。

本篇只做三件事：**把目录与生命周期讲清楚**（每一句都带 `文件:行号`）、**把能回收的列成清单**
（分「应用内可做 / 只能容器内命令 / 不建议动」）、**把查不出来的部分如实标成未定案**。

> 本篇是只读调研产物：没有改任何 Kotlin / 资源 / 前端源码，没有跑 gradle，没有连手机，没有 commit。
> 文中所有数字都标了来源标签，见 §1.2。

---

## 1. 结论速览

### 1.1 三句话

1. **容器内看到的只是「在用副本」。** 应用私有目录 `dsh-runtime/` 里除了 `current/`（在用），还可能有
   `previous/`、`retained/`、`stale-*`、`preserve-*` —— 这些**都不会出现在容器内视角**，因为
   PRoot 只把 `current/` 当成 `/`（`RuntimeCommand.kt:150-191` 的 `-r <rootPath>`）。
2. **7.46 GB 里，容器外那约 3.9 GB 最主要的成分是「多份整棵 rootfs」**：更新一次运行环境，正常路径
   **必然**多留一份完整旧副本（`retained/`，`RuntimeInstaller.kt:588-608`）；删除失败时旧副本会改名成
   `stale-*` **原地继续占磁盘**（`RuntimeInstaller.kt:847-879`，注释在 `:844-846`）。
3. **现有界面能收回来的只有一份**：设置 → 版本管理 → 「删除上一版本」（`src/App.tsx:1990-2004`
   → `MobileRuntimeController.kt:131-136` → `RuntimeInstaller.kt:249-264`）。
   **`stale-*` 与 `preserve-*` 目前没有任何应用内入口能清**（详见 §5、§6）。

### 1.2 数字来源标签（后文全部沿用）

| 标签 | 含义 |
|---|---|
| 【反馈实测】 | 用户反馈原文里的手机实测（HONOR AAP-AN00 / Android 17 / 应用 0.2.9），只读副本 `C:\Users\user\.dsh\attachments\v1\files\b6\b63ceffd97b17b721a850c0191060bc593787cb3cebf82f8cb75bb61ea53df57\dsh-反馈-图标留白与存储占用.txt` |
| 【复测实测】 | 本次调研期间在设备上复测的 `dumpsys diskstats`（0.2.9，刚从 0.2.8 更新过一次运行环境） |
| 【访客实测】 | 在容器里 `du` 出来的宿主侧读数，仓库文档已归档：`docs/真机缺陷与改进清单.md:763-777`「存储账本（实测 898 MB）」 |
| 【代码声明】 | 代码/清单里写死的常量或字段值（可被真机推翻） |
| 【代码推断】 | 从代码路径推出的结论，尚未在真机复核 |

### 1.3 两个体积口径不一致（这本身就是一个线索）

- 【代码声明】清单字段 `rootfs.extractedBytes` ≈ **778 MB**：
  `docs/真机缺陷与改进清单.md:754` 记 `BUNDLE_VERIFY_OK: entries=45480 extracted=778239642`；
  `docs/运行时更新与数据保留.md:114` 也按 778 MB 写「只保留一份」。
- 【访客实测】**实际磁盘占用 898 MB**：`docs/真机缺陷与改进清单.md:763-771` 逐项列出
  `/opt/python` 255 MB、`/opt/dsh` 315 MB、`/opt/node` 201 MB、`/usr` 106 MB、其他 ~20 MB。
- 两者差约 120 MB（表观字节 vs 磁盘字节、符号链接与硬链接的计法差异）。
  **后果**：界面上「版本管理」每行显示的体积取自清单字段
  （`RuntimeVersions.kt:100-113` 直接用 `rootfs.extractedBytes`），
  所以它**比系统里真实回收到的空间偏小约 120 MB**；而 0.2.7/0.2.8 发布说明里写的
  「界面读数约 960 MB」是另一套口径（`docs/发布说明-0.2.8.md:10`、`docs/发布说明-0.2.7.md:40`）。
  三个数字（778 / 898 / 960）不是矛盾，是**三个不同的测量点**，用的时候必须说明是哪一套。

## 2. 宿主侧目录：`dsh-runtime/` 长什么样

根路径：【代码】`runtimeParent = File(appContext.noBackupFilesDir, "dsh-runtime")`
（`android/app/src/main/java/io/deepseekharness/mobile/runtime/RuntimeStore.kt:30`）。

**先纠正一个常见误解**：`current` **不是符号链接**，是真实目录名；
`dsh-runtime/` 下面**也没有**按版本 UUID 命名的目录，没有 `backup/`、没有 `snapshot/`
（`RuntimeStore.kt:30-51` 是全部槽位定义）。用户在容器里看到的 `versions/<uuid>` 属于
**插件管理器**，不是运行时本体（见 §3.2）。

### 2.1 槽位表（全部来自 `RuntimeStore.kt:30-51`）

| 名称 | 代码位置 | 是什么 | 谁创建 | 谁删 | 删除失败会怎样 |
|---|---|---|---|---|---|
| `current/` | `RuntimeStore.kt:32` | 在用的 rootfs（PRoot 的 `/`） | 安装/提升（`RuntimeInstaller.kt:523-577`） | 只在「重置环境」时（`RuntimeInstaller.kt:187-207`） | 改名 `stale-current-<36进制时间>`（`RuntimeInstaller.kt:859`、`:925-926`） |

| `preserve-<uuid36>/` | `RuntimePreservePolicy.kt:89` | 提升期间**用户数据的暂存区**（attachments、sessions、skills、plugin-manager、workspace…） | `promoteRuntime` 第①步 `movePreservedItems`（`:523-577`） | **只在用户显式「重置环境」时**（`RuntimeInstaller.kt:681-683`，注释 `:678-680`） | 改名 `stale-preserve-<uuid>-<时间>` |

### 2.3 一次「更新运行环境」的生命周期（正常路径）

安装步骤名全程可查（`RuntimeInstaller.kt:47-180` 的步骤 token）：
`runner_check → parent_prepare → manifest → workspace → transfer → verify → extract → verify_links → retain → promote → cleanup_archive → ready`。

| 阶段 | 磁盘上的变化 | 净增 |
|---|---|---|
| 下载/拷贝归档 | 多一份 `download-*.part`（内置源）或 `rootfs-<sha>.part`（在线源） | +归档体积（内置源约 240 MB 量级，`docs/真机缺陷与改进清单.md:751` 记 `rootfs.bundle` 240,219,335 B） |
| 解压 | 多一棵 `staging-<uuid>/`（≈898 MB） | +898 MB |
| 提升 ① | 用户数据搬进 `preserve-<uuid>/`（体积 = `root/.dsh` + `root/1` + `plugin-manager`） | 不变（只是改名） |
| 提升 ② | `current → previous`、`staging → current` | 仍 +898 MB（`previous` 顶上来了） |
| 提升 ③ | `preserve-*` 回填进新 `current` | — |
| 旋转 | `previous → retained`，**旧 `retained*` 先删** | 删掉旧 retained 后，净增仍是**一份完整 rootfs** |
| 收尾 | 删归档、删 `manifest-*`、`staging-*` 已改名成 current | — |

**结论 1（【代码推断】，与 0.2.8/0.2.9 的界面读数一致）**：一次**成功**的更新之后，
磁盘上**至少有两份完整 rootfs**（`current/` + `retained/`），合计约 1.8 GB —— 这是**设计如此**
（`docs/运行时更新与数据保留.md:114` 明确写「只保留一份」，即 `retained/` 是回滚点），不是 bug。
用户 0.2.9 更新后 App Data 又涨约 0.5 GB【复测实测】与这个量级相符（同时删掉了旧 `retained`）。

**结论 2**：**删除失败**时旧副本不会消失，只会改名：
`retireIfPresent()` 先走严格删除器，失败再走兜底删除器，**两条都失败才改名挪开**
（`RuntimeInstaller.kt:847-879`、`deleteRelaxed()` 在 `:892-916`）。代码注释把话说得很直
（`:844-846`）：「挪到 `stale-*` 后目标路径立即空出来，**磁盘占用留到用户显式重置环境时随其他目录一起清理**」
—— 但 `resetWorkspace()` 并没有清 `stale-*`（见 §2.1 表末行）。**注释里的假设与实现不一致**，
这是本篇最值得记的一条。

### 2.4 失败/中断路径会留下什么

| 场景 | 留下什么 | 证据 |
|---|---|---|
| 下载中断 | `rootfs-<sha>.part`（在线源保留；内置源 `download-*.part` 不保留） | `createWorkspace` 的 `preserveArchiveOnFailure = !bundled`（`RuntimeInstaller.kt:409-413`） |
| 解压中断 | `staging-<uuid>/` | `RuntimeInstaller.kt:405-414`、清理在 `:656-669` |
| 提升中途被杀 | `previous*` 与 `current*` 的组合态之一 + 可能残留 `preserve-*` | 五分支恢复 `RuntimeInstaller.kt:416-469`；**有 `preserve-*` 时不得删 `backupRoot`**（`:427-434`） |
| 旋转中途被杀 | 半份 `retained*`（只有根或只有清单） | `reconcileRetainedSlot()` 直接丢弃（`RuntimeInstaller.kt:478-490`，注释：这种半份副本「不该继续占着数百 MB 磁盘」） |
| 清理失败 | **`stale-<原名>-<时间>`，永久占用** | `RuntimeInstaller.kt:847-879` |

## 3. 容器内（访客侧）：哪些目录会自己长大

容器内 = `current/root/`。以下都在 `runtime` 包之外，是**访客自己写出来的数据**。

### 3.1 `root/.dsh`（用户数据，跨升级保留）

【代码】保留白名单 `RuntimePreservePolicy.kt:30-44`：`sessions`、`settings.yaml`、`.credentials.yaml`、
`attachments`、`skills`；另有 `RuntimePreservePolicy.kt:57-61` 的两条外部映射
`plugin-manager → root/.dsh-mobile/plugin-manager`、`workspace → root/1`。

**明确不保留**（`RuntimePreservePolicy.kt:77-86`，注释给了理由）：`profiles`、`cache`、`tmp`、`logs`、
`llm-deepseek`、`launcher-providers.patch.json`、`runtime-secrets.env`、`plugins`。
其中 `profiles` 不保留的理由是「profiles/node_modules 是指向旧 rootfs 包的符号链接」，
与构建脚本的行为对得上（`scripts/build-embedded-runtime.py:929` 预生成
`root/.dsh/profiles/node_modules/<name>` 链接、`:853-859 add_profiles_module_fallback`）。

【反馈实测】`/root/.dsh` 248 MB，其中 `attachments` 87 MB（含一个 23 MB 视频）、`profiles` 147 MB。

**注意**：`profiles` 在**不被保留**的名单里，但反馈里它已经有 147 MB —— 说明这 147 MB 是
**当前这份 rootfs 里新长出来的**（dsh 自己往 profile 里装东西），不是跨版本搬过来的。
它会在下次更新时随旧 rootfs 一起被丢弃（但那意味着**同时也要重新长一遍**）。

### 3.2 `root/.dsh-mobile/plugin-manager`（插件保留区，跨升级保留）

【代码】固定映射 `RuntimePreservePolicy.kt:57-61`；插件管理器根
`File(store.currentRoot, "root/.dsh-mobile")`（`RuntimePluginManager.kt:17`）。

【反馈实测】`versions/ac6e6877-…` **1.2 GB**（其中 `.npm/_cacache` 560 MB，单个 sha512 blob 522 MB）、
`versions/f1d15472-…` 153 MB（`tmp/git-clone…/.git/objects/pack/tmp_pack…` 152 MB）、
`versions/41968c0f-…` 8.4 MB。`docs/项目状态.md:70` 的真机输出确认这三个事务目录分别对应
`dsh-web`、`dsh-web-mobile`、`dshmarket` 的安装事务。

**代码里没有任何淘汰逻辑**：`scripts/../assets/support/plugin-manager.cjs` 只**读** `versions/`
（`:695`、`:704`、`:862`、`:917`、`:1644`）和 `REPAIR_MAX_VERSIONS` 扫描上限（`:864`），
**没有一处删除 `versions/*`**。每装/更新一个插件就新增一份事务目录，永久累积。

同文件 `:1368-1376` 的 `npmInstall()` 传的选项是
`install <spec> --ignore-scripts --legacy-peer-deps --bin-links=false --no-audit --no-fund --omit=dev --fetch-retries=1 --fetch-timeout=30000 --registry=… --userconfig=<dir>/npmrc --globalconfig=<dir>/global-npmrc`。

- **可以确定**：这些选项里**没有** pin npm 的 cache 目录（没有 `--cache` / `npm_config_cache`），
  也**没有** `--prefer-offline`（全仓库 `scripts/` 下 grep `npm_config_cache|NPM_CONFIG_CACHE|\.npm|store-dir`
  只命中一处测试文件）。
- **不能确定**：所以「`.npm/_cacache` 为什么会出现在 `versions/<事务>/` 里」，
  **代码里未找到会把它放在那里的配置，需要真机实测确认**（三个候选：
  ① 有人在容器里手工跑过 npm / `dsh plugin add`，`--prefix` 或 cwd 把 cache 落在了事务目录；
  ② 某次 npm 在 `TMPDIR` 下的临时操作被中断，留下了 `_cacache` 形态的目录；
  ③ 环境变量来自我们看不到的 profile 配置）。
  **好消息**：不管怎么来的，`_cacache` 都是**纯下载缓存**，删掉只会导致下次重装要重新下载。

### 3.3 其它会自己长大的访客目录

| 目录 | 代码/证据 | 上限 |
|---|---|---|
| `root/1`（默认工作区，保留） | `RuntimePreservePolicy.kt:57-61` | **无上限** |
| 投递区（`/mnt/inbox`、`/mnt/outbox` 的宿主侧） | `RuntimeMailboxPolicy.kt:70`、`:73` | 20,000 条 / **512 MB** |
| `/root/.local/share/pnpm`（pnpm store） | 【反馈实测】348 MB | 无上限；**不在保留白名单里，也不会被任何清理器回收**（它只能在 rootfs 内部，随旧 rootfs 一起被丢） |

## 4. 关于那「消失的 3.9 GB」：三个候选与各自的确认证据

【反馈实测】App Data 6.96 GB，容器内约 3.1 GB；【复测实测】7.61 GB。
容器内看到的永远只有 `current/` 一棵树，所以差额只能落在 `dsh-runtime/` 的**其它槽位**，
或 `dsh-runtime/` 之外的宿主侧目录（§2.2）。

**候选 A（最可能）：`stale-*` 残留 × 多轮更新。**
该设备走过 0.2.4 → 0.2.9 的**全部**版本，而这段历史每一步都在制造残留：
0.2.4 更新必定失败（`FILESYSTEM_ERROR` 来自 `cleanupIfPresent(backupRoot)`）→ 0.2.5 改成「删不掉就改名挪走」
→ 0.2.6 因固定名 `stale-previous` 撞名再次失败 → 0.2.7 改成唯一名 + 同族最多重试 3 份
→ 0.2.8 才加不跟随符号链接的兜底删除器（链路见 `docs/项目状态.md:21-65`、
`docs/发布说明-0.2.8.md:9-10`）。0.2.7/0.2.8 文档把量级写得很明确：
「每轮更新多占一份 rootfs（界面读数约 960 MB）」。
**确认证据**：`ls -la` 应用私有的 `no_backup/dsh-runtime/`（需要 release 包之外的路径，见 §6.1），
数 `stale-*` 有几份、算它们加起来多少字节。

**候选 B（很可能同时存在）：`preserve-*` 孤儿目录。**
只要有一次提升没走完（被杀、崩溃、`RUNTIME_PRESERVE_FAILED`），
`preserve-<uuid>/` 就会留在 `dsh-runtime/` 里，而它**只在用户显式「重置环境」时才被清**
（`RuntimeInstaller.kt:678-683`）。如果里面有 `attachments` + `profiles` + `plugin-manager`，
一份就可能接近 1 GB（本轮 `root/.dsh` 248 MB + `plugin-manager` 1.2 GB 就是它的内容清单）。
**确认证据**：同样在 `dsh-runtime/` 里数 `preserve-*` 的份数与体积。

**候选 C：`current/` 里的 `plugin-manager` 与 pnpm store 被**重复**计入了两份 rootfs。**
`plugin-manager` 是**跨升级保留**的，所以它在物理上只存一份；但如果同时存在 `retained/` 与
`stale-*` 这些**旧 rootfs**，那些旧树里也可能各有一份自己的 `root/.dsh`（旧版本留下的、
没人清）。这条与候选 A 叠加时最容易把数字推上去。
**确认证据**：对 `dsh-runtime/` 下**每一棵**树分别 `du -sh`，看 `root/.dsh` 与
`root/.dsh-mobile` 出现了几次。

> **诚实边界**：以上都是**从代码推断的结构性解释**，不是实测结论。
> 代码能证明的是「这些槽位会存在、且没有任何清扫器」；
> **到底哪一份占了多少，必须真机 `du` 才能定案。**

## 5. 回收清单

排序原则：先做「应用内、无风险、立刻见效」的，再做「容器内命令」，最后是「不建议动」。

### 5.1 A 类：应用内可做（安全、有入口）

| # | 操作 | 入口（代码位置） | 预期释放 | 风险 |
|---|---|---|---|---|
| A1 | **删除上一版本** | 设置 →「版本管理」→ 运行时版本管理 → 删除上一版本（`src/App.tsx:1990-2004`；原生 `MobileRuntimeController.kt:131-136` → `RuntimeInstaller.kt:249-264`） | **约 778 MB（界面口径）/ 约 898 MB（访客实测口径）**，即一整份 rootfs | 低。只删 `retained*`，当前运行时不受影响；**删掉就没有回滚点**，下次安装会重新留一份。**安全兜底**：原生侧只接受 `target == "previous"`（`RuntimeVersions.kt:49-55`），传 `current`/`bundled` 一律以 `RUNTIME_VERSION_TARGET_INVALID` 拒绝 |
| A2 | **清空诊断日志** | 设置 →「诊断与日志」→ 清空日志（`MobileRuntimePlugin.kt:1435` `clearDiagnosticLog` → `DiagnosticLog.kt:141`） | ≤ 4 MB（`DiagnosticPolicy.kt:155`） | 无。诊断记录丢失（0.2.8 那种 `reason=fallback_*` 取证记录也会没） |
| A3 | **删会话快照** | 设置 →「版本管理」→ 会话备份 → 删除（`src/App.tsx` 的会话备份区块；原生 `MobileRuntimeController.kt:203-206`） | 每份 = 当时会话目录的字节副本，**合计上限 512 MB / 3 份**（`RuntimeSessionSnapshots.kt:43`、`:46`）；反馈设备实测约 6 MB（`docs/项目状态.md`，`bytes=6037730`） | 低。删掉就没法把旧会话回填回来了 |
| A4 | **重置环境** | 设置 →「重置环境」→ 二次确认（`src/App.tsx:1207`、`:5291`；原生 `MobileRuntimeController.kt:289-304` → `RuntimeInstaller.kt:187-207`） | 删 `current/` + `previous/` + `retained/` + `preserve-*` + 各种临时件。**能收回多少取决于当时存在几份副本**（每份约 0.9 GB），所以只能给量级：**至少 2 份 ≈ 1.8 GB**，多份残留时可达数 GB；**但 `stale-*` 一分都清不掉** | **高**。会丢掉整个运行时（要重新装、内置解压约 3 分钟【0.2.9 真机回执】），并清掉 `preserve-*` 里的用户数据。**必须在 A1 无效、且已确认 `stale-*` 是主要占用时再考虑** |

### 5.2 B 类：只能在容器内用命令完成

前提：**先停掉 Harness 与终端**（`MobileRuntimeController.kt:277-287` 的停止路径），
否则正在跑的访客进程会踩到被改动的目录。容器内命令用应用自带的终端执行。

| # | 命令 | 作用 | 预期释放 | 风险与恢复 |
|---|---|---|---|---|
| B1 | `rm -rf /root/.dsh-mobile/plugin-manager/versions/f1d15472-*` 里的 `tmp/` 子目录<br>（更稳妥：`find /root/.dsh-mobile/plugin-manager/versions -maxdepth 3 -type d -name 'tmp' -exec rm -rf {} +`） | 清掉**失败安装**留下的 git 克隆残片（`tmp/git-clone…/.git/objects/pack/tmp_pack…`） | **约 152 MB**（【反馈实测】） | 低：`versions/f1d15472-…` 是失败事务，`repair` 只会**扫描**它并跳过不可用副本，删掉更干净 |

| B3 | `rm -rf /root/.local/share/pnpm`（或 `pnpm store prune`，但 store 不在 PATH 时必须写全路径） | 清 pnpm 内容寻址 store | **约 348 MB**（【反馈实测】） | 中：这是**唯一的包缓存**，删掉后任何 `pnpm install` 都要重新下载。**先确认没有正在跑的 pnpm/Node 进程** |
| B4 | 清旧附件：`ls -lt /root/.dsh/attachments` 挑旧的删（例如那个 23 MB 视频） | 用户自己判断哪些附件不再需要 | 按选中的文件算，反馈里 `attachments` 共 **87 MB** | 中：附件是会话的一部分，删了对话里就看不到原文件 |
| B5 | `du -sh /root/* /root/.dsh/* 2>/dev/null \| sort -h \| tail -20` | **不是回收，是取证**：先看谁在长 | — | 无。**建议先跑这条**，再决定动上面哪一条 |
| B6 | `rm -rf /root/.npm /root/.cache` | 访客家目录下的通用缓存 | 未知，需实测 | 低；`/root/.cache` 可能含 dsh 自己的构建缓存 |

> 所以这些释放**只对「当前这份 rootfs」生效**；下一次运行环境更新后，`root/.dsh` 会被保留、

> 而 B3（`/root/.local/share/pnpm`）**不在保留名单里，下次更新会自动消失**。

## 6. 怎么才能看见 / 怎么才能收回来（最小功能方案与工作量）

### 6.1 现状：用户与开发者都看不见

- **应用内**：全仓库 grep `StorageStatsManager|usableSpace|totalSpace|freeSpace|getFreeBytes|diskUsage`
  在 `android/` 下**0 命中** ⇒ **没有任何「查看占用」的界面或原生接口**。
  唯一一处 `StatFs` 是自检里读当前根目录的可用字节（`RuntimeSelfCheck.kt:168`），只报「够不够装」。
- **系统侧**：`dumpsys diskstats` 只给 App Size / App Data / Cache 三个总数，不拆目录。
- **容器内**：PRoot 的 `/` 就是 `current/`，**看不到** `stale-*`、`preserve-*`、`previous/`、`retained/`
  （`RuntimeCommand.kt:150-191` 只 `-r current`）。
- **release 包**：诊断日志写在应用私有目录，**不可 `run-as`**
  （这一点 0.2.9 的发布说明也踩过：`docs/发布说明-0.2.9.md` 明确写「本轮没拿到」清理读数）。

⇒ 结果：**`stale-*` 到底有几份、占多少，目前只能靠本文 §4 的推断，无法在设备上直接读。**

### 6.2 建议的最小功能（按性价比排序）

| 优先级 | 功能 | 动手位置 | 工作量估计 |
|---|---|---|---|
| P0 | **诊断日志里加一条「运行时目录盘点」**：启动/安装后扫描 `runtimeParent` 的直接子项，按**白名单前缀**归类（`current` / `previous` / `retained` / `staging-` / `download-` / `rootfs-*.part` / `preserve-` / `stale-`），只记**类别、份数、总字节**（不记路径名，符合诊断日志的 token 白名单约束，见 `RuntimeRetireTokens.kt:23-48`、`RuntimeInstaller.kt:936-939`） | `RuntimeInstaller.kt` 新增一个记录函数 + 在 `install()` 的 `ready` 前与 `prepareRuntimeParent()` 后各调一次；沿用 `store.diagnostics.record(...)` | **0.5 天**（纯读遍历 + 一条日志） |
| P1 | **`stale-*` 有了真正的清扫器**：把「按前缀清扫」加进 `cleanTransientWorkspaces()` **或** 新增一个只在**用户显式动作**下调用的入口。⚠️ 不建议默默加进 `install()`：那会把「清理失败」变成静默的多次重试，掩盖真故障 | `RuntimeInstaller.kt:656-669`（`cleanTransientWorkspaces`）；删除用现成的 `deleteRelaxed()`（`:892-916`） | **0.5 天** |
| P1 | **「重置环境」如实说清能清什么**：现在的注释（`:844-846`）声称 `stale-*`「留到用户显式重置环境时随其他目录一起清理」，但实现里没有。二选一：改注释，或按上一条让实现追上注释 | `RuntimeInstaller.kt:187-207` 与 `:844-846`；文案在 `src/App.tsx` 的重置确认区块 | **0.25 天**（改注释）／含上一条一起做 |
| P2 | **「版本管理」页顶部加一行「运行时占用」**：显示 `current` + `retained` + `stale` 的**扫描体积**（而不是清单里的 `extractedBytes`），并在 `stale` 非零时给一个「清理残留」按钮 | 原生：`RuntimeVersionCatalog.list()` 旁边加一个 `usage()`（`RuntimeVersions.kt:99-113`）+ `MobileRuntimePlugin.kt:517-556` 加一个 call；前端：`src/App.tsx:2011-2054` 的 `RuntimeVersionsPanel` | **1.5–2 天**（含桥接与测试） |
| P3 | **插件事务目录的淘汰策略**：`versions/<事务>` 按份数/体积上限淘汰旧事务（保留最近 N 份 + 最近 M 天） | `assets/support/plugin-manager.cjs`（`repair`/`install` 生命周期处，`:850-900`） | **1 天**（要小心：`repair` 依赖历史事务里的副本来重建链接，淘汰规则必须先证伪这个依赖，见 `docs/项目状态.md:70`） |
| P4 | **插件安装时 pin npm 缓存目录**，并在事务成功后删除该事务目录下的 `_cacache` | `assets/support/plugin-manager.cjs:1368-1376` 的 `common` 选项数组 | **0.5 天**（要先按 §3.2 的候选把「`_cacache` 从哪来」查清，否则可能在修一个不存在的问题） |
| P5 | **根因收口：查出严格删除器为什么在真机上失败**（0.2.8 是绕过而不是修好，`docs/发布说明-0.2.8.md:39-40` 明确列为未解决） | 需要真机取证：`stale-*` 场景下把失败类别细化到 errno 级（`RuntimeRetireTokens.kt:57-71` 已有 errno→token 映射，等一条真读数） | **取证 0.5 天 + 修未知** |

> 合计：**P0+P1+P2 约 3 天**能拿到「看得见 + 能收回」的完整闭环；
> P3/P4 是防复发，P5 是根因。

### 6.3 想要一次把空间收干净的操作顺序（建议）

1. 应用内：**A1 删除上一版本** → 立刻回收约 0.9 GB（且这是唯一有保证的一步）。
2. 容器内：跑 **B5** 看谁在长 → 按结果执行 **B1 + B2**（约 700 MB，低风险）。
3. 如果 `App Data` 仍然远大于「容器内 × 1 + 0.9 GB」，那么差额就是 §4 的 `stale-*` / `preserve-*`，
   **此时唯一的应用内手段是 A4「重置环境」**（会丢运行时与 `preserve-*` 里的用户数据）。
4. 无论哪一步，**更新一次运行环境后重新量一次** `dumpsys diskstats`：如果 App Data 每更新一次就涨一份
   rootfs 的量级，说明 `stale-*` 仍在增长，那就必须做 §6.2 的 P1。

## 8. 一句话总结

**一份 rootfs 约 778 MB（清单）/ 898 MB（访客实测）**，设计上同时存在两份（`current` + `retained`，
约 1.8 GB）是**有意为之**；**「更新一次涨一份 rootfs」的机制在 0.2.8 之后仍未被完全关掉** ——
删除失败依然会改名成 `stale-*` 并永久占磁盘，而**应用里既看不到它，也没有能清掉它的入口**
（`resetWorkspace()` 不匹配 `stale-*`，与 `RuntimeInstaller.kt:844-846` 的注释不一致）。
下一版最值得做的是 §6.2 的 **P0（让它可见）+ P1（让它可清）**。

## 9. 本轮已实现 / 仍待做（P0 / P1 / P1'）
