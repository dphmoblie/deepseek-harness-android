# 0.2.5 测试版：运行时更新不再被清理失败卡死

基线是一份装了内置运行时 0.2.4-mobile-339、当前运行时还停在 0.2.4-mobile-337 的 HONOR 真机：
点「更新运行环境 → 确认更新」必定失败，界面只给一句「无法安全读写应用私有运行时文件」，
而用户被锁在更新页——打不开 Harness，终端还能用。

## 改动

- **清理失败不再阻塞更新**：新增 `RuntimeInstaller.retireIfPresent(target, reason)`。
  它先按原来的严格删除器删；删不掉时把目标**改名挪到 `stale-*`**，让出路径继续安装，
  只在诊断日志里留一条 `WARN|RUNTIME_PHASE|phase=cleanup|result=skipped|code=…|reason=…`。
  之所以必须挪走而不是只吞异常：`previous/`、`current/` 这些路径随后要被提升流程改名占用，
  留在原处只会让安装换一个地方继续失败。改动覆盖三处：
  - `recoverInterruptedPromotion()`：遗留备份（`previous*`）与半份当前根（`current*`）的清理；
  - `cleanTransientWorkspaces()`：`staging-*`、`manifest-*.json`、`download-*.part`；
  - `cleanResumeFilesExcept()`：`rootfs-<sha>.part` 断点续传分片。
- **安装失败写清卡在哪一步**：`install()` 全程记录步骤名，失败时除原有的
  `RUNTIME_PHASE|phase=error|code=…` 之外再写一行
  `RUNTIME_PHASE|phase=error|code=…|reason=<step>|result=failed`。
  步骤 token 覆盖 `runner_check`、`parent_prepare`、`parent_check`、`recovery`、
  `recovery_scan`、`recovery_drop_backup`、`recovery_swap_current`、`restore_preserved`、
  `retained_slot`、`transient_cleanup`、`workspace`、`transfer`、`verify`、`extract`、
  `verify_links`、`retain`、`promote`、`ready`。
  原生的失败文案从来不进 logcat、也不进审计（审计只记 `failure.code`），
  所以过去只能看到 `FILESYSTEM_ERROR` 这一个码；现在能直接定位到具体步骤。
  字段仍走诊断日志的既有约束：只允许 `[a-z0-9._-]` 这类 token，不含路径、URL 或中文。
- 沿用的上一版内容见 [发布说明-0.2.4.md](发布说明-0.2.4.md)（副屏预览节奏、触摸直传、
  目标应用切换、节点树与中文注入，以及沙箱与插件接回的修复）。

## 未解决的设备限制

- 本轮只修「清理失败把更新卡死」这一类故障。如果失败原因真是父目录不可写，
  更新依旧会失败——但诊断日志现在会直接给出 `reason=`，不必再从零排查。
- 挪到 `stale-*` 的目录会继续占磁盘，只在用户显式「重置环境」时随其他运行时目录一起清理。
- 更新门槛本身没变：APK 内置运行时版本与已装版本不一致时，仍要求先更新运行环境。

## 验证

- Kotlin 单元测试：**72 个测试类 / 573 个用例 / 0 失败 / 21 跳过**
  （`gradle :app:testDebugUnitTest`，本机 Gradle 8.11.1 + Android SDK）。
- 脚本层：**166 项 / 162 通过 / 0 失败 / 4 跳过**（`node --test scripts/*.test.mjs`，
  跳过的 4 项都是「Windows 缺 koffi 原生绑定」的跨进程写锁用例）。
- 前端本轮没有改动，仍按全量跑一遍 vitest / tsc / eslint 收口。
- 真机回执：待本版 APK 装上 HONOR 真机后，重跑一次「更新运行环境」，把
  `RUNTIME_PHASE` 的新日志与最终结果补到本节。
