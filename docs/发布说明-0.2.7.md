# 0.2.7 测试版：清理旧运行时残留不再阻塞更新

基线是 0.2.6（`versionCode 28`）的真机现场：装好之后界面又要求「更新运行环境」，点「确认更新」等 35 秒
仍停在更新门槛；诊断日志里只有两行错误、**没有** 0.2.5 那条 `phase=cleanup|result=skipped` 记录：

```text
2026-10-04T09:14:29.724159Z|ERROR|RUNTIME_PHASE|phase=error|code=FILESYSTEM_ERROR
2026-10-04T09:14:29.725195Z|ERROR|RUNTIME_PHASE|phase=error|code=FILESYSTEM_ERROR|reason=recovery_drop_backup|result=failed
```

说明失败发生在 `RuntimeInstaller.recoverInterruptedPromotion()`「丢掉上一版本」那一步，而且**连改名挪开的
回退也失败了**：0.2.5 的回退用的是固定名 `stale-previous`，而 16:33 那次更新留下的正是这棵**同样删不掉的**
同名残留，于是回退里的「先把同名残留删掉」又抛异常，被 `catch (_: Throwable) { throw failure }` 原样抛回，
整个安装中止。

## 改动

- **旧残留一律让路，绝不阻塞更新**：`retireIfPresent(target, reason)` 重写为
  「删不掉就改名挪开」，并且：
  - 改名目标改成唯一名 `stale-<原名>-<36 进制时间戳>`，不再复用固定名 ⇒ 不会和上一次的残留撞名；
  - 挪开之前先把同族残留（`stale-<原名>` 与 `stale-<原名>-*`）按**最多 3 份**重试清理，失败的只记
    诊断日志、**绝不外抛** ⇒ 旧残留的存在不会让这一次安装失败；
  - 只有连 `Os.rename` 都失败（说明运行时目录本身不可写）才把原始错误抛出去，那才是真故障。
- **所有清理点都变容错**：`cleanupIfPresent()` 由严格删除改成 `retireIfPresent(target, "cleanup")`，
  于是 `resetWorkspace()`（重置环境）、提升/保留路径、`cleanupWorkspace()` 的 staging 与压缩包、
  解压与校验失败后的目标目录，全都变成「删不掉就改名挪开 + 记一条
  `phase=cleanup|result=skipped|code=…|reason=…`」。清理只是收尾，不该拖垮一次本可成功的更新。
- **诊断日志里能看出「为什么删不掉」**：新增 `runtime/RuntimeRetireTokens.kt`，把清理失败映射成固定
  token 写进 `code`（`EACCES`/`EPERM`/`EBUSY`/`ENOTEMPTY`/`EIO`/`EROFS`/`ENAMETOOLONG`/`ERRNO_OTHER`、
  `SECURITY`/`DIR_ITER`/`FILESYSTEM`/`IO`/`UNSUPPORTED`/`UNKNOWN`），另带 `reason`（`stale_<目录名>` 之类
  的规范化名字）与 `count`（同族残留份数）。**不含路径、不含中文**，符合诊断日志「只记事件名、状态码、
  布尔值与计数」的契约。
- 版本号 0.2.6 → 0.2.7（`versionCode 29`）。
- 上一版内容见 [发布说明-0.2.6.md](发布说明-0.2.6.md)、[发布说明-0.2.5.md](发布说明-0.2.5.md)。

## 未解决的设备限制

- **那棵 `previous/` 为什么删不掉仍未查清**。现在它只会被改名成 `stale-previous-*` 留在运行时目录里，
  下一次安装会再试删一遍（每次最多重试 3 份同族残留；**删除始终失败时每轮更新仍会新增一份 `stale-*`**），
  所以它不再挡住更新，但**仍会占磁盘**：界面读数里一份 rootfs 约 960 MB。真正修掉删除器本身才算收口。
- 清理失败的容错意味着失败不再「响亮」：只有诊断日志里那一条 `result=skipped` 能看出来，界面仍显示
  更新成功。这是有意取舍（更新可用优先），但排查时要先看诊断日志。
- 副屏相关限制与 0.2.6 相同：需要 Shizuku 授权与 Android 10 及以上；触摸直传（`touchChannel=stream`）
  依赖隐藏接口 `InputManager.injectInputEvent`，被 ROM 拦掉时回退到离散的 `input -d <显示编号>`；
  节点树与中文注入要求用户手动开启应用的无障碍服务。

- Kotlin 单元测试：**73 个测试类 / 577 个用例 / 0 失败 / 0 错误 / 21 跳过**（`gradle :app:testDebugUnitTest`），
  其中新增 `RuntimeRetireTokensTest` 4 个用例（errno 映射、异常类别映射、`RuntimeFailure` 的 cause 参与
  映射、token 必须匹配 `^[A-Z][A-Z0-9_]{0,47}$`）。
- `lintRelease`：**0 Error / 48 Warning**（与 0.2.6 持平，没有新增告警）。
- 脚本层：**166 项 / 162 通过 / 0 失败 / 4 跳过**（`node --test scripts/*.test.mjs`，跳过的 4 项都是
  「Windows 缺 koffi 原生绑定」的跨进程写锁用例）。
- 前端（本轮未改）：**33 个测试文件 / 431 个用例全通过**，`tsc --noEmit` 与 `eslint .` 均无输出。
- 真机回执（HONOR / Android 17，2026-10-04 17:46 本地，UTC 09:46）：CI 出的 release APK
  （`app-release.apk` 314,410,868 B，run `37192179272`）`adb install -r` 成功（`versionCode 29` /
  `versionName 0.2.7`），重启后界面再要求更新，点「确认更新」**20 秒后进入「正在进入对话」**，门槛消失。
  诊断日志读出这一段（`设置 → 诊断与日志 → 诊断日志（最近 64 KB）`）：

  ```text
  2026-10-04T09:46:44.680908Z|WARN|RUNTIME_PHASE|phase=cleanup|result=failed|code=FILESYSTEM|reason=stale_previous|count=1
  2026-10-04T09:46:44.681402Z|WARN|RUNTIME_PHASE|phase=cleanup|result=failed|code=FILESYSTEM|reason=backup_root|count=1
  2026-10-04T09:46:44.681698Z|WARN|RUNTIME_PHASE|phase=cleanup|result=skipped|code=FILESYSTEM_ERROR|reason=backup_root|count=1
  2026-10-04T09:46:44.681945Z|WARN|RUNTIME_PHASE|phase=cleanup|result=failed|code=FILESYSTEM|reason=cleanup|count=0
  2026-10-04T09:46:44.682040Z|WARN|RUNTIME_PHASE|phase=cleanup|result=skipped|code=FILESYSTEM_ERROR|reason=cleanup|count=0
  2026-10-04T09:46:44.682448Z|INFO|RUNTIME_PHASE|phase=preparing
  2026-10-04T09:46:45.138454Z|INFO|RUNTIME_PHASE|phase=verifying
  2026-10-04T09:46:45.140919Z|INFO|RUNTIME_PHASE|phase=extracting
  2026-10-04T09:47:04.959065Z|INFO|RUNTIME_PHASE|phase=ready
  2026-10-04T09:47:04.964238Z|INFO|RUNTIME_SNAPSHOT|reason=auto|result=created|count=3|files=11|bytes=6037730
  ```

  即：删不掉的 `previous/`（`reason=backup_root`）与上一次留下的 `stale-previous`（`reason=stale_previous`）
  都只留一条 `result=failed`，改名挪开后写一条 `result=skipped`，安装照常 `preparing → ready`（20 秒），
  并照常写下自动会话快照 ⇒ 修复端到端成立。
- 真机回执还给出了删除器失败的类型：`code=FILESYSTEM` 来自
  `RuntimeRetireTokens.classify()` 的 `is FileSystemException -> "FILESYSTEM"` 分支，说明真机上抛出的是
  `java.nio.file.FileSystemException`（或其子类），不是 `ErrnoException` ⇒ 现有 errno 分支没命中，
  且 `AccessDeniedException` / `DirectoryNotEmptyException` / `NoSuchFileException` 会被该分支先吃掉。
  下一版把子类拆开（`ACCESS_DENIED` / `NOT_EMPTY` / `NO_SUCH_FILE` / `NOT_A_DIR`），并给 `stale-*`
  残留加一个**不跟随符号链接**的回退删除器，好把那约 960 MB 真正回收掉。
