# 悬浮球与内容分享设计

> 目标：让用户在其他应用里也能一键回到 Harness 对话；让 AI 生成的内容
> （对话文本、代码、Markdown、运行时文件、图片）能交给手机上的第三方应用打开。
> 本文档经确认后进入实施，实施结果以真机验收为准。

## 一、背景与范围

### 1.1 要解决的问题

1. **跨应用回到对话**：Harness 常驻后台时，用户切到别的应用后没有快捷方式回去，
   只能从最近任务或桌面图标绕。
2. **内容出不去**：AI 写出的代码、报告、Markdown 只能停留在对话里，手机上没法
   直接用其他应用打开。当前全项目只有一个导出入口——诊断日志分享
   （`MobileRuntimePlugin.shareDiagnosticLog`），对话内容与终端内容都明确不导出。

### 1.2 明确不做

- **不做保活承诺**：悬浮球能否常驻取决于系统与厂商后台策略，与「后台保持 Harness」
  的既有表述保持一致，不宣传为绝对可用。
- **不扩大设备桥命令面**：`DeviceCommand` 保持 `SCREENSHOT / UI_DUMP / TAP / INPUT_TEXT`
  四类不变（见 `docs/设备桥信任边界.md`）。分享走独立桥方法，不混进设备命令。
- **不让模型自主发起分享**：分享只由用户点击触发。理由是设备桥文档的既有结论——
  PRoot 单 uid 下审批门不是安全边界，同 uid 代码可读 `/proc/<pid>/environ` 拿到令牌
  绕过工具层，因此"AI 能不能把内容发出去"不能靠审批门兜底，只能把动作放在用户手里。
- **本轮不做客户端插件**：消息级的「分享」按钮（基于 `__ModuleLoader__` +
  `dsh-client-ui-slots` 注入）体验更好，但要绑定官方前端 0.1.5-rc.2 的插槽契约，
  升级时可能返工，留待下一轮单独评估。

## 二、总体架构

三条能力**互不依赖**，可分别实现、分别验证，共享一个 App 侧出口 `ShareExporter`：

```
① 悬浮球               ② 选区分享               ③ 运行时产物
OverlayBallService    HarnessActivity          设置页·产物列表
  WindowManager         Toolbar 菜单项             │
  PendingIntent         evaluateJavascript     RuntimeBridge
  PopupWindow 菜单      读选区缓存               listRuntimeArtifacts
      │                      │                      │
      ↓                      ↓                      ↓
KeepAliveEntryActivity    ┌──── ShareExporter ────┐
（现成的透明转发组件）     │ 文本 → ACTION_SEND     │
                         │ 文件 → cache 副本      │
                         │   + FileProvider      │
                         │   → ACTION_SEND/VIEW  │
                         └───────────────────────┘
```

## 三、悬浮球

### 3.1 权限

`SYSTEM_ALERT_WINDOW` 是特殊权限，**不会弹运行时对话框**，必须引导用户到系统设置页
手动开启。沿用 `openAllFilesAccessSettings` 的既有模式：

- 设置页显示权限状态；未授权时开关置灰，点击跳
  `Settings.ACTION_MANAGE_OVERLAY_PERMISSION`。
- 从设置页返回时用 `onResume` 重新读取 `Settings.canDrawOverlays()`，而不是信任跳转结果。

### 3.2 视图

- `WindowManager.addView` + `TYPE_APPLICATION_OVERLAY`
- 标志位：`FLAG_NOT_FOCUSABLE`（不抢输入焦点）、`FLAG_LAYOUT_NO_LIMITS` 不加
  （避免球跑到状态栏下）、不吃返回键
- 尺寸：48dp 圆形，复用品牌标识图 `app-mark.png` 作为球面
- **位置**：初始在屏幕右侧垂直居中；可拖动；松手后吸附到最近的左右边缘；
  位置持久化到设置，重启后恢复。拖动判定用 `touch slop`，避免误触发点击。

### 3.3 交互

| 手势 | 行为 |
|---|---|
| 短按 | `PendingIntent` → `KeepAliveEntryActivity`（透明转发，已认证直进 `HarnessActivity`，否则回管理页） |
| 长按 | 在当前 overlay 窗口上弹一个 `PopupWindow` 菜单 |
| 拖动 | 移动球体，松手吸附 |

**复用 `KeepAliveEntryActivity` 而不是新写一个转发 Activity**：它已经处理好了
"已认证则进 Harness、否则回管理页"，并刻意避开了 `singleTask` 的 clear-top 会连带
撤销一次性会话凭据的问题（见 `docs/ARCHITECTURE.md`）。悬浮球短按与常驻通知点击
走同一条已验证路径。

菜单项定为两项：

- **打开设置** → 回管理界面
- **隐藏悬浮球** → 直接关闭 `overlayBallEnabled` 开关（与设置页一致，不引入额外的
  "临时隐藏"状态）

> 取舍：曾考虑加「重新开始会话」，但"新开会话"需要 Harness 侧配合（会话生命周期
> 由官方前端管理），属于跨边界改动，本轮不做。

### 3.4 服务与通知

悬浮球由独立前台服务承载，否则进程被回收后球就没了。

- **刻意不与 `HarnessKeepAliveService` 合并**：「想要悬浮球」和「想保持运行时」是
  两件独立的事，合并会让用户无法只选其一。
- 通知渠道复用 `harness_keep_alive`，`IMPORTANCE_LOW`；文案为固定资源字符串，
  **不含** URL、端口、凭据、会话内容。
- 服务本身不执行 Shell、不连接 Shizuku、不持有任何凭据。
- 开关关闭、权限被系统收回（`canDrawOverlays()` 为 false）时立即 `stopSelf()`，
  不留无法解释的通知——沿用 keep-alive 的既有做法。

### 3.5 开关入口

并入现有「运行与后台」二级页，与「后台保持」同级，含权限状态与引导入口。
设置项名 `overlayBallEnabled`，默认 `false`。

## 四、② 选区分享

### 4.1 为什么用选区，而不是定位消息

rc.2 官方前端的稳定 `data-*` 属性里**没有消息容器标识**（实测只有 `data-code-block-*`、
`data-dockkit-*`、`data-file-type-mark` 等），按 DOM 结构定位"最后一条回复"会重蹈
"适配层碰 CSS Modules 哈希类"的覆辙，且官方前端一升级就断。

选区方案零 DOM 依赖，而且天然满足"用户手动决定分享什么"：用户选中哪段，就分享哪段。

### 4.2 流程

1. `harness_toolbar.xml` 新增菜单项 `action_share_selection`
2. 点击 → `webView.evaluateJavascript` 读取选区
3. 为空 → Toast 提示"请先选中要分享的内容"
4. 非空 → `ShareExporter.shareText` → `ACTION_SEND` + `text/plain` + `createChooser`

### 4.3 选区缓存

风险：点击 Toolbar 时 WebView 可能失焦，`window.getSelection()` 已被清空。

处理：页面加载完成后注入一段小脚本，监听 `selectionchange`，把**最后一次非空选区**
缓存在私有全局变量 `__dshMobileSelection`；点击时优先读缓存，回退到实时选区。

注入脚本只写这一个私有全局变量，**不读取页面状态、不发起请求、不给页面任何新能力**。

### 4.4 错误处理

| 情况 | 行为 |
|---|---|
| 选区为空 | Toast 提示，不弹分享面板 |
| 页面未就绪 | 菜单项置灰 |
| 文本超长 | 截断到上限（默认 100KB）并在分享前提示 |

## 五、③ 运行时产物

### 5.1 数据来源

rootfs 位于 `noBackupFilesDir/dsh-runtime/current/`，**是 App 私有目录下的普通目录树，
App 可以直接用 File API 读取，不需要启动 PRoot、也不要求运行时正在运行**。

访客的 `HOME=/root`（见 `RuntimeCommand`），AI 写出的产物默认落在那里。
列表因此取自 `<rootfs>/root/`。

> 待核实：`<rootfs>` 内访客 `/root` 的对应位置需按实际解包结构确认
> （`dsh-runtime/current/` 之下是否直接就是访客根）。实施第一步先核实并用单测钉住。

### 5.2 桥接口

新增两个方法（`MobileRuntimePlugin`）：

| 方法 | 参数 | 返回 |
|---|---|---|
| `listRuntimeArtifacts` | 无 | 条目数组：`name`、`size`、`modifiedAt`、`isDirectory` |
| `exportRuntimeArtifact` | `name` | 导出到分享缓存后的展示结果 |

**权限要求**：仅应用私有原生桥接调用，网页端与外部应用均不可达。浏览器预览直接拒绝
（沿用 `src/platform/browser.ts` 的既有做法：非原生环境返回不可用）。

**参数校验**（原生与前端双重）：

- `name` 只允许单层文件名，限制 255 字符以内的受控字符集
- **显式拒绝** `/`、`\`、`..`、空字节、绝对路径与前缀匹配（`/root` vs `/rootEvil`）
- 解析结果必须落在 `<rootfs>/root/` 之内，越界即拒绝

**返回值脱敏**：只返回文件名、大小、修改时间与类型；**不返回绝对路径、不返回用户路径、
不返回文件内容**。

### 5.3 列举规则

- 只列一级条目，不递归
- 跳过隐藏条目（`.` 开头）
- **不跟随符号链接**：`lstat` 判定，软链一律当作不可分享条目跳过
- 按修改时间倒序，上限 50 条
- 目录条目也列出但**不可直接分享**（本轮不做递归打包），点击给出说明

### 5.4 导出与分享

1. 校验大小上限（默认 50MB），超限直接拒绝并说明
2. 复制到 `cacheDir/share/`，目标文件名做净化（去路径分隔符与控制字符）
3. `FileProvider.getUriForFile`，按 MIME 类型分两种出口，**用户点哪个走哪个**，不自动二选一：
   - **分享**（列表项主操作）→ `ACTION_SEND` + `EXTRA_STREAM` +
     `FLAG_GRANT_READ_URI_PERMISSION` + `createChooser`
   - **打开**（列表项次操作，仅当 MIME 能被系统解析时才显示）→ `ACTION_VIEW`，
     先在 `PackageManager` 查 `resolveActivity`，无匹配则该项置灰而不是抛
     `ActivityNotFoundException`
   - 两者都必须带 `FLAG_GRANT_READ_URI_PERMISSION`，否则第三方应用拿不到 `content://` 的读权限
4. 分享后清理缓存副本；服务启动时清理上一次的残留

### 5.5 路径安全

**这是本功能最需要警惕的地方**：rootfs 是访客完全可写的，AI 完全可以造一个指向
`/data/data/...` 或 App 私有目录的软链作为诱饵，诱导 App 顺着它把容器外的文件分享出去。

因此：

- 全程 `NoFollow` 语义解析（项目已有先例：`HarnessLocaleSettings` 的路径全程 NoFollow）
- 逐段校验，而不是只校验最终路径
- 使用 `canonicalPath` 复核仍在 `<rootfs>/root/` 之内
- 软链条目在列举阶段就跳过，导出阶段再次拒绝（双重）

## 六、安全边界

- 分享**只由用户点击触发**，模型与访客代码没有任何途径发起
- 不扩大 `DeviceCommand` 命令面
- 文本只作纯文本分享，**不渲染 HTML**（沿用运行日志的既有做法：只作 React 文本节点）
- 分享内容与产物列表**不写日志、不进诊断导出**（诊断日志的既有承诺"不含终端内容或
  用户数据"不被弱化）
- FileProvider 新增专用 `cache-path`，只暴露 `cache/share/`，与诊断日志的
  `cache/diagnostics/` 分开
- 悬浮球服务不持有凭据、不执行命令

## 七、验证

**Kotlin 单测**：路径 NoFollow 与越界拒绝（含 `/root` vs `/rootEvil` 前缀陷阱、
软链诱饵、编码绕过）、大小上限、排序与截断、隐藏文件过滤、目标文件名净化。

**前端测试**：产物列表渲染与空态、错误态、非原生环境降级、英文界面、超长文本截断。

**真机验收**：权限引导跳转与回读、悬浮球拖动与吸附、短按回 Harness、长按菜单两项、
进程被杀后球消失（如实记录，不承诺常驻）、选区为空/非空两条路径、分享文本到第三方
应用、分享 rootfs 文件到第三方应用、超限文件被拒。

## 八、限制与已知取舍

1. **悬浮球不保证常驻**：厂商后台策略可能杀掉服务，球随之消失；用户需重新开启。
2. **产物列表只有一级**：不做子目录浏览与递归打包，避免文件管理器级别的复杂度。
3. **选区分享依赖用户先选中**：没有"一键分享整条回复"，因为官方前端不提供消息标识。
4. **分享缓存不持久**：`cacheDir/share/` 可能被系统清理，这不是长期存储。
5. **客户端插件未做**：消息级分享按钮留待下一轮，需先评估 rc.2 插槽契约的稳定性。
