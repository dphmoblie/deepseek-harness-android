# 悬浮球与内容分享设计

> 目标：让用户在其他应用里也能展开 Harness 对话小窗；让 AI 生成的内容
> （对话文本、代码、Markdown、运行时文件、图片）能交给手机上的第三方应用打开。
> 本文档经确认后进入实施，实施结果以真机验收为准。

## 一、背景与范围

### 1.1 要解决的问题

1. **跨应用回到对话**：Harness 常驻后台时，用户切到别的应用后没有快捷方式回去，
   只能从最近任务或桌面图标绕。
2. **内容出不去**：AI 写出的代码、报告、Markdown 只能停留在对话里，手机上没法
   直接用其他应用打开。当前全项目只有一个导出入口——诊断日志分享
   （`MobileRuntimePlugin.shareDiagnosticLog`），对话内容与终端内容都明确不导出。

### 1.2 明确不做

- **不做保活承诺**：悬浮球能否常驻取决于系统与厂商后台策略，与「后台保持 Harness」
  的既有表述保持一致，不宣传为绝对可用。
- **不把分享混入设备桥命令面**：分享仍走独立桥方法。设备桥新增的文件命令只允许投递区
  `inbox/outbox` 的相对路径、128 KiB 以内小文件和受控目录操作，不提供通用 Shell；写入类工具
  由模型工具层要求用户确认。
- **不让模型自主发起分享**：分享只由用户点击触发。理由是设备桥文档的既有结论——
  PRoot 单 uid 下审批门不是安全边界，同 uid 代码可读 `/proc/<pid>/environ` 拿到令牌
  绕过工具层，因此"AI 能不能把内容发出去"不能靠审批门兜底，只能把动作放在用户手里。
- **本轮不做客户端插件**：消息级的「分享」按钮（基于 `__ModuleLoader__` +
  `dsh-client-ui-slots` 注入）体验更好，但要绑定官方前端 0.2.0-rc.2 的插槽契约，
  升级时可能返工，留待下一轮单独评估。

## 二、总体架构

三条能力**互不依赖**，可分别实现、分别验证，共享一个 App 侧出口 `ShareExporter`：

```
① 悬浮球               ② 选区分享               ③ 运行时产物
OverlayBallService    HarnessActivity          设置页·产物列表
  WindowManager         Toolbar 菜单项             │
  PendingIntent         evaluateJavascript     RuntimeBridge
  overlay 菜单 + 遮罩   读选区缓存               listRuntimeArtifacts
      │                      │                      │
      ↓                      ↓                      ↓
KeepAliveEntryActivity    ┌──── ShareExporter ────┐
（现成的透明转发组件）     │ 文本 → ACTION_SEND     │
                         │ 文件 → cache 副本      │
                         │   + FileProvider      │
                         │   → ACTION_SEND/VIEW  │
                         └───────────────────────┘
```

## 三、悬浮球

### 3.1 权限

`SYSTEM_ALERT_WINDOW` 是特殊权限，**不会弹运行时对话框**，必须引导用户到系统设置页
手动开启。沿用 `openAllFilesAccessSettings` 的既有模式：

- 设置页显示权限状态；未授权时开关置灰，点击跳
  `Settings.ACTION_MANAGE_OVERLAY_PERMISSION`。
- 从设置页返回时用 `onResume` 重新读取 `Settings.canDrawOverlays()`，而不是信任跳转结果。

### 3.2 视图

- `WindowManager.addView` + `TYPE_APPLICATION_OVERLAY`
- 标志位：`FLAG_NOT_FOCUSABLE`（不抢输入焦点，因此也不吃返回键）+
  `FLAG_LAYOUT_IN_SCREEN`（坐标空间是整块屏幕，见下）
- 尺寸：48dp 圆形，球面是矢量 `ic_overlay_ball.xml`（品牌符号）叠在
  `bg_overlay_ball.xml`（深墨绿圆形底）上
- **位置**：初始在屏幕右侧垂直居中；可拖动；松手后吸附到最近的左右边缘；
  位置持久化到设置，重启后恢复。拖动判定用 `touch slop`，避免误触发点击。

**窗口标志为什么是这两个**：`FLAG_NOT_FOCUSABLE` 让球不抢输入法与按键，是常驻 overlay
入口的基本要求。`FLAG_LAYOUT_IN_SCREEN` 把窗口的坐标空间定成整块屏幕：位置计算与夹取
（`clampPosition` / `defaultPosition`）都按 `displayMetrics` 的整屏像素来，球在横竖屏
切换下都不会越出屏幕。代价是**球可以被拖到状态栏下面**——整屏坐标包含状态栏区域，球贴
顶时上半部分会落到系统状态栏窗口之下，那一半的触摸被状态栏吃掉，但露出的下半部分仍可
抓住、拖回。这是当前实现的真实行为，如实记录，不美化：要彻底消除它得全程扣除状态栏高度
并在拖动与吸附里补偿，对 48dp 的小目标收益有限，本轮不做。（`FLAG_LAYOUT_NO_LIMITS`
依然不加：允许窗口越过屏幕边界的语义只会让「球跑到屏幕外且点不到」更难收拾。）

**球面为什么先是矢量、现在又换回应用图标**：设计稿原定复用品牌标识图 `app-mark.png`，
实施时换成了矢量 `ic_overlay_ball.xml` + 形状背景 `bg_overlay_ball.xml`，理由是位图在
Android 侧有两个硬伤：一是**无法随主题着色**——球面符号在布局里用 `android:tint` 上品牌薄荷绿
（`#A9F0D5`），换主题或调品牌色只需改一处属性，位图做不到；二是 `app-mark.png` 是
**前端资源**（`src/assets/app-mark.png`），Android 侧要用它必须先把文件复制进 `res/`，
两端从此各存一份、必然漂移。

球面一度**直接用启动图标资源** `@mipmap/ic_launcher_round`（`match_parent` 铺满 48dp 球面、
`android:scaleType="fitCenter"`、不加 tint），当时的理由是 launcher mipmap 是 Android 侧应用图标的
唯一来源，与桌面、最近任务里看到的图标天然一致、两端不会漂移。真机取证显示这条路观感不合格：
`ic_launcher_round.png` 的主体只占画布 76%×74%（四周本来就是透明边），`fitCenter` 又原样保留这圈
透明边，于是球面出现一圈明显空白（用户 2026-10-05 反馈「图标留白」的第一条）。

现在改为 `@drawable/overlay_ball_mark` + `android:scaleType="fitXY"`：`overlay_ball_mark.png` 是
**前端 `src/assets/app-mark.png` 的逐字节副本**（119576 字节，SHA256 `457D1B5C…5683`），主体占画布
98%×95.7%，铺满球面后不再有空白。代价如实记录，与上一版相反：
一是**两端各存一份，存在漂移风险**——改前端那张图时必须同步重新生成 `res/drawable-nodpi/` 这份
（重新生成脚本见 `_probe/gen-android-icons.ps1`，同脚本还负责各密度启动图标）；
二是图标本身是彩色位图，**球面不随主题着色**（薄荷绿 tint 已去掉），观感由图标自身决定。
启动图标同一轮也按满幅重做：自适应前景保持在 62%（108dp 画布只有中心 66dp 安全区可见，
放大只会被遮罩裁边），传统方形/圆形图标取 97%/100%（不走遮罩、不裁边），
`AndroidManifest.xml` 补上 `android:roundIcon="@mipmap/ic_launcher_round"` 让圆形图回到启动器。
应用内其它位置的图标（顶栏、启动面板、运行环境标题、会话按钮）统一引用前端资源
`src/assets/app-mark.png`（`src/App.tsx:1` 的 `appMark`），原来的鲸鱼位图与 `WhaleMark`
组件已删除。

**通知栏小图标仍然是单色剪影**：状态栏图标必须是不透明单色图形，彩色应用图标在那里只会
渲染成一个白块，因此 `ic_overlay_ball.xml`（终端提示符形状）保留给
`OverlayBallService.kt:596` 的 `setSmallIcon`，不跟随球面一起换。

**对话小窗可缩放（本轮新增）**：小窗右下角多了一个圆形手柄（`RESIZE_GLYPH` = ◢，
`HANDLE_BACKGROUND_COLOR` = `0xCC3A4741`），拖动它改窗口大小。

- 手柄是**另一个独立的 overlay 窗口**，不是小窗布局里的一个子 View：小窗用
  `FLAG_NOT_TOUCH_MODAL`，它的触摸面与 WindowManager 的命中测试都在窗口矩形内，
  把拖动热区做进小窗内部会在越界拖动时丢失事件。独立窗口还让它天然浮在小窗之上，
  不需要改任何 `res/layout`。
- 尺寸约束集中在 `OverlayConversationSizePolicy`（纯函数，可单测）：最小 240×360dp，
  上限是可用屏幕的 90%（可用尺寸要扣掉 `CONVERSATION_MARGIN_H_DP` = 24dp 与
  `CONVERSATION_MARGIN_V_DP` = 72dp）。**比例上限与硬下限冲突时以下限为准**——宁可
  超出「九成」这条软约束，也不让小窗小到没法用；这一条写进了单测。
- 拖动过程实时改尺寸，**松手（`ACTION_UP`/`ACTION_CANCEL`）才落盘**，避免拖动途中
  反复写 SharedPreferences。每次改尺寸都会把窗口位置重新夹回屏幕内，并把手柄跟着重排。
- **尺寸持久化**：写进 `dsh-overlay-ball` 的 `conversation_width` / `conversation_height`
  与落盘时的屏幕宽高 `conversation_screen_w` / `conversation_screen_h`。下次打开小窗时
  用 `OverlayConversationSizePolicy.storedState` 判定：同屏 → 直接复用；屏幕尺寸变了
  （旋转、分屏、折叠展开）→ 判为 `STALE`，**退回默认尺寸**而不是硬套一个可能已经荒谬的值；
  没存过 → `ABSENT`，用默认值。
- 命中判定是**圆心 + 半径**而不是矩形包含（`hitsHandle`），手柄触摸尺寸取
  `HANDLE_TOUCH_SIZE_DP` = 44dp（视觉直径 `HANDLE_VISUAL_SIZE_DP` = 28dp），
  即「看得见的小、按得到的够」。

### 3.3 交互

| 手势 | 行为 |
|---|---|
| 短按 | 展开或收起同源 Harness 对话小窗；小窗内的「全屏」仍走 `KeepAliveEntryActivity` |
| 长按 | 在球旁展开/收起二级球（三个圆形按钮） |
| 拖动 | 移动球体，松手吸附到最近的左右边缘 |
| 拖动小窗右下角手柄 | 改小窗尺寸（松手落盘，见 3.2） |

**长按为什么从文字菜单改成二级球**：原来的长按菜单是一块
`WindowManager` overlay（刻意不用 `PopupWindow`：从 Service 弹 `PopupWindow` 需要一个
有效的 window token 来挂载，而 Service 上下文没有（token 属于 Activity），
`showAsDropDown` 会抛 `BadTokenException`——即便用 `try/catch` 兜住不崩，菜单也根本不会
出现），并且必须再补一层全屏透明遮罩接住「点击别处」，否则 `FLAG_NOT_FOCUSABLE` 的菜单会
一直挂在屏幕上。二级球把这套「菜单 + 遮罩」的两窗口结构换成**一组和球同样的 overlay 按钮**：
没有遮罩，点球本身即收起，每个按钮都是 44dp 触摸目标、带 `contentDescription`，
也不再需要计算菜单尺寸与落点。

**二级球怎么排布**：`OverlayBallSecondaryPolicy.layout` 决定——优先排在球的右侧，右侧放不下
改左侧，两侧都放不下就夹进屏幕；按钮组整体优先向下排，下方放不下就整体上翻，都放不下则收起
堆叠。安全区预留顶部与底部各 `SYSTEM_BAR_RESERVE_DP` = 24dp（`overlayReserveTop()` /
`overlayReserveBottom()`），按钮的触摸尺寸不低于 `MIN_TOUCH_SIZE_DP` = 40dp。
点中任一项都会**先收起二级球再执行动作**，避免动作改变界面后留下孤儿按钮。

**复用 `KeepAliveEntryActivity` 而不是新写一个转发 Activity**：它已经处理好了
"已认证则进 Harness、否则回管理页"，并刻意避开了 `singleTask` 的 clear-top 会连带
撤销一次性会话凭据的问题（见 `docs/ARCHITECTURE.md`）。**二级球的「回到应用」、小窗的「全屏」、
任务通知的点击**现在都走这一条已验证路径。

按 `CHOICE_ORDER` 顺序（这个顺序不要随意调换，理由见下）共三项：

- **回到应用** → 条件行为：对话存活时经 `KeepAliveEntryActivity` 把应用带回前台，
  而不是直接启动管理界面——`MainActivity` 是 `singleTask`，启动会触发 clear-top，把后台的
  `HarnessActivity` 连同一次性会话凭据一起销毁，也没有启动标志能在不清理栈上活动的前提下
  绕开；对话不在时没有会被 clear-top 清掉的受害者，才直接打开管理界面
  （`OverlayBallPolicy.canOpenManagementDirectly(harnessActivityAlive)`）
- **隐藏悬浮球** → 直接关闭 `overlayBallEnabled` 开关（与设置页一致，不引入额外的
  "临时隐藏"状态）
- **关闭无障碍** → `DeepSeekAccessibilityService.current()?.disableSelf()`；当前服务未连接时
  **不做任何动作**，只弹一次明确提示（`..._accessibility_disabled_toast`：「无障碍服务当前未开启，
  无需关闭」），不静默无反应。按钮在未开启时显示禁用态外观（`..._accessibility_off` =「无障碍未开启」）。

**为什么「关闭无障碍」必须排在最后**：它改的是**系统设置**，虽然本应用随时可以重新请求，
但用户要自己找回去要经过系统设置的「已下载的服务／已安装的应用」层级——误触成本远高于另外两项。
把最需要点两下才能恢复的动作放在离球最远的一端，三项的顺序因此固定为「回到应用 → 隐藏悬浮球 →
关闭无障碍」，不提供自定义排序。

**这里的诚实边界**：

- `disableSelf()` **只在无障碍服务已连接、且由本应用拥有时**有效；服务没连接时调用是空操作，
  所以我们自己先判 `current()`，不做「调用一定会关掉」的承诺。厂商 ROM 上 `disableSelf()`
  的实际行为（是否有确认弹窗、是否写回系统设置、是否被厂商服务守护进程立刻重启）**必须真机确认**，
  本机单测覆盖不到。
- 关闭之后，**外壳设置页的无障碍状态刷新有时延**：它由前端按既有节奏轮询
  （5s 级）读取 `AccessibilityAutomationStore.state(context)`，而该状态就是
  `DeepSeekAccessibilityService.current() != null`。因此关闭后最多要等一个轮询周期，设置页才会
  显示「未开启」。**前端不做乐观更新、也不假装立即关闭**；请以系统设置里的开关状态为准。
- 选择 `disableSelf()` 而不是「跳系统设置页让用户自己关」：跳转是异步的、还要用户再找一次开关；
  但代价是**没有二次确认**——这是刻意的取舍，因为重新开启只需要再进一次系统设置，且本项目不
  在静默状态下调用它（必然由用户长按 + 点按触发）。

> 取舍：曾考虑加「重新开始会话」，但"新开会话"需要 Harness 侧配合（会话生命周期
> 由官方前端管理），属于跨边界改动，本轮不做。

### 3.4 服务与通知

悬浮球由独立前台服务承载，否则进程被回收后球就没了。

- **刻意不与 `HarnessKeepAliveService` 合并**：「想要悬浮球」和「想保持运行时」是
  两件独立的事，合并会让用户无法只选其一。
- 通知渠道是**独立**的 `harness_overlay_ball`，`IMPORTANCE_LOW`，并关闭角标、振动与
  声音；文案为固定资源字符串，**不含** URL、端口、凭据、会话内容。
- **刻意不复用 `harness_keep_alive`**：两个服务共用一条渠道时，用户在系统设置里关掉
  该渠道会**连带影响另一个**——想静音悬浮球通知的人会连常驻保活通知一起失去。渠道
  各自独立后，两条通知的偏好可以各调各的，与「两个开关互不依赖」的设计一致。
- 服务本身不执行 Shell、不连接 Shizuku；小窗开启时仅从正在运行的 Harness 读取内存中的一次性会话凭据，关闭独立小窗时清理同源 Cookie。
- 开关关闭时立即 `stopSelf()`，不留无法解释的通知——沿用 keep-alive 的既有做法。
- **权限只在两个时机检查，运行期没有复查**：
  1. 服务的 `onStartCommand`：启动瞬间 `Settings.canDrawOverlays()` 为 false 即记录
     `overlay_denied` 并 `stopSelf()`，球不出现；
  2. 插件的 `syncOverlayBallService`：插件加载时与设置保存时各调一次，按「用户开关 +
     系统权限」决定起停服务（权限为 false 时走 `stop`）。
- 因此，**球已经在显示之后、用户再去系统设置撤销权限**，本服务不会当场收到通知，也
  不会立即 `stopSelf()`：真正收尾要等下一次检查时机（插件加载或保存设置）。球窗口
  本身的去留此时由系统决定（系统在权限撤销时可能收回 overlay 窗口，也可能重建进程），
  本实现不作保证。以上是当前实现的如实口径——运行期撤销权限的即时处理是**已知限制**，
  另有改动在跟进。

### 3.5 开关入口

并入现有「运行与后台」二级页，与「后台保持」同级，含权限状态与引导入口。
设置项名 `overlayBallEnabled`，默认 `false`。

## 四、② 选区分享

### 4.1 为什么用选区，而不是定位消息

rc.2 官方前端的稳定 `data-*` 属性里**没有消息容器标识**（实测只有 `data-code-block-*`、
`data-dockkit-*`、`data-file-type-mark` 等），按 DOM 结构定位"最后一条回复"会重蹈
"适配层碰 CSS Modules 哈希类"的覆辙，且官方前端一升级就断。

选区方案零 DOM 依赖，而且天然满足"用户手动决定分享什么"：用户选中哪段，就分享哪段。

### 4.2 流程

1. `harness_toolbar.xml` 新增菜单项 `action_share_selection`
2. 点击 → `webView.evaluateJavascript` 读取选区
3. 为空 → Toast 提示"请先选中要分享的内容"
4. 非空 → `ShareExporter.shareText` → `ACTION_SEND` + `text/plain` + `createChooser`

### 4.3 选区缓存

风险：点击 Toolbar 时 WebView 可能失焦，`window.getSelection()` 已被清空。

处理：页面加载完成后注入一段小脚本，监听 `selectionchange`，把**最后一次非空选区**
缓存在私有全局变量 `__dshMobileSelection`；点击时优先读缓存，回退到实时选区。

注入脚本只写这一个私有全局变量，**不读取页面状态、不发起请求、不给页面任何新能力**。

### 4.4 错误处理

| 情况 | 行为 |
|---|---|
| 选区为空 | Toast 提示，不弹分享面板 |
| 页面未就绪 | 菜单项置灰 |
| 文本超长 | 截断到上限（默认 100KB）并在分享前提示 |

## 五、③ 运行时产物

### 5.1 数据来源

rootfs 位于 `noBackupFilesDir/dsh-runtime/current/`，**是 App 私有目录下的普通目录树，
App 可以直接用 File API 读取，不需要启动 PRoot、也不要求运行时正在运行**。

访客的 `HOME=/root`（见 `RuntimeCommand`），AI 写出的产物默认落在那里。
列表因此取自 `<rootfs>/root/`。

> 待核实：`<rootfs>` 内访客 `/root` 的对应位置需按实际解包结构确认
> （`dsh-runtime/current/` 之下是否直接就是访客根）。实施第一步先核实并用单测钉住。

### 5.2 桥接口

新增两个方法（`MobileRuntimePlugin`）：

| 方法 | 参数 | 返回 |
|---|---|---|
| `listRuntimeArtifacts` | 无 | 条目数组：`name`、`size`、`modifiedAt`、`isDirectory` |
| `exportRuntimeArtifact` | `name` | 导出到分享缓存后的展示结果 |

**权限要求**：仅应用私有原生桥接调用，网页端与外部应用均不可达。浏览器预览直接拒绝
（沿用 `src/platform/browser.ts` 的既有做法：非原生环境返回不可用）。

**参数校验**（原生与前端双重）：

- `name` 只允许单层文件名，限制 255 字符以内的受控字符集
- **显式拒绝** `/`、`\`、`..`、空字节、绝对路径与前缀匹配（`/root` vs `/rootEvil`）
- 解析结果必须落在 `<rootfs>/root/` 之内，越界即拒绝

**返回值脱敏**：只返回文件名、大小、修改时间与类型；**不返回绝对路径、不返回用户路径、
不返回文件内容**。

### 5.3 列举规则

- 只列一级条目，不递归
- 跳过隐藏条目（`.` 开头）
- **不跟随符号链接**：`lstat` 判定，软链一律当作不可分享条目跳过
- 按修改时间倒序，上限 50 条
- 目录条目也列出但**不可直接分享**（本轮不做递归打包），点击给出说明

### 5.4 导出与分享

1. 校验大小上限（默认 50MB），超限直接拒绝并说明
2. 复制到 `cacheDir/share/`，目标文件名做净化（去路径分隔符与控制字符）
3. `FileProvider.getUriForFile`，按 MIME 类型分两种出口，**用户点哪个走哪个**，不自动二选一：
   - **分享**（列表项主操作）→ `ACTION_SEND` + `EXTRA_STREAM` +
     `FLAG_GRANT_READ_URI_PERMISSION` + `createChooser`
   - **打开**（列表项次操作，仅当 MIME 能被系统解析时才显示）→ `ACTION_VIEW`，
     先在 `PackageManager` 查 `resolveActivity`，无匹配则该项置灰而不是抛
     `ActivityNotFoundException`
   - 两者都必须带 `FLAG_GRANT_READ_URI_PERMISSION`，否则第三方应用拿不到 `content://` 的读权限
4. 分享后清理缓存副本；服务启动时清理上一次的残留

### 5.5 路径安全

**这是本功能最需要警惕的地方**：rootfs 是访客完全可写的，AI 完全可以造一个指向
`/data/data/...` 或 App 私有目录的软链作为诱饵，诱导 App 顺着它把容器外的文件分享出去。

因此：

- 全程 `NoFollow` 语义解析（项目已有先例：`HarnessLocaleSettings` 的路径全程 NoFollow）
- 逐段校验，而不是只校验最终路径
- 使用 `canonicalPath` 复核仍在 `<rootfs>/root/` 之内
- 软链条目在列举阶段就跳过，导出阶段再次拒绝（双重）

## 六、安全边界

- 分享**只由用户点击触发**，模型与访客代码没有任何途径发起
- 不扩大 `DeviceCommand` 命令面
- 文本只作纯文本分享，**不渲染 HTML**（沿用运行日志的既有做法：只作 React 文本节点）
- 分享内容与产物列表**不写日志、不进诊断导出**（诊断日志的既有承诺"不含终端内容或
  用户数据"不被弱化）
- FileProvider 新增专用 `cache-path`，只暴露 `cache/share/`，与诊断日志的
  `cache/diagnostics/` 分开
- 悬浮球服务只在小窗存活期间使用一次性会话凭据，不执行命令

## 七、验证

**Kotlin 单测**：路径 NoFollow 与越界拒绝（含 `/root` vs `/rootEvil` 前缀陷阱、
软链诱饵、编码绕过）、大小上限、排序与截断、隐藏文件过滤、目标文件名净化；
二级球排布与夹取（`OverlayBallSecondaryPolicyTest`）、小窗尺寸钳制与可逆性
（`OverlayConversationSizePolicyTest`）。

**前端测试**：产物列表渲染与空态、错误态、非原生环境降级、英文界面、超长文本截断。

**真机验收**：

- 权限引导跳转与回读、悬浮球拖动与吸附、短按展开对话小窗与输入、
  进程被杀后球消失（如实记录，不承诺常驻）。
- **二级球**：长按弹出三个按钮 → 再长按或短按球本身收起；三项动作各点一次，
  行为与 3.3 一致；「关闭无障碍」在**无障碍已开启 / 未开启**两种状态下各点一次——
  未开启时必须弹提示而**不能**无声无息。
- **关闭无障碍后的回读**：点完后进系统设置看该服务是否真的被关掉；再回到外壳设置页，
  确认最多等一个轮询周期后状态跟着变成「未开启」。厂商 ROM 上 `disableSelf()` 的
  真实行为（是否弹确认、是否被系统立刻重启）逐个记录。
- **缩放手柄**：拖右下角手柄放大/缩小，到边就停（不越界、不消失）；松手后关掉小窗再打开，
  尺寸应保持；把手机旋转 90° 后再打开，尺寸应**退回默认**而不是沿用旧值；
  手柄在窗口贴边时仍在屏幕内且能抓住。
- 选区为空/非空两条路径、分享文本到第三方应用、分享 rootfs 文件到第三方应用、
  超限文件被拒。


## 八、限制与已知取舍

1. **悬浮球不保证常驻**：厂商后台策略可能杀掉服务，球随之消失；用户需重新开启。
2. **「关闭无障碍」关闭后，外壳设置页要等一个轮询周期才更新**（见 3.3）：状态来自
   `DeepSeekAccessibilityService.current() != null`，前端不做乐观更新；以系统设置里的开关为准。
3. **`disableSelf()` 的厂商差异未在本机验证**：部分 ROM 可能弹确认、可能延迟生效、
   也可能被厂商服务守护立即重启，需真机确认（见 §七）。
4. **小窗尺寸按「屏幕尺寸变了就退回默认」处理**：旋转/分屏后不尝试按比例换算，
   避免把横屏下的尺寸硬套回竖屏。知道这是有损的，但可预测胜过猜。
5. **产物列表只有一级**：不做子目录浏览与递归打包，避免文件管理器级别的复杂度。
6. **选区分享依赖用户先选中**：没有"一键分享整条回复"，因为官方前端不提供消息标识。
7. **分享缓存不持久**：`cacheDir/share/` 可能被系统清理，这不是长期存储。
8. **客户端插件未做**：消息级分享按钮留待下一轮，需先评估 rc.2 插槽契约的稳定性。
