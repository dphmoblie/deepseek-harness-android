# 模拟器实测：运行时启动失败与前端问题清单

## 来源与边界

本清单的数据来自**一次模拟器实测**：MuMu 模拟器（Android 15 / SDK 35），设备 ABI `x86_64`
（abilist `x86_64,arm64-v8a,x86`，ARM 指令靠 Houdini 转译），屏幕 1600×900 @240dpi（横屏）；
被测包为**远程 Release `v0.2.14-mobile-429`**（Pre-release，2026-10-14，`app-release.apk` 314,779,496 B，
包名 `io.deepseekharness.mobile`，`versionName=0.2.14`、`primaryCpuAbi=arm64-v8a`），
adapter 侧记录时间 2026-10-15。

读数方式：`adb -s 127.0.0.1:16384`（MuMu）+ 截图 + `uiautomator dump` + `logcat -s dsh-runtime`。
`uiautomator` 在 MuMu 上会 SIGSEGV 崩掉（`F DEBUG: Cmdline: uiautomator … signal 11`），
**本清单的界面结论一律以截图与带 bounds 的 dump 为准**，不采信单次 dump 的「0 节点」结果。

**与真机清单的分工**：`docs/真机缺陷与改进清单.md` 记的是 HONOR 真机（aarch64，PRoot 原生执行）上的
缺陷；本清单记的是**模拟器（x86_64 + 转译）**上的运行时启动失败与随之暴露的界面问题，两者不重复收录。
本表只收录有证据的条目：`状态` 列只在有代码落地或复测依据时改动。

## 二、明细

### 边界（不是缺陷，但必须说清）

- **本地构建的 debug 包一定缺运行器**：`android/README.md:8` 要求把 CI 产出的
  `libdsh_proot.so` 与 `libdsh_proot_loader.so` 放进 `app/src/main/jniLibs/arm64-v8a/`，
  这两个文件在 `.gitignore` 里；`android/app/build.gradle:121` 是 `abiFilters 'arm64-v8a'`。
  因此本地包会出现「缺少本机运行组件」与 `W dsh-runtime: runner check failed: …(exists=false,…)`（每 5 秒一条）。
- **内置运行器只有 arm64**：本机是 `x86_64`，执行内置运行器要走 Houdini 转译，
  而 PRoot/loader 的转译执行在本机直接崩（见 M-1 证据）。**这是设备与架构边界**，
  不是前端缺陷；缺陷在于界面把这件事讲错了。

### M-1 宿主已知 `exit=139`，仍判 `RUNNER_OK`

- **现象**：运行时安装成功（顶栏绿色「已就绪」），点「打开 Harness」后启动失败并报「超时」。
- **证据（logcat 原样）**：
  ```
  W dsh-runtime: exec probe: name=loader,path=/data/user/0/io.deepseekharness.mobile/no_backup/dsh-runtime/current/root/.dsh-mobile/dsh-runner/loader,result=started,exit=139
  D houdini : [6827] executing …/dsh-runner/loader
  D houdini : [6827]   #00  pc 0000000000000144  …/loader
  F DEBUG   : Cmdline: /system/bin/houdini64 …/loader
  W dsh-runtime: loader state: code=RUNNER_OK,reason=loader_root_copy,probe=started,exit=139,detail=regular=true,size=1632,mode=0700,execAccess=true,stamped=false
  ```
- **归属判定（已更正）**：**不是我们的代码，是设备/架构边界**。原判定「崩溃被当成通过」
  是错的，修法也已被推翻 —— 详见下面的「M-1 更正」。真实缺陷只在于**界面没讲清为什么不行**。
- **代码定位（原判定，保留供追溯）**：
  - `android/app/src/main/java/io/deepseekharness/mobile/runtime/RuntimeLauncherPolicy.kt:57`
    `fun codeForProbe(observation, started)` → `if (started) return OK`
  - 调用点 `RuntimeStore.kt:1198` 的通过条件只有 `!probe.startsWith(EXEC_PROBE_STARTED)`。

#### M-1 更正：`exit=139` 是 loader 的**正常工作形态**，不是故障

原修法建议「`started && exit != 0` 不算通过」。**该修法若实施，会让真机全面回归**，
证据在仓库自己的发布说明里：

- `docs/发布说明-0.2.4.md:38` 记录的真机验收基线是
  `loader state: code=RUNNER_OK,reason=loader_symlink,probe=started,exit=139`（符号链接胜出），
  同一窗口 `PROOT_GUEST_EXEC_FAILED` **0 次**、`guest probe failed` **0 次**，
  随后 `HarnessActivity` 启动成功、界面进入真实 Harness 对话页并正常应答。
- 也就是说**真机正常工作时 `exit` 同样是 139**。全仓 `exit=` 记录只有 139 这一个值，
  它既出现在模拟器的失败里，也出现在真机的成功里 —— 退出码不区分成败。

**原因**：`loader` 是 PRoot 的 `PROOT_LOADER`，职责是被 `execve` 后由 PRoot 用 mmap 接管
访客程序；**单独执行时 SIGSEGV 是它的固有行为，且恰好证明「系统允许执行它」**。
`RuntimeStore.kt:1198` 只看 `started` 是对的：真正的区分点是**能否 `execve`**
（`started` vs `failed,error=13, Permission denied`），不是退出码。

**模拟器为什么真的不行**：本机 `abilist = x86_64,arm64-v8a,x86`，首选 ABI 是 `x86_64`，
ARM 指令靠 Houdini 转译（logcat 里的 `houdini64` 就是它）。PRoot 与它的 loader 在转译下
不受支持 —— 这是「边界」一节已写明的**设备与架构边界**，不是判定逻辑的缺陷。

#### M-1 的实际修法（已落地）

判据必须是**首选 ABI**，不是 `SUPPORTED_ABIS` 列表包含 —— 转译架构也在那个列表里
（模拟器就列了 `arm64-v8a`），所以列表包含判会让模拟器通过检查、再在 `execve` 时崩溃。

- `RuntimeStore.runnerAvailable()` 增加前置检查：`SUPPORTED_ABIS.firstOrNull() != "arm64-v8a"`
  直接返回不可用，并记一条带 `device abi=` 的警告日志。
- 这条只拦「设备原生架构就不是 arm64」，**不改变任何 arm64 真机的行为**。
- `RUNNER_UNAVAILABLE` 的前端文案改为讲清「内置 PRoot 只有 ARM64，模拟器/32 位设备请换真机」，
  用户不必再去猜「超时」是什么意思。

### M-2 运行时自检「什么都不说」

- **现象**：点「运行自检」后，面板停在 `尚未自检` + 橙字 `自检未完成，请稍后重试`，
  `dsh 版本` / `系统 WebView 版本` 仍是「运行自检后显示」。
- **归属判定**：**我们的代码**。自检要走访客逐环探测（`src/App.tsx:3722` 起的自检区块），
  loader 崩溃后整份载荷回不来，前端只落到通用失败分支（`src/App.tsx:3837`）。
- **修法**：自检结果里带上**宿主侧** launcher 实测（与 `exec probe` 同一行证据），
  并在文案上区分「宿主探测失败」与「访客探测失败」——现在两种情况的下一步都是「稍后重试」，
  对宿主机崩这一种是错的。

### M-3 失败信息不保真 + 终端页无出口

- **现象**：强制打开后，对话页显示「运行环境需要处理 / 运行环境启动失败 / **PRoot 启动 Ubuntu 超时。**」
  与两个按钮（打开对话 / 打开终端排查）；终端页 Ubuntu 标签停在不退出的「正在连接」，
  底部 toast 仍是「PRoot 启动 Ubuntu 时超时」。
- **归属判定**：**我们的代码**（失败分类与终端失败态）。真实原因是 `exit=139`，
  界面把它归类成超时，于是给用户的下一步是「重试」，而重试永远不会成功。
- **修法**：超时措辞让位于宿主已掌握的实测结果；终端页在启动失败后要有明确失败态与出口
  （切「设备 Shell」/回设置看诊断/换设备），不留无限 spinner。

### M-4 能力卡与根通道卡自相矛盾（HEAD 可复现）

- **现象**：左侧能力行「根通道（KernelSU）**需要一步设置** · 根通道开关没有打开 ·
  下一步：到「根通道」设置里打开开关」；右侧根通道卡「这台设备**没有可用的 KernelSU**」。
- **归属判定**：**我们的代码**。
- **代码定位（代码侧已核实）**：`android/app/src/main/java/io/deepseekharness/mobile/capability/DeviceCapability.kt:140-148`
  ——先判 `!facts.rootEngineEnabled` 就直接返回 `NEEDS_ACTION`，**没有先看设备层的 `facts.rootEngineStatus`**。
  同文件 `shizuku()` 分支的范式是「设备层面做不到就是 `UNSUPPORTED`（点按钮也变不出来）」。
- **修法（已落地，与原建议不同）**：原建议「先判 `rootEngineStatus == unsupported`」**不可实现**——
  `shizuku/RootEngineAccess.kt:67-104` 在开关关着时直接返回 `kernelSuStatus = KernelSuProbe.STATUS_UNSUPPORTED`
  （`unsupported` 与「还没探测」同值），两处 facts 构造（`DeviceBridgeServer.kt:236-247`、
  `MobileRuntimePlugin.kt:1635-1646`）又把它抹成 `null`；而 `KernelSuProbe` 的探测会真跑 `su -v`
  与 `su -c id -u`，设计上「关着不拉 su」。因此**问题在界面层**：开关关着时不再冒充「设备不支持」，
  而是如实说「还没查」——`src/components/RootEngineCard.tsx` 在 `enabled == false` 时只显示
  「开关关着」并加一句「关着的时候本应用不拉 su，所以现在还不知道这台设备支不支持 KernelSU；
  打开开关后才会检测。」，原因码也只在开着时才拼接；能力行的 `ROOT_ENGINE_DISABLED` 说明同步改成
  「根通道开关没有打开（打开后才会检测这台设备支不支持）」。
- **备注**：Release 429 上**没有**根通道卡（该版本尚未含第六项能力），所以这条只能在本地 HEAD 复现。

### M-5 24 处裸 `<button>`

- **现象**：诊断页两个「重新检测」实测填充 `rgb(107,107,107)`（WebView 默认灰按钮），
  与深色卡片底 `--surface #0f1317`、可用主按钮 `#86abff` 不是一个体系；
  同屏「在 GitHub 反馈问题」「导出并分享」都是设计系统按钮。
- **归属判定**：**我们的代码**。裸 `button` 只有 `src/styles.css:306-329` 的
  font / tap-highlight / disabled opacity；设计系统类在 `.button*`（`src/styles.css:630-681`）
  与 `.icon-button`（`src/styles.css:683`）。
- **位置（全仓 24 处，裸按钮；旧版清单有 6 处误报/6 处漏报）**：
  `ApplicationPicker.tsx:150`、`AutomationTaskCard.tsx:116,122,124,125`、`DeviceCapabilityCard.tsx:170,171`、
  `DeviceShellSettings.tsx:32`、`RootEngineCard.tsx:180,181`、`RuntimeCleanupCard.tsx:167,173,176,177,180,183,184,190,191,205`、
  `RuntimeResidueCard.tsx:71,74,75,85`（对照组：带样式 215 处）。
  计数方法：跨行取整个开标签（`(?s)<button\b[^>]*>`）再判标签内有无 `className`——
  单行正则会把 `className` 换行的按钮误判成裸按钮，也会漏掉同一标签内的其他属性。
- **修法（已落地）**：① `src/styles.css` 在 `button` 元素层补最小基线（padding / border / 圆角 / 文字色 /
  背景 / cursor），从此漏写类也不会掉成系统灰按钮；② 新增 `.button-quiet`（透明底、蓝色下划线文字按钮）
  给句内「重试」这类链接式动作；③ 24 处逐处补 `.button .button-secondary` / `.button-danger-quiet`
  （破坏性确认）/ `.button-quiet`（句内重试）。重扫后仅剩 `src/App.tsx` 的 5 处故意不带类
  （设置分类 chips、面包屑、toast 关闭），它们由祖先元素选择器给样式（`styles.css:3318-3327`、
  `:2804/:2850/:2888`、`:2225`），补类反而会破坏胶囊/方形尺寸。

### M-6 状态与「下一步」不匹配

- **证据**：中文输入行「**被别的前置挡住** · 中文等非 ASCII 文字只能由无障碍服务写入 ·
  下一步：到系统设置里开启本应用的无障碍服务」；副屏 / 整屏截图行「被别的前置挡住 · 还没有安装 Shizuku ·
  下一步：安装 Shizuku」。
- **修法（已落地）**：`blocked` 文案改成「**依赖未满足**」（`DeviceCapabilityCard.tsx` 的
  `STATE_LABELS.blocked`），不再用「被别的前置挡住」这种需要二次解读的说法；同一行的「下一步」
  继续由 `ACTION_NOTES` 指出具体入口，避免状态与动作指向不同前置。

### M-7 能力行缺状态 chip

- **现象**：六行能力都是「名字 + 灰字长句」，扫视性差；设置页别处已有 chip（「未安装」「未收集」）。
- **修法（已落地）**：能力行改成 `<strong>名称</strong> + 状态 chip`，chip 复用设置页既有的
  `.status-chip`（可用 `success` / 需一步设置与保护降档 `warn` / 不支持 `danger`），原因与下一步
  作为第二行小字；整行 `textContent` 与旧版一致，既有整行断言不需重写。

### M-8 同名块

- **现象**：同屏两块都叫「根通道（KernelSU）」（左：设备能力行；右：`RootEngineCard` 标题）。
- **修法（已落地）**：开关卡标题改为「**根通道设置**」（`RootEngineCard.tsx` 的 `<h3 id="root-engine">`），
  能力行保留「根通道（KernelSU）」——它描述的是设备能力，不是设置入口。锚点 `id="root-engine"`
  不变，`enable_root_engine` 动作的跳转不受影响。

### M-9 宽屏栅格留白

- **现象**：1600×900 横屏下设置页与诊断页右列短左列长，卡片被拉高留空、左下象限空。
- **判定（不改）**：`.settings-form` 在 ≥900px 是 `grid-template-columns: repeat(2, minmax(0, 1fr))`
  且已带 `align-items: start`（`src/styles.css:2326-2330`），首张卡 `grid-column: 1 / -1` 占满一行。
  同一行两张卡内容长度不同时，短的那张下方必然留白——等高网格的固有行为，不是错位。真正的密排
  要 masonry，CSS 至今没有稳定实现；在 1040px 内容列里切三栏会把文字卡压到 330px 左右，比留白更糟。
  结论：记作已知限制，不做改动，避免用布局手法掩盖内容长度差异。
- ~~修法~~（被上面的判定取代）：宽屏断点切三栏，或让卡片按内容对齐。

### M-10 离线安装成功时的在线来源警告

- **证据**：引导第 2 步「当前状态：**已安装**」，同一屏仍有「尚未配置运行时下载地址：
  请先在「设置 → 后台」填写清单地址与 SHA-256（两者必须成对）」。
- **修法**：内置（离线）安装路径成功时把这条降为二级说明，或只在用户选「在线来源」时显示。
- **2026-10-19 已改（代码侧，未在模拟器复测）**：判据从 `needsManifestConfiguration()` 换成
  `usesBundledSource(settings)`（`settings === null` 或 `manifestUrl` 为空即算内置来源），内置来源时
  显示「这次使用 APK 内置镜像，不联网也能装完。」，在线来源时说明「这次从你设置的在线地址下载」。
  那条警告连同「去设置 → 后台填清单地址与 SHA-256」的指路一起删掉——设置页里本来就没有这两个输入框。


### M-11 引导弹窗高过视口

- **证据**：第 3 步弹窗 bounds `[462,60][1138,876]`（视口 900 高），内容与「保存 API Key」可见，
  但底部「上一步 / 下一步」不在视口内（连拍两帧像素相同＝点击未命中），唯一出口是右上「跳过引导」。
- **修法**：弹窗内容超屏时把导航做成吸底固定条（sheet 内滚动），或在 900px 高视口下压缩说明文案。
- **2026-10-19 只做到一半**：引导从 6 步缩到 3 步、Shizuku 授权收进 `<details>`，内容高度明显变短，
  但 `.dialog` 仍是整块滚动（`src/styles.css:1973-1984` 只有 `overflow-y: auto`），导航条**没有**吸底。
  需要在 900px 高视口按原步骤复测；仍不达标就把 `.onboarding-nav`（`src/styles.css:2523`）做成 sticky 底条。


### M-12 「打开 Harness」的凭据守卫（设计参考）

- **现象**：未配置模型密钥时点「打开 Harness」，不静默失败：跳到「模型与密钥」+ 琥珀说明
  「没有密钥时每一轮对话都会失败，因此应用不会打开 Harness…」+ 明确出口
  「我已在 Harness 内配置过，仍要打开」。
- **价值**：这就是 M-3 缺的「解释 + 出口」范式；运行时启动失败路径应照此改造。

## 三、修复顺序与取舍
