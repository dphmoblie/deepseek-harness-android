## 1 结论速览

| # | 路径 | 判定 | 前置条件 | 需真机验证 |
| --- | --- | --- | --- | --- |
| 1a | 本应用进程在后台直启 Activity（`SYSTEM_ALERT_WINDOW` 豁免） | 有条件可行 | 已声明 `SYSTEM_ALERT_WINDOW`；命中 BAL 例外；**只保证通过后台启动检查，不保证界面真的显示、不保证不抢前台** | 是 |
| 1b | 经 shell uid（Shizuku `DeviceShellUserService` / `am start`）启动 | 可行（后台启动检查层面） | shell 通道已授权；`am` 在 system_server 侧执行，调用者 uid 为 shell | 是 |
| 2a | 无障碍读取并操作**可见但非活跃**的窗口 | 有条件可行 | `canRetrieveWindowContent` + `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` + 白名单；**需要新增代码**（当前只用 `rootInActiveWindow`） | 是 |
| 2b | 无障碍操作**完全不可见 / 后台无窗口**的应用 | 不可行 | 无窗口即无节点；`dispatchGesture` 只能投到触摸屏，无法指定后台窗口 | 是（验证失败路径） |
| 3a | freeform 自由窗口承载第三方应用 | 有条件可行 | shell 通道 + 整数窗口模式（`WINDOWING_MODE_FREEFORM`=5）+ ROM 打开 freeform 开关 + 目标应用允许 resize | 是 |
| 3b | 分屏 | 不确定 | 只有无障碍全局动作 `GLOBAL_ACTION_TOGGLE_SPLIT_SCREEN`，且须出现在 `getSystemActions()` 中 | 是 |
| 3c | 让第三方应用进入画中画 | 不可行 | `supportsPictureInPicture` 必须由目标应用自己在清单声明、并自己调用 `enterPictureInPictureMode()` | 否 |
| 3d | 把第三方界面嵌进本应用窗口 | 不可行 | 被嵌入方须声明 `android:allowEmbedded`（默认 false）；公开 SDK 里也没有承载组件 | 否 |
| 3e | 用悬浮窗承载第三方界面 | 不可行 | `TYPE_APPLICATION_OVERLAY` 只能承载自己的 View | 否 |
| 4 | 虚拟显示 / 副屏承载并操作 | 不确定 | `createVirtualDisplay` 公开但默认创建 **private** 显示（仅创建者 uid 与已在该屏的 activity 可交互）；PUBLIC/权限、无障碍可见性均未查到明文 | 是 |
| 5 | 厂商小窗（MIUI/HyperOS、ColorOS、One UI 等）可编程入口 | 不可行（无公开 API） | 未找到任何公开 API；只能靠厂商私有实现碰运气 | 是 |

一句话结论：**「不抢前台」这件事上，真正可控的两条腿是「shell 通道把目标应用放进非全屏形态」+「无障碍在多个窗口之间定位并下发动作」；本仓库第二条腿的开关已经打开（flag 已在），但代码还没用起来。**

## 2 术语与需求口径

- **操作后台应用**：让一个**不在前台**的普通第三方应用接受本应用的自动操作（点击、输入、滚动等）。
- **单独页面**：给它独立的任务栈 / 窗口 / 显示来承载，而不是抢占当前前台。
- **小窗**：自由窗口（freeform）、厂商小窗、分屏、画中画等不占满屏的形态。
- **两个不同的问题必须分开看**：
  1. **它能不能被启动/放到某个承载里**（窗口与任务层面，属于 system_server 的启动策略）；
  2. **它的界面能不能被看到、被点到**（无障碍层面，属于窗口可见性与节点可操作性）。
  任一条腿断了，另一条腿都白搭——例如目标应用成功被放进自由窗口，但无障碍只肯看当前活跃窗口，就等于看不到它。

## 3 逐路径评估

### 3.1 路径一：后台启动 Activity（及 shell uid 是否豁免）

**机制。** Android 10（API 29）起，后台进程启动 Activity 默认被拦。拦截逻辑在 AOSP `services/core/java/com/android/server/wm/BackgroundActivityStartController.java`（类注释逐字：「Helper class to check permissions for starting Activities.」）。核心方法 `checkBackgroundActivityStartAllowedByCallerInBackground(BalState state)` 的允许清单（源码第 1031 行起，逐条）：

1. 第 1034–1040 行：`if (state.mCallingUid == Process.ROOT_UID || callingAppId == Process.SYSTEM_UID || callingAppId == Process.NFC_UID)` → `BAL_ALLOW_ALLOWLISTED_UID`，理由 `"Important callingUid"`；
2. 第 1043 行：home 应用；
3. 第 1052 行：当前 IME 窗口属主 uid；
4. 第 1059 行：`state.mIsCallingUidPersistentSystemProcess`（常驻系统进程）；
5. **第 1064–1069 行：`if (hasBalPermission(state.mCallingUid, state.mCallingPid))` → `BAL_ALLOW_PERMISSION`，理由逐字 `"START_ACTIVITIES_FROM_BACKGROUND permission granted"`**；
6. 第 1071 行：recents 组件同 uid；第 1076 行 device owner；第 1081 行 affiliated profile owner；第 1087 行 companion app；
7. **第 1091–1101 行：`if (mService.hasSystemAlertWindowPermission(...))` → `BAL_ALLOW_SAW_PERMISSION`，日志逐字 `"Background activity start for <pkg> allowed because SYSTEM_ALERT_WINDOW permission is granted."`**；
8. 第 1104–1109 行：appop `AppOpsManager.OP_SYSTEM_EXEMPT_FROM_ACTIVITY_BG_START_RESTRICTION == MODE_ALLOWED`（受 DeviceConfig 键 `system_exempt_from_activity_bg_start_restriction_enabled` 开关）；
9. 第 1112 行：落到 `checkProcessAllowsBal(state.mCallerApp, state, BAL_CHECK_BACKGROUND)`，即按「调用方是否有可见窗口 / 前台服务 / 是否与前台进程绑定 / 宽限期」等再判。

**shell uid 为什么不受这条限制。** `packages/Shell/AndroidManifest.xml` 里 `package="com.android.shell"`、`android:sharedUserId="android.uid.shell"`、`coreApp="true"`，逐字声明了 `android.permission.START_ACTIVITIES_FROM_BACKGROUND`（还有 `MANAGE_ACTIVITY_TASKS`、`INTERACT_ACROSS_USERS_FULL`、`INJECT_EVENTS`、`RETRIEVE_WINDOW_CONTENT`、`ACTIVITY_EMBEDDING`、`WRITE_SECURE_SETTINGS`、`MANAGE_DISPLAYS` 等）。而 `am` 命令本身是瘦壳：`cmds/am/src/com/android/commands/am/Am.java` 的 `onRun()` 只做 `mAm.asBinder().shellCommand(...)`，真正执行在 system_server 的 `ActivityManagerShellCommand`，调用者 uid 即 shell。两侧对应，正好命中上面第 5 条例外。

**前提。**

| 手段 | 需要的权限 / API | 系统签名 | 工具链 |
| --- | --- | --- | --- |
| 应用内 `startActivity` | `SYSTEM_ALERT_WINDOW`（BAL 第 7 条例外）；或前台服务/可见窗口等条件 | 否 | 公开 API |
| `am start`（shell） | shell 的 `START_ACTIVITIES_FROM_BACKGROUND` | 否 | 任意 shell（含 Shizuku） |
| 免检查启动 | `START_ACTIVITIES_FROM_BACKGROUND` 权限本身是 `signature\|privileged`（普通应用申请书里给了也拿不到） | 是（或预装） | — |

**本仓库现有能力。**

- `android/app/src/main/AndroidManifest.xml:39` 已声明 `android.permission.SYSTEM_ALERT_WINDOW`；`SYSTEM_ALERT_WINDOW` 也是悬浮球能挂上去的前提（`OverlayBallService.kt:227` 的 `TYPE_APPLICATION_OVERLAY`）。
- 但应用内**刻意不直启**：`OverlayBallService.kt:397-415` 的 `openHarness()` 用小段 `PendingIntent.getActivity(... KeepAliveEntryActivity ...)` + `pending.send()`，注释逐字：「不直接 startActivity —— Android 10+ 限制后台启动 Activity，从 overlay 直接起会被静默丢弃。也不指向 singleTask 的 MainActivity：那会 clear-top 掉正在显示的 HarnessActivity 并撤销会话凭据。」
- 另有一处 `startActivity` 包在 `runCatching` 里（`OverlayBallService.kt:540-543`），以及常驻通知的 `contentIntent` 同样指向 `KeepAliveEntryActivity`（`OverlayBallService.kt:587-593`）。
- shell 侧已有真实通道：`shizuku/DeviceShellUserService.kt:17`（`IDeviceShellService.Stub`）、`:43`（`NativePty.spawn`）、`:212`（`DEVICE_SHELL = "/system/bin/sh"`），命令体由 `shizuku/DeviceCommandRunner.kt` 生成。但**启动应用目前只走一条会抢前台的路**：`DeviceCommandRunner.kt:433` `LAUNCH_APP -> monkey -p "$param" 1`（`monkey` 发的是 MAIN/LAUNCHER intent，必然把任务带到前台）。全仓库没有 `am start`（含 `--display` / `--windowingMode`）。
- `shizuku/ShizukuRuntime.kt:58-65` 的 `Shizuku.UserServiceArgs(...)`、`:266-286` 的 `openManager()` 只用于拉起 Shizuku Manager 自身界面，不是自动化通道。

**真机要确认什么。**

1. 用 shell 通道跑 `am start -n <包>/<Activity>`，看 `dumpsys activity activities` 里任务是否新建、原前台是否被抢占（预期：会抢）。
2. 加 `--display <id>` 或 `--windowingMode <int>` 后，是否真的不抢默认屏前台（未在真机验证）。
3. 在本应用进程内、且在后台（无可见 Activity）时直启 `HarnessActivity`，观察是否被静默丢弃；对照实验：先确认 `Settings.canDrawOverlays(this)` 为真。
4. Shizuku UserService 里 fork 出来的 `/system/bin/sh` 执行 `am`，其 binder 调用者的 uid/包名是否与 `adb shell am` 完全一致（这是「shell 权限是否 100% 等同」的核心未知项，未在真机验证）。

**风险。**

- **BAL 豁免 ≠ 一定显示成功**：`BAL_ALLOW_*` 只说明「后台启动检查放过」，后面还有任务/显示栈策略、`--display` 的存在性与信任、厂商策略等。因此本仓库那句「从 overlay 直接起会被静默丢弃」与 AOSP 例外清单**不构成硬矛盾**（见第 5 节），但措辞容易被读成「有 `SYSTEM_ALERT_WINDOW` 也不行」。
- 抢前台会破坏会话：`OverlayBallService.kt:401-402` 已经吃过「clear-top 掉 HarnessActivity 并撤销会话凭据」的亏。
- 不能把 Shizuku 当成 root 或永久保活：它的能力取决于用户授予的权限与 Android 版本（与 `docs/应用自动化能力.md:78` 一致）。

### 3.2 路径二：无障碍服务对非前台窗口的作用范围

**机制（AOSP 逐字）。** 来源 `core/java/android/accessibilityservice/AccessibilityService.java` 与 `AccessibilityServiceInfo.java`：

- `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` 的 javadoc 逐字：「This flag indicates to the system that the accessibility service wants to access content of all interactive windows. An interactive window is a window that has input focus or can be touched by a sighted user when explore by touch is not enabled. If this flag is not set your service will not receive `TYPE_WINDOWS_CHANGED` events, calling `AccessibilityService.getWindows()` will return an empty list, and `AccessibilityNodeInfo.getWindow()` will return null.」并要求 meta-data 声明 `canRetrieveWindowContent`，否则该 flag 被忽略。
- `getWindows()`（第 1050–1075 行）逐字：「Gets the windows **on the screen of the default display**. This method returns only the windows that a sighted user can interact with, as opposed to all windows.」以及「Since the user can always interact with the window that has input focus by typing, the **focused window is always returned (even if covered by a modal window)**.」
- `getWindowsOnAllDisplays()`（第 1077–1104 行）逐字同构，首句为「Gets the windows **on the screen of all displays**」，返回说明「**The key of SparseArray is display ID.**」
- `getRootInActiveWindow()`（第 1106–1123 行）逐字：「Gets the root node in the **currently active window**... The active window is the one that the user is currently touching or the window with input focus, if the user is not touching any window. **It could be from any logical display.**」
- `dispatchGesture()`（第 1249–1315 行）逐字：「**Dispatch a gesture to the touch screen.** Any gestures currently in progress, whether from the user, this service, or another service, will be cancelled.」「The gesture will be dispatched **as if it were performed directly on the screen by a user**」；要求 meta-data 声明 `canPerformGestures`。**它没有 per-window 目标参数**——手势只是注入到触摸屏，按坐标命中当时最上层可触摸的窗口，因此无法指定后台窗口，也无法指定一块看不见的虚拟显示器。
- 动作下发通道是**逐窗口**的：`core/java/android/view/accessibility/IAccessibilityInteractionConnection.aidl`（`@hide`、`oneway`）类注释逐字「Interface for interaction between the AccessibilityManagerService and **the ViewRoot in a given window**.」，方法含 `void performAccessibilityAction(long accessibilityNodeId, int action, in Bundle arguments, int interactionId, IAccessibilityInteractionConnectionCallback callback, int flags, int interrogatingPid, long interrogatingTid);`。即 `performAction` 是发到「该节点所属窗口的 ViewRoot」的、按节点而非按屏幕坐标的通道，与窗口当前是否为活跃窗口**不是同一个约束**；但 AOSP 没有明文承诺「对非活跃窗口的 `performAction` 一定成功」。

**前提。** 无障碍服务由用户在系统设置里手动开启（不能由 Shizuku 静默开启，见 `docs/应用自动化能力.md:67-70`）；meta-data 需 `canRetrieveWindowContent="true"`（`android/app/src/main/res/xml/accessibility_service_config.xml`）；要跨窗口取内容需 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`；要注入手势需 `canPerformGestures`（本仓库 XML 里**没有**声明）。均不需要系统签名、不需要 root。

**本仓库现有能力。**

- 开关已打开：`accessibility/DeepSeekAccessibilityService.kt:43-55` 的 `onServiceConnected()` 里设置了 `eventTypes` / `feedbackType` / `notificationTimeout`，并在第 51–52 行设 `flags = ... or AccessibilityServiceInfo.FLAG_RETRIEVE_INTERACTIVE_WINDOWS`。全仓库仅此一处，且**没有任何 `getWindows()` / `getWindowsOnAllDisplays()` / `dispatchGesture()` 调用**（全树 grep 无命中）。
- 取窗口只用活跃窗口：`DeepSeekAccessibilityService.kt:86` `val root = rootInActiveWindow ?: return failure("ACCESSIBILITY_WINDOW_UNAVAILABLE", "当前没有可读取的应用窗口")`；`:302` `performConfirmedAction()` 再次取 `rootInActiveWindow`。
- 操作对象被双重钉在当前前台：`:87-91` 校验 `root.packageName` 在白名单 `AccessibilityAutomationStore.allowedPackages(this)` 内；`:167` `if (request.packageName != packageName) return failure("ACCESSIBILITY_PACKAGE_DENIED", "动作目标不是当前前台应用")`；`:304` 动作前再校验前台包未变化。
- 坐标点击不是手势注入：`:103-130` 的 `observedAction()` 在节点树里找「`isVisibleToUser && isClickable && viewIdResourceName` 非空 && bounds 含坐标」的节点，再把坐标换成该 viewId 的 `click`；文本输入走 `root.findFocus(FOCUS_INPUT)`。
- 动作类型与护栏：`:313-324` 只做 `ACTION_CLICK` / `ACTION_SET_TEXT` / `ACTION_SCROLL_FORWARD|BACKWARD`（并各自要求 `isClickable` / `isEditable` / `isScrollable`）；`:92` 敏感窗口拦截；`:370-374` 锁屏/息屏拦截（`KeyguardManager.isKeyguardLocked` / `PowerManager.isInteractive`）；`:379-384` 常量（`ACTION_INTERVAL_MS = 350L`、`MAX_TREE_NODES = 120`、`MAX_TREE_DEPTH = 24` 等）。
- 无障碍 overlay 用 `TYPE_ACCESSIBILITY_OVERLAY`（`:239-240`），但确认面板路径在 tap/inputText 主流程里未被调用（`executeConfirmedAction()` 在 `:175` 直接执行）。

**结论。** 本仓库目前**结构上把操作对象限定为「当前前台/活跃窗口」**。「可见但非活跃」的窗口（分屏另一侧、小窗、被 IME 遮挡但可见的窗口）在框架层是能看到的（`getWindows()` 会列出可交互窗口，且**带输入焦点的窗口即便被遮挡也一定返回**），但要用起来必须新增代码，并且要重新定义白名单/前台校验/敏感窗口这套护栏在多窗口下怎么判。

**真机要确认什么（未在真机验证）。**

1. 目标应用处于分屏副侧或自由窗口、本应用在另一侧时，`getWindows()` / `getWindowsOnAllDisplays()` 是否列出它的窗口，数量与层级顺序如何。
2. 对其中节点的 `performAction(ACTION_CLICK)` / `ACTION_SCROLL_FORWARD` 是否真的生效（这是「per-window 通道」能否落到非活跃窗口的关键实验）。
3. 目标应用被完全遮挡（例如全屏应用盖住小窗）时，它是否仍出现在 `getWindows()` 里；若出现，`performAction` 是否仍生效。
4. 目标应用被系统冻结/进入 cached 状态后，节点信息是否变成空壳（与 `docs/应用自动化能力.md:18` 提到的「某些 ROM 可能只返回空壳」相互印证）。
5. 厂商 ROM（MIUI/HyperOS、ColorOS、One UI）是否限制了 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS` 的返回集合。

**风险。**

- **坐标手势这条路必须放弃**：`dispatchGesture` 的语义是「投到触摸屏」，它不可能点到后台窗口；本仓库现行的「坐标→节点」折衷（`:103-130`）恰恰是绕开这个限制的正确方向。
- 多窗口下「前台包」不再是唯一真相，`:167`/`:304` 的前台校验会误伤合法目标（需要改成「目标包对应的窗口是否存活且可见」）。
- 对不可见窗口的操作没有 UI 反馈，失败会静默；必须靠 `dumpsys`/日志做归因。
- 护栏不能松：白名单、敏感窗口、锁屏三件套在任何扩展里都要保留（`docs/应用自动化能力.md:32-33`、`:49-50`）。

### 3.3 路径三：小窗 / 自由窗口

范围：freeform 自由窗口、分屏、画中画、悬浮窗、以及「把别人的界面嵌进自己窗口」。

#### 3.3.1 freeform 自由窗口

**机制与 API 面。**

- 窗口模式常量在 AOSP 是**隐藏 API**：`core/java/android/app/WindowConfiguration.java:106-115` 逐字 —— `WINDOWING_MODE_UNDEFINED = 0`、`WINDOWING_MODE_FULLSCREEN = 1`、`WINDOWING_MODE_PINNED = 2`、**`WINDOWING_MODE_FREEFORM = 5`**（上一行注释 `// TODO: Remove once freeform is migrated to wm-shell.`）、`WINDOWING_MODE_MULTI_WINDOW = 6`。`android.app.WindowConfiguration` **不在** `android-35/android.jar` 里（zip 条目与 `javap` 双重确认），所以应用侧编译期拿不到这些常量。
- 应用侧对应入口 `ActivityOptions.setLaunchWindowingMode(int)` 也是隐藏 API：AOSP `core/java/android/app/ActivityOptions.java:1853-1860` 逐字 `/** Sets the windowing mode the activity should launch into. @hide */ @TestApi public void setLaunchWindowingMode(int windowingMode)`；`javap` 在 android.jar 35 里**找不到**它。
- shell 侧可以指定：`services/core/java/com/android/server/am/ActivityManagerShellCommand.java:660-661` 逐字 `} else if (opt.equals("--display")) { mDisplayId = Integer.parseInt(getNextArgRequired());`，`:664-665` 逐字 `} else if (opt.equals("--windowingMode")) { mWindowingMode = Integer.parseInt(getNextArgRequired());`；`:810-824` 组装成 `ActivityOptions.makeBasic()` + `options.setLaunchDisplayId(mDisplayId)` / `options.setLaunchWindowingMode(mWindowingMode)`。`onHelp()` 里逐字用法是 `--windowingMode <WINDOWING_MODE>: The windowing mode to launch the activity into.`（第 4379 行）与 `--display <DISPLAY_ID>: The display to launch the activity into.`（第 4381 行）。**注意：取值是整数，命令行没有 `freeform` 这类字符串取值。**
- ROM 侧开关：`Settings.Global.DEVELOPMENT_ENABLE_FREEFORM_WINDOWS_SUPPORT`，字面键名 `development_enable_freeform_windows_support`（AOSP `ActivityTaskManagerService.java` 里 `import static android.provider.Settings.Global.DEVELOPMENT_ENABLE_FREEFORM_WINDOWS_SUPPORT;`；`core/proto/android/providers/settings.proto` 中出现 `development_enable_freeform_windows_support`）。**该键在当前 ROM 上是否足以打开 freeform、以及打开后 `--windowingMode 5` 是否被接受，未逐字核实启动判定代码，需真机验证。**
- 目标应用可以拒绝：如果目标应用的 activity 声明 `android:resizeableActivity="false"`，多窗口形态会被降级为全屏（小米官方适配文档逐字：「如果将此属性设置为 true，则 activity 能以分屏和自由窗口模式启动。如果将此属性设置为 false，则 activity 不支持多窗口模式。如果此值为 false，并且用户尝试在多窗口模式下启动 activity，则 activity 会全屏显示。」）。第三方无法改别人的清单。

**前提。** shell 通道（Shizuku）+ 系统允许 freeform + 目标 activity 未声明 `resizeableActivity=false` + 该显示/任务允许承载。不需要系统签名（因为走的是 shell 的现成命令）；能力实际来自 shell 的 `MANAGE_ACTIVITY_TASKS` / `START_ACTIVITIES_FROM_BACKGROUND` 等特权，而非本应用自身。

**本仓库现有能力。** 全树 grep：`windowingMode` / `resizeableActivity` / `pictureInPicture` / `setLaunchBounds` / `createVirtualDisplay` / `DisplayManager` / `ActivityTaskManager` **零命中**；`DeviceCommandRunner.kt` 的命令枚举（第 26–56 行）里也没有 `am start`、`--display`、`--windowingMode`、`settings put`（只有只读的 `GET_SETTING -> "settings get $namespace $key"`）。即**目前完全没有这条腿**。

**真机要确认什么（未在真机验证）。**

1. `settings get global development_enable_freeform_windows_support` 的当前值；置为 1 后 `am start --windowingMode 5 -n <pkg>/<Activity>` 的实际效果（进入小窗 / 全屏 / 报错）。
2. 目标应用声明了 `resizeableActivity=false` 时的降级行为。
3. 自由窗口落在默认屏时，是否抢占前台（预期：会成为前台任务，因此需要与路径二配合）。

5. 小米/HyperOS 上的小窗是否与原生 freeform 走同一套（官方文档称「MIUI 的小窗是基于 Android 的多窗口 Freeform 方案实现的」，但小窗的**唤起**由谁控制未公开）。

**风险。** 依赖隐藏语义与 ROM 开关，系统升级可能失效；`WINDOWING_MODE_FREEFORM` 的注释明说 freeform 正在向 wm-shell 迁移；把目标应用放进小窗后它仍可能被系统冻结或降级。

#### 3.3.2 分屏

无障碍只有一个相关入口：`AccessibilityService.GLOBAL_ACTION_TOGGLE_SPLIT_SCREEN = 7`，javadoc 逐字「Action to toggle docking the current app's window」并注明「It is effective only if it appears in `getSystemActions()`」。也就是说：**它作用于「当前」任务，且不保证可用**；无法指定「把某个后台应用塞进分屏」。判定：不确定（未在真机验证）。

#### 3.3.3 画中画（PIP）

- 能否进入 PIP 由**目标应用自己**决定：`core/java/android/content/pm/ActivityInfo.java:666-670` 逐字 `/** Bit in {@link #flags} indicating if the activity supports picture-in-picture mode. See {@link android.R.attr#supportsPictureInPicture}. @hide */ public static final int FLAG_SUPPORTS_PICTURE_IN_PICTURE = 0x400000;`，判定方法在 `:1942-1946` `public boolean supportsPictureInPicture() { return (flags & FLAG_SUPPORTS_PICTURE_IN_PICTURE) != 0; }`；`core/java/android/app/Activity.java:1102-1108` 的 `enterPictureInPictureMode()` javadoc 逐字「Puts the activity in picture-in-picture mode if the activity supports.」且实现是 `if (mActivityInfo.supportsPictureInPicture())`。→ **第三方无法替别的应用声明或触发 PIP。**
- `ActivityOptions.makeLaunchIntoPip(PictureInPictureParams)` 在 `javap` 里是公开 API，但它属于「把新 activity 启动到**已经在 PIP 的**容器里」这一语义（AOSP 里对应 key `android.activity.launchIntoPipParams`），并不能凭空把第三方应用变成小窗。
- 本仓库：`android/app/src/main/AndroidManifest.xml` 全文**没有** `supportsPictureInPicture`（grep 零命中），也没有任何 PIP 代码。判定：**不可行**（对第三方目标应用而言）。

#### 3.3.4 悬浮窗

`TYPE_APPLICATION_OVERLAY` 是公开 API（`javap` 确认），本仓库悬浮球就在用（`OverlayBallService.kt:227`、`:458`、`:477`）。它的能力边界是**只承载本应用自己的 View**——无法把别的应用的界面「装」进来。判定：**不可行**（作为承载第三方界面的手段）。

#### 3.3.5 把第三方界面嵌入自己的窗口

- 被嵌入的 activity 必须自己声明 `android:allowEmbedded`：AOSP `core/res/res/values/attrs_manifest.xml:1070-1075` 逐字「Indicate that the activity can be launched as the embedded child of another activity. Particularly in the case where the child lives in a container such as a Display owned by another activity. <p>The default value of this attribute is <code>false</code>.」，声明为 `<attr name="allowEmbedded" format="boolean" />`。第三方应用基本不会声明。
- 承载组件也不在公开 SDK：`android.app.ActivityView` 在 AOSP `android-10.0.0_r1` 里存在但是 `@hide`（`core/java/android/app/ActivityView.java:65` `@hide`、`:68` `public class ActivityView extends ViewGroup`），在 `android-13.0.0_r1` 与当前 `master` 里**已 404 移除**，`android-35/android.jar` 里也没有。判定：**不可行**。

### 3.4 路径四：虚拟显示 / 副屏

**机制与前提。**

- 创建虚拟显示是公开 API：`android.hardware.display.DisplayManager.createVirtualDisplay(...)`（`javap` 在 android.jar 35 里确认存在多个重载，含 `(String,int,int,int,Surface,int)`），**不需要系统签名**。
- 但 `surface` 必须是应用自己提供的：AOSP `core/java/android/hardware/display/DisplayManager.java:1102-1108` 的签名里 `@Nullable Surface surface`，`:1139-1140` 逐字「@param surface The surface to which the content of the virtual display should be rendered, **or null if there is none initially**.」；`:1114-1120` 逐字「The content of a virtual display is rendered to a `Surface` provided by the application.」「Because a virtual display renders to a surface provided by the application, it will be released automatically when the process terminates and all remaining windows on it will be forcibly removed.」
- 默认创建出来的是**私有**显示：`:1122-1124` 逐字「By default, virtual displays are created to be private, non-presentation and unsecure. **Permissions may be required to use certain flags.**」；`VIRTUAL_DISPLAY_FLAG_PUBLIC = 1 << 0`（`:237`）的 javadoc 逐字「A public virtual display behaves just like most any other display that is connected to the system such as an external or wireless display. Applications can open windows on the display and the system may mirror the contents of other displays onto it.」，而私有显示的约束逐字是「A private virtual display belongs to the application that created it... **the only processes that are allowed to enumerate or interact with the private display are those that have the same UID as the application that originally created the private virtual display or as the activities that are already on that display.**」（`:206-231`）
- 把 activity 送到指定显示：`ActivityOptions.setLaunchDisplayId(int)` 是公开 API（`javap` 确认）；shell 侧是 `am start --display <int>`（见 3.3.1 的逐字解析）。
- 无障碍侧跨显示取材：`AccessibilityService.getWindowsOnAllDisplays()`（公开，返回 `SparseArray<List<AccessibilityWindowInfo>>`，key 为 display ID）。

**本仓库现有能力。** 零：全树没有 `DisplayManager` / `createVirtualDisplay` / `setLaunchDisplayId` / `--display` 的任何使用。

**这条路是不是只停留在纸面上。** 关键在于：**能创建** ≠ **第三方应用能在上面跑、并且我们的无障碍能操作它**。公开 API 层面 `createVirtualDisplay` 没问题，但要跨进程把别人的 activity 放上去、还要让无障碍枚举到那个屏上的窗口，目前只能确证「有公开入口」，不能确证「实际成立」。判定：**不确定，未在真机验证**。

**真机要确认什么（未在真机验证）。**

1. 用一个 `ImageReader`/`SurfaceTexture` 作为 surface 创建虚拟显示（先 `VIRTUAL_DISPLAY_FLAG_PUBLIC`，再对照 `OWN_CONTENT_ONLY`），`am start --display <id> -n <第三方包>/<Activity>` 是否成功把第三方界面投上去。
2. 同一时刻 `<我们的无障碍服务>` 的 `getWindowsOnAllDisplays()` 是否包含该 displayId 及其窗口；若包含，`performAction` 是否生效。
3. PUBLIC / AUTO_MIRROR 是否需要额外权限（AOSP 只说「Permissions may be required」，**未逐字列出**，本文不猜）。
4. 用户可见性：虚拟显示的画面只到 Surface，若不做 `Presentation`/自绘，用户根本看不到这块屏——「小窗」要给人看，还得再套一层显示载体。

**风险。** 私有显示只有创建者 uid 能交互（无障碍服务属别的 uid），这可能直接掐死路径二与路径四的组合；`OWN_CONTENT_ONLY` / `AUTO_MIRROR` 的权限边界未知；虚拟显示随进程终止被回收，其上窗口「will be forcibly removed」。

## 代码与官方文档能确定的

1. **后台启动检查的例外清单是白纸黑字**：`START_ACTIVITIES_FROM_BACKGROUND` 权限与 `SYSTEM_ALERT_WINDOW` 都在 `BackgroundActivityStartController.checkBackgroundActivityStartAllowedByCallerInBackground()` 的豁免里；shell 持有前者，本应用已声明后者。
2. **shell uid 走 `am` 不受后台启动限制**：`Am.java` → `ActivityManagerShellCommand` 在 system_server 侧执行 + shell 清单声明 `START_ACTIVITIES_FROM_BACKGROUND`，两侧互证。
3. **`am start` 支持整数形式的 `--display` 与 `--windowingMode`**，并把它们变成 `ActivityOptions.setLaunchDisplayId` / `setLaunchWindowingMode`；但 `WindowConfiguration.WINDOWING_MODE_FREEFORM = 5` 与 `setLaunchWindowingMode` 都**不在公开 SDK**（android.jar 35 无 `WindowConfiguration`、无 `setLaunchWindowingMode`）。
4. **无障碍的窗口可见范围**：`FLAG_RETRIEVE_INTERACTIVE_WINDOWS` 是「看得到多个窗口」的开关，`getWindows()` 只覆盖默认屏、`getWindowsOnAllDisplays()` 覆盖所有屏并以 displayId 为 key；带输入焦点的窗口即便被遮挡也一定返回。
5. **`dispatchGesture` 只能投到触摸屏**，没有 per-window 目标参数；`performAction` 则是逐窗口（ViewRoot）通道，与「是不是活跃窗口」不是同一个约束。
6. **PIP 由目标应用自己声明**：`FLAG_SUPPORTS_PICTURE_IN_PICTURE` + `Activity.enterPictureInPictureMode()` 的判定都在目标 activity 自己的 `ActivityInfo` 上。
7. **嵌入第三方界面在公开 SDK 里已经没有组件**：`allowEmbedded` 默认 false，`ActivityView` 在 `android-10` 是 `@hide`、到 `android-13`/`master` 已被移除，android.jar 35 无此类。
8. **虚拟显示是公开 API，但默认是私有显示**，且内容渲染到应用自己提供的 Surface；PUBLIC/AUTO_MIRROR 可能需要额外权限（AOSP 未列出）。
9. **本仓库现状**：已声明 `SYSTEM_ALERT_WINDOW`、已开 `FLAG_RETRIEVE_INTERACTIVE_WINDOWS`、已有 shell 通道；但**没有** `getWindows()` 调用、**没有** `am start`/`--display`/`--windowingMode`、**没有** PIP/freeform/虚拟显示相关代码；无障碍只认 `rootInActiveWindow` 并额外校验「目标包 == 当前前台包」。

## 4 组合建议：单独页面与小窗各自的最小可行路径

### 4.1 「单独页面」的最小可行路径

**目标：不抢占当前前台，同时把目标应用放在一个我们能操作的地方。**

- **第 1 步（必须先做，纯应用内改动）**：把无障碍的取材范围从 `rootInActiveWindow` 扩到「目标包对应的可见窗口」。做法是在现有 flag（已开）基础上，用 `getWindows()` / `getWindowsOnAllDisplays()` 找到白名单包的窗口，再对该窗口的根节点走现有的动作白名单（`ACTION_CLICK` / `ACTION_SET_TEXT` / `ACTION_SCROLL_*`），并保留敏感窗口与锁屏拦截。
  为什么先做：不依赖 shell、不依赖 ROM 开关、不需要新权限；而且**后续任何承载形态的收益都取决于这条腿能不能动**。
  验收：分屏或厂商小窗（由用户手动放置目标应用）下，能对非活跃窗口完成一次点击与一次滚动。
- **第 2 步**：shell 通道新增「非前台启动」命令（`am start`，可选 `--display` / `--windowingMode`），与现有 `LAUNCH_APP -> monkey -p ...`（`DeviceCommandRunner.kt:433`，必然前台）区分开，作为独立诊断项与独立工具暴露。
  为什么排第二：它需要真机确认 ROM 是否接受这些参数，且一旦成功，目标应用会变成前台任务——收益要靠第 1 步来接。

### 4.2 「小窗」的最小可行路径

- **首选：freeform 自由窗口**（路径 3.3.1）。理由是它是 Android 原生形态、有 shell 参数入口（整数 `--windowingMode`）、并且厂商小窗（MIUI/HyperOS）官方自述就是基于 freeform 实现的——把 freeform 打通，等价于同时押注厂商小窗。
  步骤：真机确认 freeform 开关 → `am start --windowingMode 5` 把目标应用放进自由窗口 → 用第 1 步的无障碍能力操作它 → 记录「是否抢前台」。
- **次选：分屏**（3.3.2）。只有 `GLOBAL_ACTION_TOGGLE_SPLIT_SCREEN` 且不保证可用，作为免费尝试，不作为主路径。
- **不建议投入**：画中画（3.3.3）、嵌入第三方界面（3.3.5）、悬浮窗承载别人界面（3.3.4）——三条都在公开 API 层面就关死了。
- **最后再评估**：虚拟显示/副屏（3.4）。它的组合风险最大：私有显示只允许创建者 uid 交互，而这恰好会把无障碍挡在门外。

### 4.3 优先顺序

```
第 1 步  无障碍多窗口取材（纯应用内，先证明「能操作非活跃窗口」）
   ↓
第 2 步  shell 非前台启动 + freeform（证明「能不抢前台地把目标应用摆好」）
   ↓
第 3 步  两者合流：小窗里的目标应用 + 无障碍自动操作（端到端）
   ↓
第 4 步  分屏兜底 / 虚拟显示探索（按真机结果决定是否继续）
```

## 5 与仓库现有结论的张力、以及措辞边界

1. **`OverlayBallService.kt:400` 的注释**逐字是「不直接 startActivity —— Android 10+ 限制后台启动 Activity，从 overlay 直接起会被静默丢弃」。AOSP 的例外清单里 `SYSTEM_ALERT_WINDOW` 是**明确豁免项**（`BAL_ALLOW_SAW_PERMISSION`），所以这句话如果被读成「有悬浮窗权限也不能起」，与 AOSP 不符。**更好的表述**是：命中 BAL 例外只说明通过了后台启动检查；能不能真的显示、会不会抢前台、会不会被任务/显示策略与厂商策略影响，是另一回事——本仓库选择 `PendingIntent` + `KeepAliveEntryActivity` 的保守做法仍然合理（且 `clear-top` 会话凭据的教训是真实约束）。
2. **`docs/应用自动化能力.md:19`** 的 `mobile_device_tap` 承诺「坐标范围受限；必须来自最近一次观察，原生服务仍检查白名单、锁屏和敏感窗口」——本评估不推翻它：坐标点击在本仓库是「坐标→节点」的折衷（`DeepSeekAccessibilityService.kt:103-130`），而不是会命中任意窗口的触摸注入。若未来引入 `dispatchGesture`（当前 XML 未声明 `canPerformGestures`），这条承诺必须重新评估。
3. **`docs/应用自动化能力.md:21`** 的 `mobile_device_background_tasks` 明确「只返回 Android Shell 可见的摘要，不代表能读取后台界面或私有数据库」；`docs/应用自动化能力.md:69-74` 也说明无障碍不能静默开启、不能保证锁屏后可操作、拿不到私有数据库与后台业务接口。本文的第 3.2 节与这些结论一致（扩展的是「可见窗口」，不是「后台界面」）。
4. **`docs/应用自动化能力.md:78`** 「Shizuku 的实际能力取决于用户授予的权限和 Android 版本，不能把它描述成 root」——本文所有 shell 侧结论都建立在这条前提上，且不把 Shizuku 当保活手段。
5. **`docs/应用自动化能力.md:81-85`** 只声明在 MuMu 12 上验收过外壳导航/安全区/设置布局，未宣称 Shizuku 授权、悬浮窗或锁屏后台恢复在该模拟器通过。本文因此把所有路径标注为**未在真机验证**，并要求真机验收时把 freeform、多显示器、厂商 ROM 差异纳入清单。
6. **新增能力必须同步文档**：若落地第 4 节的第 2 步，`mobile_device_launch_app` 的语义（前台拉起）与新命令的语义（可指定显示/窗口模式）必须分开描述，不能混为一谈。
