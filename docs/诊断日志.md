# 诊断日志

设置里的「诊断日志」用于把设备上出现的问题带出来。它默认**关闭**，只在用户显式打开后
才开始记录，并且可以随时导出、分享或清空。

同一个页面下方还有一个**不会离开设备**的「运行日志」（Harness 访客进程输出尾部）：
它与诊断日志是两样东西，边界见下文《界面上的「运行日志」不是诊断日志》。

## 与审计日志的区别

| | 审计日志 `PrivateAuditLog` | 诊断日志 `DiagnosticLog` |
| --- | --- | --- |
| 用途 | 安全事件留痕 | 排障时间线 |
| 开关 | 不可关闭 | 用户开关，默认关闭 |
| 保留 | 固定 90 天 | 1–30 天（默认 3 天），可调 |
| 导出 | 不导出 | 可导出并分享 |
| 位置 | `noBackupFilesDir/audit/` | `noBackupFilesDir/diagnostics/` |

两者共享同一条底线：**只写受控枚举与受控键值**。

## 记录了什么

时间线覆盖排障最需要的几段：

| 事件 | 触发点 | 典型字段 |
| --- | --- | --- |
| `APP_START` | 插件加载完成 | `result` `active` `enabled` |
| `APP_DESTROY` | 插件销毁（含划掉最近任务） | `result` `active` |
| `RUNTIME_PHASE` | 运行时阶段变化（含失败码） | `phase` `reason` `code` |
| `HARNESS_START` / `HARNESS_STOP` | 启动（成功与失败都记）、停止 Harness | `result` `phase` `code` |
| `DEVICE_BRIDGE` | 设备桥创建 / 复用 / 失败 | `result` `code` |
| `KEEP_ALIVE` | 前台服务启停 | `reason` `active` `running` `enabled` |
| `RECOVERY` | 回收残留 Harness 进程 | `reason` `count` |
| `LOG_SETTINGS` / `LOG_EXPORT` | 日志自身的设置变化与导出 | `enabled` `days` `files` `bytes` |
| `SELF_CHECK` | 运行时自检与权限修复（见下节） | `result` `code` `count` |

一行形如：

```
2026-09-12T10:20:30Z|WARN|RECOVERY|reason=reaped_pid_file|count=1
```

### 运行器落地状态（`RUNTIME_PHASE|phase=launcher`）

每次启动前都要把运行时要用的 loader 落到运行时根里，并确认它**真的能被执行**——不只是字节
一致、权限位正确（0.2.4 的真机教训：`mode=0700`、`access(X_OK)` 通过、SELinux 也 `granted`，
应用却依然执行不了自己数据目录里的常规文件，PRoot 只会报
`execve("/usr/bin/env"): Permission denied`，界面只显示「PRoot 无法加载 Ubuntu 程序。」）。
因此启动时按三种落地形态**逐个实测**，第一个能起来的胜出：

| 形态（同时是 `reason` 取值） | 落地位置 |
| --- | --- |
| `loader_root_copy` | 运行时根内的实体拷贝 `root/.dsh-mobile/dsh-runner/loader` |
| `loader_symlink` | 运行时根内指向 APK `nativeLibraryDir` 的符号链接（exec 目标落在 `apk_data_file` 上） |
| `loader_private` | 应用私有目录里的那份（根外，只救未受限启动） |

胜出形态记进 `SharedPreferences(runtime_loader_form)`，下次优先试它（否则每次启动都要在两种形态
之间来回改写文件，还会连带清掉执行位巡检标记）。这一步的结果写一条 `RUNTIME_PHASE`，字段固定为
`phase=launcher` 加 `result`、`code`、`reason`：

```
2026-10-03T18:29:36Z|INFO|RUNTIME_PHASE|phase=launcher|result=ok|code=RUNNER_OK|reason=loader_symlink
```

`result` 只有在**实测真的起来了**（`exec probe` 返回 `started,…`）时才是 `ok`；三种形态全不行时
不写 `ok`，而是以 `RUNNER_PREPARE_FAILED` 直接让启动失败，消息里按尝试顺序带上形态与原因。
`code` 取值：`RUNNER_OK` / `RUNNER_MISSING` / `RUNNER_NOT_REGULAR` / `RUNNER_EMPTY` /
`RUNNER_NOT_EXECUTABLE`（缺属主执行位）/ `RUNNER_EXEC_DENIED`（同权限位无关，执行仍被拒绝）。

- **`reason=loader_private` 只代表「未受限启动能用」**：受限（`workspace-write`）进程只认
  Landlock 授权树（运行时根）内的 loader，回退的那份在根外，沙箱内命令与沙箱内 PTY 仍会失败。
  见到这一行请把日志反馈回来。
- 权限位、`access(X_OK)`、属性有无与探测结果属于自由文本，**不进诊断日志**；它们只出现在
  `adb logcat -s dsh-runtime` 的 `loader state: code=…,reason=…,probe=…,detail=…` 一行里
  （`probe` 形如 `started,exit=0`、`started,timeout=true`、`failed,detail=Cannot run program …: error=13, Permission denied`，
  `detail` 形如 `regular=true,size=1632,mode=0700,execAccess=true,stamped=true`）。

### 访客执行位巡检（`RUNTIME_PHASE|phase=exec_repair`）

真机回归的第二层成因：荣耀等 ROM 的 SELinux 不允许应用创建符号链接，rootfs 解压器会把
`/lib/ld-linux-aarch64.so.1` 这类链接降级成「复制目标内容」，而复制时用的 `File.setExecutable`
在这些机器上**静默失败**。现在降级复制统一改用 `Os.chmod` 按源文件真实权限位落位（失败写
logcat `rootfs copy chmod failed:`），每个运行时根另做**一次**有界执行位巡检，结果写一条 `RUNTIME_PHASE`：

```
2026-10-03T18:05:12Z|WARN|RUNTIME_PHASE|phase=exec_repair|result=ok|code=EXEC_BIT_REPAIRED|reason=scan_completed
```

| `code` | 含义 |
| --- | --- |
| `EXEC_BIT_REPAIRED` | 扫到「看起来可执行却缺属主执行位」的文件并补上了执行位（解压器降级路径的病根） |
| `EXEC_BIT_INTACT` | 没扫到需要修的文件（正常路径） |

| `reason` | 含义 |
| --- | --- |
| `scan_completed` | 整个运行时根扫完了（只有扫完才写标记，之后不再重复扫） |
| `scan_stopped` | 触到文件数/耗时上限或被取消：**没有**写标记，下次启动继续扫 |

- 只加不减：仅当文件「缺属主执行位」且文件头是 ELF（`\x7fELF`）或 `#!` 时才补属主执行位，其它文件一律不碰。
- 已经扫过的根不再重复扫（logcat 里是 `exec repair: skipped,reason=marker`），但**执行探测照样进行**。
- 真机证据表明这层巡检**不是** 0.2.4 那轮启动失败的原因（关键路径 `execAccess` 全为 `true`、
  解释器实体 `0755`，失败一字未变），保留为加固：`File.setExecutable` 静默失败已复现。
- 细节同样只在 logcat：每次启动按关键路径打 `guest file: path=…,kind=file|symlink|directory|missing,target=…,size=…,mode=0755,execAccess=true`
  （`lib/ld-linux-aarch64.so.1`、`usr/lib/ld-linux-aarch64.so.1`、`usr/lib/aarch64-linux-gnu/ld-linux-aarch64.so.1`、
  `usr/bin/env`、`usr/bin/bash`、`usr/bin/sh`、`bin/sh`、`usr/local/bin/node`、`opt/node/bin/node` 各一行）、
  `exec repair: scanned=…,repaired=…,failed=…,elapsedMs=…,completed=…`（跳过时为 `exec repair: skipped,reason=marker`），
  以及**每次启动无条件**实测的一条
  `exec probe: name=loader,path=…,result=started,exit=N`（能起 = 这个路径真的可执行）或
  `result=failed,detail=Cannot run program …: error=13, Permission denied`（系统策略层面的拒绝）。
  这三行是「权限位问题」与「系统策略问题」的分界证据。

### 移动端沙箱运行器（`phase=sandbox_runner`）

`workspace-write` 在移动端走的不是上游默认档：App 把 `nativeLibraryDir`（`PROOT_LOADER` 的真实路径）
绑到访客 `/.dsh-native`，并用 `assets/support/sandbox-runner.sh`
（访客路径 `/root/.dsh-mobile/sandbox-runner.sh`）把上游给的 bwrap 形态档参数翻译成 `landlock-run`
的授权参数。链接方式写在启动器补丁里（`launcher-providers.patch.json`）：

```json
{"id":"sandbox-local","config":{"runnerCommand":["/bin/sh","/root/.dsh-mobile/sandbox-runner.sh"],
 "runnerFailureSignatures":["dsh-sandbox-runner: "]}}
```

- 运行器失败时**始终**以 `125` 退出并在 stderr 打印 `dsh-sandbox-runner: <原因>`；上游按
  `runnerFailureSignatures` 把这种情况判成「运行器没跑起来」，而不是「用户的命令被权限拒绝」。
  两者在界面上的结论不同，日志里也就能分开：`sandbox_exec=EXEC_LAUNCHER_FAILED` 之前的输出里
  带签名行 ⇒ 是运行器自己拒绝执行（参数不认识、loader 目录不在、启动器找不到），
  没有签名行却带 `Permission denied` ⇒ 才是内核/LSM 层面的拒绝。
- 运行器只认上游会生成的那几个档参数（`--ro-bind` / `--bind` / `--tmpfs` / `--dev` / `--proc` /
  `--unshare-pid` / `--die-with-parent`），其余一律失败关闭 —— 上游新增档参数时应当**在这里补翻译**，
  而不是让命令悄悄跑在没有授权的位置。
- 脚本或绑定准备失败时写一条 `HARNESS_START|result=failed|code=SANDBOX_RUNNER_PREPARE_FAILED`
  （`RuntimeSandboxRunner.prepare` 抛出的 `RuntimeFailure`），启动直接失败，不进入探测。

### 启动失败也必须留下痕迹

只记成功是不够的：用户导出日志后若只看到 `HARNESS_START|result=ok`，
「dsh 为什么没起来」就无从复盘。因此**每一条把运行时阶段置为 ERROR 的启动路径**
（前置校验、Node/dsh 自检、端口占用、启动器装配、拉起进程、等待就绪、等待被中断、
访客进程自行退出……）都会写一条：

```
2026-09-15T10:20:30Z|ERROR|HARNESS_START|result=failed|code=HARNESS_START_TIMEOUT
```

- 记录只有 `result=failed` 与 `code`（受控错误码，取值来源见上文《一个必须写清的边界》）；
  运行时未安装、rootfs 校验不过这类**不改变阶段**的前置失败同样会被记下来。
- 写入集中在 `RuntimeSupervisor` 的启动失败统一出口（`failStart`）：新增失败路径只会走
  同一个出口，不会再出现「某个分支忘了记录」。记录内容由纯逻辑
  `HarnessStartFailurePolicy` 决定，并由它的单测锁定字段与事件。
- 访客输出、路径、端口、命令与凭据一律不写：失败原因只以受控错误码的形式出现。
- 分层：运行时层（`failStart`）覆盖面最广，凡把阶段置为 ERROR 的路径都在这里；
  `MobileRuntimePlugin` 的启动分支另有一条同样字段的补记，用来覆盖**运行时层之前**就失败的
  路径（`RUNTIME_BUSY` / `RUNTIME_CLOSED`、插件自愈等）。因此插件发起的失败可能看到两行
  相同的 `HARNESS_START|result=failed`：它们来自两层，不是重复故障。
  用户主动取消在运行时层不算失败（走取消分支，不记），插件层仍会如实写下一个
  `code=HARNESS_START_CANCELLED` 的 `failed` 行。

## 不记录什么

**绝不写入**：URL、端口、模型 API Key、Harness 临时 Basic Auth 密码、设备桥 token、
终端输入输出、文件路径、进程号、会话标识、异常消息文本、设备标识或账号信息。

保证来自三层，缺一不可：

1. **事件与级别是固定枚举**，不接受自由文本。
2. **字段名白名单**：只有 `phase` `code` `result` `reason` `enabled` `days` `files`
   `bytes` `count` `residual` `installed` `running` `permission` `connected` `active`
   `version` `sdk` `abi` 可以出现；`password` `token` `path` `api_key` 之类一律丢弃。
3. **字段值按类型校验**：布尔字段只接受 `true`/`false`；计数字段只接受 1–12 位数字；
   `code` 只接受大写错误码；`result`/`permission` 只接受封闭集合；`phase`/`reason`/
   `version`/`abi` 只接受小写 token。

非法字段被**丢弃**而不是让整行失败：事件本身比上下文更值得保留，且任何情况下都不会
写出不受控内容。

### 一个必须写清的边界

全大写且只含 `A-Z0-9_` 的字符串在**形态上**与错误码无法区分 —— `SECRETTOKEN` 与
`HARNESS_START_TIMEOUT` 同形。因此 `code` 字段的真实保证不是字符集，而是**取值来源受控**：
它只接受 `RuntimeFailure.code` 与状态快照里的 `errorCode`，两者都是固定的内部枚举，
永远不来自用户输入、WebView 或任何外部数据。字符集规则的作用是拦住小写、混合大小写、
含空格/引号/斜杠等自由文本形态。

## 界面上的「运行日志」不是诊断日志

设置 → 诊断与日志里有**两样不同的东西**，不要把它们的隐私边界混为一谈：

|  | 诊断日志（可查看、可导出） | 运行日志（只在界面） |
| --- | --- | --- |
| 内容 | 受控枚举 + 计数 | Harness 访客进程的 stdout/stderr 尾部（窗口 8 / 64 / 256 KB） |
| 是否含用户数据 | **绝不包含** | **可能包含会话内容**（工具参数、报错栈、代码片段） |
| 存放 | `noBackupFilesDir/diagnostics/`，按保留期删除 | 只存在于运行时的输出缓冲区（内存） |
| 去向 | 应用内查看最近一段；导出并分享全部文件 | 只在设备上的设置页里展示，可手动复制 |
| 进导出吗 | 它就是导出内容 | **不进导出**，也不落盘、不新增诊断事件或字段 |

也就是说：诊断日志的承诺（不含终端内容或用户数据）**不因运行日志而放宽**，两者互不影响 ——
关掉诊断日志不会让运行日志消失，导出诊断日志也永远带不走它。

## 应用内查看与判读

两个折叠区块都支持直接在应用内阅读，不必先导出文件：

- **诊断日志（最近 64 KB / 256 KB）**：走 `readDiagnosticLog`，读的是**尾部窗口**，
  只读、不落盘、不产生导出文件。被截断时界面明说「这里是最近一段，导出可获取全部内容」。
  正文与导出同源，因此仍然只有受控字段（窗口由原生侧夹到 1 KB..256 KB）。
- **运行日志（最近 8 / 64 / 256 KB）**：窗口由用户选择。缓冲区按**最大档**分配
  （`ProcessOutputTail` 的 256 KB），读取时再按 UTF-8 边界截取尾部 —— 只有先留住内容，
  事后才可能放大查看。原生侧把请求收敛到这三档（`clampHarnessTailBytes`），
  前端再用 `HARNESS_LOG_WINDOW_OPTIONS` 校验回传的 `maxBytes`，两边都只认同一组取值。

两者共用同一套阅读器（`LogText`）：关键字过滤（只显示匹配行，并给出 `匹配 N / M 行`）、
按级别着色、一键复制。渲染上限 2000 行，超出时只渲染**最近**的部分并在界面上写明省略了多少行 ——
窗口最大 256 KB，整段铺进 DOM 会让设置页明显变卡；过滤与判读仍在完整文本上执行。

### 判读提示

日志原文对用户几乎不可读：`Cannot read properties of undefined (reading 'prepare')` 看不出是
插件目录里多了一份运行时副本，`HARNESS_STOP_TIMEOUT` 还会盖住真正的启动失败原因。因此阅读器
在命中**已确诊签名**时给出结论与下一步（`src/logInsights.ts`）：

- 只匹配已经确诊、并且写进 `docs/项目状态.md` 的签名，不做自由猜测；
- 措辞一律是「通常是」「若同时看到」，不写成绝对判断；
- 命中不到就不显示任何东西 —— 宁可不说，也不给编造的结论。

判读针对**完整文本**而不是过滤后的结果：用户筛 `error` 时，结论仍然基于整段日志。

### 为什么需要它

工具调用失败时，界面只报一句**不带栈信息**的报错，排查无法进行；唯一能定位原因的线索，
是 dsh 自己打在 stdout/stderr 上的完整报错（Node.js 异常栈、插件加载失败原因等）。
为了既拿到这条线索、又不把它带出设备，读取入口做了三条限制：

1. **按需读取**：只有用户在设置页展开折叠区块（或切换窗口）时才读一次，进入设置页不读；
2. **只读有界**：原生侧最多回传所选窗口的字节数（默认 8 KB，可选 64 / 256 KB），
   `HarnessOutputTail` 按 UTF-8 字符边界截断，不会产生半个汉字；前端再校验
   `available`/`text`/`maxBytes` 的类型、长度上限与窗口档位，非法载荷直接拒绝；
3. **只在界面**：文本按纯文本渲染（绝不解析为 HTML），不写入诊断日志、不落盘、不随导出离开设备。

运行时不持有 Harness 输出时如实返回 `available = false`，界面显示「当前没有可读取的运行日志」
并隐藏复制按钮，不猜造任何内容。运行日志的读取是只读接口，不改变诊断日志的开关、字段或保留策略。

## 运行时自检（`SELF_CHECK`）

「运行时自检」与「修复运行时权限」各写一条 `SELF_CHECK`，字段只有受控键：

```
2026-09-16T10:20:30Z|ERROR|SELF_CHECK|result=failed|code=PTY_EXIT_EARLY|count=2
2026-09-16T10:21:02Z|INFO|SELF_CHECK|result=ok|count=0
2026-09-16T10:22:10Z|WARN|SELF_CHECK|result=denied|code=SELF_CHECK_FAILED|count=0
```

- `result=ok`：自检跑完且没有 `fail` 项（`warn` / `skipped` 不算失败，但会在界面上单独显示）；
- `result=failed`：`code` 是**按契约顺序**的第一个失败码，`count` 是失败项数；
- `result=denied`：自检本身没跑成（脚本准备失败、载荷不可信、进程失败），与「检查项确实失败」严格区分；
- 修复动作只记 `count` = 实际改动数（补执行位与补建附件目录的次数）。

自检结果里**只有封闭枚举与计数**：检查项 id、状态、受控错误码与可用字节数。路径、原始报错文本、
PTY 输出一律不过桥 —— 这一点由 `RuntimeSelfCheckPolicy` 的白名单与 `RuntimeSelfCheckPolicyTest` 锁定，
访客脚本自身也只输出一行 JSON。

## 怎么读一份导出的日志（判读口径）

日志是**状态流水**，不是错误清单。按下面四步看，不必逐行读：

1. **先看头部**：应用版本、Android SDK、ABI、保留期与时间范围决定了这份日志能说明什么。
   比当前版本更早的日志不能用来说明新版修了什么。
2. **只看 `WARN` / `ERROR`（以及任何 `result=failed`）**：`INFO` 是正常路径的状态流水。
3. **按事件名分组看趋势**：同一事件连续出现几次、间隔多久，比单行更说明问题。
4. **判据是「错误之后有没有恢复」**：`ERROR` 之后若出现 `HARNESS_START|result=ok` 或
   `RUNTIME_PHASE|phase=running`，说明已经自愈；一直卡在同一个错误上才是真故障。

| 现象 | 怎么判 |
| --- | --- |
| `SELF_CHECK result=failed code=EXEC_LAUNCHER_FAILED` | 沙箱启动器检查项失败，同一份日志里的 `sandbox_probe` / `sandbox_exec` / `pty_sandbox` 会被跳过；随后出现 `phase=running` 说明只是一次性故障 |
| `SELF_CHECK result=failed code=EXEC_LAUNCHER_DENIED` | 受限执行被内核拒绝（`Permission denied`）。0.2.3 及更早版本的真机就是这个原因：`PROOT_LOADER` 指向的 loader 落在 Landlock 授权根之外；0.2.4 起 loader 以实体文件落进运行时根内的 `root/.dsh-mobile/dsh-runner/loader`，升级后若仍见这一行，请把日志反馈回来 |
| 同时出现 `sandbox_exec=EXEC_LAUNCHER_DENIED` 与 `pty_sandbox=PTY_EXIT_EARLY` | 两条是同一个成因（沙箱内命令与沙箱内 PTY 都跑不起来），按上一条处理，不需要分别排查 |
| `SELF_CHECK` 里只有 `sandbox_probe=ok` | 探测只建规则集、不执行程序，**不能**当成沙箱内命令可用的证据；判据看 `sandbox_exec` 与 `pty_sandbox` |
| `RECOVERY reason=unclean_exit` | 上一次进程没走正常退出（被系统杀死、强制停止，或**安装了新 APK**），如实记录，不是本次故障 |
| `RUNTIME_SNAPSHOT reason=auto result=created` | 安装/升级前的自动备份成功，`count` 是当前保留份数 |
| `APP_DESTROY result=failed` | 插件销毁收尾有一步没干净完成；这一行定位不到具体步骤，要结合紧随其后的启动事件看 |
| 连续多条 `HARNESS_START result=failed code=RUNTIME_CLOSED` | 旧句柄已失效（旧实例收尾把运行时关掉了，或控制器早已 shutdown）。0.2.2 正式版之前的构建会出现；当前版本已修，界面也会明确提示「需要重新连接」 |
| `KEEP_ALIVE` 持续 `active=false enabled=false` | 后台保持没开或前台服务没起来；`permission` 反映通知权限，`running` 反映 Harness 是否在跑 |

`APP_DESTROY|result=failed` 与紧随其后的 `RUNTIME_CLOSED` 曾同时出现在真机 0.2.2 预览版的日志里，
根因与修复见 `docs/后台保持与恢复.md` 的《什么时候才真正释放运行时》。

## 定时删除
用户可设 1–30 天（默认 3 天）。删除时机：

- 每次写入前检查，若当天还没清理过就执行一次完整扫描（与审计日志同样的「每天一次」策略）；
- 删除「超出保留期」的文件，以及「目录总量超过 4 MB」时从最旧开始删除的文件；
- 单个日志文件上限 512 KB，达到后当天停止追加，避免单日刷爆存储。

本应用不引入 WorkManager 等后台调度依赖：清理发生在**应用或前台服务有活动时**。
这不会造成日志无限增长 —— 没有活动就没有新日志写入。

## 导出

「导出并分享」会把全部日志合并成一个文本文件，再由系统分享面板交给用户选择去向
（微信、邮件、文件管理器等）。文件头只包含：

```
# 应用版本 / Android SDK / ABI / 保留策略 / 内容说明
```

不含设备标识、账号、URL、路径或凭据。**也不含界面上的运行日志**（访客进程输出）与终端内容：
两者都不在诊断日志里，自然也不会被导出带走。

实现细节：日志本体在 `noBackupFilesDir`（不参与备份，也不可被 FileProvider 分享）；
导出时复制到 `cacheDir/diagnostics/`，通过只暴露该子目录的 `FileProvider`
（`${applicationId}.diagnostics`）以 `FLAG_GRANT_READ_URI_PERMISSION` 临时授权。
分享结束后导出文件仍在缓存目录，会被系统按需回收，也可用「清空日志」立即删除。

## 关闭开关时会发生什么

关闭只停止**新的写入**，不会删除已有文件 —— 用户可能先关掉再导出。需要立即清除请用
「清空日志」。已有文件仍受保留策略约束，到期会被自动删除。
