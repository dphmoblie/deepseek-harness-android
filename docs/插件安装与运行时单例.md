# 插件安装与运行时单例

本文说明三件事：为什么插件目录里出现**第二份** `@deepseek-ai/*` 真实副本会让**所有**工具调用失败；
安装插件时怎样保证不再留下这种副本；设备上已经装坏的插件怎样在不重新下载的前提下恢复。

相关代码：`android/app/src/main/assets/support/plugin-manager.cjs`（去重与修复）、
`android/app/src/main/java/io/deepseekharness/mobile/runtime/RuntimePluginManager.kt`（调用与受控校验）、
`android/app/src/main/java/io/deepseekharness/mobile/runtime/MobileRuntimeController.kt`（触发时机）。

## 一、Symbol 身份：同一份物理副本才行

- `@deepseek-ai/dsh-tools` 导出 `TOOL_RUNTIME_SCHEDULER = Symbol('@deepseek-ai/dsh-tools.scheduler')`。
  `Symbol()` 每次求值都造一个新身份，**字符串相同不代表 Symbol 相等**。
- `ToolRuntime` 用这个 Symbol 作为 key，把工具调度器挂进 cordis 注册表；`dsh-agent-loop` 再用
  `ctx.tools[TOOL_RUNTIME_SCHEDULER].prepare(call.exec)` 取回来派发工具调用。
- 树里存在两份物理 `dsh-tools` 时，注册用的是 A 副本的 Symbol，取回用的是 B 副本的 Symbol，
  两者不相等 ⇒ `ctx.tools[symbol]` 是 `undefined` ⇒ **每一次**工具调用都在 `.prepare` 上抛
  `Cannot read properties of undefined (reading 'prepare')`。对话与模型输出不受影响，所以症状是
  「聊天正常、工具全挂」。

受这条约束的不只 `dsh-tools`：凡是用 Symbol 在注册表里挂服务的 `@deepseek-ai/*` 包都必须是单例。
`scripts/check-runtime-dedupe.mjs` 列出了其中 10 个（dsh-tools、dsh-llm、dsh-attachment、
dsh-system-prompt、dsh-base、dsh-scope、dsh-session、dsh-agent、dsh-fs、dsh-jobs）。

**为什么 CI 看不见**：CI 的去重检查只扫 rootfs 自己的 `.pnpm` 虚拟store，而设备上那份额外副本是
插件管理器在运行时装出来的，产物检查覆盖不到 —— 只能在安装/修复这条路径上保证。

## 二、第二份副本是怎么进到设备上的

1. `npmInstall` 把插件**及其依赖以真实副本**装进
   `/root/.dsh-mobile/plugin-manager/versions/<事务 id>/node_modules/`
   （`npm install <插件> --ignore-scripts --legacy-peer-deps --omit=dev ...`）。
2. dsh 插件普遍依赖 `@deepseek-ai/dsh-base` / `@deepseek-ai/dsh-agent-loop`，而这两个包自己又把
   `@deepseek-ai/dsh-tools` 声明为依赖。`--omit=dev` 不装 peer，但依赖照装 ⇒ 每装一个有功能的插件
   就多一份真实 `dsh-tools`。
3. 顶层副本（npm 的提升结果）过去会被「核心 SDK 一律改用运行时实例」的分支换掉，但**嵌套副本**
   （`--legacy-peer-deps` 下版本冲突时 npm 把副本嵌进 `node_modules/<包>/node_modules/`）从来没人处理，
   于是留在插件目录里被插件加载 —— 这就是设备上那份副本。
4. 另一条坏形态来自运行时升级：插件目录会被跨版本保留，而里面指向运行时包的**绝对链接**带着旧版本号
   与 peer 哈希，新根目录里已经不存在 ⇒ 悬空链接 ⇒ 插件加载直接失败。这类链接不能靠「重新安装插件」
   顺手解决（重装要重新下载、且用户可能没有网络）。

## 三、安装后去重（`npmInstall` 完成之后立即执行）

`reconcileRuntimePackages(stageModules, directory)` 的判定规则：

| staging 里的形态 | 动作 |
| --- | --- |
| `@deepseek-ai/*` 真实目录副本 | 删除后改建为指向**运行时那一份**的符号链接（junction） |
| `@deepseek-ai/*` 悬空链接或指向别处的链接 | 重新指向运行时那一份 |
| `@deepseek-ai/*` 已指向运行时那一份的链接 | 不动（幂等） |
| 名字在运行时解析不到 | 保持 npm 装好的真实副本（见第五节第 5 条） |
| 非 `@deepseek-ai/` 的名字 | 一律不动 |

- **「运行时那一份」按实际解析结果判定**：复用文件里已有的安装锚点
  （`opt/dsh/node_modules/@deepseek-ai/dsh/package.json` + `createRequire().resolve.paths()`）
  与 `resolvePackage(name)`，覆盖 pnpm 隔离布局；**绝不**从既有链接的字符串里反推版本号或 peer 哈希。
- **嵌套副本同样处理**：递归进入每个包目录内的 `node_modules`（深度上限 4 层、目录上限 256、
  单次处理上限 512 个作用域条目），`npm` 在 `--legacy-peer-deps` 下产生的嵌套副本因此也被消除。
- **版本不一致不再让整次更新失败**：以前顶层 `@deepseek-ai/*` 副本与运行时版本不同会报
  `PLUGIN_DEPENDENCY_UNSUPPORTED`。现在一律改为指向运行时实例，计数里保留 `versionMismatch` 供排查。
  理由：多一份副本必然让所有工具调用失败，而运行时那一份本来就是唯一可用的实例，
  插件层面的 dsh 引擎兼容性已由 `selectNewestCompatible` 校验过。运行时**没有**这个包名时，
  仍旧按原逻辑拒绝整次更新（受控错误码不变）。
- **失败语义**：单个包处理失败只计入计数，不抛异常、不打断整次安装。所有动作在 `--ignore-scripts`
  语义下安全：只做 readdir / lstat / realpath / rm / symlink，不执行任何脚本。

安全边界（三层，均使用文件里已有的 `within`）：

1. 处理范围本身（`node_modules`）的真实路径必须落在本次事务目录内，且整体仍在访客根目录内；
   `node_modules` 被换成指向别处的链接时整条跳过。
2. 每个被删除或改建的条目，其**真实路径**必须落在本次处理的 `node_modules` 内 —— 任何一层祖先链接
   都不允许把动作带出去。悬空链接无法 `realpath`，因此改为校验**它所在目录**的真实路径
   （`unlink` 只删除链接本身，不会跟随）。
3. 作用域目录（`@deepseek-ai`）与包目录本身是链接时一律不进入：无法判断链接目标是否与别的安装共享。

## 四、修复动作（`repair`）：已装坏的插件不重装即可恢复

- 入口：guest 侧 `manager.repair()`，CLI 操作为 `repair`（`node plugin-manager.cjs repair`）。
- 扫描范围：`root/.dsh-mobile/plugin-manager/versions/<事务 id>/node_modules`
  （目录名必须是 UUID 形态，最多扫 64 个版本目录），对每个版本目录跑与第三节完全相同的对齐规则，
  因此真实副本与悬空链接两种坏形态都能就地修好。
- 触发点（Kotlin）：`RuntimePluginManager.repairInstalledIfNeeded()` 在
  **Harness 启动前**（`MobileRuntimeController.startHarness`）与**读取插件列表时**
  （`managePlugins("list")`，且 Harness 与终端都没在跑时）各调用一次。
  同一运行时代次只做一次，指纹为 `runtimeId + 版本 + rootfs 摘要`（进程内记忆，App 重启后再做一次）；
  失败不推进指纹，下次调用会重试 —— 自愈失败不应让插件列表或 Harness 启动中断。
- 幂等：第二次调用 `linked = 0`，全部条目计入 `unchanged`；可无条件重复调用。
- 只做链接改写，不删除任何插件内容、不动运行时本体（运行时那一份永远是链接的**目标**）。

## 五、为什么只处理 `@deepseek-ai/` 作用域

- 只有这些包用 Symbol 在 cordis 注册表里挂服务，「第二份副本」才会造成工具调用全挂；
- 插件自己的第三方依赖（`zod`、`zustand` 等）保持 npm 装好的真实副本，重复不影响正确性，
  改动面越小越安全、出问题时越好回滚；
- 运行时提供的其他受保护包（`react`、`react-dom`、`cordis`）仍走原有 `protectedPackage` 分支，
  本次不改；`@deepseek-harness/dsh-mobile-shizuku` 虽是受保护包但不在该作用域内，同样保持原逻辑。

## 六、可观测

- 安装：更新结果里多一个 `runtimeDedupe` 字段 —— `scanned`（检查过的作用域条目数）、`linked`、
  `unchanged`、`versionMismatch`、`failed`、`refused`（越界拒绝数，是 `failed` 的子集）。
- 修复：返回 `versions`（实际处理的版本目录数）+ 上述同一组计数。
- 两者都只输出**计数**，不含路径、不含异常原文；仍走既有 JSON 输出协议（单行、220000 字节上限、
  `safeDetail` 过滤），未新增诊断事件 token，也未改动 `DiagnosticPolicy` / `DiagnosticEvent`。

## 七、未覆盖的边界

1. **插件把运行时包藏在非标准位置**：例如不在任何 `node_modules` 下的 vendored 目录、改过名的目录、
   被打包进 bundle 的压缩副本。扫描只认 `node_modules/<名>` 与 `node_modules/@scope/<名>`，
   这类副本不会被发现。
2. **插件源码用绝对路径直接 import**：如 `import '/opt/dsh/node_modules/@deepseek-ai/dsh-tools/lib/index.js'`
   或用绝对路径 `createRequire` 绕开解析。本动作只保证「目录里没有第二份真实副本」，管不住插件主动绕开。
3. **作用域目录本身是链接**（指向别处或悬空）：一律不进入（见第三节边界 3），这类畸形布局需要人工处理。
4. **超出上限的依赖树**：嵌套深度超过 4 层、或单次超过 512 个作用域条目时不继续处理（正常插件远达不到）。
5. **运行时锚点解析不到的名字**：保持 npm 装好的真实副本；顶层副本随后仍会被既有的
   `PLUGIN_DEPENDENCY_UNSUPPORTED` 分支拒绝整次更新。
6. **运行时自己就有两份同名副本**（rootfs 构建问题）：本动作不负责，由 CI 的
   `scripts/check-runtime-dedupe.mjs` 拦截。
7. **插件目录之外的链接**：例如 `opt/dsh/node_modules/<插件名>` 指向插件目录的链接，由运行时更新与
   数据保留策略负责，不在本动作范围。
8. `repair` 不是插件管理桥接操作：它不接受 WebView 传参，只由原生内部触发（桥接操作仍是
   `list` / `enable` / `child` / `update`）。

## 八、验证

- 脚本测试（`node --test scripts/*.test.mjs`，`scripts/plugin-manager.test.mjs`）覆盖：顶层与嵌套真实
  副本被替换为指向运行时实例的链接、插件第三方依赖不被改动、版本不一致时的处置、运行时缺失该包名时
  仍拒绝更新、修复动作对已安装目录生效且幂等、悬空链接被重新指向、越界链接（`node_modules` /
  作用域目录 / 包目录三种形态）一处都不动。
- 真机判定命令见 `docs/项目状态.md` 第三节：第 1 条应只剩符号链接、第 2 条应只有一个真实路径、
  第 4 条（`find ... -xtype l`）应为空。
