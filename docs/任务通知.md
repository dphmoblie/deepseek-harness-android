# 任务通知（登记册 §5.5 首选条目）设计口径

本文定义「任务通知」要做什么、**能知道什么**、以及刻意不做什么。它是 §5.5 里价值最高的一条，
并且按登记册要求与 §5.6-C（轮询合并）**一起设计**——后者已经改了前提，见第一节。

## 一、前提变化（5.6-C 落地带来的硬约束）

`5.6-C` 已让前端**真正停表**：页面进入后台时 `clearInterval`，不再有任何 WebView 计时器在跑状态轮询
（改动见 `src/App.tsx` 的后台轮询段与 `src/App.test.tsx` 的「后台状态轮询（5.6-C）」用例）。

**因此任务通知的状态来源必须在原生侧**，不能指望前端在后台继续喂状态。这是「C 须与 5.5 一起设计」
的实质含义，也是本文所有取舍的起点。

## 三、决定

### 3.1 独立通道，不复用保活通道

新建通道 `dsh_tasks`，`IMPORTANCE_DEFAULT`（可提醒、可由用户单独调低或关闭），
与 `harness_keep_alive`（`IMPORTANCE_LOW`、静默、常驻）**分开**。

理由：两者性质相反。保活通知必须常驻静默，任务通知的价值恰恰在于「离开应用后仍能得知」。
塞进同一个通道，用户就只能**同时**接受或**同时**关闭两者——这正是 Android 通道模型要避免的事。
分开之后，用户可以「关掉保活提示但保留任务提醒」，也可以反过来。

### 3.2 通知 id 与生命周期

本应用现在有三个前台/任务通知，**id 必须互不相同**（下表是核实后的事实）：

| id | 归属 | 性质 |
|---|---|---|
| `0x44534801` | `HarnessKeepAliveService` | 保活，常驻静默 |
| `0x44534802` | `OverlayBallService` | 悬浮球前台服务，常驻静默 |
| `0x44534803` | `TaskNotification`（操作/退出类：已停止、未能启动、安装完成、更新完成、导出完成、导入完成） | 可划掉，不常驻 |
| `0x44534804` | `TaskNotification`（任务完成类，见 3.7） | 可划掉，不常驻 |

- **为什么操作类与完成类要分成两个 id**：共用一条意味着「谁后发谁覆盖」。用户按了导出、
  紧接着对话完成一轮，导出完成那条就会被静默替换掉——而它描述的是**用户自己发起的操作**的
  结果，不该被系统事件吞掉。代价是同一天里最多同时存在两条任务通知，都在回到应用时一并清除。
- 修复记录：`0x44534802` 曾经被 `TaskNotification` 与 `OverlayBallService` **同时使用**，
  于是「回到应用清掉任务通知」会把悬浮球的常驻通知一起撤掉，悬浮球进前台又可能顶掉任务通知。
  改 id 是修复这类互相干扰的唯一正确做法（在同一个 id 上分先后是做不到的）。
- 用**独立 id**（与 `0x44534801` 不同），不 `setOngoing`：任务通知是**可被用户划掉**的。
- **不常驻**：没有进行中的任务时通知不存在。常驻的「任务通知」等于第二个保活通知，会把通道语义搞混。
- 用户打开应用即清除（`setAutoCancel(true)` + 进入前台时主动 `cancel`）：应用已经在前台时，
  通知没有存在价值。


### 3.3 能通知什么（本轮范围）

只通知**内容确定**的三类，全部来自原生侧可得的状态：

1. **运行时生命周期**：安装中 / 启动中 / 运行中 / 已停止（含停止原因，例如
   `RECOVERY|reason=harness-exited`） / **需要重新连接**（`reconnectRequired`，例如进程被系统强制停止后
   旧认证会话无法恢复——这一条按既有约束必须显示为「需要重新连接」，不能伪装成仍在运行）。
2. **用户主动发起的操作结果**：安装完成、更新完成、导出完成、导入完成。这类通知在应用转后台后
   仍然有意义（用户按了导出就去干别的了）。
3. **前台推送的「最后已知」会话标记**：应用在前台时，前端可通过桥把「当前有会话在运行」这类
   **布尔标记**推给原生缓存；应用转后台后，原生按这个缓存显示一条**明确标注为「最后已知」**的通知。
   **不做**实时进度、不做百分比（不知道就不显示，宁可少说）。

### 3.4 锁屏可见

需求原话是「在锁屏通知最好」，因此本轮把可见性显式提到 `VISIBILITY_PUBLIC`：

- **每条通知**都设 `setVisibility(NotificationCompat.VISIBILITY_PUBLIC)`（`TaskNotification.post` 里统一设置）。
- 渠道侧同时设 `lockscreenVisibility = VISIBILITY_PUBLIC`（`ensureChannel`）。

**为什么敢在锁屏上公开**：任务通知的文案**全部来自固定字符串资源**，不含地址、端口、凭据、
工作区路径、会话内容、用户输入的任何东西——「锁屏能看到」因此不额外泄露任何一比特信息，
而用户在锁屏上最需要知道的恰恰是「它完事了没有」。这条约束不是描述性的，而是可检查的：
`postTurnCompleted` 与 `post` 都只接受 `@StringRes` 与一个整数计数，**没有**接受任意文本的参数。

**已有设备上可能不生效（必须如实记录，不要以为改了就一定好）**：Android 在通道创建之后
**不允许改变锁屏可见性**，应用对已存在通道的该字段调用会被忽略。因此：

| 情形 | 期望结果 |
|---|---|
| 全新安装（应用数据被清除过） | 通道按新设置创建，锁屏上直接可见 |
| 已安装并升级（通道早已创建） | 渠道设置**可能仍是旧值**；此时靠通知自身的 `setVisibility` 兜底 |

选择**不改新通道 id**：新建通道会让所有存量用户重新看到一次「运行状态提醒」的通知权限提示，
还要再走一遍重要性设置——代价比「部分老用户要卸载重装才能拿到锁屏可见」更大。
两害相权取其轻，选保留现有通道（`dsh_tasks` 的 id 与渠道语义都未变）。

真机验收必须**分这两种情形**各验一次，否则无法判断是代码没生效还是通道设置没生效。

### 3.5 点击行为

点击打开应用并落到对应视图。**落点是 `KeepAliveEntryActivity` 这个透明转发入口**，
标志是 `FLAG_ACTIVITY_NEW_TASK or FLAG_ACTIVITY_SINGLE_TOP`（与保活通知一致）：

- 它已处理好「已认证则进 Harness 对话界面、否则回管理页」，并且刻意避开了 `singleTask` 的
  clear-top 会连带撤销一次性会话凭据的问题（见 `docs/ARCHITECTURE.md`）。
- 早先的实现直接指向 `MainActivity` 并带 `FLAG_ACTIVITY_CLEAR_TOP`。由于 `MainActivity` 是
  `singleTask`，这条路径会**把正在后台的 Harness 对话界面连同一次性凭据一起销毁**——
  用户点通知想看「任务完成得怎么样」，结果落回管理页、对话还丢了。这正是本轮要修的第二个缺陷。

**不**做「点通知直接执行动作」（例如点一下就停止运行时）：那是一个隔着锁屏就能触发的破坏性操作入口。


### 3.6 权限未授予时

Android 13+ 未授予 `POST_NOTIFICATIONS` 时：
- **不静默降级**：设置页要明确说明「通知未授权，离开应用后不会收到进展提醒」，并给出请求入口；
- 不得因为没有通知权限就改用别的常驻手段（例如偷偷起前台服务）来「补偿」。

### 3.7 「任务完成」通知（本轮新增，含访客侧契约）

用户需求是「当任务完成时，回到对话界面，避免用户不知道任务进度情况」。落地形态是
**一条说清「任务已完成」的可点击通知**，点击回到对话界面（3.5 的落点）。

**信号来源**：桌面外壳**拿不到**会话内部状态（见第二节），因此完成事件由**访客内的插件**
通过设备桥主动上报——已落地的是
`scripts/runtime-profile/plugins/dsh-mobile-shizuku/lib/turn-signal.js`：它订阅
`ctx.on('session/event')`，只在 `event.type === 'turn/end'` 时上报，跳过 `interrupted`/`forked`
这两种「事后补写或 fork seed」的收口，并按 `(会话摘要, turn 号)` 在内存里去重。
上报是 **best-effort**：`AbortSignal.timeout(2_000)`、不 await、不重试、失败静默。
**原生侧本轮只做收单点**，不做任何状态推断。

> **几点必须如实说明**（不是卖点，是边界）：
> 1. 这套依赖**访客侧插件被装上并生效**；插件不在（或用户没启用）时，原生侧收不到任何事件，
>    表现就是「任务完成没有通知」——这是降级而不是错误。
> 2. 也依赖**每一轮都真的产生 `turn/end`**。这一点**只能在上真机（或 CI 的端到端）时确认**：
>    本机能证明的只有原生收单点与策略的纯逻辑，证明不了 dsh 的会话事件流。
> 3. `reason` 目前**只发 `turn-end`**；契约里保留的 `turn-error` 还没有发送方
>    （见下表的说明：原生侧刻意不为它另编文案）。

> 登记册 §5 曾把「新增 guest→native 实时状态通道」列为本轮不做。这里要区分：
> 被否掉的是**持续的双向状态通道**（心跳、进度、百分比）；本轮加的是**单向上报的离散事件**——
> 只有一个命令、一个极小参数、限流后静默忽略、失败不影响 Harness。成本与风险都不在同一个量级。

**命令**：`notify-turn-complete`

| 项 | 值 |
|---|---|
| 方法/路径 | `POST /device-command`（与既有设备桥完全一致） |
| 鉴权 | `Authorization: Bearer <DSH_DEVICE_BRIDGE_TOKEN>`，`MessageDigest.isEqual` 比较；失败 401 `UNAUTHORIZED` |
| body | `{"command":"notify-turn-complete","param":"<极小的 JSON 字符串，可为空串>"}` |
| 真实请求（访客侧已落地的形态） | `{"command":"notify-turn-complete","param":"{\"session\":\"<16 位小写十六进制摘要>\",\"reason\":\"turn-end\"}"}`；拿不到合法会话标识或超长时 `param` 退化为 `""` |
| 未经 Shell | 它是**内建命令**：在 `DeviceCommand.fromName` 之前就被拦下，不创建设备 Shell 会话、不吃 60 秒超时（访客侧给的 2 秒超时因此足够） |
| 与既有命令面的关系 | 命令名加进同一张受控清单，但**不扩大**「模型可自主发起」的能力面：它只能触发一条固定文案的通知，不返回任何用户数据，也不读会话内容 |

**`param` 允许的字段**（只有这三个，多一个键整条请求作废）：

| 字段 | 类型 | 允许值 | 说明 |
|---|---|---|---|
| `session` | string | `^[0-9a-f]{16}$` | 会话标识的**哈希**，不是原始 id。可选 |
| `reason` | string | `turn-end` / `turn-error` | 可选 |
| `sessions` | int | `1..20` | 可选；「这一轮里完成了几件事」 |

- 长度上限 96 字符（`TurnCompletionPolicy.MAX_PARAM_CHARS`），超长在解析前就拒绝。
- **明确拒绝**：空对象 `{}`（说了话却什么都没说，更可能是协议实现错了）、任何非白名单键
  （会话正文、文件路径、凭据都可能被塞进这种额外字段）、原样 UUID（必须哈希）、任意自造的 `reason`。

**限流**（`TurnCompletionPolicy.State.claim`）：最小间隔 **1000ms**；命中即**静默忽略**。

- 另有每秒配额 `MAX_CALLS_PER_SECOND = 3` 与 `DropReason.LIMIT`，但**当前策略下这个分支不可达**：
  最小间隔恰好等于每秒窗口的长度（1000ms），任何一秒内最多只有一次能通过最小间隔。
  这是如实记录，不当成缺陷掩盖，也不删枚举值——它是给未来放宽最小间隔时留的语义位。
  单测里有一条用例专门记录这一行为（`最小间隔先于每秒配额生效`）。
- 跨越窗口的请求**不会被永久卡住**：限流窗口按 `elapsedRealtime` 计算，时钟回拨不会造成死锁
  （单测 `时钟回拨后不会把事件永久卡住`）。

**返回契约**：HTTP 200 + 既有的 `{"ok","exitCode","text","truncated","errorCode"}` 形状，
`text` 是 `{"accepted":<bool>,"queued":<bool>}`。

| `errorCode` | `ok` | 含义 | 访客侧应当 |
|---|---|---|---|
| `null` | true | 已受理（`accepted=true`） | 什么都不做 |
| `null` | true | **被限流静默忽略**（`accepted=false`） | 什么都不做（**不要重试**） |
| `TURN_NOTIFY_INVALID` | false | `param` 不合法（长度/JSON/键/取值） | 修实现，不要重试 |
| `TURN_NOTIFY_UNAVAILABLE` | false | 原生侧拿不到应用上下文（只在进程启动极早期可能） | 什么都不做 |

`queued=true` 表示「这次事件被收下了、稍后会响」，**不是**「此刻已经发出通知」：合并窗口意味着
真正的投递发生在最多 10 秒之后。

**审计**（新增 `AuditEvent.TURN_NOTIFY`，detail 只记受控码，**从不记请求原文**）：
`TURN_NOTIFY_INVALID` / `TURN_NOTIFY_TOO_SOON` / `TURN_NOTIFY_RATE_LIMITED` /
`TURN_NOTIFY_UNAVAILABLE`（以上 `FAILED`/`DENIED`）/ `TURN_NOTIFY_QUEUED` /
`TURN_NOTIFY_SUPPRESSED` / `TURN_NOTIFY_COALESCED`（`SUCCEEDED`）。

**节流与合并**（`TurnCompletionNotificationPolicy`，纯 JVM 可单测）：

| 参数 | 值 | 作用 |
|---|---|---|
| `MIN_COALESCE_MS` | 1500 | 静默期：首个事件之后等这么久，把同一轮里的多次完成合并成一条 |
| `MAX_COALESCE_WINDOW_MS` | 10000 | 自首个事件起的**硬上限**，避免持续刷事件导致通知永不发出 |
| `MIN_INTERVAL_MS` | 6000 | 两次通知之间的最小间隔；**触及下限时顺延，不丢弃** |
| `MAX_BATCH` | 20 | 一条通知里显示的最大条数（再多也只显示 20） |

**前台抑制**：应用在前台时**不发**通知（`AppForeground.isForeground()`）——用户正看着屏幕，
通知没有存在价值；但进程内计数**照记**（见下），这样外壳能据此提示「任务已完成」。

**进程内可读状态**（外壳用既有 5 秒轮询读取，**不新增第二条通道**）：

| 符号 | 类型 | 语义 |
|---|---|---|
| `TaskNotification.lastTurnCompletedAtMillis` | `@Volatile var Long` | 最近一次**成功受理**的完成事件的墙钟时间；0 表示从未受理过 |
| `TaskNotification.turnCompletionSequence` | `@Volatile var Long`（`private set`） | 单调递增的受理计数；每次成功受理 +1 |

- 二者**只在成功受理时**推进：参数不合法、拿不到上下文、被限流**都不计入**——保持
  「通知确实被受理了」的语义一致，外壳不会因为限流期间的空转而反复弹提示。
- **不写盘、不跨进程、不跨重启**：进程被杀后归零是**预期行为**，不要在任何界面或文档里
  把它描述成持久状态。


## 四、验收（真机项）

- 通道独立性：单独关闭 `dsh_tasks` 不影响保活通知，反之亦然（系统设置里可分别看到两个通道）。
- 完成类通知：应用中触发导出 → 立即切到后台 → 应收到完成通知；点击回到**对话界面**
  （落点与 3.5 一致）。
- 「需要重新连接」：进程被系统强制停止后（可用 `adb shell am force-stop` 复现）再次打开应用，
  通知/界面都必须显示「需要重新连接」，**不得**显示为仍在运行。
- 应用在前台时：不应存在任务通知（已清除）。
- 权限未授予：设置页出现明确说明与请求入口；授权后无需重启应用即可生效。
- **点通知回到对话界面**（本轮新增判据）：在对话进行中切到后台，点任务通知 →
  必须回到**对话界面**，且**对话与一次性凭据都还在**（历史消息可见、能继续发消息）。
  若落回管理页或对话被清空，即为该缺陷复现。
- **通知 id 互不干扰**（本轮新增判据）：先让悬浮球前台服务发出常驻通知，再产生一条任务通知，
  然后回到应用（`MainActivity.onResume` 会清除任务通知）→ 悬浮球那条常驻通知**必须还在**。
  反向亦然（悬浮球服务重启不得顶掉任务通知）。
- **锁屏可见（两种安装情形各验一次）**：
  1. 清除应用数据（通道会按新设置重建）→ 锁屏状态下产生任务通知 → 锁屏上**应直接可见**完整文案；
  2. 不清除数据的升级安装 → 同样操作 → 结果可能不同（见 3.4 的说明）。两次结果都要如实记录，
     若第 2 种不可见，属于**已知平台限制**，不作为回归失败。
- **任务完成通知**（本轮新增判据）：
  1. 应用切到后台，让访客侧发一次 `notify-turn-complete`（`adb` 或调试面板触发）→
     应在 **1.5~10 秒内**收到一条「任务已完成」通知，点击回到对话界面；
  2. 1 秒内连发 3 次 → **只有一条**通知（限流+合并），且不出现任何错误提示；
  3. 应用**在前台**时发同样的请求 → **不出现**通知（但进程内计数应 +1）；
  4. 连续多轮完成（间隔 > 6 秒）→ 每条都能收到，不因限流而永久沉默。

## 五、刻意不做的事（与既有约束一致）

- **任务通知不是保活手段**：它不阻止、也不能阻止 Android 或厂商系统杀死进程；
  **不得**在界面或文档里宣称可以绝对防止进程被杀。进程一旦被强制停止，通知也可能随之消失，
  恢复路径是「重新连接」，不是「通知还在所以进程还活着」。
- 不伪造实时进度或百分比；拿不到的状态就不显示。
- 不新增 guest→native 的**实时状态通道**（本轮）：那需要改访客内 dsh 侧代码并与上游版本对齐，
  成本远高于本条的收益，等确有需求再单独评估。注意 3.7 的 `notify-turn-complete` **不属于**
  这一类：它是单向上报的离散事件（一个命令、一个极小参数、限流后静默忽略），不是持续通道。
- 不在通知上提供破坏性操作入口。
- 不把「任务通知」做成第二个常驻通知。
