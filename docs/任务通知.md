# 任务通知（登记册 §5.5 首选条目）设计口径

本文定义「任务通知」要做什么、**能知道什么**、以及刻意不做什么。它是 §5.5 里价值最高的一条，
并且按登记册要求与 §5.6-C（轮询合并）**一起设计**——后者已经改了前提，见第一节。

## 一、前提变化（5.6-C 落地带来的硬约束）

`5.6-C` 已让前端**真正停表**：页面进入后台时 `clearInterval`，不再有任何 WebView 计时器在跑状态轮询
（改动见 `src/App.tsx` 的后台轮询段与 `src/App.test.tsx` 的「后台状态轮询（5.6-C）」用例）。

**因此任务通知的状态来源必须在原生侧**，不能指望前端在后台继续喂状态。这是「C 须与 5.5 一起设计」
的实质含义，也是本文所有取舍的起点。

## 二、现状（按代码核实）

| 事实 | 位置 | 含义 |
|---|---|---|
| 保活前台服务已有自己的通知与通道 | `HarnessKeepAliveService.kt`：通道 `harness_keep_alive`（`:189`）、通知 id `0x44534801`（`:190`）、`IMPORTANCE_LOW` + `setShowBadge(false)` + `enableVibration(false)` + `setSound(null, null)`（`:173-186`）、通知本体 `setOngoing(true)` / `setSilent(true)` / `CATEGORY_SERVICE`（`:159-170`） | 它是**常驻且静默**的，用途是「让系统别太快回收」，不是为了提醒用户 |
| 悬浮球服务也有自己的通道 | `OverlayBallService.kt:602` 起 | 同上，独立通道 |
| 通知权限已可请求 | `src/platform/types.ts:415`（`requestNotificationPermission`），Kotlin 侧 Android 13+ 走 `POST_NOTIFICATIONS` | 权限链路已存在，不需要新建 |
| 运行时状态在原生侧可得 | `RuntimeStatus` / `RuntimeSupervisor`（phase、errorCode）、`KeepAliveState`（含 `foregroundServiceActive`、`reconnectRequired`、`lastPhase`） | 这是**唯一可靠**的状态来源：进程活着就能拿到，不依赖 WebView |
| 会话/Agent 内部状态**原生拿不到** | 会话数据在访客内 `/root/.dsh/sessions`（`RuntimePreservePolicy.kt:31-32`） | 原生要读到「Agent 正在思考 / 等待输入」需要新增 guest→native 通道，本轮**不做**（见第五节） |

## 三、决定

### 3.1 独立通道，不复用保活通道

新建通道 `dsh_tasks`，`IMPORTANCE_DEFAULT`（可提醒、可由用户单独调低或关闭），
与 `harness_keep_alive`（`IMPORTANCE_LOW`、静默、常驻）**分开**。

理由：两者性质相反。保活通知必须常驻静默，任务通知的价值恰恰在于「离开应用后仍能得知」。
塞进同一个通道，用户就只能**同时**接受或**同时**关闭两者——这正是 Android 通道模型要避免的事。
分开之后，用户可以「关掉保活提示但保留任务提醒」，也可以反过来。

### 3.2 通知 id 与生命周期

- 用**独立 id**（与 `0x44534801` 不同），不 `setOngoing`：任务通知是**可被用户划掉**的。
- **不常驻**：没有进行中的任务时通知不存在。常驻的「任务通知」等于第二个保活通知，会把通道语义搞混。
- 用户打开应用即清除（`setAutoCancel(true)` + 进入前台时主动 `cancel`）：应用已经在前台时，
  通知没有存在价值。

### 3.3 能通知什么（本轮范围）

只通知**内容确定**的三类，全部来自原生侧可得的状态：

1. **运行时生命周期**：安装中 / 启动中 / 运行中 / 已停止（含停止原因，例如
   `RECOVERY|reason=harness-exited`） / **需要重新连接**（`reconnectRequired`，例如进程被系统强制停止后
   旧认证会话无法恢复——这一条按既有约束必须显示为「需要重新连接」，不能伪装成仍在运行）。
2. **用户主动发起的操作结果**：安装完成、更新完成、导出完成、导入完成。这类通知在应用转后台后
   仍然有意义（用户按了导出就去干别的了）。
3. **前台推送的「最后已知」会话标记**：应用在前台时，前端可通过桥把「当前有会话在运行」这类
   **布尔标记**推给原生缓存；应用转后台后，原生按这个缓存显示一条**明确标注为「最后已知」**的通知。
   **不做**实时进度、不做百分比（不知道就不显示，宁可少说）。

### 3.4 点击行为

点击打开应用并落到对应视图（复用既有的「打开应用」`PendingIntent` 模式）。
**不**做「点通知直接执行动作」（例如点一下就停止运行时）：那是一个隔着锁屏就能触发的破坏性操作入口。

### 3.5 权限未授予时

Android 13+ 未授予 `POST_NOTIFICATIONS` 时：
- **不静默降级**：设置页要明确说明「通知未授权，离开应用后不会收到进展提醒」，并给出请求入口；
- 不得因为没有通知权限就改用别的常驻手段（例如偷偷起前台服务）来「补偿」。

## 四、验收（真机项）

- 通道独立性：单独关闭 `dsh_tasks` 不影响保活通知，反之亦然（系统设置里可分别看到两个通道）。
- 完成类通知：应用中触发导出 → 立即切到后台 → 应收到完成通知；点击回到应用。
- 「需要重新连接」：进程被系统强制停止后（可用 `adb shell am force-stop` 复现）再次打开应用，
  通知/界面都必须显示「需要重新连接」，**不得**显示为仍在运行。
- 应用在前台时：不应存在任务通知（已清除）。
- 权限未授予：设置页出现明确说明与请求入口；授权后无需重启应用即可生效。

## 五、刻意不做的事（与既有约束一致）

- **任务通知不是保活手段**：它不阻止、也不能阻止 Android 或厂商系统杀死进程；
  **不得**在界面或文档里宣称可以绝对防止进程被杀。进程一旦被强制停止，通知也可能随之消失，
  恢复路径是「重新连接」，不是「通知还在所以进程还活着」。
- 不伪造实时进度或百分比；拿不到的状态就不显示。
- 不新增 guest→native 的实时状态通道（本轮）：那需要改访客内 dsh 侧代码并与上游版本对齐，
  成本远高于本条的收益，等确有需求再单独评估。
- 不在通知上提供破坏性操作入口。
- 不把「任务通知」做成第二个常驻通知。

## 六、实现进展（按片落地，别把第一片当成做完）

**第一片已落地**（`9553bdd`），**只覆盖第三节第 1 类中的一种情形**：

| 内容 | 状态 |
|---|---|
| 通道 `dsh_tasks`（独立于保活通道、`IMPORTANCE_DEFAULT`、不常驻、可划掉、点击只回应用） | **已落地**（`TaskNotification.kt`） |
| 「运行中的 Harness **自行退出**」通知（按退出前阶段分岔「已停止 / 未能启动」） | **已落地**（`TaskNotificationPolicy.forHarnessExit` + `RuntimeSupervisor.onHarnessExited` 接线） |
| 未授予通知权限时静默不发、且不改用别的常驻手段「补偿」 | **已落地**（`areNotificationsEnabled()`） |
| 用户回到应用即清掉通知 | **已落地**（`MainActivity.onResume`） |
| 安装/更新**完成**通知（第三节第 2 类里最有价值的一种） | **已落地**（`TaskNotificationPolicy.forInstallCompleted` + `MobileRuntimeController.install` 接线；判定在安装**之前**取，否则装完就分不出「首次安装」与「更新」） |
| 工作区**导出/导入完成**通知（第三节第 2 类其余部分） | **已落地**（`postWorkspaceExported` / `postWorkspaceImported`，带**条目数**——那是操作返回的确定值，不是进度百分比；接线在 `MobileRuntimePlugin` 的两个桥方法里，放在 `audited(...)` **之外**，因此只有成功才发） |
| 前台推给原生的「最后已知」标记（第三节第 3 类） | **未做** |
| 「应用在前台时抑制通知」 | **已落地**（`AppForeground` 计数器 + `TaskNotification.shouldNotify()`；用计数器是因为有两个 Activity 且后者叠在前者之上，布尔标志会在关闭控制台时误判成「已切后台」。与「回到前台清除」合起来才成立：仅清除会让前台完成的操作先弹再消失，仅抑制会让后台发出的那条一直留着） |
| 「需要重新连接」通知（`reconnectRequired` 由假变真） | **刻意不做，理由已核实**：`reconnectRequired` 是在 `MobileRuntimeController.keepAliveSnapshot()` 这个**只读查询**里按需算出来的（`HarnessKeepAlivePolicy.requiresReconnect(...)`），在那里发通知等于**每次轮询都发一遍**——属于在读路径里塞副作用。要做对，得先在原生侧有**独立的状态监听**（前台服务里的低频检查或进程死亡回调），那是另一条独立的活。另外这个状态在**用户看着应用时**才有意义（界面已经按既有约束显示「需要重新连接」），而前台通知已被本节的抑制规则挡掉——收益因此很低 |

接线点选在 `onHarnessExited` 是有意的：它**只**在自行退出时走到——用户主动停止会先清空进程引用、
观察者直接返回，因此不会在用户刚按完「停止」时打扰他。

**仍然成立的根本约束**：任务通知不是保活手段，它不阻止也不能阻止 Android 或厂商系统杀死进程；
进程被强制停止后通知也可能随之消失，恢复路径是「重新连接」。
