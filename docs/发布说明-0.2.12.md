# 0.2.12 发布说明

本版把「目标应用副屏」从实验性开关做成一套**可配置能力**：新增独立设置页、取帧档位扩到十档、
自动跟随三策略与生命周期动作（启动 / 重启 / 重连）、AI 可直接在副屏里跑设备命令；同时修掉一处
「注入被取帧锁拖住、且报成功但画面不动」的输入缺陷，并补上无障碍规则的事件驱动执行器。
**副屏仍需要真机验收**：本页「未验证」一节列出的项目都没有在真机上复测过。

## 一、副屏独立设置页（新增）

- 新增页面 `src/components/VirtualScreenSettings.tsx`，把原本散在「Shizuku 与设备 Shell」页里的
  副屏配置收拢成一页：目标应用（复用应用选择器，运行中的目标自动预填）、屏幕方向（自动 / 竖屏 /
  横屏）、自适应规格开关与手填分辨率（宽高 200..4096、DPI 120..640，越界就地夹取并提示）、
  十档取帧节奏、自动跟随策略、启动 / 停止 / 重启，以及九行状态区。
- 设置与状态各自三态（读取中 / 可用 / 读不到并给出原因与重试）。读不到时明确写「这不代表副屏
  没有在运行」，不把「读不到」显示成「未运行」，也不把未知读数显示成 0。
- 入口从「Shizuku 与设备 Shell」页分离为独立设置项；原「打开系统副屏页面」保留为新页里的次级
  通路（那是预览与悬浮小窗页，不是设置页）。
- 新增五个桥方法：`getVirtualScreenSettings`、`setVirtualScreenSettings`、`startVirtualScreen`、
  `stopVirtualScreen`、`getVirtualScreenState`。浏览器端对五条一律如实拒绝，不假装成功。

## 二、取帧档位、显示器刷新率与自动跟随

- 取帧档位由六档扩到**十档**：省电 / 15 / 30 / 60 / 90 / 120 / 144 / 165 / 185 / 240 FPS。
  界面与文案明确写成「取帧档位」并注明「档位决定预览取帧节奏；虚拟屏实际刷新率以状态区的读数
  为准」，不把档位说成显示器刷新率。
- 创建虚拟显示时按档位调用 `setRequestedRefreshRate`，并**读回真实刷新率**写进状态
  （`displayRefreshRate`）；系统不接受请求时如实显示读回值或「未知」，不谎报高档位已生效。
- 自动跟随三策略：`off` / `pull_back`（把主屏最前台的目标拉回副屏）/ `promote`（把副屏里真正
  前台的应用提升为会话目标）。宿主健康循环按回显值决定是否周期性调用 `autoFollowTick`，该动作
  在设备 Shell 侧已实现（此前只有调用点、没有实现）。
- 生命周期动作补齐：`start` / `restart`（用留档的同一份规格重建显示与会话，并保住原会话编号）/
  `reconnect`（把调用方 binder 重新挂上，挂不上就抛异常）。
- 错误码细分：`TARGET_LEFT`（目标已离开副屏，重试没有用）、`STALE_FRAME`（画面还没就绪或已过期，
  原地等几百毫秒重试即可）、`SESSION_DEAD`（会话已结束）。空白帧仍照常返回，不并入 `STALE_FRAME`。
- 副屏状态增补「副屏当前前台应用 / Activity」，主屏与副屏各读一次，文本取不到时回未知。
- 非 ASCII 输入走剪贴板通道：`cmd clipboard set-primary-clip` 写入后**立刻读回核对**前 16 个字符，
  对不上就不认为通道可用，也不报告成功。

## 三、悬浮小窗与输入延迟

- 悬浮窗恢复拖动：窗口只显示画面（无工具栏、无档位行），但窗口本身可以拖动。为避免把副屏里的滚动、
  翻页当成在拖窗，判定改成**长按 ≥350 毫秒后再拖**（`LONG_PRESS_DRAG_MILLIS = 350L`，另有 8dp 静置
  容差）：350 毫秒之内的移动一律照常透传给副屏；一旦改判为拖窗，先给副屏补发一个 CANCEL（避免目标
  应用停在「按下」状态），之后按 8ms 节流更新位置并夹在屏幕范围内（左右不出屏、上不盖状态栏、
  下不盖导航栏）。
- 修「注入被取帧锁拖住」：取帧快照方法不再整个持有实例监视器，等待只锁帧对象本身，注入不再排在
  5–16ms 一次的预览取帧后面；硬件缓冲取用失败不再被静默吞掉，会记录异常类名到诊断字段。
- 修「报成功但画面不动」：离散手势不再退化成一次近似 `input swipe`，改为逐事件注入
  `motionevent`（按下 → 移动 → 抬起，末端点永不合并，过采样点合并或丢弃但按下/抬起永不丢）；
  **退出码 0 不再当作落地**，输出里出现拒绝字样即判未落地，失败补发 CANCEL 并抛出注入失败。
- 注入诊断字段新增 `injectionChannel` / `injectionMillis` / `injectionEvents` / `injectionMerged` /
  `injectionDropped` / `injectionError`，便于区分「注入成功」与「注入了但对方没接受」。

## 四、AI 直接操作副屏（新增工具）

- 新增工具 `mobile_virtual_screen_shell`：让 AI 在**当前副屏会话**里执行设备命令，命令里自动带上
  该副屏的显示编号（脚本前缀导出 `DISPLAY_ID`，可直接写 `input -d "$DISPLAY_ID" tap 622 880`、
  `am start --display "$DISPLAY_ID" -n 包名/Activity`）。
- 约束：脚本必填、非空、UTF-8 不超过 16 KiB、不含 NUL；`displayId` 选填，省略即用会话副屏，显式
  指定必须与会话一致，显式 0（主屏）与负数一律拒绝。错误码
  `DEVICE_COMMAND_INVALID` / `VIRTUAL_SCREEN_DISPLAY_INVALID` / `VIRTUAL_SCREEN_UNAVAILABLE` /
  `DEVICE_SHELL_DISABLED`。
- AI 工具面走的是设备命令桥（`DeviceBridgeServer`），不是 WebView 的插件方法，两者都已接上同名命令。

## 五、无障碍自动化执行器（引擎侧）

- 新增 `AutomationRuleExecutor.kt`：纯函数闸门（四层节流：事件通知间隔 → 动作最小间隔 → 规则冷却 →
  规则次数上限；节点指纹去重；连续失败三次停用该规则）+ 执行器，时间戳全部由外部注入，可 JVM 单测。
- `DeepSeekAccessibilityService` 的 `onAccessibilityEvent` 从空实现改为接线到执行器（事件类型与
  通知间隔沿用既有订阅），既有的一次性确认浮层与限流逻辑保持不变；执行前确认事件包名在白名单内，
  且默认不对应用自身执行动作。
- 配套桥命令、AI 工具面与设置页界面**本版未包含**，执行器目前只能由应用内事件触发。
- 顺带按用户要求**删除无障碍应用白名单的 16 项上限**：前端校验、应用选择器里的「最多 16 个」提示与
  「超过上限」警告整体去掉，界面只显示已选个数；原生侧（`AccessibilityAutomationPolicy` /
  `AccessibilityAutomationStore`）本就只校验包名格式、重复项与保留包名，两侧口径现在一致。

## 七、未验证与已知问题

- **本节列出的项目都没有在真机上复测过**：副屏能否按新设置启动、十档取帧与实际刷新率的真实读数、
  自适应规格与方向、自动跟随三策略的实际行为、启动 / 重启 / 重连、非 ASCII 输入与剪贴板通道回读、
  副屏前台应用 / Activity 的读数、AI 直接操作副屏的端到端效果、悬浮窗拖动的手感与边界、
  逐事件注入是否真的让画面变化、无障碍执行器的实际触发与节流。
- 逐事件注入的判据是「截图前后 SHA-256 必须不同，否则必须拿到注入失败」；两者都不出现即视为没修好。
- 本机虚拟屏实测只暴露 `fps=60.0` 一档，请求更高刷新率很可能被系统忽略（状态区会如实显示读回值）。
- 运行时残留目录的清理在真机上仍然失败：严格删除器与兜底删除器都返回 `ACCESS_DENIED`，界面会
  如实显示残留份数与体积，但清不掉（不影响会话与当前运行时）。
- 外壳「会话工作区」的会话列表在本机读不出来，界面显示「读不到会话列表」而不会假装空态。
- 副屏上目标应用跳转到另一个应用会落在哪个显示器，只在机制上分析过，未做实测。
- **真机反馈（0.2.11 上发现）**：无障碍应用白名单的应用选择器里输入 `gkd` 或 `GKD` 都搜不到「GKD」，
  用户最后是在完整列表里翻到的。本机已用单测钉住匹配规则——包名 `li.songe.gkd` 与标签「GKD」在
  `gkd` / `GKD` / `songe` 三种查询下都必须命中，且清单声明了 `QUERY_ALL_PACKAGES`、分页不按
  「是否可自动化」过滤，所以按规则侧应当能搜到；下一版需要在真机上确认：选择器列表里到底有没有
  这一行、它显示的标签与包名是什么、两个筛选开关（只看可自动化应用 / 隐藏系统组件）是不是被勾上了。
