# 0.2.13 发布说明

本版是 **Shizuku 集成修复版**：真机反馈「Shizuku 更新到新版之后无效了——版本对不上号、连不上、
点打开 Shizuku 会卡」，逐条落到三处改动：状态读取不再堵住界面线程、界面把「Shizuku 应用版本」与
「服务端 API 版本」分开显示、连接失败时给出可执行的中文指引。副屏与无障碍部分与 0.2.12 相同，
本版没有改动它们。
**本页「未验证」一节列出的项目仍没有在真机上复测过**：本版修的是读状态与提示，真机上的
「更新 Shizuku 后能不能连上」还需要装到手机上验。

## 一、状态读取不再拖住界面（卡顿修复）

- 前端每 5 秒轮询一次 Shizuku 状态，而一次状态读取里每一步（`resolveContentProvider`、
  `pingBinder`、`checkSelfPermission`、`shouldShowRequestPermissionRationale`、`getVersion`）
  最终都会落进 Shizuku 服务端的 binder 调用，binder 调用**既不返回也不超时**；服务端卡住时，
  卡住的读取会把桥的执行线程逐个占满，整个运行时跟着僵住——真机反馈的「点打开 Shizuku 会卡」
  就是这么来的。
- 新增闸门 `ShizukuStateCache`：同一时刻只允许一次状态读取。有读取在途时**不再发起新的 binder
  调用**，直接返回上一次成功读取的结果；连一次成功读取都还没有时返回兜底状态（只查「Shizuku
  是否安装」，一个 binder 调用都不做），界面按未就绪显示，用户仍能点「打开 Shizuku」去重启服务。
  读取抛异常时照旧放开闸门——一次失败不会永久堵死后续读取。
- 桥方法 `getShizukuState`（每 5 秒轮询的那条）与 `openShizuku` 从「同步跑在 WebView 线程」改为
  交给后台执行线程，WebView 线程不再被可能卡住的 binder 调用占住。
- binder 到达或断开时主动作废缓存与在途读取（用代号区分「哪一次读取」）：否则服务端重启之后，
  卡死的那次读取永远不会回来，闸门会一直以为「有人在读」，界面也永远停在兜底状态。

## 二、两种版本分开显示（版本识别）

- 此前界面上那个 `（v13）` 是 **Shizuku 服务端 API 版本**，不是 Shizuku 应用版本：Shizuku 的
  `Shizuku.getVersion()` 读的是服务端上报的 API 版本，13.x 各版应用上报的都是 `13`，所以用户把
  Shizuku 更新到 13.6.0 之后看到「v13」，自然会认为版本识别错了。
- 现在分开显示：`Shizuku 应用 13.6.0 · 服务端 API 13`。应用版本名取自系统包管理器
  （`versionName`）；读不到时只显示服务端版本，**不编造**应用版本。
- 服务端 API 版本只认正数：权限未授予时 `Shizuku.getVersion()` 不抛异常而是返回 `-1`，
  改前会显示成「服务端 API -1」这种像乱码的版本。
- 桥方法返回值新增 `appVersion` 字段，前端类型定义与格式校验同步（只接受字母、数字与 `._-`，
  最多 32 个字符，与既有的标识符校验口径一致）；版本名里混进别的字符时宁可不显示，也不让整份
  状态被前端校验丢弃。

## 三、连不上时给出可执行指引（错误文案）

- 更新 Shizuku **应用**之后，手机上可能仍在跑更新前启动的**旧服务端**（Shizuku 的服务端进程不随
  应用更新自动重启），此时绑定设备服务会超时。这一条我们无法在应用内自动修复——Shizuku 没有对
  第三方开放「重启服务」接口，本应用也没有重启它的通路——所以只能把下一步写进提示。
- 五条错误码补上明确中文文案：`SHIZUKU_SERVICE_TIMEOUT`、`SHIZUKU_SERVICE_FAILED`（都写明
  「请在 Shizuku 中停止服务后重新启动（或重启手机），再回到本页重试」）、
  `SHIZUKU_SERVICE_INTERRUPTED`、`SHIZUKU_BINDER_TIMEOUT`、`SHIZUKU_BINDER_UNAVAILABLE`。
  英文界面同步翻译。

## 五、未验证与已知问题

- **本节列出的项目都没有在真机上复测过**：Shizuku 更新后的连接恢复（需要在真机上故意「更新
  Shizuku 后不重启服务」来复现）、双版本显示在真机上的实际读数、卡顿是否真的消失。
- 应用内**无法重启 Shizuku 服务端**（Shizuku 没有对第三方开放的接口），「更新后连不上」只能靠
  上述文案引导用户在 Shizuku 里操作。能不能做成自动恢复，要先确认 Shizuku 端有没有可用接口，
  这属于独立改动。
- 0.2.12 列出的副屏与无障碍未验证项依旧未复测（副屏十档取帧的真实读数、自动跟随三策略、
  逐事件注入是否真的让画面变化、无障碍执行器的实际触发与节流等）。
- 真机反馈的「无障碍白名单应用选择器里搜 `gkd` / `GKD` 搜不到 GKD」仍未拿到复现信息：需要真机
  确认列表里有没有这一行、它显示的标签与包名、以及两个筛选开关（只看可自动化应用 / 隐藏系统组件）
  的状态。规则侧已有单测钉住（包名 `li.songe.gkd` 与标签「GKD」在 `gkd` / `GKD` / `songe` 下都命中）。
- 运行时残留目录的清理在真机上仍然失败（严格删除器与兜底删除器都返回 `ACCESS_DENIED`，界面会如实
  显示残留份数与体积，但清不掉）。
- 外壳「会话工作区」的会话列表在本机读不出来，界面显示「读不到会话列表」而不会假装空态。
- 与本版代码无关的人工待办：轮换已经暴露过的模型 API key。
