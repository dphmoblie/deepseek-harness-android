# 目标应用副屏

更新：2026-10-10。

本功能让用户选择的目标安卓应用运行在独立虚拟屏幕，再把副屏画面显示到 DSH 独立页面或可拖动小窗。AI 使用专用的状态、截图和动作工具操作该会话。

## 使用入口

1. 在壳内设置中连接并授权 Shizuku，开启 **允许 AI 调用 Shell**。
2. 打开 **目标应用副屏**，搜索并选择一个有启动入口的应用。
3. 尺寸规格由 `VirtualScreenSpec`（`android/app/src/main/java/io/deepseekharness/mobile/virtualscreen/VirtualScreenSizing.kt`）统一持有，页面文案里的 dp 数字与建立会话用的像素值同源：竖屏预设 **726×1600 像素、320 dpi**（363×800 dp），横屏预设 **1280×580 像素、256 dpi**（约 800×363 dp）。两个预设的数值与改造前逐字一致。规格的取值区间是边长 200..4096、dpi 120..640，越界时**夹取**而非报错；`VirtualScreenPolicy.dimensions` 仍是启动前的硬闸门（宽 ≤ 1440、高 ≤ 2560、面积 ≤ 2073600）。页面把规格通过 Intent 的三个整型 extra（`widthPx`/`heightPx`/`densityDpi`）传给会话服务，服务读不到或读到非法值时整体回退竖屏预设；旧版只发 `landscape` 布尔的 Intent 仍按原样工作。
4. 页面支持点击、滑动、应用返回、结束副屏；预览区域在触摸直传通道可用时逐事件转发指针，底部一行按钮切换预览节奏（省电 / 15fps / 30fps / 60fps）。授予悬浮窗权限后，可切换为可拖动小窗；小窗的可视区域宽高比按当前副屏比例换算（`VirtualScreenWindow.overlaySize`），并保留「不超过屏幕 94% 宽、84% 高」的上限，因此预览画面的 `FIT_CENTER` 不再留出黑边。页面预览区与小窗**共用同一个画面容器**（`VirtualScreenFrame`）：尺寸走同一套换算，右下角都有一个 44dp 的手柄，拖动它可**等比**改变大小（只记宽度，高度按副屏比例反算，因此永远不会有黑边、触摸坐标也不会失真）；宽度记在偏好 `overlayWidthPx` 里（`0` 表示跟随可用区域最大，正数夹在 120..4096），下次打开沿用。收起小窗或退出页面保留会话，通知可重新打开或结束副屏。
5. 返回对话后，让 AI 先查询副屏状态、截图观察，再操作。现有主屏截图、主屏无障碍工具继续使用原来的通道。

选择应用会启动或迁移其任务，关闭副屏可能结束该副屏内的任务。目标应用是否允许多屏、多实例以及后台渲染，由其自身和设备系统决定。首次使用需用非关键任务验证。

## 机制和兼容模式

- `ShellVirtualScreen` 在 Shizuku 用户服务中创建独立显示，并持续消费 `ImageReader` 缓冲区。页面和小窗从同一会话读取 PNG，关闭某个预览不会重建目标应用。
- 图像只在内存中保存；Binder 跨进程通道使用管道传输，避免把整张图塞进单次 Binder 事务。画面静止时复用最后一帧，返回的状态包含最近一帧的时间。采集时按固定步长采样判定空白帧：空白帧不会被当作有效画面缓存，状态与截图结果都会给出 `frameBlank`，避免把白帧当成新画面继续使用。
- 预览节奏可选：默认「省电」沿用限帧采集（180 毫秒合并，静止画面复用最后一帧），也可切到 15/30/60 fps（采集间隔 66/33/16 毫秒）。状态返回实际生效的 `previewMode`（`limited-fps` 或 `realtime-<模式>`）、`frameIntervalMs` 与最近 24 帧测得的 `frameFps`。帧率只提高采集与预览频率，不改变「静止页面复用最近一帧」的事实，也不代表目标应用自身以该帧率渲染。
- 触摸透传：预览区域把手势逐事件发给副屏（进程内 `InputManager.injectInputEvent`），状态字段 `touchChannel` 为 `stream`；通道不可用时自动回退为离散的 `tap`/`swipe` 命令（`touchChannel=discrete`），行为与旧版一致。每次输入前按副屏编号确认目标应用仍处于该屏已恢复的活动中，再调用带 `-d` 的系统输入命令。
- 有 `ADD_TRUSTED_DISPLAY` 权限的 Android 13 以上环境才请求受信任副屏；Android 14 以上才进一步请求独立焦点。权限不足时使用普通独立副屏，不创建主屏镜像。`independentFocusRequested=false` 表示未请求独立焦点，需要单独验证主屏与副屏并行交互体验。
- 无法创建副屏、无法确认目标应用位置、系统命令失败或会话过期时返回错误，不将副屏操作改为主屏操作。部分系统仍可能自行改写应用启动位置，所以不能把“请求副屏启动”视为绝对不影响主屏的保证。
- 显示销毁时使用销毁内容标志；用户结束、授权关闭、Shizuku 断开、宿主进程死亡均有资源回收路径。页面旋转与页面/小窗切换保留服务会话。

## AI 与命令接口

权限要求：设备桥的本机 Bearer 认证、用户已开启 AI Shell、Shizuku 已授权、用户已从原生页建立副屏会话。副屏接口不能替用户打开授权开关或任选系统显示编号。状态查询不发送全部应用清单。

| 工具 | 本机命令 | 参数与结果 |
| --- | --- | --- |
| `mobile_virtual_screen_state` | `virtualScreenState` | 无参数；返回是否运行、会话标识、显示编号、目标包名、像素尺寸、采集时间、焦点模式，以及预览节奏（`previewMode`/`frameIntervalMs`/`frameFps`）、触摸通道（`touchChannel`）与节点树可用性（`treeSupported`） |
| `mobile_virtual_screen_screenshot` | `virtualScreenCapture` | 必须带 `sessionId`；返回该副屏 PNG，附件服务转换格式后保留真实 MIME；结果带 `frameBlank`，为 true 表示该帧为空白或目标未渲染，可稍后重试或先用 `action` 唤醒目标应用；必须使用支持图像输入的模型 |
| `mobile_virtual_screen_action` | `virtualScreenAction` | 必须带 `sessionId` 和 `action`；支持 `tap`、`swipe`、`long_press`、受控 `keyevent`、`text`、`back`、`stop`、`touch`、`gesture`、`launch`、`follow`，以及下列三条工具各自封装的 `config`、`target`、`tree`。四个新动作都要求副屏会话处于运行状态：`gesture` 是一次连续轨迹（`points` 2～64 个 `{x,y}` ＋ 可选 `durationMs`），适合拖动与滑动；`touch` 是分步触摸直传（`phase` 取 `down`/`move`/`up`/`cancel`，`down` 先确认目标仍在副屏前台，之后**必须**补一次 `up` 或 `cancel`）；`launch` 在**这块副屏上**打开某个应用或链接（`component`/`package`/`uri` 三选一）；`follow` 把跳出到主屏的目标应用拉回副屏 |
| `mobile_virtual_screen_config` | `virtualScreenAction`（`action=config`） | 必须带 `sessionId` 和 `previewMode`（`limited`/`15fps`/`30fps`/`60fps`）；只改采集节奏，不重建显示器 |
| `mobile_virtual_screen_target` | `virtualScreenAction`（`action=target`） | 必须带 `sessionId` 和 `packageName`；把该应用启动或迁移到当前副屏显示，会话不重启；校验失败时报错且不改变当前目标 |
| `mobile_virtual_screen_tree` | `virtualScreenAction`（`action=tree`） | 必须带 `sessionId`，可选 `maxDepth`（1～8，默认 4）；返回受限节点树，需要用户先在系统设置里启用 DSH 的无障碍服务 |
| `mobile_virtual_screen_shell` | `virtualScreenShell` | 必须带 `script`（非空、UTF-8 ≤16 KiB、不含 NUL 与回车），可选 `displayId`（整数）；脚本在副屏的 displayId 上执行，环境已导出 `DISPLAY_ID`。详见下方「副屏直通 Shell 通道」一节 |

动作校验：坐标为整数且在实际副屏宽高内；滑动终点同样校验，持续时间为 100～2000 毫秒；长按持续 500～3000 毫秒。`keyevent` 仅允许 BACK、ENTER、DEL、TAB、方向键、SPACE 和 ESC；`text` 限制为 1～512 个字符且不含控制字符，可带可选的 `submit`；含中文、emoji 在内的所有文字注入都先走本进程的无障碍回退链（见下方一节）。`previewMode` 只接受四种模式名，`packageName` 必须是完整包名（≤192 字符），`maxDepth` 只接受 1～8。会话必须匹配宿主正在管理的会话；显示编号由服务持有，调用方不能覆盖。会话切换瞬间（包括 `back` 之后）可能返回 `VIRTUAL_SCREEN_STOPPED`，重新读取状态后重试即可，不应把它当成副屏不可用。启动入口和 Shell 参数使用分别校验后的参数数组，不拼接成脚本。`gesture` 的点数、整数坐标（必须落在实际副屏宽高内，越界直接拒绝而非夹取）与时长在工具侧和设备侧各校验一次；`launch` 的 `component` 用与 `target` 相同的组件规则，`package` 是完整包名（≤192 字符）并由设备侧 `cmd package resolve-activity --brief` 解析启动入口，`uri` 只允许 `http`/`https`/`market` 且不含空格、引号、分号、竖线、反引号、换行等字符（长度 1～2048）；`follow` 不接受额外参数，跟随对象只能来自主屏最前台，AI 不能指定。手势注入没能落地时报 `VIRTUAL_SCREEN_INJECTION_FAILED`（副屏会话本身正常，可稍后重试或改用 `tap`/`swipe`）；解析不到启动入口报 `VIRTUAL_SCREEN_LAUNCH_UNRESOLVED`，系统拒绝这次启动报 `VIRTUAL_SCREEN_LAUNCH_FAILED`，启动后 3 秒内没能在副屏上确认到前台报 `VIRTUAL_SCREEN_TARGET_TIMEOUT`；`follow` 没有可跟随的应用时返回 `followed: false` 与 `VIRTUAL_SCREEN_FOLLOW_NONE`，那是**正常结论**而不是错误。接口正文最多 4096 个字符。

文字注入的回退链（逐级尝试、逐级记账：结果里 `method` 是真正生效的那一级、`chars` 是实际写入的字符数、`steps` 是逐级说明）：① 副屏上已有聚焦的可编辑输入框 → 无障碍 `ACTION_SET_TEXT`；② 没有聚焦节点但树里有可编辑候选 → 先聚焦（`ACTION_FOCUS`／`ACTION_CLICK`）再写入；③ 输入框拒绝写入 → 剪贴板写入后 `ACTION_PASTE`；④ 纯 ASCII 且以上都没落地 → 接回设备 Shell 的 `input text`／逐字符 `input keyevent`。全部不成立才报 `VIRTUAL_SCREEN_TEXT_UNSUPPORTED`（这台设备或这个目标输入框当前写不进去，请在副屏上手动输入或改用点击操作），它**不等于** `VIRTUAL_SCREEN_UNAVAILABLE`（副屏功能本身不可用）。
输入法不参与写入：不代点输入法候选词，兼容性来自不依赖输入法的写入通道。`submit: true` 只在文字**确实写进去之后**才按一次回车（搜索框、聊天发送）；回车送不出去时 `submit=false` 并在 `steps` 里说明；Android 11 以下没有等价的输入法回车入口，如实拒绝而不假装已发送。
无障碍侧的拒绝码原样透传：`ACCESSIBILITY_DEVICE_LOCKED`（设备锁定或屏幕未交互）、`ACCESSIBILITY_RATE_LIMITED`（两次写入间隔小于 350 毫秒）、`ACCESSIBILITY_SENSITIVE_WINDOW`（密码/验证码/支付/授权窗口）、`ACCESSIBILITY_WINDOW_UNAVAILABLE`（那一刻副屏上没有可写入的窗口）、`ACCESSIBILITY_ACTION_INVALID`（文本参数不合法：长度或控制字符不合规时直达）。

错误码包括 `DEVICE_SHELL_DISABLED`、`VIRTUAL_SCREEN_NOT_STARTED`、`VIRTUAL_SCREEN_STOPPED`、`VIRTUAL_SCREEN_LOCKED`、`VIRTUAL_SCREEN_BUSY`、`VIRTUAL_SCREEN_INVALID`、`VIRTUAL_SCREEN_UNAVAILABLE`、`VIRTUAL_SCREEN_TEXT_UNSUPPORTED`、`VIRTUAL_SCREEN_INJECTION_FAILED`、`VIRTUAL_SCREEN_LAUNCH_UNRESOLVED`、`VIRTUAL_SCREEN_LAUNCH_FAILED`、`VIRTUAL_SCREEN_TARGET_TIMEOUT`、`VIRTUAL_SCREEN_FOLLOW_NONE`（正常结论而非故障）、`VIRTUAL_SCREEN_UNSUPPORTED`（系统版本低于 Android 10）。错误不包含系统命令输出、图像或私有路径。`VIRTUAL_SCREEN_BUSY` 表示前一步仍在处理，应等待后重新观察，不能盲目重复操作；`VIRTUAL_SCREEN_STOPPED` 表示会话已切换或副屏正在结束，重新读取状态后再操作。

Shell 中也可通过 `dsh-device virtualScreenState` 查询，另两条命令把 JSON 作为单个参数传入。截图响应是 Base64 编码 PNG；模型插件会处理附件，并在工具结果中报告 `packageName`、`frameAtElapsedMs`、`frameReused` 与 `frameBlank`，不需要 AI 自行猜测图像格式。缩放截图使用原始尺寸与附件尺寸的精确比例恢复坐标。

## 隐私与当前边界

- 画面中可能包含目标应用的个人信息。原生本地预览不上传图像；AI 截图请求会把图像送入当前会话及其模型服务。界面和工具提示明确说明这一点，模型不得采集与任务无关的隐私内容。
- 审计只记录副屏会话、读取、操作的类别和结果，沿用本项目至少 90 天保留规则；不记录目标包名、截图、坐标、输入文本和命令正文。
- 锁屏、熄屏时暂停本通道的读取与输入，预览清空。未请求“始终解锁”显示标志，也不保证目标应用在锁屏后继续渲染或自动恢复。
- 副屏节点树由应用自己的无障碍服务按显示编号读取（只读、限层级与节点数：最多 400 个节点、8 层、单个文本字段 120 字符），需要用户先在系统设置里启用 DSH 的无障碍服务；未启用时 `available=false` 并给出原因，**不会**回退到主屏窗口，也绝不复用主屏的节点树。状态里的 `uiTreeSupported=false` 说明设备 Shell 通道本身不提供节点树，能否读取副屏树一律以应用侧字段 `treeSupported` 为准。敏感窗口整棵拒绝。中文与 emoji 通过同一条无障碍定向注入通道输入，只作用于聚焦的可编辑、非密码输入框。
- 仍不支持多指手势；预览帧率可调但仍是采样与轮询管线，不承诺视频级的连续性。多副屏并行会话本轮未实现：状态里始终只有一块副屏、一个 `sessionId` 与一个显示编号。
- 安全窗口、DRM 内容或应用自身的多屏限制可能导致黑屏或拒绝启动。不会绕过目标应用登录或 Android 的保护。
- 模型推理与网络耗时仍参与整个自动化循环。设备输入耗时不能当成“AI 看到界面后完成操作”的端到端延迟。

## 验证方法

`androidTest` 包包含独立的 `VirtualScreenProbeActivity`，仅显示计数按钮，不读取用户数据。`scripts/android/VirtualScreenDeviceProbe.java` 可通过 `adb shell app_process` 加载主 APK 的副屏实现，以 Shell UID 验证竖屏、横屏、PNG、定向点击、静止画面、主屏任务和过期会话。

该探针运行于 Android 13 以上测试设备（使用系统 `InputStream.readAllBytes`）；应用副屏入口最低为 Android 10，较低版本仍需另行测试。探针不替代 Shizuku 授权、Binder 绑定、真实应用、小窗生命周期和锁屏测试。

构建先执行前端构建和 `cap copy android`，再执行 `:app:assembleDebug`、`:app:assembleDebugAndroidTest`、`:app:testDebugUnitTest`、`:app:lintDebug`。可用 JDK 的 `javac --release 11` 编译探针，类路径为 Android SDK 的 `android.jar` 和 `app/build/tmp/kotlin-classes/debug`，使用 SDK 的 `d8` 转成 dex 并封装到 jar，再与主 APK 一起作为 `CLASSPATH` 交给 `app_process`。产物仅放在忽略目录，不能提交 APK、dex、PNG 或日志。

`VirtualScreenPageTest` 在设备当前尺寸验证原生选择页的列表可用高度和按钮边界；窄屏与宽屏测试后应恢复模拟器原始尺寸和密度。

  1. 小窗里根本没有状态行：`VirtualScreenPreview.report` 在 `showOverlay()` 里从未接线（默认空实现），用户看不到「为什么没有画面」，面板就只是一块黑背景。

- **修复思路**：判定权威从宿主挪到客户端（在**解码后的位图**上采样），空白帧一律不上屏、也不清屏，状态行如实说明当前是哪一种情况。
  - `VirtualScreenPolicy.kt`：采样改成网格。宿主侧 `frameSampleRows(extent)` 固定 24 行（含首尾、严格递增）逐行相接成「行缓冲」交给 `blankFrame` 判「接近纯色」；客户端按 `previewSampleRows` / `previewSampleColumns`（96×128）取亮度，`frameHasContent` 用亮度极差 > `PREVIEW_CONTENT_SPREAD`（24）判「这一帧有可显示内容」，`frameChanged` 用「任一点亮度差 > `PREVIEW_SAMPLE_DELTA`（12）」判「与上一张显示的帧是否不同」。阈值依据写在 KDoc 里：24 是在「极淡灰底（实测极差 11）」与「一行文字 / 一个小图标」之间留出的余量；12 既能滤掉渲染抖动，又不会把单点真实变化说成「画面暂无变化」。
  - `previewOutcome(alive, decoded, blank, changed)` 四态：会话不可观察 → `CLEAR`（**唯一允许清屏的情形**）；这一拍读不到帧 → `KEEP` +「未读到新帧」；新帧接近纯色 → `KEEP` +「当前帧接近纯色」（不上屏，继续显示最近一张非空白画面）；与上一帧相同 → `SHOW` +「画面暂无变化」（新帧仍是新帧，画面时刻照常前移）；其余 → `SHOW`。
  - 状态行统一由 `previewFrameLabel` 产出：有内容时报实测帧率（还没测出来就说「帧率待测」），三种暂停原因各说各的，**没有「复用最近一帧」这类说法**；还没有任何画面时统一说「等待副屏画面（未读到新帧／当前帧接近纯色）」，第一张画面画上去之后立刻改口。
  - 小窗（`VirtualScreenService.showOverlay()`）在档位行下面**新增一行状态文字**并接上 `VirtualScreenPreview.report`；点击档位成功后立刻显示「已切到 <档位>，等待新的帧率读数」，下一次取帧再用真实读数覆盖——不假装已经切好、也不假装已经出画面。
- **隐私提醒**：悬浮小窗**不再加 `FLAG_SECURE`**（原先它会连用户自己的截图一起挡掉，实测报 `Failed to take take screenshot. Capturing failed.`）。代价是**小窗里的副屏内容可能出现在截图、录屏与投屏里**；全屏查看器 `VirtualScreenActivity` 当时还保持 `FLAG_SECURE` 不变（该页随后也在下一轮去掉了，见下条）。
- **未验证**：真机上小窗是否真的出画面、状态行文案与实测帧率是否符合观感、点击档位后 `frameFps` 是否随档位变化、96×128 采样在真实页面上的误判率、`frameError` 诊断字段的实际取值，全部**未在设备上走查**；本轮只跑了 JVM 单测。

#### 1. 动作集：新增 `start` / `restart` / `reconnect` / `autoFollowTick`

对话窗口动作（`mobile_virtual_screen_action` 的枚举已追加这四个值；插件侧的 `mobile_virtual_screen_action` 只在 `autoFollowTick` 时透传可选 `selfPackage`，其余动作请求体不变）。三者都返回 `{action, ok, state, sessionId, displayId, previousSessionId, targetPackage, reason}`，**不做假的成功**：

- `start`：会话已在运行时返回 `state=already_active` 且**不重建**（重建意味着换一块显示、目标应用闪一次，不能当默认行为）；会话不存在时返回 `VIRTUAL_SCREEN_SESSION_DEAD`——真正的建立入口仍然是用户在设置页点开副屏，工具面不能凭空创建会话（拿不到授权与规格）。
- `restart`：用会话里保存的原规格（组件、宽、高、dpi）重建显示与会话，并**保住原 `sessionId` 编号**。保住编号是硬要求：宿主健康循环每约 800 毫秒核对 `live.sessionId == 自己的 sessionId`，编号一变就会被判成「副屏已停止」并停服。规格已丢失（会话从未建立或已被清空）或会话不存在时返回 `VIRTUAL_SCREEN_RESTART_UNSUPPORTED`。
- `reconnect`：解掉旧的 binder 死亡回调、按当前会话重挂，并重新 `linkToDeath`。副屏显示已被释放时返回 `VIRTUAL_SCREEN_RECONNECT_UNSUPPORTED`（**不假装重连成功**：显示被 `release()` 之后只能由设置页重新建立会话）。
- `autoFollowTick`：平时由宿主健康循环自动发出（约每 800 毫秒一次），设备端自带 2 秒节流且幂等，手动触发一般没有必要；`selfPackage` 用于把「本应用自己」排除在提升目标之外，可省略。

**未实现**：副屏被系统回收/被用户从系统侧关掉之后，`restart` 与 `reconnect` 都不会替用户重建显示器（缺授权上下文与规格来源）；这两个动作的语义严格限定在「同一进程内会话仍在」。

#### 2. 错误码细分：`STALE_FRAME` / `TARGET_LEFT` / `SESSION_DEAD`

以前一个 `VIRTUAL_SCREEN_UNAVAILABLE` 同时承担「会话没了」「目标跑了」「这一帧取不到」三种情况，调用方无法决定下一步。本轮拆成三个互斥的码，判据写在 `VirtualScreenPolicy.frameFailure(sessionAlive, targetVisible, frameStale)` 这个纯函数里（顺序即优先级）：

- `VIRTUAL_SCREEN_SESSION_DEAD`：`displayId <= 0` 或请求的 `sessionId` 与当前会话不一致 ⇒ 会话已经失效。
- `VIRTUAL_SCREEN_TARGET_LEFT`：会话在、但目标应用已不在副屏 `<id>` 的 resumed activity 上 ⇒ 先切回副屏再操作。
- `VIRTUAL_SCREEN_STALE_FRAME`：会话与目标都在、但这一帧过期或取不到 ⇒ 稍后重试。`frameStale` 判据：有 `frameError`、从未取到帧（`frameAt <= 0`）、或最近一帧距今 ≥ `FRAME_STALE_AFTER_MILLIS`(2000ms)。

落到具体入口：`snapshot(sessionId)` 原来用 `check(targetVisible())`、`check(frameAt > 0 && frame != null)`，现在分别抛 `TARGET_LEFT` 与 `STALE_FRAME`（空白帧仍照常返回画面，因为「空白」是有效读数）；`frame(sessionId)`（硬件帧预览路径）把「还没取到硬件帧」也改成 `STALE_FRAME`，并**刻意不查** `targetVisible`——那条路径每帧都会被拉一次，每帧跑一次 `dumpsys activity` 会把帧率毁掉。`requireSession` 保持原样仍报 `VIRTUAL_SCREEN_STOPPED`（宿主按这个码收尾，不动它）。

`VIRTUAL_SCREEN_UNAVAILABLE` 保留为**兜底**：只有真正无法区分时才用（例如预览组件自身抛 `IllegalStateException`），语义不变。另有两个「这一步现在做不到」的码：`VIRTUAL_SCREEN_RESTART_UNSUPPORTED`、`VIRTUAL_SCREEN_RECONNECT_UNSUPPORTED`。

#### 3. 副屏前台可观测量与 `autoFollow` 回显

`state` 新增三个字段：

- `virtualForegroundPackage` / `virtualForegroundActivity`：副屏的 resumed activity 取自设备 Shell 执行 `dumpsys activity activities` 后按 `Display #<显示编号>` 段落解析 `mResumedActivity`/`topResumedActivity`（与 `follow` 判定用的是同一个 `resumedComponent`，不另起一套解析）。**拿不到就返回空串，绝不回退成主屏前台**——把主屏应用说成「副屏前台」会让模型对着错的界面发坐标。
- `autoFollow`：当前自动跟随策略（`off`/`pull_back`/`promote`），来自 `config` 动作的写入，未写入时为 `off`。

工具面渲染：`mobile_virtual_screen_state` 现在先给一行「副屏前台 X（Y）。自动跟随策略 Z。」再附原始设备数据；设备返回的不是 JSON（或字段缺失）时这行退化为空、原始数据照旧完整打印，不吞内容。

#### 4. 自动跟随（三策略 + 节流 + 幂等）

判定抽成纯函数 `VirtualScreenPolicy.autoFollowDecision(...)`（无 IO、可单测），策略：

- `off`：什么都不做，理由「自动跟随已关闭」。
- `pull_back`：目标应用跳到主屏别的应用（主屏最前台不是会话目标、也不是本应用自己）时，把**会话目标拉回**副屏（复用 `launchOnDisplay`）。已在副屏的目标不会被重复拉。
- `promote`：把副屏当前前台的应用**提升为会话目标**；候选不可跟随（桌面、输入法、`com.android.systemui`、`com.android.shell`、本应用 `selfPackage`、非法包名）时不动作，理由里带 `VIRTUAL_SCREEN_FOLLOW_NONE` 的原文。
- 两个策略看的方向不同：`promote` 只看副屏前台，`pull_back` 只看主屏最前台——这样同一个 tick 不会既提升又拉回。
- 幂等：目标已经是会话目标（含同包的另一个 Activity）时直接跳过；节流由 `FollowThrottle(2000ms)` 实现，窗口内同一「规则 + 目标」不重复动作，**换规则或换目标立刻放行**（否则用户手动改策略会被上一笔的节流窗口吞掉）。
- 返回 `{sessionId, displayId, autoFollow, applied, rule, reason}`：没动作时 `applied=false` 且 `reason` 说清为什么，执行失败时 `reason` 里带错误码与原因。

**未实现**：`promote` 提升的是「副屏前台应用」，不是「用户想看的应用」；没有做多应用轮换或前台历史。**未真机验证**：三策略在真机上的实际拉回/提升效果全部未走查。

#### 5. `target` 参数增强与一处跨层字段不匹配

- `confirm_budget_ms`：确认窗口，默认 3000，设备端夹取 500～15000（给超范围的值不报错、按夹取后的值执行，只有不是数字才拒绝）。
- `prewarm`：先在**副屏**冷启动一次目标应用（`am start -W --display <id>`），把冷启动耗时从确认窗口里挪出去。**决策**：不在主屏先起一次再迁移——那会让目标在主屏闪一下，用户看到的副屏目标会对不上。
- `rollback`：这次切换失败时把原目标拉回副屏；返回消息里如实写明回滚成功还是「回滚也没能确认上屏」，不把回滚说成成功。
- 失败时 `reason` 字段区分 `NOT_ACCEPTED`（启动请求没被系统接受：无入口/命令被拒）、`NOT_FOREGROUND`（启动了但没在窗口内进入前台，含超时）、`SESSION_DEAD`（会话失效）。`reason` 只是载荷，顶层码仍是 `VIRTUAL_SCREEN_TARGET_TIMEOUT` / `VIRTUAL_SCREEN_SESSION_DEAD` 等既有码。
- **顺带修掉一处必踩的跨层不匹配**：插件面 `mobile_virtual_screen_target` 一直只发 `{sessionId, action:'target', packageName}`，而设备侧原先只认 `component` 字段 ⇒ AI 调 `target` 必然得到 `VIRTUAL_SCREEN_INVALID`。现在设备侧新增 `targetRequestField`：`component` 与 `packageName` **必须且只能给一个**，给包名时由设备端用 `cmd package resolve-activity --brief` 解析入口，解析不到报 `VIRTUAL_SCREEN_LAUNCH_UNRESOLVED`（带 `reason=NOT_ACCEPTED`）。既有 `targetRequest`（只认 `component`）保持原行为不动，工具面 `packageName` 的请求形态也不变。

#### 6. 非 ASCII 输入：设备 Shell 侧的剪贴板通道（诚实边界）

`textAction` 遇到非 ASCII 时新增一条尽力而为的通道：`cmd clipboard set-primary-clip <文本>` → `cmd clipboard get-primary-clip` **读回核对**（读回核对排在报错正则**之前**：用户要输入的文字里带 `error` 这类英文单词时，不能把一条能用的通道判成不可用）→ `input -d <副屏显示编号> keyevent 279`（`KEYCODE_PASTE`）。判定抽成纯函数 `clipboardProbe(...)`，三态 `available`/`failed`/`absent`。成功后结果里 `method=PASTE`，并明确带 `verified=false` 与说明：设备 Shell 侧读不到副屏输入框内容，是否真的落到目标字段要用截图或节点树复核。

**必须说清的边界（本轮最重要的诚实结论）**：正常 AI 调用 `text` 时，非 ASCII 且无障碍不可用，是在**主进程** `VirtualScreenTree` 那一层就返回 `VIRTUAL_SCREEN_TEXT_INJECTION_REQUIRED` 的（那一层不在本轮可改范围），**根本不会**走到设备 Shell 的 `textAction`。所以上面这条剪贴板通道目前是**纵深防御**：对直接打设备 Shell 通道的调用方（`dsh-device` 命令、宿主降级路径、后续把该层接起来）有效，用户可见的失败码仍由主进程那一层决定。文档不对它作「非 ASCII 已打通」的暗示。

**做不到的部分**：设备 Shell 进程拿不到无障碍服务实例 ⇒ 没有 `ACTION_PASTE`（只能发粘贴键）、也没有「聚焦后写入」。无障碍不可用时非 ASCII 仍然不能保证落地，失败一律报 `VIRTUAL_SCREEN_TEXT_UNSUPPORTED` 并给一句可操作提示：`开启无障碍服务后可走剪贴板与聚焦写入通道（含中文）`；文本确实进了系统剪贴板但粘贴键没能发到副屏时报`已把文本写入系统剪贴板，但粘贴键没能发到副屏；请在副屏输入框里长按选择「粘贴」`。**未真机验证**：`cmd clipboard` 在该 ROM 的 shell uid 下是否可用、`keyevent 279` 是否真的触发粘贴、剪贴板通道在中文/emoji 上的落地效果，全部未走查。

#### 7. 刷新率：向系统请求档位，但只报读回值

- 走 `VirtualDisplayConfig`（Android 14 / API 34 及以上）创建副屏时，现在会接上 `setRequestedRefreshRate(VirtualScreenPolicy.requestedRefreshRate(frameMode))`：`limited` 档传 60f，其余档位传档位对应的数值（如 `185fps` → `185f`）。低版本仍走旧的 `createVirtualDisplay` 重载，没有这个请求参数。
- **必须说清楚的边界**：预览档位（`limited`/`15fps`…`185fps`）首先是**取帧节奏**——`FRAME_MODES` 里的毫秒间隔决定设备 Shell 多久采一帧、编码一帧，它不等于显示器真的跑在那个刷新率上。系统**可以忽略**这个请求：本机该虚拟屏的 `supportedModes` 只有 `fps=60.0` 一档，请求 `185f` 很可能就被忽略。
- 所以 `state` 的 `displayRefreshRate` 读的是显示器**实际**值（`display.display.refreshRate`），读不到就回 `0f` 表示未知；**不要**把它当成「请求值已生效」，也**不要**因为档位写了 185 就对外说 185Hz 生效。文档与工具描述都不作这种暗示。
- **未真机验证**：`setRequestedRefreshRate` 在真机上是否被接受、被忽略时会怎样、读回值与档位在各 ROM 上的对应关系，本轮全部没有真机读数。

## 副屏直通 Shell 通道（指定 displayId 的 `input` / `am`）

用途：`mobile_virtual_screen_action` 走的是应用自己的定向注入通道；但系统级命令（`input -d`、`am start --display`）只能靠 Shell。`mobile_virtual_screen_shell` 把一次性 Shell 脚本放到**副屏的 displayId** 上执行，并在脚本环境里导出 `DISPLAY_ID`，脚本里可以直接写：

```sh
input -d "$DISPLAY_ID" tap 622 880
am start --display "$DISPLAY_ID" -a android.intent.action.VIEW -d https://example.com
```

本机命令是设备桥的 `virtualScreenShell`（`DeviceBridgeServer` 分派；复用与 `shell` 完全相同的一次性 Shizuku 会话执行路径，不新建执行器）。工具参数：`script`（必填；非空、UTF-8 ≤16 KiB、不含 NUL 与回车，与 `mobile_device_shell` 同一套校验）、`displayId`（选填整数，省略时用当前会话副屏）。工具结果是 `exitCode`、`output`、`truncated`；设备桥响应里另带本次实际使用的 `displayId`。

注入前缀是确定性文本（同一 displayId 与同一脚本必然生成完全相同的命令，可单测）：三行中文注释 + `export DISPLAY_ID=<id>;`，注释里写明 `input -d "$DISPLAY_ID" …` 与 `am start --display "$DISPLAY_ID" …` 的用法。脚本交给设备侧已有的 `/system/bin/sh -s` 一次性进程执行，因此开头的 `export` 对后续每一行都有效；前缀不重复叠加（同一脚本重复注入结果一致）。

规则与错误码：

- 省略 `displayId`：使用当前副屏会话的显示编号。
- 显式传 `displayId`：必须**等于**会话的副屏显示编号，否则 `VIRTUAL_SCREEN_DISPLAY_INVALID`；显式传 `0`（主屏）一律拒绝，同一错误码——本通道只服务副屏，主屏请用 `mobile_device_shell`、`mobile_device_tap` 等既有工具。
- 副屏会话未运行或尚未取得显示编号：`VIRTUAL_SCREEN_UNAVAILABLE`（与既有语义一致）。
- 未开启 AI Shell：`DEVICE_SHELL_DISABLED`；脚本为空、超长、含 NUL/回车，或 `displayId` 不是整数：`DEVICE_COMMAND_INVALID`。
- 校验顺序固定为「脚本 → 会话 → displayId」：脚本合法性是输入契约，不该随副屏开关状态漂移（同一个坏脚本任何时候都必须报同一个码）。

已实测 / 未实测边界：

- **已实测（本机 JVM 单测，非真机）**：`VirtualScreenShellPolicy` 的前缀确定性、缺省/相等/不等/主屏 `0`/负数 displayId、脚本空/空白/超长/NUL/回车边界与错误码区分；Node 契约测试覆盖工具注册与注册顺序、参数形态（省略 `displayId` 时请求体只有 `script`）、`displayId` 直传、脚本校验与设备侧错误码直通。
- **此前已由用户真机实测**：`input -d <逻辑 displayId> tap …` 在这块副屏上确实生效（点开了 Edge 的「添加到主页」面板）。
- **未真机验证**：本轮**没有**在真机上跑过 `mobile_virtual_screen_shell` 的端到端流程。具体未验项：`am start --display "$DISPLAY_ID"` 在副屏上的落地效果、带前缀的多行脚本经 Base64 → `sh -s` 后的实际执行结果与退出码、副屏会话运行中该通道与 `mobile_virtual_screen_action` 同时使用时的相互影响、真实设备上输出被截断的时机。
- 本通道**不碰渲染链路**：预览与截图仍走应用自己的通道（`screencap -d` 只认 SurfaceFlinger 的 64 位 id，与这里使用的逻辑 displayId 不是同一个编号）。
