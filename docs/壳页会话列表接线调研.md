# 壳页会话列表接线调研

**本轮结论：不存在干净通道，因此没有实现代码。**

理由是机制性的，不是「暂时没做」：外壳页（Capacitor WebView）与 Harness 宿主之间**只有
一条桥**——原生插件 `MobileRuntime`，而这条桥上**没有任何会话相关端点**。要拿到会话列表，
必须**同时**改 `android/` 下的 Kotlin 与 `src/platform/` 的桥类型定义，这超出了本轮
「只改 `src/`、不动 Kotlin」的边界，因此按任务书第 3 条改为「只出调研与方案」。

本文记录事实与证据，免得日后重复排查；将来真要接线时，从「推荐路径」一节开始。

来源：真机反馈《图标留白与存储占用》第三节「会话列表恒为 0」。

---

## 1. 现状：外壳的会话列表是**本地空数组**

`src/components/SessionManager.tsx:18` 就是全部真相：

```ts
const INITIAL_SESSIONS: SessionEntry[] = []
```

- `useState(INITIAL_SESSIONS)` ⇒ 初始永远 0 条；
- `createSession()` 只往本地数组塞一条 `新会话 N` 然后调 `onOpenHarness()`（打开运行时 UI，
  真正的会话由宿主在里面建）；
- `removeSession(id)` 只在本地数组里 `filter` 掉，**不会删掉磁盘上任何会话**。

文件头注释写明这是有意为之：

> Harness 内部的会话由运行时管理，外壳不读取也不复制会话正文；这里仅提供轻量入口、筛选和
> 本地导航状态，避免把可能含敏感信息的对话内容写入浏览器存储。

**所以这不是 bug，是当时的取舍**：宁可列表空着，也不把对话正文复制进 Web 存储。
同理，`docs/真机缺陷与改进清单.md:577` 已经登记过「**会话列表**：尚未实现……
它才是将来要重新评估的那一处」（当时是在讨论要不要为它引虚拟化库）。

真正能看会话的地方是**运行时自己的 UI 抽屉**（WebView 里官方前端渲染），
不是外壳这一页。

---

## 2. 宿主侧**确实有**干净的元数据通道

好消息：宿主（HOST 侧）的 `ApiSessionList` 正好就是「只要元数据、不要正文」的投影。

包：`@deepseek-ai/dsh-api-session-controller`（0.1.7-rc.2）`lib/types/list.d.ts`，
类注释就是 **"Cold-safe Session list and search projection"**：

```ts
/**
 * Read every visible attached and persisted Session without activating an Agent.
 * @param signal - optional cancellation for persistence reads.
 * @returns visible Session summaries ordered by activity.
 */
list(signal?: AbortSignal): Promise<SessionSummary[]>
summaryFor(session: Session): SessionSummary
/** @returns authorized bounded Session search results. */
search(query: string, signal: AbortSignal): Promise<SessionSearchValue>
```

`SessionSummary` 的字段（同包 `lib/types/types.d.ts`）：

```ts
export interface SessionSummary {
  readonly agentAvailable: boolean
  readonly sessionId: SessionId
  readonly updatedAt: number
  readonly running: boolean
  readonly blank: boolean
  readonly parentSessionId?: SessionId
  readonly origin?: 'subagent'
  readonly cwd?: string
  readonly projections?: SessionProjectionHints
}
```

**关键：`list()` 拿不到标题。** 标题是另一条投影 —— `@deepseek-ai/dsh-session-title` 的
`titleProjectionDefinition` / `foldSessionTitle(events)` / `SessionTitleService`，
要通过 `SessionSummary.projections`（`SessionProjectionHints`）再读一次投影才有。
将来接线时这一步不能漏，否则列表只能显示 uuid 和时间。

**另一个要小心的**：同包的 `search()` 返回的是
`SessionSearchItem { sessionId, snippet }`，`snippet` 上限
`SESSION_SEARCH_SNIPPET_MAX_CODE_POINTS = 240` —— 那是**会话正文片段**。
「只拿标题/时间/数量」这条约束下，`search()` 应当**不要**接进外壳，
或者接了就必须只渲染、绝不落进 `localStorage`。

## 3. 为什么壳页**够不着**这条通道（逐条核实）

### 3.1 桥上没有会话端点

- 壳侧桥：`src/platform/types.ts` 的 `RuntimeBridge`（interface 起于 `:729`）。
  与会话沾边的只有**终端**的 `createTerminal/writeTerminal/resizeTerminal/closeTerminal`、
  `execDeviceCommand`（各自的 `sessionId` 是终端/命令通道 id，不是会话 id），
  以及 `getRuntimeSessionSnapshotState/createRuntimeSessionSnapshot/`
  `restoreRuntimeSessionSnapshot/deleteRuntimeSessionSnapshot`（`:940` 起）。
  **注意名字骗人**：这几个是「运行时**快照**」= 整目录备份/恢复（见
  `src/platform/types.ts:115` 的注释「快照只装访客里的**可变数据**（会话、设置、凭据、工作区）」），
  是灾难恢复用的整包，不是会话列表。
- 原生侧：`android/app/src/main/java/io/deepseekharness/mobile/MobileRuntimePlugin.kt`
  的全部 `@PluginMethod`（setAppLanguage / setAppTheme / managePlugins / getState /
  runtimeVersions / install / startHarness / openHarness / stopRuntime /
  createTerminal / execDeviceCommand / shareRuntimeWorkspace / mailboxDirectory /
  storageDirsState / listInstalledApplications / overlayBallState / …）
  **零会话端点**。全 `android/` 目录 grep `session\.list` / `listSessions` /
  `sessions-trash` / `mobile-nav`：**无命中**。

### 3.2 反馈里那条 `/api/mobile-nav.session.delete` **不在本仓库**

- `harness-web/` 的 `*.mjs` grep `session|mobile-nav`：无命中；
- `harness-web/dist/assets/index-5SrrfWpU.js`（0.2.0-rc.2 官方前端）
  grep `session.list` / `sessions/list` / `mobile-nav` / `session.delete`：**均无命中**。

反馈里提到的 `dsh-web-mobile 3.0.3` 是**运行时里另外装的插件**，不在本仓库源码内。
⇒ 本仓库既没有这条路由，也没有接它的位置；照抄那条实现无从下手。

### 3.3 就算直连 loopback 也走不通（四道门）

「让壳页直接 `fetch('http://127.0.0.1:<port>/…')`」这个想法在真机上过不了：

1. **端口是动态的**：`RuntimeModels.kt` 的 manifest `harnessPort` +
   `RuntimeSupervisor.ensurePortAvailable`，不是固定 3080。
   壳侧唯一能拿到的地址是 `RuntimeState.harnessUrl`（`src/platform/types.ts:80`），
   而它只在 `phase === 'running'` 时有值。
2. **令牌读不到**：入口 URL 带 `?token=`（`HarnessWebAuth.parseLaunchUrl`，
   `TOKEN = [A-Za-z0-9_-]{43}`），会话 cookie 是
   `dsh_mobile_token=…; Path=/; HttpOnly; SameSite=Strict`
   （`HarnessActivity.AUTH_TOKEN_COOKIE` / `HarnessPageSession.HarnessSessionCookie.authenticated()`）。
   **HttpOnly ⇒ 壳页 JS 读不到**，而且 cookie 是按 origin（127.0.0.1:port）存的，
   与壳页 `https://localhost` 不同源，不会自动带上。
3. **混合内容被拦**：`capacitor.config.ts` 的 `android:{allowMixedContent:false}`，
   壳页 origin 是 `https://localhost`（`server.androidScheme:'https'`），
   对 `http://127.0.0.1:<port>` 的请求属**混合内容**，platform 层直接拦掉。
   `network_security_config.xml` 允许 127.0.0.1/localhost 明文，是为了 Harness 自己的
   WebView，不改变这一条。
4. **宿主根本不提供 HTTP REST**：`@deepseek-ai/dsh-api-gateway` 的传输是
   **一条精确的 WebSocket 路由**（"Exact WebSocket route carrying every Typert Remote
   stream"，`url.protocol = https? 'wss:' : 'ws:'`），Typert Remote 协议自己带
   方法作用域与令牌。它既不是 REST，也没有给第三个 WebView 留注入令牌的口子。

### 3.4 还违反文件头那条安全约束吗？

**标题/时间/数量属于元数据，不违反** —— 那条约束针对的是「对话正文」。
但要守住两点：不要把 `search()` 的 `snippet`（正文片段）接进来；
标题投影本身也是从消息里折出来的文本（`fallbackSessionTitle` 取用户消息头部），
所以它应当**只在内存里渲染**，不落 `localStorage`。

## 4. 推荐路径（将来做的时候）

**一句话：加一个桥方法，由原生侧去问宿主，壳页只收元数据。**

### 4.1 要动的文件（跨了三层，所以本轮不做）

| 层 | 文件 | 改动 |
| --- | --- | --- |
| 原生 | `android/app/src/main/java/io/deepseekharness/mobile/MobileRuntimePlugin.kt` | 新增 `@PluginMethod sessionList`（以及可选的 `sessionDelete`），内部向宿主要列表 |
| 原生 | 同目录的宿主交互层（现有 `HarnessWebAuth` / 端口与令牌来源处） | 复用现有鉴权路径，**不要**新造明文通道 |
| 桥类型 | `src/platform/types.ts`（`RuntimeBridge`，`:729` 起） | 新增 `sessionList(): Promise<SessionMeta[]>` |
| 桥实现 | `src/platform/native.ts`（`registerPlugin<NativeRuntimePlugin>('MobileRuntime')`）+ `src/platform/browser.ts`（浏览器预览桩） | 各自实现；浏览器桩返回空列表 |
| 校验 | `src/platform/validation.ts` | 对返回的元数据做字段/长度校验（该文件已有 `harnessUrl` 等先例，`:431`） |
| 界面 | `src/components/SessionManager.tsx` | 用真实列表替换 `INITIAL_SESSIONS`，失败回空态 |

### 4.2 原生侧拿列表的可选实现

按侵入性从小到大：

1. **转调宿主的投影**（首选）：`ApiSessionList.list()` + 会话标题投影。
   需要原生与宿主之间已有/新增一条受鉴权的调用路径 —— 这是本方案的主要成本所在。
2. **直读会话目录自己做投影**：会话落盘在
   `sessions/<projectKey(cwd)>/session-<uuid>/session.v4.jsonl.zstd`（zstd，见反馈第三节）。
   只读**事件里的标题与时间**即可得到列表，不碰正文。缺点：口径要自己跟宿主保持一致
   （`applySessionListMetadata` / `truncateUnicodeCodePoints` 那套折叠规则），
   将来格式升版（`v4` → `v5`）会静默读错 —— **属于重复实现，不推荐**。

### 4.3 风险点（接线时必须一起处理）

- **隐私**：只回 `sessionId` / 标题 / `updatedAt` / `running`，**不回正文**；
  标题不写 `localStorage`；`search()` 的 snippet 不要接。
- **鉴权**：列表是「本机用户能看到的会话」，必须走与入口 URL 同一条鉴权，
  不能新开一条无鉴权 loopback 端点。
- **性能**：`list()` 是冷读取（要读 zstd 落盘文件）。会话上百时首屏会慢 ⇒
  界面上要有加载态，不要让「尚未加载」显示成「暂无会话」。
- **删除语义**：宿主/插件侧的删除是把会话目录移进 `<root>/.sessions-trash/`。
  外壳若要提供删除，必须是**同一个语义**（可恢复），并且删完要重新拉列表；
  「本地 filter 掉」那条现状代码绝不能当成删除来用。
- **失败兜底**：拿不到列表 ⇒ 回到现在的空态并给一句可读的提示，
  不要抛错、不要把外壳打死（本页是设置入口，崩了会拖垮整个 WebView）。
- **虚拟化**：`docs/真机缺陷与改进清单.md:577` 已经把「会话选择器落地」定为
  「重新评估要不要引虚拟化」的触发条件。接线时顺手按实测会话数量决定，
  别提前引依赖。
