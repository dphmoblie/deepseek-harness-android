# 运行时沙箱自检与权限修复

`sandbox_launcher=ok`、`sandbox_probe=PROBE_UNUSABLE` 表示启动器存在且有执行权限，但 Landlock 探测在当前环境中失败。可能是内核缺少支持，也可能是启动环境无法完成探测。不能仅凭这份结果断言是哪一种，更不能将单独的 `sandbox_exec` 或 `pty_sandbox` 失败当成所有沙箱后端均不可用。

“修复运行时权限”只补 `landlock-run`、`rg` 的执行位，并创建缺失的附件目录。它不能恢复缺失的程序，也不能增加内核能力。修复后自动重新自检，保留本次修复计数并以复检结果替换旧结果；复检失败会明确显示“自检未完成”。

## 沙箱内命令与沙箱内 PTY 失败怎么读

`sandbox_exec` 是把 `/bin/true` 真的放进启动器的授权根里执行一次；`pty_sandbox` 是把最简命令放进 PTY 再跑一遍。两者失败时的结论码含义不同：

- `EXEC_LAUNCHER_FAILED`：启动器自己在执行阶段失败 —— 授权根目录不存在、规则集写错，或根本没有拿到退出码（进程没起来、超时被杀）。
- `EXEC_LAUNCHER_DENIED`：受限执行**被内核拒绝**（启动器输出里有 `Permission denied`）。0.2.3 及更早版本在真机上就是这个形状：PRoot 会把受限进程的 `execve` 改写成对 `PROOT_LOADER` 的 `execve`，而那份 loader 落在授权根之外，Landlock 因此拒绝这次执行（退出码 125）。**0.2.4 起 loader 以实体文件落进运行时根内的 `root/.dsh-mobile/dsh-runner/loader`**（符号链接无效：Landlock 按路径指向的最终对象判定，必须是一份真文件）；升级后这一条若仍出现，说明拒绝的原因不再是 loader 位置，请导出诊断日志反馈。**注意不要把这一条与 loader 本身的可执行性混起来**：自检里的“修复运行时权限”补的是 `landlock-run` 与 `rg` 的执行位，补执行位对上面两条都没有作用；而运行时根里那份 loader 的执行位由应用在每次启动前自己确认（不足就补，补不动就回退私有副本并记 `RUNTIME_PHASE|phase=launcher`，见 `docs/诊断日志.md`）。
- `EXEC_COMMAND_FAILED`：启动器起来了，是被包裹的命令自己失败。

`--probe` 只建规则集、**不执行任何程序**，所以探测通过并不说明沙箱内命令能跑：「探测通过 + `sandbox_exec` 失败」这一组合正是两者分开报的原因。沙箱内 PTY 失败时同理 —— `pty_sandbox=PTY_EXIT_EARLY` 与 `sandbox_exec=EXEC_LAUNCHER_DENIED` 同时出现时，指向同一次执行被拒。

## 编译环境（C 工具链）

`c_compiler`、`make`、`python3` 三项是**能力项**，回答的是“这台设备现在能不能现场构建含原生模块的插件”，不是运行链路故障。三项在载荷里仍然只有 `{id, status, code}` 三个字段（受控枚举，由原生侧白名单复核），只会以 `warn` 出现，不参与整体失败判定，也没有修复入口：编译器不是应用能代装的东西。

- `CC_MISSING` / `MAKE_MISSING` / `PYTHON3_MISSING`：运行时里确实没有这个程序。C 编译器按 `cc` → `gcc` → `clang` 的顺序在运行时固定 bin 根与访客 `PATH` 里找（node-gyp 找 `make`/`python3` 走的也是同一个 PATH）。
- `CC_UNUSABLE` / `MAKE_UNUSABLE` / `PYTHON3_UNUSABLE`：程序找到了，但它自己以非 0 退出码作答。C 编译器要真做一次最小“编译 + 链接”（从标准输入喂一段带 `<stdio.h>`、并调用一次 libc 的源码，产物落在被检根下的可写目录并当场删除），因此只有版本串能打印、缺 binutils 或 C 库头文件的半装工具链会被如实判为不可用；另外两项只问一次 `--version`。
- `CC_PROBE_UNKNOWN` / `MAKE_PROBE_UNKNOWN` / `PYTHON3_PROBE_UNKNOWN`：探测没有拿到退出码 —— 进程没起来、超时被杀，或连可写的产物目录都没有。这一态按**不可用**呈现：探测不出来就不说它可用。

探测沿用既有预算：版本查询 2 秒、最小编译 4 秒，最坏新增约 10 秒，仍在单次自检 45 秒上限之内；不联网、不长时间编译、不改变运行时的任何文件。

三项只报能力，不报承诺。本应用不内置 C 编译器与 make（Python 3 由运行时自带），也不代为安装，缺少编译器时**不会假装插件能编译**。终端里能做什么是另一件事：运行时基于 `ubuntu-base-24.04`，`apt`/`dpkg` 在但没有包列表，访客内能否联网取包尚未在真机验证，因此界面只提示“可在运行时自带的 Ubuntu 终端里尝试安装 build-essential”，并明确写出这一前提尚未验证，不断言装完就能编译。

插件侧引用：安装流程在判断“要不要编译、能不能编译”时应引用同一组结论码（`CC_*`、`MAKE_*`，`PYTHON3_*` 是 node-gyp 的前提），把失败原因按上表如实转述；不得另外输出“已支持 gcc”这类结论。

## 宿主追加的四项设备事实（插件 / 无障碍 / 副屏 / WebView）

自检载荷现在是 **18 项 = 访客脚本 14 项（前 11 项链路 + 3 项编译能力）+ 宿主 4 项设备事实**。这四项与前面几节不同：**访客脚本 `android/app/src/main/assets/support/runtime-self-check.cjs` 一行未改**，它仍然只产出前 14 项（`scripts/runtime-self-check.test.mjs` 也仍按 14 项断言）；`plugins`、`accessibility`、`virtualscreen`、`webview` 由 Android 侧读取设备事实后追加，并走**同一套** id / 结论码白名单与状态规则（`RuntimeSelfCheckPolicy.sanitize`），载荷里仍然是 `{id, status, code}` 三个字段。老载荷（不带这四项）仍然合法。

事实来源（宿主只取值，判定在 `SelfCheckHostFacts` 里做，后者不依赖 Android API、可 JVM 单测）：

- `plugins`：`RuntimePluginManager.recoverySnapshot()` 的 `missing` 与 `failed` 计数（不重新扫盘；必须复用应用内那一个实例，计数是实例内状态）。
- `accessibility`：`DeepSeekAccessibilityService.current() != null`。
- `virtualscreen`：`Settings.canDrawOverlays(context)`（副屏画面用悬浮窗承载）。
- `webview`：`WebView.getCurrentWebViewPackage()`（null 即不可用；非 null 取其 `versionName`）。

每项的结论码与状态语义：

| 检查项 | 码 | 状态 | 含义 |
| --- | --- | --- | --- |
| `plugins` | `PLUGIN_LINK_MISSING` | `warn` | 有已启用的插件在运行时里缺少链接文件（可人工修） |
| `plugins` | `PLUGIN_LINK_FAILED` | `warn` | 最近一次插件修复没有成功，插件文件仍不可用 |
| `plugins` | `PLUGIN_PROBE_UNKNOWN` | `warn` | 这次没读到插件计数 |
| `accessibility` | `ACCESSIBILITY_NOT_CONNECTED` | `warn` | 无障碍服务未连接（可选功能，只影响应用自动化） |
| `accessibility` | `ACCESSIBILITY_PROBE_UNKNOWN` | `warn` | 这次没读到连接状态 |
| `virtualscreen` | `OVERLAY_PERMISSION_MISSING` | `warn` | 没有悬浮窗权限（可选功能，只影响副屏） |
| `virtualscreen` | `OVERLAY_PROBE_UNKNOWN` | `warn` | 这次没读到权限状态 |
| `webview` | `WEBVIEW_UNAVAILABLE` | `fail` | 系统 WebView 不可用 —— 界面本身靠它渲染 |
| `webview` | `WEBVIEW_PROBE_UNKNOWN` | `warn` | 这次没读到 WebView 信息 |

三点必须说清的状态语义：

- 只有 `WEBVIEW_UNAVAILABLE` 会报 `fail`；其余一律 `warn`，不参与整体失败判定。缺无障碍、没给悬浮窗权限、插件链接需要修，都不是运行时链路故障。
- `*_PROBE_UNKNOWN` 是「宿主这次没读到事实」，一律按 `warn` 呈现：既不用 `ok` 掩盖「没测到」，也不写成 `fail` 凭空造一个故障。插件那一项要求 `missing` 与 `failed` **两个计数都读到**才下结论，只读到一半同样按未知处理。
- 宿主四项**不使用 `skipped`**。`skipped` 的语义是「这一项没有可测的前提」（例如启动器缺失导致沙箱项无法测），而这四项的前提（插件管理器、系统服务、包管理器）始终存在，读不到属于探测失败，用 `*_PROBE_UNKNOWN` 如实报出。

版本字段：`webViewVersion` 与 `dshVersion` 同层，是**纯信息**而不是检查项（`ok` 项按契约不能带码）。宿主只回传过形态白名单的文本（与前端 `VERSION_TEXT_PATTERN` 同规则：`^[0-9A-Za-z][0-9A-Za-z._+-]{0,63}$`），不合形态一律回 null；前端 `validateSelfCheckReport` 用同一条白名单复核，形态不符即拒收整份载荷（与 `dshVersion` 保持一致）。界面在「dsh 版本」下方多一行「系统 WebView 版本」，读不到时显示占位符。

`repair` **不新增任何副作用**：宿主四项只读，`repair` 仍然只补 `landlock-run`、`rg` 的执行位并创建附件目录。插件链接的修复入口在「插件设置」页的「立即修复插件」，无障碍与悬浮窗权限只能在系统设置里授予，系统 WebView 只能由系统商店更新 —— 因此这些码都**不在** `SELF_CHECK_REPAIRABLE_CODES` 里，也不会让「修复运行时权限」按钮出现。

以下部分**本次未做真机验证**，只能由真机确认（不要在别处声称已验证）：

- 无障碍服务是否真的连上（需要用户在系统设置里手动开启服务）；
- 悬浮窗权限是否真实授予（`Settings.canDrawOverlays` 的返回值随系统与厂商 ROM 而异）；
- 系统 WebView 的真实版本号，以及 `getCurrentWebViewPackage()` 是否会被系统拒绝返回 null；
- 插件 `missing` / `failed` 计数在真实修复失败、真机删除保留区副本后是否按上表出现。

## 在不支持 Landlock 的设备上继续使用

在当前 Harness 会话的权限预设中选择 `danger-full-access`，或者直接在会话输入：

```text
/permission danger-full-access
```

随后重试命令，例如让 Harness 的 bash 工具执行 `pwd`。**该预设会关闭 dsh 文件系统沙箱和命令审批**，进程仍受 Android 应用权限约束；PRoot 不提供额外的内核隔离。应用不会因自检失败自动选择此模式。

“设置 → 运行与后台 → Harness 启动权限”可设置启动默认值，保存后会重启已运行的 Harness，正在执行的任务会中断。该值通过 `DSH_PERMISSION_MODE` 注入 `env -i` 后的访客环境。dsh `0.2.0-rc.2` 中的优先级为（换版后按新版源码复核过 `dsh-base/cordis.patch.yml` 的 `sandbox-policy.mode` / `approval.policy` 与 `dsh-permission-presets` 的解析顺序）：

1. 已有会话记录的权限保持不变，需要在该会话切换。
2. Harness 自身保存的 `permission.defaultPreset` 决定新会话默认值。
3. 没有保存默认值时，从应用注入的启动默认值推导权限。

因此仅重启不能保证改变旧会话。自检仍直接测试 Landlock，即使会话已关闭沙箱，相关检查仍可能失败；这不代表无沙箱会话的命令不能运行。

## 桥接契约

- 权限：只允许应用内部管理桥接调用现有的设置与自检接口。
- 参数：`harnessPermissionMode` 只接受 `workspace-write` 或 `danger-full-access`；省略更新保留原值。空值、非字符串和未知枚举拒绝。旧存储缺键或损坏时启动默认值回落至 `workspace-write`。
- 返回：设置与自检仅回传该枚举，自检中的值是检查时的启动默认值，不代表当前会话权限。不会返回命令输出、私有路径或凭据。

## 真机复测

1. 权限缺失时运行自检，点修复，确认自动复检更新结果；仍失败的 Landlock 项保留，修复按钮不会为此重复出现。
2. 在当前会话切到 `danger-full-access`，通过 Harness 的 bash 工具执行 `pwd`，确认无沙箱执行链路。
3. 保存应用启动默认值，确认运行中的 Harness 重启；分别验证全新会话、已设置 Harness 默认值的新会话和旧会话遵循上述优先级。
4. 切回 `workspace-write`，在当前会话也切回该预设；设备没有可用后端时应拒绝命令，不得静默回退。
5. 自检的裸 PTY 与沙箱内 PTY 分开判读：裸 PTY 通过、沙箱内失败时优先查沙箱；两者都失败时先查 PTY 和运行日志。
6. 编译环境三项按设备实际情况对照：没有编译器的设备上应显示“确实没有”或“探测没拿到判决”，给出安装提示但不出现修复按钮；装有工具链的设备上应为正常项。随后装一个含原生模块的插件，确认失败信息与自检结论一致（缺编译器时不得提示“可以编译”）。`apt` 能否在访客内联网取包仍属未验证项，需要在真机终端上单独确认后再改文案。
7. 宿主四项按设备实际情况对照：系统设置里关闭/开启无障碍服务，`accessibility` 应在 `ACCESSIBILITY_NOT_CONNECTED` 与正常之间切换；撤销悬浮窗权限后 `virtualscreen` 应报 `OVERLAY_PERMISSION_MISSING`，授予后恢复正常；在插件设置页删掉某个已启用插件的运行时链接后重跑自检，`plugins` 应报 `PLUGIN_LINK_MISSING` 而不是 `ok`；「dsh 版本」下方应显示系统 WebView 的真实版本号。任一项显示为 `*_PROBE_UNKNOWN` 时，说明宿主没取到事实，应连同日志反馈，不要把它读成“已通过”。
