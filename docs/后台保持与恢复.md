# 后台保持与恢复

本文说明「后台保持 Harness」的实现边界、可验证行为与已知限制。所有结论都以本仓库
当前实现为准，不构成任何保活承诺。

## 目标与非目标

**目标**：让本机 Harness 运行时在锁屏、返回桌面、划掉最近任务之后，仍有机会继续运行，
并在确实无法继续时给出可操作的「需要重新连接」提示。

**非目标**：

- 不承诺绝对不被 Android 或厂商系统杀死。前台服务只**提高**进程存活优先级。
- 不把 Shizuku 当作永久保活手段：设备 Shell 的实际权限取决于 Shizuku 启动模式，应用只用于授权与连接
  状态检测、连接恢复辅助和健康检查。
- 不持久化任何临时凭据。Harness 的 Basic Auth 密码只在进程内存中存活。
- 不新增宽泛 Shell 命令执行能力，前台服务不执行任何 Shell 命令。

## 组成

| 组件 | 位置 | 职责 |
| --- | --- | --- |
| `HarnessKeepAliveService` | `android/app/src/main/java/io/deepseekharness/mobile/HarnessKeepAliveService.kt` | 前台服务与常驻通知；只标记进程优先级，不执行命令、不持有凭据 |
| `RuntimeHost` | `.../runtime/RuntimeHost.kt` | 进程级运行时持有者；决定插件销毁/服务销毁时何时真正释放运行时 |
| `HarnessKeepAlivePolicy` | `.../runtime/HarnessKeepAlivePolicy.kt` | 纯决策逻辑（无 Android 依赖），可单元测试 |
| `RuntimeEventSink` | `.../runtime/RuntimeEventSink.kt` | 可替换的事件出口；插件销毁后事件被安全丢弃 |
| `RuntimeStore` | `.../runtime/RuntimeStore.kt` | 只保存运行意图、最近阶段与时间，绝不含凭据 |
| `ShizukuRuntime.healthCheck()` | `.../shizuku/ShizukuRuntime.kt` | 只读健康检查，不抛异常、不执行命令、不写日志 |

## 生命周期

```
用户开启「后台保持 Harness」并启动 Harness
        │
        ├─ 插件：controller.startHarness() 成功 → 阶段 running
        │        keepRuntimeInBackground && running == true
        │        → HarnessKeepAliveService.start() → 前台服务 + 常驻通知
        │
锁屏 / 返回桌面
        │
        └─ Activity 未销毁：运行时与前台服务都不受影响
        │
划掉最近任务
        │
        ├─ HarnessActivity.onDestroy() → 撤销一次性 Harness 会话凭据
        └─ MobileRuntimePlugin.handleOnDestroy()
                 ├─ 回收插件自有资源（线程池、发起中的设备命令）
                 └─ RuntimeHost.detachPluginSink(插件订阅者)
                          └─ 前台服务仍在负责、或仍有其他订阅者（新实例已接管）
                                   → 不 shutdown，Harness 继续运行
        │
重新打开应用 / 点常驻通知
        │
        ├─ 通知入口是 KeepAliveEntryActivity（全透明转发），不是 MainActivity
        └─ RuntimeHost.acquire() 复用同一 MobileRuntimeController 与同一会话凭据
```

### 什么时候才真正释放运行时

`RuntimeHost` 释放运行时必须同时满足两个条件
（`HarnessKeepAlivePolicy.shouldReleaseRuntimeOnPluginDetach()`）：

| 条件 | 只看前一个条件会怎样 |
| --- | --- |
| 前台服务不再负责运行时 | 划掉最近任务会立刻终结 Harness，后台保持失去意义 |
| 没有其他插件订阅者 | 「新实例已接管、旧实例才收尾」时会把新实例正在使用的运行时关掉 |

插件销毁（`MobileRuntimePlugin.handleOnDestroy()`）与前台服务销毁（`HarnessKeepAliveService.onDestroy()`）
都只移除自己那一个订阅者，只有最后一个持有者退出时才调用 `MobileRuntimeController.shutdown()`。

`RuntimeHost.takeControllerLocked()` 另外保证「先摘除控制器引用、再执行清理」：清理任何一步抛错
都不能留下**已关闭但仍被登记**的控制器。0.2.2 的真机诊断日志里出现过这种状态——设备桥仍是
`DEVICE_BRIDGE|result=reused`，而随后的每一次 `HARNESS_START` 都只返回 `RUNTIME_CLOSED`，
24 秒内重试三次都无法恢复；这种僵尸句柄只能靠重启进程清除。释放过程中若清理步骤真的抛错，
异常仍会上抛给插件销毁路径（诊断日志记为 `APP_DESTROY|result=failed`），但引用已经失效，
下一次 `acquire()` 会创建全新运行时，不会再卡在旧句柄上。

### 通知入口为什么不是 MainActivity

`MainActivity` 是 `launchMode="singleTask"`。任务栈为 `[MainActivity, HarnessActivity]` 时，
把通知直接指向它会在启动瞬间触发 clear-top，销毁正在显示的 `HarnessActivity`；
而 `HarnessActivity.onDestroy()` 会撤销一次性会话凭据，用户看到的就是
「对话界面闪一下就没了，再也回不去」。

因此通知指向 `KeepAliveEntryActivity`：全透明、无动画、不导出、不进最近任务，只做一次转发：

- 会话凭据仍有效 → 把已有的对话界面带回前台（同一任务栈，不重建任何 Activity）；
- 否则（进程被回收、用户已退出对话）→ 回到管理界面。

### 设备桥与设备命令为什么是进程级

保活生效时 Harness 进程仍在运行，而 Activity 会被销毁重建。设备桥必须与运行时同生命周期：

- **不能重建**：`RuntimeSupervisor.configureDeviceBridge` 在 Harness 运行时拒绝重新配置
  （`RUNTIME_BUSY`）。旧实现把桥挂在插件上，Activity 重建时重复配置会抛异常并让 `load()`
  失败 —— 而 `load()` 失败意味着 `MobileRuntime` 插件根本没注册，整个管理界面（含设置页）
  失去原生桥。
- **不能拆**：guest 侧注入的桥端口与 Bearer token 在 Harness 存活期间一直有效，
  提前拆桥会让容器内的 `dsh-device` 工具直接失效。

现在桥与设备命令由 `RuntimeHost` 以 `RuntimeScopedResource` 持有，仅在运行时真正释放时拆除；
`stopRuntime` 与 `reset` 只终结发起中的设备命令，不再拆桥。另外，`load()` 中设备桥的构建
被刻意包在 `try/catch` 里：它只服务设备 Shell，属可选能力，任何失败都不得升级为插件注册失败。

### 前台服务的启动顺序

`onStartCommand()` 必须先无条件调用 `startForeground()`，再判断是否立即结束。
Android 12+ 对 `startForegroundService()` 启动的服务有 5 秒硬性要求，超时未进入前台会抛
`ForegroundServiceDidNotStartInTimeException` 并终结整个进程；「先判断、再进入前台」的写法
存在这段窗口。

显式停止路径：

- `stopRuntime`：先 `stopService` 撤销前台服务，再停止 Harness 与终端。
- `reset`：确认文本通过后立即撤销前台服务，随后清理运行时覆盖层。
- 关闭「后台保持 Harness」并保存：同步撤销前台服务。

## 进程被系统回收后的行为

应用进程被强制停止或回收后：

1. PRoot→node 的 Harness 子进程**可能**仍然存活并继续占用回环端口，pid 文件也会保留。
2. 本进程内存中的临时 Basic Auth 凭据**已经消失**，旧会话无法恢复。
3. 因此界面不把状态伪装成「已恢复」：

   - `RuntimeStatus` 构造时只依据已安装清单给出 `ready` / `not-installed`，不会给出 `running`。
   - `RuntimeSupervisor.hasResidualHarness()` 只读检查残留进程（pid 文件 + `/proc/<pid>/cmdline`
     必须匹配受信任运行器路径），不发送信号。
   - `HarnessKeepAlivePolicy.requiresReconnect()` 在「本进程未持有正在运行的 Harness」且
     「检测到残留进程」或「上次意图为运行中」时返回 true。
   - 前台服务在没有可管理运行时时立即结束，不留空转通知。
4. 用户点击「重新连接」后走常规 `startHarness()`：先回收残留进程树，再以全新凭据启动新会话。

## 通知与权限

- 通知渠道：`harness_keep_alive`，重要级别 `IMPORTANCE_LOW`，不显示角标、不振动、无声音。
- 通知文案固定为资源字符串，**不含** URL、端口、密码、API Key、终端内容、会话标识或版本号。
- 清单声明 `FOREGROUND_SERVICE`、`FOREGROUND_SERVICE_SPECIAL_USE`（targetSdk 35 的前台服务
  类型要求，并在 `<property>` 中给出用途说明）与 `POST_NOTIFICATIONS`。
- Android 13（API 33）及以上：界面上「后台保持 Harness」开关会触发一次通知权限申请；
  被拒绝时前台服务照常运行，只是不显示常驻通知（系统任务管理器仍可看到该应用在运行）。
  界面的「通知权限」一行会显示 `已授予` / `未授予` / `系统不支持`。
- Android 12 及以下：`notificationPermission` 恒为 `unsupported`，不需要该权限。

## Shizuku 的边界

- 只做三件事：读取 binder 是否可用、读取用户是否授权、读取 UserService 是否存活。
- `ShizukuRuntime.healthCheck()` 不抛异常、不执行命令、不写日志；未安装、未授权或断开时
  返回不可用状态，界面显示「设备 Shell 辅助：不可用」，其余功能不受影响。
- 设备 Shell 的既有安全模型不变：宿主桥只接受固定命令类型，令牌不持久化、不写日志。
- Shizuku **不参与**后台保持决策：关闭 Shizuku 不会停止 Harness，开启 Shizuku 也不会
  提升保活能力。

## 厂商后台策略（自启动 / 后台运行 / 省电 / 任务清理）

前台服务被系统拒绝后，代码侧只剩一件事可做：把用户送到能改策略的地方。仓库里**没有**
「这台设备是哪个 ROM」的判断——`KeepAliveState` 不带厂商字段，`openApplicationSettings`
只依赖 `Settings.ACTION_APPLICATION_DETAILS_SETTINGS`——所以指引文案按「品牌中立 + 点名
最普及的几家 ROM」写，不按机型分支，也不假装一次点击能直达具体开关。

### 四类限制的分工

所有 ROM 的限制都能归到这四档。它们的触发时机不同，所以「症状」也不同——排查时先看症状
对上哪一档，再去改对应的开关：

| 限制类型 | 触发时机 | 各家叫法 | 本应用能观察到的现象 |
| --- | --- | --- | --- |
| 自启动拦截 | 开机 / 首次拉起时拒绝起服务 | 自启动、允许自启动、Auto Launch | 开「后台保持」后前台服务立刻起不来（`foregroundStartError`） |
| 后台运行限制 | 进程在后台超过 ROM 的宽限期即被回收 | 省电策略、耗电管理、后台高耗电、后台活动、后台使用限制 | 服务起过，锁屏或切后台一段时间后被停（`lastPhase` 停在运行态、服务不再存活） |
| 电池优化（Doze） | 灭屏久置进入 Doze，网络与唤醒被掐 | 电池优化、耗电异常优化、后台使用限制 | 服务还在，但连接断开 / 请求超时，亮屏后恢复 |
| 最近任务清理 | 用户一键清理或上滑划掉卡片 | 锁定、加锁、保持打开 | 无错误日志，划掉卡片后进程直接消失 |

四类里只有第一、二类会让「开开关就报错」；第三类表现为断连；第四类表现为被用户或系统
清理。指引弹窗只在**开启后服务没能起来的那个时刻**触发一次（`background-blocked`，见
`src/App.tsx` 里 `recheckForegroundServiceAfterSettle` 的宽限期复核），命中的多半是第一类，
也可能是第二类里「刚起来就被回收」的情况——原生只下发 `foreground_declined` /
`start_disallowed` 这类受控令牌，分不出是哪一档，所以弹窗把三档一起列出来让用户逐项检查。
服务先跑起来、之后才被停（第二类后半段）或断开（第三类），没有弹窗，只有设置页的状态行；
第四类连日志都不留。

- **HarmonyOS 5 及以上是纯血鸿蒙，不运行 APK**，本应用装不上，所以华为一栏只覆盖

## 已知限制

1. **无法对抗强制停止**：用户在系统设置里「强行停止」应用后，进程、前台服务与 Harness
   子进程都会被结束；此时必须重新打开应用并重新连接。
2. **厂商后台策略**：部分 ROM 会在锁屏后冻结后台、清理前台服务或限制自启动；本应用不做
   也无法做跨厂商的规避，只能给出各家入口让用户手动改（见上一节的四类限制与厂商矩阵）。
   界面不做机型判断，也不承诺跳转能直达具体开关。
3. **前台服务类型**：使用 `specialUse`，需要在应用商店上架时提供用途说明；本仓库不自动发布。
4. **通知权限被拒绝**：Android 13+ 不显示常驻通知，用户对「正在后台运行」的感知下降，
   但服务与运行时不依赖该权限——这是 `HarnessKeepAliveService.startForegroundCompat()` 的
   既定行为，指引文案也按「建议开启」而非「必须有」来写。
5. **本地会话凭据不可恢复**：这是设计取舍——凭据只存在内存中，进程结束即失效。
6. **设备侧行为需真机验收**：锁屏/返回桌面/划掉最近任务受 ROM 影响，必须按
   `docs/mobile-acceptance-checklist.md` 在真机上逐项确认；单元测试只覆盖可脱离设备验证的决策逻辑。

## 悬浮球

悬浮球是**独立于后台保持**的能力：设置里是两个开关，可以只开其中一个。

- 需要「显示在其他应用之上」（`SYSTEM_ALERT_WINDOW`）权限。这是特殊权限，不会弹
  运行时对话框，只能由用户到系统设置手动开启；未授权时设置页显示状态与跳转入口，
  开关不可用。
- 短按展开二级球快捷菜单（对话小窗、目标副屏、回到应用、隐藏球、关闭无障碍），长按直接展开 Harness AI 对话小窗（可拖动、可调整大小、可切到全屏），拖动后吸附到
  最近一侧并记住位置。二级球点击任一项或点主球本身即收起。
- 「回到应用」是条件行为：对话存活时经 `KeepAliveEntryActivity` 把应用带回前台，不
  销毁对话；对话不在时才直接打开管理界面。不能一律直接启动 `MainActivity`：它是
  `singleTask`，启动会 clear-top 销毁后台的 `HarnessActivity` 并撤销一次性会话凭据，
  也没有启动标志能绕开（详见 `docs/悬浮球与内容分享.md` 第三章）。
- 屏幕旋转后会把球夹回新的可视范围：球的坐标是绝对像素值，而它是 `FLAG_NOT_FOCUSABLE`
  的 overlay 窗口——一旦落到屏幕外，用户既看不到也点不到，无法靠拖动自救。
- 由独立前台服务 `OverlayBallService` 承载，通知渠道 `harness_overlay_ball`，重要级别
  `IMPORTANCE_LOW`；通知文案固定，不含 URL、端口、凭据或会话内容。
- **不承诺常驻**：与后台保持同样的限制——Android 与厂商系统的内存回收、强制停止、
  电池与后台策略都可以随时结束本进程，球会随进程一起消失。这与后台保持的既有表述
  一致，不要把悬浮球当作可靠的常驻入口。
- 服务不执行 Shell、不连接 Shizuku，也不参与运行时归属管理。小窗仅在 Harness 已运行时读取进程内一次性会话凭据；未打开完整对话页时，小窗关闭即清除同源 Cookie。
- 设置开关与系统权限分开判断：开关记着开启、系统权限却已被撤销时，设置页如实显示
  「系统权限已关闭」，不把状态伪装成正常。

真机验收步骤见 `docs/mobile-acceptance-checklist.md` 的「悬浮球」小节。
