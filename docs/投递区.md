# 外置投递区（mailbox）

投递区是**手机侧与 PRoot 访客之间的批量搬运通道**：用户把 tar 放进 inbox，App 一键解包到工作区；
App 一键把工作区打成 tar 放进 outbox，用户在手机侧取走。

它**不是工作区**，也不承担保留语义。设计前提与真机实测结论见
`docs/真机缺陷与改进清单.md` §四；本轮落地的代码口径见同文件 §4.7。

## 1. 路径

| 用途 | 路径 |
|---|---|
| 用户放入（宿主，用户可见） | `/storage/emulated/0/Documents/DSH/inbox` |
| 产物取出（宿主，用户可见） | `/storage/emulated/0/Documents/DSH/outbox` |
| 访客内挂载点 | `/mnt/inbox`、`/mnt/outbox` |
| 导入落点（工作区内） | `<工作区>/mailbox-import/` |
| 导出产物（outbox 内，固定名） | `dsh-workspace.tar`、`dsh-workspace.manifest.json`、`dsh-workspace.tar.sha256` |

`DSH` 及其两个子目录由 App 创建。绑定源使用 `/storage/emulated/0` 这个**真实路径**，
不是 `/sdcard`（它是符号链接，不能作为 PRoot 的绑定源）。

**绑定只在目录确实可访问时才建立**：已授予「所有文件访问」，且 `DSH/{inbox,outbox}` 都是真实目录
（不是符号链接）、可读可写可进入、写探测通过时，才向 PRoot 追加这两个 `-b` 绑定；任何一条不满足
就**一个都不追加**。原因是绑定一个不存在的宿主路径会让 PRoot 直接起不来——那比「投递区不可用」
严重得多。若 PRoot 仍因为这两个绑定失败，`profileFallbacks` 会把它们（连同 `/sdcard`）一起撤掉重试，
可选能力不拖垮会话启动。

## 2. 权限

投递区需要 **T2「所有文件访问」**（`MANAGE_EXTERNAL_STORAGE`）。这是特殊权限：不会弹运行时对话框，
只能由用户在系统设置里手动开启，因此界面提供「去开启「所有文件访问」」入口，回到应用后自动重读状态。

档位与 `docs/真机缺陷与改进清单.md` §5.1 的 T0–T3 口径一致：

| 状态 | 档位 | 含义 | 界面 |
|---|---|---|---|
| `available` | T2 | 已授权且目录真实可读写 | 两个按钮可点 |
| `needsPermission` | T0 | 系统支持但尚未授予 | 按钮禁用 + 授权入口 |
| `unsupported` | T0 | 系统不存在这一档（Android 11 以下） | 按钮禁用 + 说明改用控制台上传，**不给入口** |
| `unwritable` | T0 | 已授权但目录仍不可写 | 按钮禁用 + 如实说明 |

**没有权限时不会静默降级到别的目录**：投递区要么是上面那三个目录，要么就是不可用。
媒体读取权限（T1）**不解锁投递区**，投递区只看 T2。

## 3. 导入

1. 在 inbox 里放**一个** tar（可以是 App 自己导出的，也可以是访客内 `tar -cf` 造出来的）。
2. 在「运行与后台 → 投递区」点「导入到工作区」。
3. 内容落到 `<工作区>/mailbox-import/`；该目录被**整体替换**，不是合并。

输入选择是**确定性**的：优先取名为 `dsh-workspace.tar` 的文件；否则要求 inbox 里恰好只有一个
`.tar`；一个都没有、或出现多个而无法确定时明确报错。**散文件永远不会被导入**，只计入结果里的
「被忽略的散文件数」。

同名的 `*.manifest.json`（或 inbox 根下的 `manifest.json`）与 `*.sha256` 存在时会逐条校验：
归档自身的 sha256、条目数、总字节数，以及每个条目的类型、字节数与内容 sha256。**任何一项不符
即整单拒绝**，不做部分导入。

### 限额

| 项 | 上限 |
|---|---|
| 条目数（含目录与链接） | 20000 |
| 内容总字节 | 512 MiB |
| 单个常规文件 | 256 MiB |
| 归档自身 | 512 MiB |
| 条目相对路径 | 240 字符 / 32 层 / 单段 255 字符 |

超限一律明确报错，不截断、不部分导入。

### 安全判定

- **拒绝**绝对路径条目、`..`、`.` 分段、空段（`a//b`）、反斜杠、NUL/CR/LF、超长与超深路径；
- **拒绝**重复条目；
- 符号链接**一律拒绝绝对目标**（例如 `/root/.dsh`）。这一条比 rootfs 解压更严：rootfs 会把绝对
  符号链接改写成暂存根内的相对链接，而用户投来的 tar 没有保留绝对链接的正当需求，绝对链接正是把
  私有区钓出落点的手段；
- 相对符号链接目标按 POSIX 语义（相对链接所在目录）规范化后，必须仍在 `mailbox-import/` 内；
- 硬链接条目按**内容复制**落地（本机 `link(2)` 被拒，见 P0-1），不做 `link` 调用；
- FIFO、字符/块设备、套接字、稀疏文件一律拒绝；
- 解包顺序固定为「目录 → 常规文件 → 硬链接 → 符号链接 → 目录权限」，写入期不存在任何链接，
  因此链接不可能把写操作引出落点。

### 幂等与失败语义

- 解包先落到应用私有暂存目录，全部成功后才整体改名替换 `mailbox-import/`：
  **重复导入不会累积出第二份条目**，失败时落点保持原样（旧内容先改名到暂存父目录，新内容就位后
  才删除旧内容；改名失败会把旧内容放回原位）。
- 校验（路径、链接、限额、manifest）全部发生在写第一个字节**之前**，所以被拒绝的导入在访客私有区
  里不产生任何改动。

## 4. 导出

1. 在「运行与后台 → 投递区」点「导出工作区」。
2. outbox 里出现三个固定名文件：

```
dsh-workspace.tar              归档本体（未压缩的 tar）
dsh-workspace.manifest.json    清单
dsh-workspace.tar.sha256       "<sha256>  dsh-workspace.tar"
```

导出的是**整个工作区**；指定子目录的能力已实现（平台层 `exportMailbox(subdirectory)`），本轮界面
只提供整个工作区这一个入口。三个文件先各自写临时文件、全部成功后才逐个改名，因此中途失败只会留下
临时文件（会被清理），不会留下半个产物。

写完之后还有一道**导出自证**：把刚写出的归档重新读一遍，用同一份 manifest 逐条比对（条目数、每条
字节数与 sha256、符号链接目标、tar 自身摘要）。工作区在「扫描」与「写盘」之间被改动时（例如 Agent
正在写文件）这一步会失败并丢弃临时产物，而不是留下一个 manifest 与 tar 不符的产物让导入端去拒。

条目名按字典序排序，权限位、uid/gid、时间戳显式给定，因此**同一棵未改动的工作区连续导出两次得到
相同的 sha256**。重复导出只覆盖同一组固定文件名，不会在 outbox 里堆出多份。

### manifest 形状

```json
{
  "format": "dsh-mailbox-export/1",
  "subdirectory": null,
  "entryCount": 2,
  "totalBytes": 42,
  "tarName": "dsh-workspace.tar",
  "tarBytes": 10240,
  "tarSha256": "…64 位小写十六进制…",
  "skipped": { "linksOutside": 0, "special": 0 },
  "entries": [
    { "path": "src", "type": "directory", "bytes": 0 },
    { "path": "src/main.txt", "type": "file", "bytes": 42, "sha256": "…" }
  ]
}
```

符号链接条目另含 `target`（落点内的相对目标）。**manifest 里只允许相对路径**：不含绝对路径、
不含宿主路径、不含私有区路径。

导出侧还会跳过两类条目并计数（写进 manifest 的 `skipped`，也回报给界面）：目标越出导出起点的
符号链接（绝对目标与指向起点的外部），以及无法用 tar 表达的类型（FIFO、设备节点、套接字）。
跳过的原因是不让产物里出现私有区路径。

## 5. 边界与已知约束

1. **投递区不能用 dsh 的 `write` 工具写**（实测 EACCES，与 P0-1 同根因）。这是**预期行为**，
   也是「投递区不是工作区」的判据：搬运只能走 App 侧按钮或访客内的 `bash` / 终端，
   不要试图「修好」它。
2. **投递区不在运行时保留白名单内**（`RuntimePreservePolicy`）。它在应用私有存储之外，运行时更新
   不会碰它，因此不需要进白名单；inbox / outbox 里的文件也不受运行时更新影响。
3. **工作区仍在应用私有目录**，没有被搬到公共存储；投递区只承担「可访问性」，不改变工作区的
   私有性与 POSIX 语义。
4. **符号链接的落盘**依赖设备允许 App 在应用私有存储内创建链接。部分 ROM 的 SELinux 策略会拒绝，
   此时导入含符号链接的条目会以 `MAILBOX_LINK_UNSUPPORTED` 失败并回滚，**不降级成复制**——
   降级会让「符号链接仍是链接」这条验收判据失真。
5. 「分享文件进来」的老入口（`MainActivity` 接收 `ACTION_VIEW/SEND/SEND_MULTIPLE` → 复制到
   `root/1/inbox`）**保持不变**，与投递区并存：前者是系统分享面板的一次性入口，后者是用户可见的
   双向目录。
6. **不会自动搬运**：导入与导出都必须由用户点击界面上的按钮触发。没有任何后台/自动路径。
