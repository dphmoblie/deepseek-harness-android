# 设备桥的信任边界

本文记录 `mobile_device_*` 工具链路上的一个**设计层面**结论，来源是真机排查报告
《设备工具在真机上全部不可用》的附录。

## 事实

1. `DeviceBridgeServer` 用 Bearer token 鉴权，token 由 App 每次启动生成后投递给访客。
   投递方式已随 P0-6 修复改变：**不再是进程环境变量，也不再是 argv 元素**，
   而是访客内的一份 0600 环境文件（详见下文「凭据从 argv 迁出」一节）；
2. 插件对 `mobile_device_tap` / `mobile_device_input_text` 设有用户审批
   （`plugins/dsh-mobile-shizuku/lib/index.js` 的 `ctx.on('tools/pre-execute', …)`）。
3. **但同一 uid 的访客代码可以直接读到宿主的进程环境**：

   ```sh
   tr '\0' '\n' < /proc/<harness_pid>/environ | grep DSH_DEVICE_BRIDGE
   ```

   拿到 token 后直接 `POST http://127.0.0.1:<port>/device-command`，
   **完全不经过工具层，因而不触发任何审批**。

## 结论（比报告里的表述更强）

**在 PRoot 单 uid 模型下，审批门不是安全边界，只是协作边界。**

理由是机制性的、不是实现缺陷：访客里的所有进程（插件的 host half、模型调用的 `bash` 工具、
任何被安装的第三方插件）**都是同一个 uid**。因此：

- `/proc/<pid>/environ` 对它们彼此可读；
- 任何**投递进访客的**秘密（环境变量、文件、Unix socket 路径、一次性票据）同样可读。

所以「改成按请求签发一次性票据」**不能解决这个问题** —— 票据本身也要投递进访客，
同样会被同 uid 的代码读到。把桥从 loopback HTTP 换成 App 内 IPC 也一样，只要访客代码
能发起那次 IPC 调用。

**尤其要注意**：这条绕过对**模型自己**同样成立。也就是说，用户为 `tap` / `input_text`
点下的「允许」，可以被同一会话里的 `bash` 工具绕过。审批门挡得住的是「误操作」，
挡不住「有意绕过」。

## 处置决定（已确认）

**仅记录事实，改造当前不做。** 用户明确选择「只写明」。

不做改造的理由（记录在案，免得日后重复讨论）：

- 任何**投递进访客的**秘密都无法被保护（同 uid 互相可读），所以「换更好的令牌」
  「改成一次性票据」「换成 App 内 IPC」都不能解决问题 —— 那是**机制性**的，不是实现缺陷；
- 真正能建起的门只有一道：**把「同不同意」的判断挪到 App 侧、由用户本人确认**。
  访客可以「请求」，但无法「自行批准」。这需要新增 App 侧的确认队列与界面，
  并且会让每次点击/输入都多一次人工确认 —— **属于产品取舍**，当前不采用。

## 仍然生效的两条约束

即使不做改造，下面两条仍然必须遵守：

1. **不要扩大设备桥的命令面。** 桥只暴露截图 / UI dump / 点击 / 文本输入四类命令，
   并有白名单校验（见 `DeviceCommandRunner` 的 `DeviceCommand`）。保持它最小，
   不要为便利新增命令 —— 命令面越大，可被静默滥用的面越大。
2. **不要把审批门宣传成安全保障。** 它是协作边界（挡误操作），不是安全边界（挡不住有意绕过）。
   新增文案、文档与新功能说明都应按此口径表述，不要写成「防止未授权操作」这类断言。

## 凭据从 argv 迁出（P0-6 修复）

### 缺陷

修复前，App 把设备桥令牌、移动端认证令牌与各供应商的 API Key **逐个作为 `proot` 的
argv 元素**注入：`RuntimeCommand.prootArgv` 在 `/usr/bin/env -i` 之后追加
`<PROVIDER>_API_KEY=<明文>`、`DSH_DEVICE_BRIDGE_TOKEN=<明文>`、`DSH_MOBILE_AUTH_TOKEN=<明文>`。

后果比上面记录的环境变量风险**更外露**，因为它绕过了「读 `/proc/<pid>/environ`」这一步：

- 任何同 uid 的访客进程、以及**普通 `ps -eo pid,args`** 都能读到取值（真机实测
  `ps -eo pid,args | grep -c DEEPSEEK_API_KEY` = **3**）；
- 取值会被 **bugreport / ANR / 厂商诊断**采集（它们抓的就是命令行）；
- 取值在整个进程生命周期驻留命令行，而不是只在启动瞬间。

### 修复方式（两条路，都不让取值进 argv）

1. **模型凭据走 dsh 自己的凭据文档。** `~/.dsh/.credentials.yaml`（访客内
   `/root/.dsh/.credentials.yaml`）是 pinned dsh 的
   `@deepseek-ai/dsh-credentials-local` 的托管文档，官方前端「模型页」写的正是它，
   它已经在 `RuntimePreservePolicy` 的保留白名单里。该 provider 的分层是

   ```text
   继承的进程环境（只读，优先）
   > $DSH_HOME/.credentials.yaml（provider 管理的可写文档）
   > <调用目录>/.env
   > $DSH_HOME/.env
   ```

   所以**只要不设同名环境变量**，dsh 就从这个文件解析凭据。App 侧由原生代码以
   **0600 + 目录 0700 + 临时文件 fsync 后 rename** 的方式并写该文档的 `refs` 段：
   只增不删，`records`（OAuth 授权记录）与全部注释、格式逐行保留，写盘前用自己的解析器
   重新解析比对（解析不出预期内容就放弃写入）。权限必须在 rename **之前**设好 ——
   dsh 的 `assertOwnerOnly` 会拒绝任何带 group/other 位的凭据文档并让插件激活失败。
   这条路径顺带修掉一个既有症状：环境层存在时 dsh 把该引用判为**只读**，
   模型页对同一把 key 的保存会直接失败。

2. **每次启动生成的临时令牌**（`DSH_MOBILE_AUTH_TOKEN`、`DSH_DEVICE_BRIDGE_TOKEN`）
   不能进那份跨升级保留的长期文档。它们写进访客内的 0600 环境文件
   `/root/.dsh-mobile/runtime-secrets.env`（宿主 `currentRoot/root/.dsh-mobile/`），
   argv 里只留下**这一个路径**；入口由一层固定的 `sh -c` 包装在 `exec` dsh 之前
   `set -a; . <路径>` 载入。包装脚本本身是常量（无取值、无路径、无赋值形态）。

凭据文档不可安全编辑时（形态陌生、目录或文件不可信、写入失败），模型凭据**回落**到同一个
环境文件：功能不变、argv 形态完全相同。回落是刻意的 —— 为了命令行清洁让 Harness 起不来是本末倒置。

### 残留边界（如实记录）

- **「同 uid 的访客进程仍能读到凭据」这一根本约束没有消失。** 单 uid 模型下访客里的所有进程
  彼此不可隔离：环境文件是 0600 且属主就是它们，`/proc/<pid>/environ` 也依旧可读。
  这次修复减少的是**暴露面**，不是消除可达性 —— 不再暴露给 `ps`、不再进 bugreport / ANR 采集、
  不再驻留命令行。上面「结论」一节的全部推论（审批门是协作边界而非安全边界）依然成立。
- **临时令牌确实会短暂落盘。** 位置、权限与清理时机：
  - 路径 `currentRoot/root/.dsh-mobile/runtime-secrets.env`，位于应用私有目录（rootfs 内），
    随运行时升级换代一起消失；
  - 文件 0600、目录 0700，原子替换写入；
  - 每次启动整份重写；停止运行环境（`RuntimeSupervisor.clearHarnessState`）时删除；
    某次启动没有秘密要投递时当场删除。
  - 取舍：**落盘（0600、应用私有、随停即删）比出现在 argv 风险更低。** argv 是全局可见的
    （`ps`/bugreport 都能读到，且同 uid 之外也可读），而这份文件只有同 uid 的访客代码能读 ——
    而那正是「根本约束」里已经承认无法防住的那一类主体。换句话说，落盘没有引入**新的**读者，
    只是把本来就防不住的读者换了个入口，同时把**不需要特殊权限就能看到**的全局暴露收掉了。
  - 残留风险：应用进程被系统强杀时删除动作不会执行，文件会留到下次启动被整份覆盖。
    由于两个令牌每次启动重新生成，旧文件里的取值对新一次运行没有任何作用。
- **模型凭据落盘在 `~/.dsh/.credentials.yaml`。** 这不是新增暴露：该文件本来就是 dsh
  存储模型 key 的地方（模型页写入同一份）。修复后 App 侧写入的是**同一份**用户数据，
  没有引入第二处真源。
- **模型凭据不再进入访客进程环境。** 这是一处刻意的行为变化：修复前
  `DEEPSEEK_API_KEY` 等会出现在 dsh 及其子 shell 的环境里，现在只存在于 dsh 自己的凭据文档中
  （dsh 通过凭据 seam 按请求解析）。也就是说，访客 shell 里 `echo $DEEPSEEK_API_KEY` 不再有输出。
  这正是「凭据不进进程环境」的直接含义；需要 shell 环境变量的场景仍可回落到环境文件路径
  （凭据文档不可用时自动走那条路）。
- **跨进程写锁没有参与。** dsh 自己的写入走 `withFileLock` + `writeFileAtomic`；App 侧是
  原子替换但**不取那把锁**。App 只在启动前写入（此时 dsh 尚未运行，旧实例已停止），
  竞争窗口实际不存在；但若日后把写入挪到运行中，必须一并处理这把锁。

## 供日后选择的两个方案（已评估，未实施）

| 方案 | 默认模式（workspace-write） | 完全权限（danger-full-access） | 成本 |
| --- | --- | --- | --- |
| ① 令牌按模式注入 | 设备工具**不可用**，绕过路径不存在 | 设备工具可用，不逐步确认 | 小：需在 App 增加「完全权限」开关并据此决定是否注入 |
| ② App 侧确认框 | 设备工具**可用**，但点击/输入每次由 App 弹确认（访客伪造不了） | 设备工具可用，不逐步确认 | 大：需在 App 实现待确认队列与界面 |

注意：**我们 App 目前从未设置 `DSH_PERMISSION_MODE`**（`RuntimeCommand.prootArgv` 使用的是
一份固定环境清单），访客因此一直取默认值 `workspace-write`。方案 ① 需要先补上这个开关。
