# 审查报告：Shizuku 链路与安全链路 + UI 自动化设计 + 荣耀 16KB 验证清单

> 日期：2026-08-16 ｜ 审查对象：本仓库 main（93693a4）｜ 审查人：DSH 会话（对照 legacy-dsh-mobile-fork 桥 v2 设计）
> 范围：android/ 的 Shizuku 链路、运行时安全链路、scripts/mobile-auth-preload.cjs、HarnessActivity

## 1. 总体结论

整体工程质量明显高于旧 dsh-mobile-apk fork：manifest 双字段 pin、rootfs 全链路校验、解包防护、
循环口 127.0.0.1 + 恒定时间 Basic 认证、审计不落敏感数据——ARCHITECTURE.md 的声明逐条在代码中核实属实。
发现 1 个严重问题（Shizuku 用户服务未在 manifest 声明，设备 Shell 大概率无法绑定）与若干中低风险项。

## 2. Shizuku 链路

### 2.1 已核实的设计优点

- 权限模型正确：用户服务由 Shizuku 服务端以 shell 特权启动（UserService 路线，shizuku-api 13.1.5，
  api+provider 双依赖，AAR 自动合并 ShizukuProvider 以开启多进程支持）；
- 注入面最小：DeviceShellUserService 固定 execve(/system/bin/sh)，argv/env 全部常量
  （HOME/PATH/TMPDIR=/data/local/tmp，TERM=xterm-256color，LANG=C.UTF-8）；AIDL 面只有
  createSession/write/resize/close/closeAll/destroy——调用方不能选可执行文件、不能加参数；
- 会话门控：sessionId 为服务端生成 UUID，两端均以 ^[a-f0-9-]{36}$ 校验；写/改/关只接受客户端集合中
  存在的会话；输入 ≤ 32KB（两端双重校验）；输出块 ≤ 32KB（回调侧再校验）；
- 生命周期：TERM→2s 后 KILL 升级、linkToDeath、readLoop 异常路径全清理 fd 并回传退出码（0-255 钳制）、
  destroy 延迟 3s 退出服务进程、unbind 超时 2s 兜底；
- 原生层：forkpty + FD_CLOEXEC、EINTR 重试、参数/环境/IO/尺寸限额、execve 失败显式报错。

### 2.2 严重：DeviceShellUserService 未在 AndroidManifest 声明

- 证据：全仓库（android/ 下所有 manifest 变体）无任何 <service> 条目；无 BIND_USER_SERVICE intent-filter；
  无 moe.shizuku.manager.permission.API_V23 的服务声明。
- 影响：Shizuku 官方 13.1.5 用户服务规范要求 manifest 声明（BIND_USER_SERVICE intent-filter），
  bindUserService 时管理器无法解析该组件 → 设备 Shell 创建会话失败（SHIZUKU_SERVICE_TIMEOUT）。
  Ubuntu 终端不受影响（不经 Shizuku）。
- 建议修复（android/app/src/main/AndroidManifest.xml，application 内）：

    <service
        android:name=".shizuku.DeviceShellUserService"
        android:exported="false"
        android:permission="moe.shizuku.manager.permission.API_V23">
        <intent-filter>
            <action android:name="moe.shizuku.client.BIND_USER_SERVICE" />
        </intent-filter>
    </service>

- 验证：真机安装 Shizuku 后授权 → 打开设备 Shell；修复前表现为 10s 后 SHIZUKU_SERVICE_TIMEOUT，
  修复后 createSession 返回 UUID。建议同时补一条单测覆盖 manifest 声明存在性。

### 2.3 低风险项

- ShizukuRuntime.write 首块发送完整数组、后续块按剩余切片——行为正确但写法易误读，建议统一循环切片；
- state() 每次读 SharedPreferences——低频可接受；
- openManager() 的 Play 商店兜底在国内不可达——建议提示 GitHub Releases 侧载。

### 3.2 建议增强（低优先）

- org.json 用 toDouble 判断整数——1.6GB 级数值可接受，建议改 long 直读（防御性）；
- requiredString 已拒 ISO 控制字符，可加一行拒 U+2028/U+2029（JSON 换行注入）；
- RuntimeHttp 补单测：下载中途服务端改长度（content-length 与实际不符）的行为。

## 4. 对照旧 fork 桥 v2 的差距分析

| 能力 | 旧 fork 桥 v2 | 本仓库现状 | 差距/建议 |
|---|---|---|---|
| 特权 shell | 反射调用隐藏 newProcess，argv JSON 直 exec | UserService + 固定 sh + PTY 会话 | 本仓库模型更安全；补 manifest 声明即可用 |
| 权限门 | token/页面来源/拒绝列表三重门 | Shizuku 显式授权 + 会话门控 + 输入限额 | 等价或更强 |
| 截图/UI 树/点击输入 | screencap/uiautomator/input 方法 | 缺失（仅终端手打） | 见 §5 |
| 危险命令 | 拒绝列表 | 无（交互终端内命令皆用户输入） | 自动化接口需加确认层（§5.4） |
| 审计 | 无 | 事件枚举审计 | 本仓库更好 |
| 16KB | termux-exec 钩子规避 ELF 限制 | PRoot 二进制外部预编译 + CMake 无对齐参数 | 见 §6 |

## 5. 设备 UI 自动化设计（会话打字方案，零 AIDL 变更）

原则：不新增特权执行面；复用现有固定 sh + 用户可见会话 + 32KB 限额模型。自动化 = 对已打开的
可见设备 Shell 会话执行脚本化按键序列并解析 PTY 输出。

### 5.1 方法映射（全部为系统命令，无新增可执行文件）

| 能力 | 会话内输入 | 输出处理 |
|---|---|---|
| 截图 | screencap -p 管道 toybox base64 + 哨兵行 | 以哨兵切分，base64 解码为 PNG（PTY 不传裸二进制） |
| UI 树 | uiautomator dump 到 /data/local/tmp 后 cat + 哨兵行 | 文本直读 |
| 点击 | input tap x y + 退出码哨兵 | 无输出，echo EXIT code 回传 |
| 文本输入 | input text (ascii)（中文走剪贴板/IME 后续） | 同上 |

### 5.2 实现位置（三处，均为既有模式）

1. Kotlin 侧：MobileRuntimePlugin 新增 execDeviceCommand(sessionId, argv, requestId)——校验会话归属
   （shizuku.contains）→ 拼装输入串（含哨兵）→ write() → onTerminalOutput 按 requestId 聚合 →
   超时（30s）兜底。不新增 AIDL 方法、不新增服务能力。
2. JS/React 侧：platform/native.ts 增加调用，TerminalPanel 或新 DevicePanel 暴露按钮；
3. 协议细节：输入前先 stty -echo（关回显防输出污染）；命令串计入 32KB 限额；哨兵用随机 requestId
   避免与用户输出冲突。

### 5.3 安全边界（保持不变）

固定 sh、无参数注入（argv 语义仅作按键流写入 PTY）、会话必须用户已打开且可见、危险命令
（reboot/rm -rf /dd/pm uninstall 自身）在 Kotlin 侧拒绝或要求用户确认、审计沿用 TERMINAL_OPEN/
CLOSE 事件（不落命令内容——与既有审计策略一致）。

### 5.4 采纳边界说明

若上游认为自动化按键流超出产品边界，则退化为：设备自动化仅限用户在终端内手动执行，本设计作为
SKILL 文档（agent 操作手册）交付，不并入代码。二选一在 README 记录决策。

## 6. 荣耀 Android 16（arm64 / 16KB 页面）适配验证清单

### 6.1 原理

Android 15+ 要求系统支持 16KB 页面；荣耀 Android 16 新机大概率运行 16KB 页内核。所有打包进 APK
的原生 ELF（.so）必须 16KB 对齐（p_align 16384），否则加载即拒绝/崩溃：dsh_pty.so（本仓库自建）
与 libdsh_proot.so / libdsh_proot_loader.so（外部预编译，最危险）。

### 6.2 检查清单

| # | 检查项 | 方法 | 判定 |
|---|---|---|---|
| 1 | dsh_pty.so 对齐 | CMake 加 -Wl,-z,max-page-size=16384（当前无）；readelf -l 查 LOAD 段 | p_align==0x4000 |
| 2 | PRoot runner/loader 对齐 | 对两个 libdsh 二进制同上 readelf | 全部 0x4000；不满足则向 Operit2 工具链索取 16KB 构建并记录 commit+hash |
| 3 | 目标设备页大小 | adb shell getconf PAGE_SIZE | 16384=16KB；4096 则降级为常规验证 |
| 4 | rootfs ABI | manifest architecture==arm64-v8a；rootfs 内 ELF 为 aarch64 | 全符合 |
| 5 | 真机安装链路 | 装 APK → 安装运行时 → Ubuntu 终端 uname -m → 启动 Harness | 全通 |
| 6 | Shizuku 设备 Shell | 授权 → 打开设备 Shell（含 §2.2 修复） | createSession 成功且可执行 |
| 7 | GPL/AGPL provenance | RELEASE_CHECKLIST 记录 Operit2 commit、两 ELF sha256、构建方法、源码可得 | 齐全 |
| 8 | 回归 | 4KB 页面设备仍可运行（16KB 对齐二进制向后兼容 4KB 内核） | 双验证 |

### 6.3 建议新增到 RELEASE_CHECKLIST 的条目

- 所有 .so 通过 16KB ELF 对齐检查（p_align==0x4000）；
- 荣耀/Android 16 真机验证记录（页大小、运行时安装、Harness 可达）。
