## 一、已确诊的缺陷与根因

### D1 工具调用全部失败（`Cannot read properties of undefined (reading 'prepare')`）

**症状**：对话与模型输出正常，但**任何**工具调用（bash 最明显）都失败。

**机制**：

- `dsh-agent-loop/lib/index.js:588` 是普通工具派发路径：
  `const prepared = await ctx.tools[TOOL_RUNTIME_SCHEDULER].prepare(call.exec);`
- `TOOL_RUNTIME_SCHEDULER = Symbol('@deepseek-ai/dsh-tools.scheduler')`，由 `dsh-tools` 在
  **每个物理模块副本里各造一个**；`ToolRuntime` 的调度器是该类的无条件字段
  （`dsh-tools/lib/index.js:2578`）。
- 树里存在两份物理 `dsh-tools` ⇒ 两个不相等的 Symbol ⇒ `ctx.tools[symbol]` 为
  `undefined` ⇒ 每次工具调用在 `.prepare` 抛错。

**根因（两处，均已修复）**：

1. 版本钉不自洽：插件用 `peerDependencies` 精确钉死 `dsh-tools@0.1.5-rc.1`，而
   `dsh@0.1.5-rc.1` 内部依赖写的是范围 `^0.1.5-rc.1`（解析到 rc.2），pnpm 只能再装一份。
   → 已统一到 `0.1.5-rc.2` 并加 `overrides` 兜底 + CI 去重断言。
2. **插件安装引入的第二份副本（主因）**：`plugin-manager.cjs` 用
   `npm install <插件> --omit=dev` 把插件依赖**以真实副本**装进
   `/root/.dsh-mobile/plugin-manager/versions/<txid>/node_modules/`。
   dsh 插件普遍依赖到 `@deepseek-ai/dsh-base` / `dsh-agent-loop`，
   二者都把 `dsh-tools` 声明为依赖，于是这些副本里就有一份 `dsh-tools`。

   **注意**：不要把这个成因写成「补链逻辑不动已存在的名字」——那是另一个机制
   （`linkUnresolvedRuntimeDependencies` 只为解析不到的裸导入补链）。提交 `bcc3702`
   的正文就是这样写的，不准确。顶层副本其实**早已**被「核心 SDK 一律改用运行时实例」
   的分支换成符号链接（`protectedPackage` 覆盖整个 `@deepseek-ai/` 作用域），
   真正泄漏的是两条：
   - **嵌套副本**：`stagedNames` 只枚举 `node_modules` 的**一层**，
     `node_modules/<包>/node_modules/@deepseek-ai/...`（`--legacy-peer-deps` 下版本冲突时
     npm 会把副本嵌进去）从未被检查；
   - **历史安装**：消重只在安装/更新插件时执行，**从不回溯已安装的插件**，
     因此早期版本装下的真实副本会一直留在设备上。

   两者的修法一致，结论与修复不受影响。
   → **已修复**：安装后把插件目录内 `@deepseek-ai/*` 的真实副本（含嵌套副本）改为指向当前
   运行时的符号链接；并提供 `repair` 修复动作处理设备上已装坏的插件（含指向旧 rootfs 的悬空
   链接），在 Harness 启动前与读取插件列表时由原生内部触发。判定规则、安全边界与未覆盖边界见
   `docs/插件安装与运行时单例.md`。

**为什么 CI 与产物检查都看不见它**：CI 构建的 rootfs 里没有安装任何用户插件；
去重检查只扫 `.pnpm`，而那份副本在插件目录里。

### D3 Bash 沙箱不可用，同时 grep / glob 报 ripgrep provider failure

**产物证据**（`0.1.20-preview-mobile-207`，修复前）：

| 程序 | rootfs 内位置 | 权限 |
| --- | --- | --- |
| Bash | `usr/bin/bash`，`bin` 链接到 `usr/bin` | `0755` |
| ripgrep | pnpm 包 `@vscode/ripgrep-linux-arm64@1.18.0` 的 `bin/rg` | **`0644`** |
| Landlock 启动器 | pnpm 包 `@deepseek-ai/node-addon-system-linux-arm64@0.1.2` 的 `bin/landlock-run` | **`0644`** |

`build-embedded-runtime.py` 的 `add_windows_tree` 原先把 DSH 依赖中的所有常规文件设为
`0644`；解压器按归档权限还原，未补执行位。`dsh-sandbox-local@0.1.5-rc.2` 在 Linux 上

  旧产物因 rg 权限错误被新校验拒绝，避免“对话可用但工具无法启动”的镜像再次通过 CI。

**验证边界**：tar 行为回归测试覆盖构建/重建后的权限、二进制内容不变、相似路径不被授权、

内核没有的隔离能力。本修复保留沙箱策略，不自动切换到 `danger-full-access`。

本地以旧 rootfs 副本重建，并同步当前支持脚本后，完整 `verify-bundle.py` 校验通过

### D4 设备上 dsh 的 bash 工具报 `PTY shell exited during startup`（待自检定位）

**现象**（设备实测，2026-09-16）：dsh 的 `bash` 工具连续 12+ 次报
`PTY shell exited during startup`；同一轮里 dsh 还报 `Unable to persist attachment.`；
`mobile_device_screenshot` 能采集到数据却落盘失败；`mobile_device_ui_dump` 报 `UI_DUMP_EMPTY`。

**报错出处**：`@deepseek-ai/dsh-terminal-bash/lib/index.js` 的 `initialize()`，
条件是 `result.waitReason === "session_exit"` —— 即 **PTY 子进程在就绪前退出**，
不是「bash 未安装」，也不是沙箱不可用。

**已经排除的两条**：

| 假设 | 为什么排除 |
| --- | --- |
| PRoot 或访客 bash 坏了 | 应用内 Ubuntu 终端正常。它走同一条 PRoot 启动（`RuntimeLaunchResolver.launch(manifest.shellArgv)`），只是**不经 PTY、不挂沙箱** |
| `landlock-run` 缺执行位（D3 那条） | 它**不会**产生这条报错。dsh 用 `landlock-run --probe` 探测（`@deepseek-ai/node-addon-system/lib/index.js` 的 `probe`：`spawnSync` 失败时 `status !== 0` → `unusable`），此时报的是 `sandbox mode "workspace-write" is requested but no sandbox backend is usable`。现在报的是 PTY 秒退，说明**探测通过了** |

**因此断链在「探测通过、真实执行失败」这一段**，候选只有两条，且都能被同一条自检切开：

1. **真实 confine exec 失败**：`landlock-run` 用 `--ro/--rw` 的**授权根**建规则集，
   根目录不存在属于 launcher 级失败（CLI 契约：一律 exit 125）。`--probe` 建的是自己的规则集，
   所以它能通过、真实 exec 仍会失败 —— 这正好解释「探测通过 + 子进程立刻退出」。
2. **PTY / node-pty 层**：`/dev/ptmx` 分配或 node-pty 加载失败。

**自检设计**（应用内「运行时自检」，不需要 bash）：分别验证 `bash`/`node` 是否存在、
沙箱启动器是否存在且有执行位、`--probe` 判定、**真实 confine exec**（`/bin/true` 是否返回 125）、
**裸 PTY** 与**沙箱内 PTY** 两组 node-pty 冒烟测试、`/root/.dsh` 与 attachments 的写入、
`rg` 执行位，以及宿主侧可用空间。三种组合的含义：两组 PTY 都失败 ⇒ PTY 层；
只有沙箱内失败 ⇒ 沙箱层；都成功 ⇒ 问题在 dsh 配置或插件层，去看运行日志。

**一条必须守住的语义**：`status` 里的 `skipped` 表示「这一项**没有可测的前提**」，
**不得**用 `fail` 去表达「没测」。启动器缺失/无执行位时，`sandbox_probe`、`sandbox_exec`、
`pty_sandbox` 三项都报 `skipped` + `LAUNCHER_MISSING`，精确原因只由 `sandbox_launcher` 那一行给出。
原因很直接：这三项若报 `PROBE_UNUSABLE`，界面会说成「这台设备的内核不支持 Landlock」——
那是**未经验证的断言**，会把用户引到错误方向（这一路已经踩过多次）。
`PROBE_UNUSABLE` 的文案也要同时覆盖两种来源（内核不支持，或启动器被尝试执行却拿不到结果），
不能写成绝对判断。`RuntimeSelfCheckPolicy` 会在 Kotlin 侧丢弃 `skipped+PROBE_UNUSABLE`、
`fail+LAUNCHER_MISSING` 这类自相矛盾的载荷，`RuntimeSelfCheckPolicyTest` 锁定这一点。

**与 N2 的关系**：`Unable to persist attachment.` 与 PTY 失败**共同点只有「都在访客侧」**，
不能据此推断 rootfs 损坏 —— harness 主进程活着只证明 node 与已加载模块在内存里，
证明不了任何目录可写。attachments 目录是否存在/可写由上面那条自检直接回答。

**真机自检结果（已确证，2026-09-14）**：设备上三项沙箱相关检查依次失败 ——
`sandbox_probe` 报 `PROBE_UNUSABLE`（启动器**确实被执行过** `--probe` 却未返回强化生效）、
`sandbox_exec` 报 `EXEC_LAUNCHER_FAILED`（真实 confine exec 在启动器层失败）、
`sandbox_pty` 报 `PTY_EXIT_EARLY`。`sandbox_launcher` 未出现在失败项里，说明启动器存在且有执行位。

结论链：**这台设备上 Landlock 后端无法强化，镜像里也没有 bwrap**（D3 已记录），
而 `dsh-sandbox-local` 在 Linux 上按 `["bwrap", "landlock"]` 顺序探测、且**fail-closed**
（`selectRunner` → `chainVerdict` 全不可用即抛 `SandboxUnavailableError`），
因此 `workspace-write` 下任何命令都无法启动；被沙箱包裹的 PTY 子进程在启动阶段退出，
这正是 dsh bash 工具报 `PTY shell exited during startup` 的完整链条。
**D3 里那句「目标手机是否支持 Landlock 仍需真机验证」到此有了答案：不可用。**

尚未确定的是**为什么**不可用：内核本身没有 Landlock，还是 PRoot 不转发 `landlock_*`
系统调用。两者对修法的含义不同（前者只能用 dsh 自己的权限预设关闭沙箱，后者或许能换后端）。

**仍未发布**：D3 的 `rg` / `landlock-run` 权限修复至今没有随运行时发到设备（见上节末行），
因此设备上若 `grep` / `glob` 也报 `ripgrep provider failure`，说明装的是修复前那份运行时，
需要重装/更新运行时；但它**不解释**本节的 PTY 报错。

## 二、凭据注入路径（已核对，本身无缺陷）
| 启动点 | `includeCredentials` |
| --- | --- |
| `RuntimeSupervisor:96`（真正的 Harness 启动） | `true`：注入各供应商的 `*_API_KEY` |
| `RuntimePluginManager:14`（插件操作） | `false`：最小权限 |

`ModelProvider.DEEPSEEK` 的环境变量名是 `DEEPSEEK_API_KEY`，与 dsh 报错信息给出的

## 三、真机验证命令（修复后应在 App 终端里跑）

诊断日志只覆盖应用自诊断，看不到访客内部状态。下面几条命令用来直接确认修复是否真的生效。

**1) 是否还存在「真实的」第二份 `dsh-tools`（修复后应只输出符号链接，不应出现「真实副本」）**

```sh
find /root/.dsh-mobile/plugin-manager -path '*node_modules/@deepseek-ai/dsh-tools' 2>/dev/null |
  while read p; do [ -L "$p" ] || echo "真实副本: $p"; done
```

**2) 全盘所有 `dsh-tools` 是否都指向同一份真实目录（修复后应只有一个不同的真实路径）**

```sh
find / -xdev -name dsh-tools -path '*node_modules*' 2>/dev/null |
  while read p; do printf '%s => %s\n' "$p" "$(readlink -f "$p")"; done
```

**3) 用户数据是否还在（升级后应仍然存在）**

```sh
ls -la /root/.dsh/.credentials.yaml /root/.dsh/settings.yaml /root/.dsh/sessions /root/.dsh-mobile/plugin-manager 2>/dev/null
```

**4) 符号链接是否悬空（跨运行时版本升级后可能出现）**

```sh
find /root/.dsh-mobile/plugin-manager -xtype l 2>/dev/null | head -20
```

判定要点：

- 第 1 条只要有输出，说明插件目录里仍有真实副本 ⇒ 工具调用会继续报
  `Cannot read properties of undefined (reading 'prepare')`。
- 第 2 条如果出现**两个不同的真实路径**，就是 Symbol 身份分裂的直接证据。
- 第 4 条有输出说明插件依赖指向了已不存在的旧运行时路径，需要触发插件修复动作。

### 应用内自动取证：模块图探测（诊断事件 `MODULE_GRAPH`）

上面的命令需要用户在终端里手动执行，而且只反映**执行那一刻**的状态。为了让 App 自己把「设备上
到底有几份 `dsh-tools`」写进诊断日志，`plugin-manager.cjs` 增加了一个**只读**探测（CLI 操作
`graph`，Kotlin 侧 `RuntimePluginManager.scanModuleGraph()`），在**每次 Harness 启动前**、与插件
自愈同一个位置执行并记录为诊断事件 `MODULE_GRAPH`（只读、不参与自愈的代次指纹，因此不会被跳过）。

- **为什么需要**：`dsh-tools` 的调度器用 `Symbol('@deepseek-ai/dsh-tools.scheduler')` 注册，
  Symbol 在**每个物理模块副本里各造一个身份**。只要设备上存在两份**真实副本**，
  `ctx.tools[调度器 Symbol]` 就是 `undefined`，之后每一次工具调用都在 `.prepare` 上抛
  `Cannot read properties of undefined (reading 'prepare')`。此前这条链路只能靠排除法推断，
  探测把它变成可观测的事实。
- **判据只有一条：不同真实路径数（`count`）> 1**。同一个真实目录被多个链接引用多少次都只算一份
  ——链接不改变模块身份，因此 pnpm 里那几百条依赖链接不会被误报成重复；`files` 是出现位置总数
  （真实目录 + 符号链接），只用来看「扫到了什么」、判断不到时也便于发现探测没扫到东西。
- **边界**：只遍历固定候选根（`/opt/dsh/node_modules`、`/opt/dsh/plugins`、
  `/root/.dsh/profiles/node_modules`、`/root/.dsh/profiles/web/node_modules`、
  `/root/.dsh-mobile/plugin-manager`），缺失即跳过；深度上限 4（pnpm 的
  `node_modules/.pnpm/<条目>/node_modules/@deepseek-ai/dsh-tools` 正好在这一层），目录与条目
  上限只作失控保护 —— 真实依赖树有几百个条目，预算必须够大，否则漏算一份真实副本就会让判据失效；
  **链接目录一律不进入**（因此不会走出候选根），探测只读、失败只吞掉，**不记录任何路径**。

日志长这样（`count` 与 `files` 都是纯数字，不含路径）：

```
2026-09-12T10:20:30Z|INFO|MODULE_GRAPH|result=ok|count=1|files=3
2026-09-12T10:21:04Z|WARN|MODULE_GRAPH|result=failed|count=2|files=4
2026-09-12T10:22:11Z|WARN|MODULE_GRAPH|result=denied|count=0|code=PROBE_FAILED
```

判定要点：`result=failed` 且 `count>1` ⇒ **两份模块实例，工具调用必然全部失败**；
`result=denied` 是探测本身没跑成（不等于判据成立，需要人工按本节命令确认）。

## 四、打开 Harness 的前置条件（模型密钥门禁）

- **规则**：本机没有保存过任何模型凭据时，应用不打开 Harness。`launchHarness` 是唯一打开入口，
  因此引导页、首页按钮与「打开应用时自动启动」都走同一条判断：提示后直接落到「模型与密钥」页；
  引导页最后一步也不出现「打开 Harness」按钮，只说明原因并给出返回密钥步骤的入口。
  理由是没有密钥时每一轮对话都会以缺少凭据失败，打开只会得到一个用不了的界面。
- **判据**：`hasConfiguredModelCredential()`（`src/modelProviders.ts`）同时检查 App 加密存储与 Harness
  网页端的凭据状态。原生侧对 `~/.dsh/.credentials.yaml` 做固定路径、常规文件、`0600` 权限、
  256 KiB 大小和 YAML 结构校验，只回传匹配白名单环境变量的供应商标识；密钥值不返回 WebView。
  两种来源使用独立字段，管理端不会把 Harness 网页凭据误显示为可由 App 清除。设置尚未读取
  （`settings === null`）时放行，避免一次设置读取失败就把用户永久挡在门外。
- **兼容放行**：引导页最后一步与「模型与密钥」页仍保留「我已在 Harness 内配置过，仍要打开」
  入口，用于旧版或无法安全读取凭据状态的运行时。实现上是两个独立入口 —— `launchHarness()`
  （检查）与 `launchHarnessConfirmed()`（放行）；放行标志必须是显式布尔参数。

## 六、网络工具组件组（git / curl / CA 证书）

### 动机（真机实测缺口）

Android 16 / HONOR 上经 PRoot 实测，访客里：

| 缺口 | 后果 |
| --- | --- |
| 没有 `git` | 编码 Agent 无法 clone / diff / commit；插件 `dsh-client-ui-git-graph` 拿不到数据，等于死的 |
| 没有 `curl` / `wget` / `openssh` | 访客内无法取网络资源、无法用 SSH remote |
| `libcurl`、`libexpat` 缺失 | 即使补上 git 二进制也起不来 |
| `/etc/ssl/certs` 是空的 | 即使补上 git 二进制，`git clone https://` 也会先在证书校验上失败 |

这不是「少装一个包」的问题：二进制、运行期依赖、CA 信任库三件事必须同时到位，
否则任何一件缺失都会表现成「git 不可用」。

### 组件清单与体积

包由 CI 在 `ubuntu-24.04-arm` runner 上取（与镜像**同发行版同架构**），
`scripts/stage-network-tools.sh` 按 rootfs 路径预置，构建脚本再写进镜像；
**镜像里不跑 apt**。

| 组件 | 内容 | 预估体积（未压缩，需 CI 实测） |
| --- | --- | --- |
| `git` | `/usr/bin/git` + `/usr/lib/git-core/*`（内建子命令、`git-remote-https`、`git-credential-*`、`git-upload-pack` …）+ `/usr/share/git-core/templates` | ≈ 7 MB（`usr/bin/git` 与 `git-core/git` 两份真实载荷；其余上百个内建子命令按硬链接去重；去 man/doc） |
| `curl` | `/usr/bin/curl` | ≈ 0.55 MB |
| `libcurl` + 传递依赖 | `libcurl4t64`（`curl` 用，OpenSSL flavour）与 `libcurl3t64-gnutls`（`git-remote-https` 用）及其 `ldd` 闭包（`libssl3t64`、`libnghttp2`、`libpsl`、`libssh2`、`libldap`、`libbrotli` …）；已在基线镜像里的库不重复打包 | ≈ 4–8 MB |
| `libexpat1` | XML 解析（`git` 的运行期依赖） | ≈ 0.2 MB |
| `ca-certificates` | `/usr/share/ca-certificates/mozilla/*.crt` + 重新生成的 `/etc/ssl/certs`（`*.pem`、`<hash>.0`、`ca-certificates.crt`） | ≈ 0.4 MB |
| `openssh-client`（**可选**） | `ssh` / `scp` / `sftp` / `ssh-keygen` / `ssh-keyscan` / `ssh-add` / `ssh-agent` + `/usr/lib/openssh` | ≈ 2–3 MB |

合计约 12–30 MB 未压缩（本表按包体积与 `git-core` 硬链接去重推算，属**预估**；
`docs/真机缺陷与改进清单.md` §5.7 的估算是 20–30 MB）。真实数字只能在 CI 上量，
`stage-network-tools.sh` 会把表观字节与磁盘字节都打进构建日志，供核对硬链接是否保住。

**凭据模型（沿用 `docs/真机缺陷与改进清单.md` §5.7 的口径）**：单 uid 下访客内的
token / SSH key 能被同 uid 的代码读到，因此镜像里**不预置任何凭据**，也不配置
`credential.helper=store`（明文落盘）；需要 push 时由 App 临时写入 `0600` 文件并在用后清除。

**有意不装**：`git` 的 perl 依赖（`git add -p`、`git send-email`、`git svn` 因此不可用）、
man page（`git-man` 包）、`/usr/share/doc`、locale、分页器 `less`。
最后一条的实际影响：在**有 tty 的 Ubuntu 终端里**跑 `git log` / `git diff` 会因为找不到
`less` 而报错（Harness 的 bash 工具没有 tty，不受影响）。终端里请用
`git --no-pager log …`，或先 `git config --global core.pager cat`。
把 `less` 纳入组件组是后续候选（约 180 KB），本次按约定的组件清单执行，不擅自扩大范围。

**CA 信任库是重新生成的**，不是照搬 runner 上的 `/etc/ssl/certs`：runner 上那份可能
已包含本机额外注入的 CA（企业代理的中间人证书），照搬等于把额外信任锚带进用户设备。
预置脚本只从发行版包提供的 `mozilla/*.crt` 生成 `*.pem`、`<hash>.0` 链接与
`ca-certificates.crt`。

### 裁剪（预算对冲）

- 打包时剔除 `*.map` sourcemap：真机实测 **4507 个文件 / 约 37 MB**。只删 `.map`
  本身，`.js` / `.json` 一律保留（sourcemap 不是运行依赖，`require.resolve` 不解析它）。
- 计数与字节数写进构建日志：`build-embedded-runtime.py` 打印
  `trimmed sourcemaps: files=… bytes=…`，并在末尾 JSON 汇总里给出
  `trimmedSourcemaps` / `trimmedSourcemapBytes`；`rebuild-rootfs-frontend.py`
  在重建旧 bundle 时按同一口径剔除并给出 `trimmedSourcemap*`。
- **后续候选（本次刻意不做）**：按 provider 裁剪 SDK、移除捆绑 pnpm、Python 瘦身。
  移除 pnpm 会直接废掉插件安装，风险最高，不在本次范围。

### 执行位与 ELF 校验口径

D3 的教训（`rg` / `landlock-run` 被打成 `0644`）在这里被推广：

- 构建侧：`usr/bin`、`usr/lib/git-core`、`usr/lib/openssh` 下的常规文件一律 **`0755`**，
  不只给 `/usr/bin/git`；硬链接去重只作用于 `usr/lib/git-core`，
  但 verify 要求的入口（`usr/bin/git`、`usr/bin/curl`、`usr/lib/git-core/git-remote-https`）
  始终落成真实常规文件。
- 校验侧（`scripts/verify-bundle.py`，**不放宽任何既有检查**）：
  1. `usr/bin/git`、`usr/bin/curl`、`usr/lib/git-core/git-remote-https` 与既有
     `bash` / `rg` / `landlock-run` 一样，必须**存在 + `0755` + 非空 + ARM64 ELF**；
  2. `usr/lib/git-core/` 下**每个**常规文件都必须是 `0755`（缺执行位时
     `git clone`/`push` 会静默不可用，是最难在真机上定位的一类故障）；
  3. `/etc/ssl/certs` 下的 CA 文件（`*.pem` / `*.crt` / `<hash>.N`）**至少 64 个**
     —— 空目录、只剩一个 `ca-certificates.crt` 都算失败；该下限与构建脚本的
     `NETWORK_TOOLS_MIN_CA_FILES` 保持一致；
  4. `openssh-client` 是**可选**组件：存在就必须通过同样的检查，缺失不算失败。
- 组件可关：构建脚本 `--without-network-tools`（移动 profile 默认启用）；
  对应的校验侧开关是 `verify-bundle.py --without-network-tools`，CI 不使用它。
- 体积兜底：预置树超过 96 MB 直接失败 —— 硬链接没保留时 `git-core` 会从约 4 MB
  膨胀到数百 MB，必须当场暴露而不是发一个巨包。

### 法律材料

- `git` 是 GPL-2.0，`curl`/`libcurl` 是 curl 许可，`ca-certificates` 是 MPL-2.0，
  `libexpat1` 是 MIT，`openssh-client` 是 BSD 类（逐文件）。
- 既有机制是**手工登记**（`android/app/build.gradle` 的 `legalAssetSources`：来源缺失或为空
  即终止构建），只覆盖「源码在仓库里」的组件。新组件是 Ubuntu 二进制，因此补上**收集步骤**：
  CI 在 arm64 runner 上跑 `scripts/legal-notices.py collect`，把每个包的
  `/usr/share/doc/<pkg>/copyright`（含 `ldd` 带进来的传递依赖库，由 `dpkg -S` 反查）
  复制到 `android/app/src/main/assets/legal/ubuntu-packages/`，即 APK 内
  `assets/legal/ubuntu-packages/`；打包前由 `scripts/legal-notices.py verify` 做**发版门禁**
  （必需组件齐备 + 非空 + 许可证标记命中 + GPL-2.0 未删节全文在位）。
- GPL 的「提供对应源码」口径**不自创**，沿用 `docs/RELEASE_CHECKLIST.md` 的既有表述
  （必须按许可证允许的方式提供确切二进制的完整对应源码，只给上游链接不构成要约）。
- 待办：把 `assets/legal/ubuntu-packages/` 也登记进 `android/app/build.gradle` 的
  `legalAssetSources`，可让**本地**构建同样 fail-closed（本次未改该文件，见下节边界）。

### 真机验收（必须按顺序做完）

升级到含本组件的运行时后，在 App 的 Ubuntu 终端里：

```sh
# 0) 终端里有 tty，但镜像没打包分页器 less：先关掉分页，避免误判成 git 不可用
git config --global core.pager cat

# 1) 组件与 CA 是否到位
git --version && curl --version | head -n1
ls /etc/ssl/certs | wc -l          # 期望 >= 64（*.pem + <hash>.0 + ca-certificates.crt）
cat /etc/deepseek-harness-network-tools.json   # 组件清单与 CA 条目数

# 2) 公共仓库 clone（先在证书校验这一关验证 CA 信任库）
cd /root && rm -rf dsh-git-check && git clone --depth 1 https://github.com/git/git.git dsh-git-check
cd dsh-git-check && git --no-pager log --oneline -n 3

# 3) commit 往返
git config user.email dsh@example.invalid && git config user.name dsh
git checkout -b dsh-check && echo ok > dsh-check.txt && git add dsh-check.txt
git commit -m "dsh 网络工具组件真机验收" && git --no-pager log --oneline -n 1

# 4) 子命令与 remote helper 真的可执行（0755 口径的现场验证）
ls -l /usr/bin/git /usr/lib/git-core/git-remote-https
git -c http.sslVerify=true ls-remote https://github.com/git/git.git HEAD
```

判定要点：

- 第 2 步若报 `server certificate verification failed`，说明 CA 目录没进镜像（或被裁掉），
  不要用 `GIT_SSL_NO_VERIFY=true` 绕过 —— 那是把缺口藏起来。
- 第 4 步若报 `cannot run git-remote-https` 或 `Permission denied`，说明执行位又被打回 `0644`
  （D3 同类故障）。
- 最后在 Harness 里让 `dsh-client-ui-git-graph` 指向第 2 步 clone 出来的仓库，
  确认能出图 —— 这是本组件「真的可用」的最终判据。

### 验证边界（哪些只能在 CI 上验证）

完整 rootfs 需要 CI 的 `ubuntu-24.04-arm` runner 与 Ubuntu/Node 官方归档，
本机（Windows）**无法**端到端构建，因此下列内容只能由 CI 覆盖，不能在本地伪造结论：

- `scripts/stage-network-tools.sh` 的实际取包、`ldd` 闭包、硬链接保留与包清单生成；
- `git`/`curl` 二进制的真实性（ARM64 ELF、`0755`）、`/etc/ssl/certs` 的实际条目数；
- 构建日志里的 sourcemap 剔除量（4507 / 37 MB 是**真机实测值**，CI 实际数字可能不同）；
- `legal-notices.py collect` 在真实 `/usr/share/doc/<pkg>/copyright` 上的结果；
- APK 内 `assets/legal/ubuntu-packages/` 的最终内容。

本地可以验证的部分：`scripts/build-embedded-runtime.selfcheck.py`（含新组件与裁剪的夹具自测）、
`node --test scripts/*.test.mjs`、`scripts/legal-notices.py verify` 的正/负夹具。
