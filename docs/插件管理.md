# APK 插件管理

入口：应用设置 → 插件管理。按官方、第三方区分，按组合包声明的配置文件分组；展开文件可管理其中有稳定标识的子插件。界面支持简体中文和英语。

管理器不启动 Harness，也不导入插件模块；Harness 启动失败时仍可读取和修改配置。Ubuntu、PRoot 和内置 Node.js 本身需要可用。列表反映配置中的启停状态，并非运行时健康检查或插件依赖是否满足的保证。

修改前先点击“停止运行时”，关闭 Harness 和 Ubuntu 终端。原生生命周期锁也会拒绝运行中的修改，防止绕过界面直接写入。文件禁用后保留子插件选择，再启用时恢复；安全组件和核心配置文件受保护。第三方配置文件损坏时仍保留包级禁用入口。

子插件状态写入独立启动补丁 `launcher-plugins.patch.json`，不修改插件源码，也不覆盖模型供应商配置。文件级禁用保存在配置档案清单中，保留原文件顺序。当前范围是 `web` 配置档案的组合包配置文件；不提供任意路径的文件编辑器，也不管理代理预设内动态创建的插件实例。

第三方更新以包为单位，从固定 npm 注册表读取最新版本，隔离安装并禁用安装脚本。使用实际 Harness 安装锚点解析包，兼容 pnpm 隔离目录。安装完成后会把插件目录内 `@deepseek-ai/*` 的真实副本（含嵌套副本）统一改为指向当前运行时的符号链接，保证带 Symbol 的运行时服务包只有一份物理副本；判定规则、计数与边界见 `docs/插件安装与运行时单例.md`。插件自己的第三方依赖保持原样，其他已安装的共享依赖仍必须与新包安装结果一致，否则保留旧版本并提示不兼容。需要安装脚本、原生编译或新核心 SDK 的包不能通过此入口升级。官方包随运行时升级，避免覆盖 Android 兼容修补。

更新先准备新包，再记录事务并切换链接；失败回滚，上次中断的事务在下次修改或 Harness 启动前恢复。设备不支持链接时保留原插件。已提交版本的暂存目录可能继续被模块引用，因此不做未经引用检查的删除；更新失败且无需恢复时清理失败下载。

### 从包名或地址导入

除按包名更新外，`import` 支持三种来源：npm 包名（含作用域名 `@scope/foo`）、`https://` 直链（npm 视为 tarball）、`git+https://` 仓库地址（可带 `#<ref>`）。来源只作为**一次调用的参数**：不写入清单、不进审计、不出现在返回值里；命令以参数数组交给 npm，不经过 Shell。

校验规则在访客脚本、原生与网页端**三处同一套**：长度 ≤512；字符白名单；拒绝 `http://`、`git://`、`ssh://`、`file:`、`data:`、任何 `..`（含 `%2e` 编码形式）、空白/引号/尖括号/反引号/换行；拒绝以 `-` 开头的输入（防 npm 选项注入）；URL 拒绝 userinfo（`https://user:pass@host/...`）。失败一律返回 `PLUGIN_SOURCE_INVALID`，且**不回显**用户输入。

`git+https://` 要求运行时里真的能用 git：先在访客内执行 `git --version`，三种结果分开处理——可用则继续；**确实没有**（spawn 报 `ENOENT`）返回 `PLUGIN_GIT_MISSING`；**探测不了**（超时、被拦、异常退出）返回 `PLUGIN_GIT_UNVERIFIED`，不把"探测不了"谎报成"没有 git"。

导入与更新共用同一条事务路径（暂存安装 → 既有全部校验 → 提交点 → 提交点之后才改清单）。包已在清单里就等同更新；不在清单里则在提交后加入 `dsh.profile.bundles`，并按 `dshMobile.bundleOrder`、`dshMobile.disabledBundles` 的既有约定补齐顺序、清掉禁用行——重复导入同一包不会产生重复条目。地址形态装完后若无法确定装进来的是哪个包（有多个候选或给的名字对不上），返回 `PLUGIN_IMPORT_UNRESOLVED` 而不是猜一个。

### 数据目录在更新前后保留

插件包内的可变数据目录沿用既有约定名 `data`、`config`、`storage`、`.config`：更新或导入时从"当前已安装版本"完整搬到新版本（含嵌套子目录），再切换链接，因此失败或取消时旧版本仍然完好。

迁移**不跟随符号链接**：目录内出现链接、非常规文件，或嵌套超过 8 层时报 `PLUGIN_DATA_UNSAFE`；累计超过 16 MiB（或文件数超过 4096）时报 `PLUGIN_DATA_TOO_LARGE`。两种情况都放弃本次更新并保留旧版本，不留下半成品。旧包没有这些目录时按正常更新处理，不报错。

### 状态跨运行时升级的迁移

启停状态写在 `root/.dsh/profiles/web/package.json` 与 `root/.dsh-mobile/launcher-plugins.patch.json`，而运行时升级**不保留**这两处，升级后状态会丢。管理器因此在被保留的 `root/.dsh-mobile/plugin-manager/` 目录里留一份自身快照 `state-snapshot.json`（只含包名、启停状态与子插件禁用行，不含路径、地址或凭据），并把快照指纹写进清单的 `dshMobile.stateToken`。

- 回填由 `recover()` 负责（Harness 启动前与每次修改前都会调用）；`list()` 保持只读——既不写快照也不回填清单，避免只读接口产生写入副作用。
- 清单里**已有**我们的状态（指纹一致）时绝不覆盖用户当前选择；只有清单里找不到我们的状态时才按快照补回缺失项，重复调用幂等、不产生重复条目。
- 快照损坏或清单损坏时按"无法回填"处理：不崩、不清空用户数据，清单原样保留。
- 写入全部走 `atomic()`，且管理操作要求运行时已停止（原生生命周期锁也会拦），因此不会与运行中的 Harness 争抢同一份清单。

### 已安装插件版本账本

`state-snapshot.json` 记的是**启停状态**（用户的选择），`installed-lock.json` 记的是**版本事实**：每个已装插件的包名、解析到的版本号、包本体所在的事务目录名（`versions/<事务>` 的那一段；官方包没有这个目录，为 `null`）、来源（`bundle` 官方包 / `npm` / `url` / `git` / `unknown`）与该条事实的写入时间。两份文件都在被保留的 `root/.dsh-mobile/plugin-manager/` 里，同一次操作各刷一份，但**键不重叠**——账本里不出现 `enabled`，快照里不出现版本号，避免同一件事有两个真相。

- 写入时机是"改完盘之后"：安装/导入、回滚、启停（含子插件）、`recover`、`repair` 五条路径各刷一次；`list()` 保持纯读，不写账本。
- 写账本**永远不会让主流程失败**：写不进去（新文件、磁盘满、权限不足）只把结果记成 `failed`，清单与插件包一个都不动。原生侧记住最近一次 `failed`，下一次成功写入即清除。
- 只有三种受控结果回到原生侧：`written`（写成了）、`failed`（想写但没写成）、`skipped`（这次没有可登记的事实——清单还不存在或读不出来）。清单读不出来时**保留升级前留下的那一份账本**、不清空。
- 账本损坏或超限（`schemaVersion` 不符、JSON 坏掉、超过 256 条、超过 64 KiB）时按"还没有账本"处理，下一次写入按盘上事实重建；**绝不因为账本读不出来就删插件包**。
- 账本只登记**当前清单里的插件**：插件被卸载（从清单里去掉）后它的条目在下次刷新时删除 —— 留着的话，下一次应用升级迁移会把这个已经不存在的包算成"包不在设备上"，界面就会误报"需要重新安装"。清单读不出来时按上面那条 `skipped` 处理，旧账本一个字节都不动。
- 账本只写包名、版本、事务目录名、来源与时间戳：不写路径、不写安装地址、不写凭据，也不写命令输出。事务目录名只用于"这个包还在不在"的核对。

### 应用升级迁移（按 APK versionCode）

判定是纯逻辑（`runtime/PluginMigrationPolicy`，零 Android 依赖）：输入「上次迁移成功的 `versionCode` + 当前 `BuildConfig.VERSION_CODE` + 运行时代次是否变化」，只在**从未迁移过**、**应用升级**、**应用降级**、**运行时代次变化**时返回"要跑"，版本与代次都没变则返回"不用跑"。降级也要跑的理由：盘上的状态可能是更新版本的应用写下的，核对幂等，而不跑却把"上次迁移成功"记成新版本号等于谎报这一步做过了。

需要跑时由 `RuntimePluginManager.migrateIfNeeded()` **串行复用**既有两步——`recoverIfNeeded()`（回放未提交的事务）与 `repairInstalledIfNeeded()`（按代次自愈链接），不另写一套接链接逻辑，也不重复起访客进程（只有"不需要迁移"时才退回到启动路径里各调一次）。随后按 `installed-lock.json` 逐个核对包名对应的 `versions/<事务>/node_modules/<包名>` 是否还在，不在就如实计入"缺失"：**不自动重装、不删任何目录**，插件包内 `data`/`config`/`storage`/`.config` 的用户数据一个字节都不动（迁移只读账本与目录存在性）。

失败不许静默：

- `recover` 抛错时以 `PLUGIN_MIGRATION_RECOVER_FAILED` 记一条 WARN 诊断，并把异常继续抛出（启动照旧中断，与既有行为一致），迁移状态置 `failed`。
- 迁移跑完但"上次迁移成功的版本号"没写成时记 `PLUGIN_MIGRATION_RECORD_FAILED`，状态 `failed`，下次启动会再跑一次。
- 跑完仍有缺失/失败/拒绝的缺口时记 `PLUGIN_MIGRATION_PARTIAL`，状态 `partial`（界面按"需要重新安装"提示）；全都干净才是 `done`。
- 诊断只写受控码、结果与计数，不写路径，也不写包名清单。

**回显**：迁移结果进 `recoverySnapshot()` 新增的三个受控字段——`migration`（`none` / `done` / `partial` / `failed`）、`lock`（`ok` / `missing` / `invalid` / `unwritable`）、`checked`（本次按账本核对过几个插件）。插件管理页据此多给一句说明（迁移完成并核对了 N 个、需要重新安装、版本记录损坏或写不进去），界面文案只说人话，不出现文件名或内部字段名。

### 版本回滚

提交更新或导入时**不删除**旧的插件包目录，而是把它登记为该插件的"上一版"（记录在 `previous.json`）；每个插件只留一份，不留历史链——再成功更新一次时替换成最近一次成功的那版。被淘汰的那份按既有"被引用检查"口径处理：拿不准就不删，宁可留着也不破坏仍被引用的模块。

`rollback` 把运行时指向该插件的链接切回上一版，走与更新同一套事务与 `recover()` 机制；**回滚本身可再回滚**（刚被换下来的那版成为新的"上一版"）。没有上一版、上一版目录已被清理或该包受保护时报 `PLUGIN_ROLLBACK_UNAVAILABLE`；切换后校验不通过时报 `PLUGIN_ROLLBACK_FAILED`，并恢复到操作前的状态。`list` 如实报告当前版本与可回滚到的版本号（没有时该字段为 `null`）。

`repair` 做两件事：对齐插件目录内 `@deepseek-ai/*` 运行时副本，并把被运行时升级抹掉的**插件自身链接**接回配置档案的模块根（包本体一直在保留区，因此不必重装）。它不改插件自身的版本目录与已经可用的链接；`recover` 只回放未提交的事务日志，而回滚成功后事务日志已经删除——两者都不会把回滚结果改回去。

插件链接为什么会丢：安装时链接落在 `root/.dsh/profiles/node_modules/<包名>`（`modules` 里已有该包时落在那一处），而 `root/.dsh/profiles` **不在**跨版本保留名单里，升级后随新运行时整体重建。此时清单经 `recover()` 回填后仍把插件列为“已启用”，包本体也还在保留区，但没有任何模块根指向它——列表显示“未安装”，Harness 也加载不到该组合包。`repair` 按“最近一次安装”的副本把链接接回原位：已经能解析、目标位被别的有效实体占着时不动（只清掉本来就是坏的悬空链接），保留区里确实没有副本时只记 `missing`（这种情况只能重装），全程失败只计数。

**人工入口（2026-10-11 新增）**：设置页的插件卡片在两种情形下都会给出「立即修复插件」按钮——原生侧最近一次自愈报出非 `none` 的恢复状态，或列表里存在**已启用却解析不到**的插件包（后者覆盖「自愈还没跑过」的空档：刚升级完还没启动过 Harness 时，升级抹掉的链接只表现为列表里的“未安装”）。按钮走 `managePlugins({operation:'repair'})`，原生修完立刻回读一次 `list`，因此点完界面上的版本号会跟着变；修不回来的包（保留区里副本也没了）在按钮下方的说明里如实写明需要重新安装，本轮不做自动重装引导。

**验证状态（2026-10-03，真机 HONOR AAP-AN00）**：`dshmarket`、`dsh-web`、`dsh-web-mobile` 三个第三方插件在一次内置运行时升级后同时从“已安装”变成“未安装”（`root/.dsh/profiles/web/` 里只剩 4 个构建期文件、没有 `node_modules`），而它们的包本体仍在 `root/.dsh-mobile/plugin-manager/versions/<事务>/node_modules/` 下。接回逻辑已按这份真机形态写成脚本测试（升级模拟 + 接回 + 幂等 + 无副本只记 `missing`），**2026-10-04 又补上这条链路的真机复测**：装 `0206374` 构建（`app-release.apk` 314,398,628 B）后更新内置运行时，设备终端里 `ls -l /root/.dsh/profiles/node_modules/dsh*` 报 `No such file or directory`（三条链接确实被抹掉），点「重新连接」启动 Harness 后再查，三条 junction 都在并指向保留区 `versions/<事务>/node_modules/<包名>`（`dshmarket` 取的是保留区里最新一次安装的事务目录），`…/dshmarket/package.json` 也能直接读到；插件管理页三条从「未安装」变成带版本（`dshmarket` 1.66.8、`dsh-web` 0.4.4、`dsh-web-mobile` 3.0.3）且仍是「已启用」。没有逐个验证这些插件在 Harness 里的实际功能表现。

## 桥接接口

`managePlugins` 仅通过应用私有原生桥接调用，允许操作如下：

| 操作 | 参数 | 含义 |
| --- | --- | --- |
| `list` | 无 | 列出文件及子插件元数据 |
| `enable` | `id`、`enabled` | 整体启停配置文件 |
| `child` | `id`、`childId`、`enabled` | 调整子插件开关 |
| `update` | `id` | 更新所属第三方插件包 |
| `import` | `source`（必填）、`id`（可选，期望的包名） | 从 npm 包名或连接地址导入 |
| `rollback` | `id` | 回滚到该插件的上一版本 |
| `repair` | 无 | 用户主动重跑一次插件链接接回（绕过自愈的代次闸门与冷却窗口） |

`import`、`rollback` 与 `repair` 的返回值沿用 `list` 的投影（同一份插件元数据），不额外回传地址、路径或凭据。每一次管理操作的返回值里都带一份 `recovery` 快照（原生侧 `RuntimePluginManager.recoverySnapshot()`）：既有的 `status`/`restored`/`relinked`/`missing`/`failed`/`refused` 含义不变，**2026-10-11 起**新增三个受控字段 `migration`（`none` / `done` / `partial` / `failed`）、`lock`（`ok` / `missing` / `invalid` / `unwritable`）与 `checked`（本次按版本账本核对过几个插件）。网页端对这三个字段是**可选校验**：旧版原生不带它们时按"没有迁移信息"处理，界面行为与改动前一致；带了就必须落在上面的取值里，否则整份返回值按无效丢弃。

上表是桥接允许的全部操作。`recover`（回滚中断的更新事务、并在清单被重建时回填状态）与 `graph`（只读模块图探测：只统计 `@deepseek-ai/dsh-tools` 的出现次数与**不同真实路径数**）由原生在 Harness 启动前与读取插件列表时内部触发，不接受网页端传参，也不回传插件清单，只回传处理计数。

`repair` 兼有两种触发路径，语义不同：原生自愈（启动 Harness 前、读取插件列表时）沿用「同一运行时代次只修一次」的闸门与失败冷却窗口；用户点设置页的「立即修复插件」属于人工重试，`explicit=true` 时闸门与冷却都不拦它。人工重试还有两处差异：修复计数**按本次结果覆盖**而不再取历史最大值（否则插件重装好之后再修一次，界面仍停在旧的「缺失 N 个」），失败会按受控错误码 reject 而不是吞掉（自愈失败照旧只计数并进入冷却）。

包名限制为 214 字符以内的 npm 名称，拒绝路径穿越；子插件标识限制为 128 字符以内的受控字符；导入来源限制为 512 字符以内且只接受上面的白名单形态。原生与脚本双重校验，进程使用参数数组，不拼接 Shell 命令。返回值只含包名、相对配置文件名、版本、可回滚版本和启停状态，限制数量与响应大小；不返回配置内容、用户路径、凭据或原始进程日志。网页端再次校验并由 React 转义展示。

管理进程不接收模型 API 密钥、Harness 认证凭据或设备桥接凭据。审计只记录操作类型及受控结果码（导入、回滚与人工修复各有自己的事件类型，且**不记录来源地址**；自愈不经桥接、不产生审计事件，因此审计里出现 `PLUGIN_REPAIR` 就等于「用户手动重试过一次」），沿用至少 90 天的保留策略。

## 验证范围
