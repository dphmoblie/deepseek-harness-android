代码定位基于 `@deepseek-ai/dsh 0.1.5-rc.2` 与仓库 main。其中**若干条已由我们在仓库代码侧独立核实**

## 二、缺陷明细

### P0-1 `link(2)` 被拒 → `write` 工具无法新建文件

- **现象**：访客内 `write` 工具无法**新建**文件；**覆盖已存在的文件正常**。`ln` 全部失败，`mv` / `rename` 正常。
- **真机证据**：`ln` 在 f2fs（`/root/1`）、tmpfs（`/tmp`）、FUSE（`/sdcard`）**三处全部 EACCES**；
  `mv` / `rename` 正常。连带影响（存储）：pnpm 无法硬链接 ⇒ store 与 `node_modules` 各存一份真实副本，
  实测 link count = 1 而非 2，设备上每装一次插件就多一份 store。
- **归属判定**：**PRoot / 主机策略（触发方）**。依据：tmpfs 本身支持硬链接，而 `/tmp` 上同样 EACCES；
  `rename(2)` 在同一个访客里正常 ⇒ **不是文件系统能力问题**，也不是我们的调用参数问题。
  修复落点横跨两侧：触发方不在我们手里，**而「没有回退路径」这一半在我们依赖的 dsh 代码里**——
  命中 `dsh-fs-local.writeFileAtomic()`：`createIfAbsent` 分支走 `linkFile()`（新建），否则走 `rename()`（覆盖），
  因此「覆盖正常、新建必失败」的现象与该实现完全吻合。代码侧已核实该定位与现象一致。
- **修法（已落地）**：`link` 失败回退 `rename`（同目录同文件系统，语义等价），并对 `createIfAbsent` 加
  存在性复核，避免回退后覆盖掉并发写入的文件。落地形态是**仓库既有的 pnpm 补丁通道**
  （`scripts/runtime-profile/pnpm-workspace.yaml` 的 `patchedDependencies`，与既有
  `patches/@earendil-works__pi-ai@0.85.1.patch` 同一条通道）：
  `patches/@deepseek-ai__dsh-fs-local@0.1.5-rc.2.patch` 命中 `writeFileAtomic()` 的 `createIfAbsent` 分支，
  新增 `isLinkUnavailableError()` 判定后改用 `rename` 发布。
  两条既有约束没有变：① 补丁键**必须与 dsh 版本精确对应**，dsh 升级时要重新对齐并更新 `pnpm-lock.yaml`
  里的补丁摘要（`allowUnusedPatches` 默认关闭，版本一动安装即失败——这是刻意的：宁可安装失败，
  也不要补丁静默失效后跑在没有回退路径的代码上）；② **上游修复仍是首选**，本补丁是过渡手段。
  另外，**自检现在能直接报出这一层**：`hardlink` 探针（见 P0-2）建链失败即报 `fail` + `HARDLINK_DENIED`，
  不必再靠手工 `ln` 才能确证「这台设备上硬链接不可用」。
- **状态**：**已修（过渡补丁）**。提交 `507ab2a`；CI 绿（run `34965336685`）——该 run 里
  `Prepare dsh runtime for linux/arm64`（真实 rootfs 内安装）、`Runtime packaging self-check`、
  `Script tests (node --test)` 与 APK 构建 + 单测全部成功，因此补丁在真实安装流程中被接受
  （版本键不匹配时 frozen 安装会直接失败，这正是该通道的自检方式）。
  **尚未真机复测**：访客内 `write` 工具能否新建文件、`pnpm add` 后 link count 是否仍为 1，
  都要按 `docs/mobile-acceptance-checklist.md` 在设备上复核后才算闭环。
  归因不变：**触发方（PRoot / 主机策略拒绝 `link(2)`）没有修，只是我们这边补上了回退路径。**

### P0-2 附件持久化全废（P0-1 的同一根因）

- **现象**：`read_image` 与 `mobile_device_screenshot` 均报 `Unable to persist attachment.`。
- **真机证据**：截图 base64 **已通过插件校验**（PNG 签名正确）才进入 `saveImage`，说明 Shizuku 侧成功、
  失败在落盘；`dsh-attachment-local.publishStagedObject()` 用 `link()` 发布对象 ⇒ 与 P0-1 同一根因。
  早期版本中「截图取回成功但落盘失败」已归入本条。
- **归属判定**：同 P0-1（发布路径用 `link()`）。**另记一条自检盲区，归属我们的代码（代码侧已核实）**：
  应用内「运行时自检」的附件项只做 `open + write + unlink`
  （`android/app/src/main/assets/support/runtime-self-check.cjs` 的 `writable()`：`fs.openSync(probe,'wx',0o600)`
  → `writeFileSync` → `unlinkSync`，`checkAttachments()` 只调用它），**从不尝试硬链接**，
  因此 `attachments=ok` 只证明「这个目录能创建小文件」，**不能作为「附件链路正常」的正面证据**；
  它掩盖了真实失败。**该盲区已实现修补**：自检新增第十项 `hardlink`（`shell → node → sandbox_launcher
  → sandbox_probe → sandbox_exec → pty → pty_sandbox → dsh_home → attachments → hardlink → rg`），
  在访客数据目录 `/root/.dsh` 里独占创建一个小文件（`wx`、0600）→ `fs.linkSync(源, 链接名)` → 清理两个文件；
  能建链报 `ok`，被拒报 `fail` + 受控码 `HARDLINK_DENIED`（不把 errno 文本带回上层）。
  `HARDLINK_DENIED` 覆盖 `EACCES` / `EPERM`（本机 PRoot / 内核策略一律拒绝，同目录与跨目录都是它）
  **以及 `EXDEV`**：后者含义不同 —— 它是**跨设备**（源与链接不在同一文件系统），与权限无关；
  但两者对上层是同一个结论「硬链接在这个环境里不可用」，因此共用同一个码。
- **修法（已落地，两条发布路径的回退方式刻意不同）**：自检增加 `hardlink` 探针（新建 + 删除一个硬链接，
  失败时以受控码如实报出，而不是并入 `attachments` 的 `ok`）——**探针已落地**（见上）。
  发布路径由 `patches/@deepseek-ai__dsh-attachment-local@0.1.5-rc.2.patch` 覆盖，**两条都补了**，
  但方式必须不同（照抄会出错，评审时专门确认过这一点）：
  - `publishStagedObject()`（被 `publishImmutableObject()` / `publishImmutableObjectStream()`
    经 `stageImmutableObject()` 调用；**图片与截图的落盘链路走这支**）→
    `isLinkUnavailableError()` + `renameStagedObject()`：暂存名是一次性的，`rename` 搬走正好。
  - `publishImmutableAlias()`（调用方是 `saveFileVerbatim()` 与 `saveFileStreamVerbatim()`，
    即**通用文件附件的只读别名发布**）→ `copyImmutableAlias()`：这里 `source` 是**内容寻址对象**
    （`fileObjects/<前两位>/<sha256>`），`rename` 会把对象库里那条记录本身搬走、破坏其它引用，
    **因此只能复制**。不可变性改由**写后摘要复核**保证（目标字节必须等于声明的 `sha256`），
    而不是由「共享同一个 inode」保证；半途失败留下的残片必须删除，否则下一次重试会看到已存在的目标、
    报 `ATTACHMENT_CORRUPT`，把「写失败」伪装成「存储损坏」。
  - **代价（不掩饰）**：复制路径下同一份字节占两份盘（`link` 可用时占一份）。这不是等价替换，
    是「可写优先」的有意识取舍——`link(2)` 被整体拒绝的设备上，二者只能选一个。
- **状态**：**已修**（提交 `507ab2a` 补对象发布、本次补别名发布；CI 绿）。
  **自检探针已实现**：访客脚本新增 `checkHardlink()`，原生侧 `RuntimeSelfCheckPolicy` 白名单加入 `hardlink`
  → `HARDLINK_DENIED=fail`，界面为此给出结论与下一步（「硬链接（原子写入的前提）」）。
  **尚未真机复测**：图片 / 截图与通用文件附件各走一次、以及复制路径在大文件上的耗时，
  都要与 P0-1 一起在同一台设备上验（同一根因）。

### P0-3 `workspace-write` 在本机完全不可执行

- **现象**：任何 `workspace-write` 命令直接失败，报
  `sandbox mode "workspace-write" is requested but no sandbox backend is usable on this host ...`。
- **真机证据（自检实测结果，可直接引用）**：`sandbox_launcher=ok`、`sandbox_probe=PROBE_UNUSABLE`、
  `sandbox_exec=EXEC_LAUNCHER_FAILED`、`pty_sandbox=PTY_EXIT_EARLY`；其余项
  （`shell` / `node` / 裸 `pty` / `dsh_home` / `attachments` / `rg`）全部 `ok`。
- **归属判定**：**ROM / 内核**（Android 内核无 bwrap，Landlock 启动器探测失败）叠加 **dsh 侧 fail-closed**。
  **已确证**，不需要再改沙箱策略去「先让它能跑」。
- **拟修法**：本机明确降级 `danger-full-access`，或在启动前给出前置报错；界面不要把
  `workspace-write` 描述为当前设备上的安全能力。
- **状态**：已确证；用户已手动切到 `danger-full-access` 绕过（与 `docs/项目状态.md` 中「不要为让它能跑
  而改沙箱策略」的既有约定不冲突：这里是**如实降级并说明**，不是掩盖失败）。

### P0-4 访客 `/etc/hosts` 为空 → `localhost` 无法解析

- **现象**：访客内 `cat /etc/hosts` 为 **0 字节**；`dns.lookup('localhost')` → `ENOTFOUND`（`127.0.0.1` 正常）；
  `pnpm test`（vitest）启动即失败。
- **真机证据**：见上（0 字节 `/etc/hosts`、`ENOTFOUND`）。
- **归属判定**：**我们的代码（rootfs 镜像没写、启动期也没绑定）**。报告称「全仓检索确认没有任何代码写
  `/etc/hosts`」，当时在代码侧复核成立：全仓对 `/etc/hosts` 的写入点**检索 0 命中**，而 `/etc/resolv.conf`
  确实是运行期由 App 绑定的（`RuntimeLaunchResolver.kt` 绑定到 `store.resolverFile`，
  即 `RuntimeStore.kt` 的 `filesDir/runtime-resolv.conf`）。**也就是说：镜像里 `/etc/hosts` 是空文件、
  而启动期只绑了 `resolv.conf`，没人给 `localhost` 兜底**——现象与这一点完全吻合。
  原先因为「修法两条路线未定」而记作待确认，现在路线已定并落地（见下）。
- **修法（已落地，选的是运行期绑定）**：新增 `RuntimeDns.kt`——启动前从 `ConnectivityManager` 取 DNS
  并校验字符集，取不到时回落固定地址，写入 `RuntimeStore.hostsFile`（`filesDir/runtime-hosts`）后
  由 `RuntimeLaunchResolver` 绑定到 `/etc/hosts`（`RuntimeDns.refreshHosts` 调用点与绑定同处一个
  启动解析流程）。**没有选构建期写入**：`/etc/hosts` 的内容与设备网络环境相关，写死在镜像里
  既无法随网络变化，也会让「同一个镜像在不同设备上行为不同」这件事藏进构建产物里。
- **状态**：**已实现**（提交 `0acf3a4`）；**待真机验收**——访客内 `dns.lookup('localhost')` 应能解析，
  `pnpm test` 不应再因它启动即失败。

### P0-5 工作区不在保留白名单（升级即静默丢失）

- **现象**：运行时升级后工作区（`/root/1`）内容消失，且升级对话框没有提示。
- **真机证据**：`RuntimePreservePolicy` 的 `PRESERVED_NAMES = sessions / settings.yaml / .credentials.yaml /
  attachments / skills`，外加 `plugin-manager`；**`/root/1` 两个列表都不在**，且实测**不是挂载点**
  （`mountinfo` 命中 0）⇒ 随旧 rootfs 一起删除。现有验收只覆盖「会话与插件仍在」，未覆盖工作区文件。
- **归属判定**：**我们的代码**（代码侧已核实：
  `android/app/src/main/java/io/deepseekharness/mobile/runtime/RuntimePreservePolicy.kt:30-59`，
  白名单为扁平名字 `sessions` / `settings.yaml` / `.credentials.yaml` / `attachments` / `skills`
  加上 `PRESERVED_OUTSIDE_HOME` 里的 `plugin-manager → root/.dsh-mobile/plugin-manager`；
  `/root/1` 不在其中，也不在任何绑定点里）。
- **合并一条同源问题（必须一起处理）**：经 `dsh plugin add` 装进 `root/.dsh/profiles` 的插件**同样不在保留名单**，
  因此 App 更新对话框里「**你安装的插件会保留**」这句文案（`src/App.tsx:733`、`src/App.tsx:2092`，
  契约测试 `src/App.test.tsx:171` 固定了这句）对**终端里装的插件是失实的**。
  注意这里不能简单地「把 `profiles` 加进白名单」：`RuntimePreservePolicy.kt:61-80` 明确把 `profiles`
  列为**不保留**，理由是 `profiles/node_modules` 是指向旧 rootfs 的符号链接、`profiles/web` 是按旧 dsh 版本
  生成的产物，整体搬运会同时造成悬空符号链接与新旧两套运行时模块并存（即 Symbol 身份分裂的同一类故障）。
  于是三件事必须**一起改才自洽**：**扩白名单**（含 `profiles` 的可行形态：记录终端安装的包名并在新运行时
  重装，而不是搬运目录）/ **收窄文案**（把「你安装的插件会保留」限定为 App 托管的插件）/ **补验收**。
- **修法（工作区那一半已落地）**：把工作区纳入保留策略——**已实现**：`RuntimePreservePolicy` 的
  `PRESERVED_OUTSIDE_HOME` 现有两项，`"plugin-manager" to "root/.dsh-mobile/plugin-manager"` 与
  `"workspace" to "root/1"`，即工作区随运行时升级保留，且原样留在应用内私有存储。
  剩下的**插件那一半仍未做**，做法与工作区不同（不能搬目录，要按包名重装），见上一条的「三件事必须一起改」。
- **状态**：**部分已修**——工作区保留已实现（提交 `0acf3a4`，**待真机验收**：升级前后 `/root/1` 内容应一致）；
  **文案已收窄**（本次）：两处更新对话框不再笼统承诺「你安装的插件会保留」，改成
  「……默认工作区，以及**在应用内安装的**插件会保留。**在终端里用 `dsh plugin add` 装进运行时的插件
  不会保留，更新后需要重装**」；`src/App.test.tsx` 里同时钉住这句限定，防止被改回去。
  **仍未做**：`profiles` 仍未纳入任何可行的保留形态（正确做法是记录终端安装的包名、
  在新运行时里重装，而不是搬目录）——**文案收窄只是不再说谎，不等于问题解决**。
  **投递区不解决这一条**：投递区只管搬运，工作区本身仍在 rootfs 内。

### P0-6 密钥明文出现在 `proot` argv

- **现象**：`/proc/<pid>/cmdline` 含 `DEEPSEEK_API_KEY`、`DSH_DEVICE_BRIDGE_TOKEN`、`DSH_MOBILE_AUTH_TOKEN`。
- **真机证据**：`ps -eo pid,args | grep -c DEEPSEEK_API_KEY` = **3**。
- **归属判定**：**我们的代码**（App 通过 PRoot 参数注入凭据）。代码侧已核实：
  `android/app/src/main/java/io/deepseekharness/mobile/runtime/RuntimeCommand.kt:67-95` 在
  `/usr/bin/env -i` 之后把 `HOME=...`、`<PROVIDER>_API_KEY=<明文>`、`DSH_DEVICE_BRIDGE_TOKEN=<明文>`、
  `DSH_MOBILE_AUTH_TOKEN=<明文>` 逐个作为**参数**追加到 proot 的 argv；宿主进程（即 proot 进程）的
  命令行因此全程携带这些取值。比 `docs/设备桥信任边界.md` 已记录的 environ 风险**更外露**：
  同 uid 的访客进程、普通 `ps` 即可见；会被 **bugreport / ANR / 厂商诊断**采集；密钥在整个进程生命周期
  驻留命令行（`RuntimeSupervisor.kt:202` 已有的 `CREDENTIALS count` 诊断只记条数，能帮助区分
  「App 未注入」与「dsh 未使用」，但不降低暴露面）。
- **修法（已落地）**：取值不再进 argv，两条投递路径都只让 argv 出现**路径**：
  - 模型凭据并写 dsh 自己的凭据文档 `~/.dsh/.credentials.yaml`（已在保留白名单内）。
    pinned dsh 的 `@deepseek-ai/dsh-credentials-local` 分层是「继承的进程环境 > 该文档 > `.env`」，
    因此**不设同名环境变量**时 dsh 就按凭据 seam 从文档解析；原生侧以 0600 + 目录 0700 +
    临时文件 fsync 后 rename 写入，只并写 `refs` 段、逐行保留 `records` 与注释，写盘前重新解析比对。
    这同时修掉了「App 注入环境变量 → dsh 把该引用判为只读 → 模型页保存同一把 key 失败」的既有症状。
  - `DSH_MOBILE_AUTH_TOKEN` / `DSH_DEVICE_BRIDGE_TOKEN` 写进访客内 0600 环境文件
    `/root/.dsh-mobile/runtime-secrets.env`，由入口前一层固定的 `sh -c` 包装 `source` 后 `exec`；
    argv 只留该路径，每次启动整份重写、停止运行环境时删除。
  - 凭据文档不可安全编辑时模型凭据**回落**到同一个环境文件（功能不变、argv 形态相同）。
  - 回归防线：`RuntimeCommandSecretTest` 用哨兵取值断言「构造出来的 argv 不含任何密钥取值」，
    并断言 argv 里不出现 `API_KEY=` / `TOKEN=` 这类赋值形态。
  - 残留边界（含「临时令牌短暂落盘」的取舍与清理时机）见 `docs/设备桥信任边界.md`
    的「凭据从 argv 迁出」一节；**同 uid 的访客进程仍能读到凭据这一根本约束没有消失**。
- **状态**：**已修复**（代码 + 文档）；真机验收按 `docs/mobile-acceptance-checklist.md` 的 R8 复核
  （`ps -eo pid,args | grep -c DEEPSEEK_API_KEY` 与 `... grep -c DSH_MOBILE_AUTH_TOKEN` 都应为 0）。
  **轮换已暴露的 key 仍是当前最高优先级动作，且属用户的人工动作，不由本次代码修复代劳。**

## 四、待办：外置投递区（mailbox）

> **状态：已实现**（App 侧代码落地）。落地口径、限额与边界见 §4.7；用法说明另见
> `docs/投递区.md`。§4.6 的验收项**仍是真机项**，未在真机上跑过之前保持未勾选。

### 4.1 设计前提

**工作区始终留在应用内**：保住 POSIX 语义与 I/O 性能，同时让工作区保持私有（不落到公共存储）。
**可访问性完全由投递区承担**——用户从手机侧访问文件不走工作区，而是走投递区。

```
手机侧（随时可访问）                              访客内（固定挂载点）
/storage/emulated/0/Documents/DSH/inbox    →   /mnt/inbox     用户放 tar 给 Agent
/storage/emulated/0/Documents/DSH/outbox   ←   /mnt/outbox    App 放 tar + manifest 给用户
工作区 <currentRoot>/root/1（私有 f2fs，保持不动）
```

实现使用 `/storage/emulated/0` 而**不是** `/sdcard`：后者是符号链接，PRoot 的绑定源必须是
解析后的真实路径（`RuntimeMailboxLayout.PUBLIC_DOCUMENTS`）。原设计里的 `/sdcard/...` 只是
用户视角的等价写法，实际绑定源以本条为准。

### 4.2 实测结论（决定实现方式）

- **tar 往返完全保真**：执行位与符号链接都保留——这是「结构化内容一律走 tar」的依据。
- **`write` 工具写投递区 EACCES**：投递区不能被 `write` 工具写；bash `cp` / 重定向正常。
- 安装目标（profile 目录）在 f2fs，pnpm 需要的符号链接建在 f2fs 上（实测正常）；从 FUSE 路径直接安装
  未实测，实践上先 `cp` 进私有区再装更稳。

**实现状态（2026-09 落地）**：上面三条实测结论**没有改变**，且第 1 条被本实现**刻意保留**——
投递区仍然不是工作区、仍然不能被 `write` 工具写（这是验收判据，不是缺陷）。本次落地的是
§4.4 的 App 侧搬运链路：Kotlin 侧 `RuntimeMailbox` / `RuntimeMailboxPolicy` /
`RuntimeMailboxArchive`，桥方法 `mailboxState` / `importMailbox` / `exportMailbox`，
界面在「运行与后台」的「投递区」区块；口径细节见 §4.7。


### 4.3 四条约束

1. **投递区不能用 `write` 工具写**（实测 EACCES），只能由 bash / App 侧搬运。
2. **结构化内容一律走 tar**：散文件 `cp` 会丢符号链接 / FIFO / 执行位。
3. **导入全程 NoFollow + 拒绝 `..` 逃逸**：防 symlink 钓出私有区。报告在此引用了「§5.5 有先例」，
   但 §5.5「其他候选」列的是任务通知、小组件、剪贴板等条目，**看不到对应的先例**（该交叉引用**待确认**）。
   仓库内可核实的同类先例是另一处：`SafeRootfsExtractor` 的 rootfs 解压——绝对符号链接被改写为暂存根内的
   相对链接，规范化后逃出暂存根的相对链接一律拒绝，tar 硬链接推迟到常规条目解压完成后、且只允许指向
   暂存根内 NoFollow 的常规文件（`android/README.md:29`）。投递区导入建议直接复用这套判定。
4. **只做批量搬运**，不要把它当工作区使用（它不是工作区，也不承担保留语义）。

### 4.4 App 侧自动化

- 一键 inbox → 工作区；一键工作区 / 产物 → outbox。
- 结构化导出用 **tar + `manifest.json` + sha256**：`manifest.json` 列出条目与摘要，导入端逐条校验，
  **摘要不符时报错，不做部分导入**。
- 可选新文件通知。
- 挂载落点：访客内固定 `/mnt/inbox`、`/mnt/outbox`；宿主侧为 `/sdcard/Documents/DSH/{inbox,outbox}`。
  实现上属于运行期绑定（与 `/etc/resolv.conf`、`/sdcard` 同一条链路，
  见 `RuntimeLaunchResolver` 的 `bindMounts`），需同时决定是否保留现有的「`/sdcard` 整体绑定」。

### 4.5 分层与降级

- **无存储权限时降级 T0（控制台上传）**：投递区不可用是**预期降级**，不是故障；界面要如实说明，
  且不影响 Harness 启动。
- 多目录（≤8 个挂 `/mnt/<slug>`）后续扩展——与 `docs/项目状态.md` 的「**访客可见目录收紧**（≤8 目录）」
  是同一条实现的两种用途（投递区是其中固定的两项）。

### 4.6 验收标准（可勾选）

- [ ] 访客内 `ls -la /mnt/inbox /mnt/outbox` 指向手机侧 `/storage/emulated/0/Documents/DSH/inbox` / `outbox`；
      手机侧新增文件在访客内可见，访客内新增文件在手机侧可见。
- [ ] **tar 往返保真（正向）**：手机侧放一个 `0755` 脚本与一个符号链接 → 导入工作区后 `stat` 显示
      权限位仍为 `0755`、符号链接仍是链接（不是被跟随后的实体文件）。
- [ ] **tar 往返保真（反向）**：工作区打 tar 导出到 outbox，在手机侧解压后执行位与符号链接同样保留。
- [ ] **负向断言**：`write` 工具写 `/mnt/inbox` / `/mnt/outbox` **失败**并给出受控错误
      （这是「投递区不是工作区」的判据，不能因为「能写」而当成改进）。
- [ ] **导入安全门**：构造含 `../` 条目或指向私有区（如 `/root/.dsh`）的符号链接的 tar →
      导入被拒绝，且访客内**不产生任何改动**（NoFollow 生效，不跟随链接写出去）。
- [ ] **摘要校验**：`manifest.json` 条目数与 sha256 与源侧逐一核对一致；人为改一个字节后导入必须报错，
      且不出现「导了一半」的中间状态。
- [ ] **未带 manifest 的内容**：给 App 一个散文件或非 tar 内容时行为明确（按 §5.2 的落点语义处理，
      或明确报错），**不静默写进工作区**。本轮口径：非 tar 内容报 `MAILBOX_INPUT_NOT_TAR`，
      只有散文件时报 `MAILBOX_INPUT_INVALID`，两者都不写工作区。
- [ ] **无存储权限**：界面落到 T0（控制台上传）并说明投递区不可用；Harness 仍能启动与对话。
- [ ] **运行时更新后**：投递区挂载点仍在，inbox / outbox 内文件不受影响（它们在应用外）。
- [ ] **私有性未回退**：工作区仍在应用内私有目录，没有被搬到 `/sdcard`；P0-5 的保留策略独立生效。

### 4.7 实现口径（本轮落地）

落地代码：`RuntimeMailbox`（门面：状态、权限、绑定、编排）、`RuntimeMailboxPolicy`（纯路径与
链接判定、限额、错误码）、`RuntimeMailboxArchive`（tar 读写、manifest、树操作）。绑定追加点仍在
`RuntimeLaunchResolver`，**没有**改动凭据注入路径（P0-6 的修复在另一处，两者只在 `buildLaunch`
的参数列表上相邻）。

**路径与绑定**

| 位置 | 值 |
|---|---|
| 用户可见目录 | `/storage/emulated/0/Documents/DSH/{inbox,outbox}`（`DSH` 及其两个子目录由 App 创建） |
| 访客内挂载点 | `/mnt/inbox`、`/mnt/outbox` |
| 导入落点 | `<工作区>/mailbox-import/`（整个目录被整体替换） |
| 导出产物（固定名，在 outbox） | `dsh-workspace.tar`、`dsh-workspace.manifest.json`、`dsh-workspace.tar.sha256` |

绑定分支只有两条，都在 `RuntimeLaunchResolver.preferredProfile()`：宿主目录确实可访问
（已授予「所有文件访问」且 `DSH/{inbox,outbox}` 是真实目录、可读写可进入、写探测通过）时追加
两个 `ProotBindMount`；**否则一个都不追加**——绑定一个不存在的宿主路径会让 PRoot 直接起不来，
比「投递区不可用」严重得多。可用性变化会进 `profileKey`，缓存档随之失效并重新探测。
`prootProfileFallbacks` 把这两个绑定与 `/sdcard` 一样当作**可选绑定**：PRoot 因它们失败时整体撤掉，
可选能力不拖垮会话启动。

**导入语义**：inbox → 工作区。输入选择是确定性的——优先取 `dsh-workspace.tar`，否则要求 inbox 里
恰好只有一个 `.tar`，否则明确报错（不猜、不按时间挑）；散文件与其它类型**一律不导入**，只计入
「被忽略的散文件数」。同名 `*.manifest.json` / `*.sha256` 存在时逐条校验，**不符即整单拒绝**。
校验分两步：先只读地规划（校验全部条目并逐个算 sha256），再解包到应用私有暂存目录，最后整体
改名替换 `mailbox-import/`；失败时暂存目录整树删除，落点保持原样。

**导出语义**：整个工作区（或指定的相对子目录）→ outbox 的 tar + manifest + sha256。条目名按
字典序排序，权限位、uid/gid、时间戳显式给定，因此**同一棵未改动的工作区连续导出两次得到相同的
sha256**。manifest 只写相对路径：每条含 `path` / `type` / `bytes`（常规文件另含 `sha256`，
符号链接另含落点内的相对 `target`），另有 `format` / `subdirectory` / `entryCount` / `totalBytes` /
`tarName` / `tarBytes` / `tarSha256` / `skipped`；tar 自身的 sha256 同时写进 manifest 的
`tarSha256` 字段与 `dsh-workspace.tar.sha256`（内容是 `<sha256>  dsh-workspace.tar`）。
三个产物先各自写临时文件，全部成功后才逐个改名；改名之前还有一道**导出自证**——把刚写出的归档
重新读一遍，用同一份 manifest 逐条比对，工作区在扫描与写盘之间被改动时在这里失败并丢弃临时产物。

**限额**（超限一律明确报错，不截断、不部分导入）：条目数 ≤ 20000；内容总字节 ≤ 512 MiB；
单文件 ≤ 256 MiB；归档自身 ≤ 512 MiB；条目路径 ≤ 240 字符、≤ 32 层、单段 ≤ 255 字符。

**安全判定**：条目名拒绝绝对路径、`..`、`.` 分段、空段、反斜杠、NUL/CR/LF；符号链接**一律拒绝
绝对目标**（比 `SafeRootfsExtractor` 的「改写为根内相对链接」更严——用户投来的 tar 没有保留绝对
链接的正当需求，而绝对链接正是把 `/root/.dsh` 这类私有区钓出落点的手段，§4.6 的 R2 按拒绝判定），
相对目标规范化后必须仍在落点内；硬链接按**内容复制**落地（本机 `link(2)` 被拒，见 P0-1），
不做 `link` 调用；FIFO、设备节点、稀疏文件一律拒绝。解包顺序固定为「目录 → 常规文件 → 硬链接 →
符号链接 → 目录权限」，写入期不存在任何链接。

**P0-1 / P0-2 未修带来的约束（仍然成立）**

1. **投递区不能用 dsh 的 `write` 工具写**（实测 EACCES）：本实现**不去修**它，搬运只走 App 侧
   按钮与此处的 tar 通道。它仍是「投递区不是工作区」的判据（R3）。
2. **硬链接在访客内一律被拒**：所以导入侧把硬链接条目落成内容副本，导出侧把工作区里的硬链接
   按常规文件导出（tar 里不会出现 `LF_LINK` 条目）。
3. **投递区不在运行时保留白名单内**（`RuntimePreservePolicy`）：它在应用私有存储之外，运行时
   更新本来就不会碰它，因此**不需要**进白名单；工作区仍在白名单内，两条策略互不影响。
4. 设备拒绝 App 创建符号链接时（部分 ROM 的 SELinux 策略），导入含符号链接的条目会以受控错误
   `MAILBOX_LINK_UNSUPPORTED` **失败并回滚**，不降级成复制——降级会让「符号链接仍是链接」这条
   验收判据失真。这一支只能在真机上验证（见 §4.6）。

### 5.7 明细：内置 Git 与网络工具链（**正在实施**）

- **现状（实测）**：`git` 缺失；`curl` / `openssl` / `ssh` **全无**；`libcurl`、`libexpat` **缺失**
  （`libpcre2` / `libz` / `libssl` 有）；`/etc/ssl/certs` **0 个文件**——所以即使补上 git 二进制，
  HTTPS 也会先在证书校验上失败。`dpkg` / `apt-get` 存在但无包列表，且 PRoot 内 apt 可用性未验证。
- **最小组件集与代价**：

  | 组件 | 作用 | 约 |
  |---|---|---|
  | `git`（去 man/doc 的精简装） | CLI 本体 | 12–20 MB（完整含 perl 版 35–45 MB） |
  | `libcurl4` / `libcurl3-gnutls` + 依赖 | `git-remote-https` 走 HTTPS | ~2 MB |
  | `libexpat1` | libcurl 依赖 | ~0.2 MB |
  | `ca-certificates` | HTTPS 证书链 | ~1 MB |
  | `openssh-client`（可选） | SSH 远端 | ~5 MB |
  | `curl`（建议顺手加） | Agent 通用网络能力 | ~1 MB |

  合计 **20–30 MB**，可由已识别的 350–400 MB 裁剪空间完全抵消（见 §六）。
- **三个坑**：① **执行位**——项目有 D3 前科（`0644` 导致 `rg` / `landlock-run` 不可执行）；git 还需覆盖
  `/usr/lib/git-core/*`（`git-remote-https`、`git-credential-*`），并纳入 `verify-bundle.py` 的
  「存在 + 0755 + 非空 ARM64 ELF」校验。② **CA 证书**：不加 `ca-certificates` 等于没加 git。
  ③ **凭据模型**：单 uid 下 guest 内的 token / SSH key 可被同 uid 代码读取（与 P0-6 同类）→ **不预置凭据**；
  需要 push 时由 App 临时写 0600 文件、用后清除；明确禁止 `credential.helper store`（明文落盘）。
- **为什么值得**：① 编码 Agent 没有 git 就无法 clone / diff / commit / branch；② 插件生态已假设它有——
  `dsh-web-all` 内含 `@linxin666/dsh-client-ui-git-graph`，缺 git 时该插件无法工作；③ 替代路径不划算——
  `apt install git` 在 PRoot 下未验证（postinst + 无 CA 双坑），`isomorphic-git` 替代不了 CLI。
- **落地与验收**：`build-embedded-runtime.py` 增加「网络工具」组件组；`verify-bundle.py` 扩展执行位校验；
  做成**可选组件**（与已有「远程运行时源」机制一致）；真机验收 `git --version` → clone 公共仓库 → commit →
  `git-graph` 插件出图。
- **许可证要求（不可省）**：新增二进制进入 `assets/legal/` 与 `THIRD_PARTY_NOTICES.md`；
  GPL-2.0 / GPL-3.0 / AGPL-3.0 / LGPL-3.0 的完整文本与对应源码获取方式按 `docs/RELEASE_CHECKLIST.md`
  的既有口径执行——**「写了一句声明」不等于满足全文要求**。

## 六、容易被忽略、但将来会用到的实测事实

### 6.1 存储账本（实测 898 MB）

| 目录 | 大小 | 说明 |
|---|---|---|
| `/opt/python` | **255 MB** | Python 3.13.5；不在 PATH，但 `mobile-session-publish.py` 与 `dsh-mobile-auth.cjs` 引用 |
| `/opt/dsh` | **315 MB** | node_modules；含 pnpm 自身 37 MB、sharp 18、openai 17、google 14、anthropic 14 |
| `/opt/node` | 201 MB | Node 24（含 npm 18） |
| `/usr` | 106 MB | Ubuntu base |
| 其他 | ~20 MB | `/tmp` 15 + `/var` 4.8 |

- **可回收**：strip sourcemaps（实测 **4,507 个 / 37 MB**）、按 provider 裁剪 SDK、移除捆绑 pnpm（37 MB）、
  Python 瘦身（idle / pip / pydoc / tests）。粗估可省 **350–400 MB**——这笔预算正好用来支付 §5.7 的
  Git 与网络工具链（20–30 MB），**净占用仍会下降**。
- **测量边界**：以上仅为访客内 rootfs；APK、下载的 rootfs 包、WebView 缓存、App 数据都在宿主侧，
  访客看不到 ⇒ **App 总占用更高**，不能把 898 MB 当作应用体积。

### 6.2 插件安装、注册与卸载（终端内操作，先停运行时）

- **三步缺一不可**：① `dsh plugin --profile web add <包> --ignore-scripts` 把包装上；
  ② 把包名加进 `dsh.profile.bundles`（**不加不加载**）；③ 重启 Harness。
- **`--dump-config` 预检有效**：`dsh --profile web --dump-config` **不启动即可**报出无法解析的 bundle
  （实测 exit=1 并点名）——这一步应作为安装流程的固定环节。
- **卸载顺序不能反**：**先从 `dsh.profile.bundles` 移除，再 `dsh plugin --profile web remove`**。
  顺序反了会报 `cannot resolve profile bundle` 且 Harness 起不来（可恢复，删掉那行即可）。
- **最常见的失败不是网络，而是漏注册**：表现为 Harness 起不来并点名 `cannot resolve profile bundle`。
- **生效范围**：只需重启 Harness；Ubuntu 终端不用管（同一 rootfs 上的 shell，且停止运行时本就会一并关闭）。
  启动前 App 会跑 `repair`（把插件内 `@deepseek-ai/*` 副本改链成运行时单例）+ 模块图探测。
- **保留边界**：`root/.dsh-mobile/plugin-manager` **保留**；`root/.dsh/profiles` **不保留** ⇒
  `dsh plugin add` 装进 profile 的包会在运行时升级后消失，需重装（这一条与 P0-5 的文案口径绑定）。
- **App 界面不能装新插件**：桥接只开放 `list / enable / child / update`；「禁用」只写启动补丁
  `launcher-plugins.patch.json`，**不是卸载**；仓库文档无卸载口径。

### 6.3 从手机本地导入插件（实测）

| 来源 | 能否直接装 | 说明 |
|---|---|---|
| npm registry 包名 | ✅ | `dsh plugin --profile web add <包名> --ignore-scripts` |
| **本地 `.tgz`**（GitHub Release 资产 / `npm pack` 产物） | ✅ **实测通过** | `pnpm add xxx.tgz --ignore-scripts` → **517 ms** 完成 |
| **GitHub 源码归档**（codeload `tar.gz`） | ⚠️ **pnpm 能装，通常跑不起来** | 实测 pnpm 会自动剥掉顶层目录，装出的结构与 `require.resolve` 都正常；**门槛在构建**：归档一般不含 `lib/`，需 `pnpm install && pnpm build`，而设备上 `--ignore-scripts` 跳过脚本、devDependencies 的原生模块难编译 |
| `git+https://…` 直装 | ❌ | 设备无 `git`（实测 `command not found`） |
| **手动解压拷贝进 profile** | ❌ **禁忌** | 产生第二份 `@deepseek-ai/*` **真实副本** → **Symbol 身份分裂** → 所有工具调用报 `Cannot read properties of undefined (reading 'prepare')` |

- **无 curl / wget / git 时的下载办法**：Node 24 的 `fetch`（把 `<URL>` 换成实际地址）：

  ```sh
  node -e 'fetch(process.argv[1]).then(r=>r.arrayBuffer()).then(b=>require("fs").writeFileSync("/root/dl.tgz",Buffer.from(b)))' '<URL>'
  ```

  `npm pack <包名>` 实测可用（产出 `xxx-1.0.0.tgz`）。
- **投递区可用**：tarball 放 `/sdcard/Download/` 没问题——读取端在 FUSE 上不影响，安装目标（profile 目录）
  在 f2fs，pnpm 需要的符号链接建在 f2fs 上（实测正常）；先 `cp` 进私有区再装更稳。
- **实践建议**：优先选发布方提供的 **npm 包或 Release 里的 `.tgz`**；只有源码归档时，先在别的机器上
  `pnpm install && pnpm build && pnpm pack` 再导入。
- **网络注意**：`/etc/hosts` 为空（P0-4）⇒ 任何解析 `localhost` 的工具会失败；DNS 只来自
  `/etc/resolv.conf` 的 1.1.1.1；需要镜像或代理时用 `pnpm config set registry` 或 `npm_config_registry`。
