# 0.2.6 测试版：修复副屏会话无法启动的回归

基线是 0.2.5（`versionCode 27`）的真机现场：装好之后「目标应用副屏」能打开设置页、能选目标应用，
但点任何一个应用都立刻停在 **「副屏启动失败：请检查 Shizuku 授权、目标应用和设备副屏支持」**。
Shizuku 服务在跑、授权正常、重启 App 与重启用户服务都不改变结果；`dumpsys display` 里只有主屏，
`dumpsys window` 里 `VirtualScreenActivity` 的窗口是 `frame=[0,0-0,0]`、`contentSize=0x0`。

## 改动

- **副屏会话不再因为构造顺序被自己的校验拒绝**：新增的触摸直传在 `ShellVirtualScreen.start()`
  里用 `VirtualScreenInjector.Gesture(id(), w, h)` 建手势，而 `id()` 在显示器创建之前返回 `-1`
  （`display?.display?.displayId ?: -1`）；`Gesture` 的构造函数里那句
  `require(displayId > 0) { "不能向主屏发送副屏输入" }` 于是**在启动阶段就抛
  `IllegalArgumentException`**，被 `start()` 的统一 catch 吞成一句泛化失败文案。修法是把手势持有的
  显示编号改成取值函数（`() -> Int`），**注入那一刻才取编号**：
  - `handle()` 开头 `require(displayId() > 0) { "副屏显示器尚未就绪" }`；
  - `send()` 里编号 ≤ 0 时直接不注入，仍然绝不把事件落到主屏。
  这样显示器创建、释放、会话重启的先后顺序都不会再让启动失败，而「不向主屏注入」这条约束照旧成立。
- **启动失败不再只剩一句泛化提示**：`VirtualScreenService` 的 catch 改成把原生原因（调用方的
  `check`/`require` 文案、也就是 `ShellVirtualScreen` 包装进来的 cause message）显示到界面上，
  没有原因时才退回原来的「请检查 Shizuku 授权、目标应用和设备副屏支持」。这条改动是为了让下次
  真机失败能直接读出卡在哪一步，而不是只能靠 adb 反推。
- 沿用 0.2.5 的运行环境更新修复（清理失败把目录改名挪到 `stale-*` 而不是让安装失败、
  失败步骤写进诊断日志）。
- 上一版内容见 [发布说明-0.2.5.md](发布说明-0.2.5.md) 与 [发布说明-0.2.4.md](发布说明-0.2.4.md)。

## 未解决的设备限制

- 副屏仍然要求 Shizuku 授权与 Android 10 及以上；ROM 或目标应用不支持虚拟显示时依旧会失败，
  区别只是现在界面会给出原生原因。
- 触摸直传（`touchChannel=stream`）依赖隐藏接口 `InputManager.injectInputEvent`，被 ROM 拦掉时
  自动回退到离散的 `input -d <显示编号>` 通道，行为与更早的版本一致。
- 节点树与中文注入仍要求用户手动开启应用的无障碍服务；未开启时 `treeSupported=false`，
  不回退主屏。
