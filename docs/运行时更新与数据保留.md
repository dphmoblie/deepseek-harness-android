# 运行时更新与访客数据保留

## 问题

每次升级运行时（在线更新或安装 APK 内置的新 rootfs），访客里的**全部用户数据都会丢失**：
对话会话、用户自己安装的插件、dsh 配置文件。

成因在 `RuntimeInstaller.promoteStaging()`：

1. `currentRoot`（`noBackupFilesDir/dsh-runtime/current`）改名为 `backupRoot`；
2. 新解压的 `stagingRoot` 改名为 `currentRoot`；
3. **`cleanupIfPresent(store.backupRoot)` 直接删掉旧根目录**。

而 dsh 的用户数据写在访客的 `$DSH_HOME`（即 `/root/.dsh`，对应宿主
`currentRoot/root/.dsh`）里，因此第 3 步等于把用户数据连同旧根目录一起删除。
应用内那句「更新会替换当前 Ubuntu 根目录…未导出的文件将被清除」正是这个行为的描述。

访客数据位置。**每一项都由 dsh 源码确认过出处**（出处一并列出，便于日后核对）：

| 路径 | 内容 | 出处 | 处置 |
| --- | --- | --- | --- |
| `root/.dsh/sessions` | 对话会话 | `scripts/mobile-session-publish.py` 的 `SESSION_ROOT` | 保留 |
| `root/.dsh/settings.yaml` | dsh 设置 | `dsh-settings-file/lib/index.js:32` | 保留 |
| `root/.dsh/.credentials.yaml` | 模型凭据 | `dsh-credentials-local/lib/index.js:49,58` | 保留 |
| `root/.dsh/attachments` | 用户上传的附件 | `dsh-attachment-local/lib/index.js:986` | 保留 |
| `root/.dsh/skills` | 用户技能 | `dsh-skill-filesystem/lib/index.js:172` | 保留 |
| `root/.dsh-mobile/plugin-manager` | 用户安装的插件 | `plugin-manager.cjs:282,756` | 保留（**不在 `$DSH_HOME` 下**） |
| `root/.dsh/profiles` | 指向 rootfs 内包的符号链接，版本绑定 | `dsh-app-boot` 的 profile 逻辑 | 不保留 |
| `root/.dsh/{cache,tmp,logs}` | 运行时缓存、临时文件与日志 | —— | 不保留 |
| `root/.dsh/llm-deepseek` | 远端文件上传缓存 | `dsh-llm-deepseek/lib/index.js:766` | 不保留 |
| `root/.dsh-mobile/launcher-providers.patch.json` | 应用生成的启动配置 | 应用每次启动重新生成 | 不保留 |

### 曾被误列为保留项、已被源码证伪的三项

显式记录在这里，避免它们以「防御性条目」的名义回到白名单：

- `settings.json` —— dsh 的设置文件名是 **`settings.yaml`**（`dsh-settings-file:32`）。
  名字写错导致用户设置从未被保留。
- `$DSH_HOME/plugins` —— **不是 dsh 的路径**。用户安装的插件真实位于
  `root/.dsh-mobile/plugin-manager`；这一项写错导致「每次更新删光用户插件」长期未被发现。
- `$DSH_HOME/projects` —— 同样没有出处。

### 凭据文件的权限位（很容易踩的坑）

`dsh-credentials-local` 会**拒绝读取**权限宽松的凭据文件并直接报错
（`lib/index.js:104`：`is readable beyond its owner (mode ...)`）。
因此保留必须用 `Os.rename`（inode 与权限位原样保留），**绝不能用复制** ——
umask 会把 `0600` 变成 `0644`，反而让 dsh 拒绝启动。

### 未覆盖的边界

跨运行时版本保留 `plugin-manager` 会让插件依赖里指向旧 rootfs 的路径变成**悬空符号链接**
（`.pnpm` 目录名含版本号与 peer 哈希）。这一条由插件侧的「修复动作」负责，
不在保留机制内处理，详见 `docs/项目状态.md`。

## 为什么是白名单，而不是整个 `$DSH_HOME`

`root/.dsh/profiles/node_modules/*` 是**指向 rootfs 内包的符号链接**，
`profiles/web/*` 也是按当前 dsh 版本生成的产物。
把旧版本的 `profiles` 整体搬进新根目录会同时制造两类问题：

- 悬空符号链接（旧 rootfs 已被删除）；
- 新旧两套运行时模块并存 —— 这正是 `docs/ARCHITECTURE.md` 的
  「运行时依赖版本钉与 Symbol 身份」小节所述「同名包出现两份物理副本会让 Symbol 身份不一致」
  的同一类故障。

因此只搬运明确的用户数据，运行时产物一律由新 rootfs 提供。

## 实现约定

1. 新增强制性白名单对象 `RuntimePreservePolicy`（`runtime` 包）。白名单分两部分：

   - `$DSH_HOME` 下的**扁平名字**：`sessions`、`settings.yaml`、`.credentials.yaml`、
     `attachments`、`skills`；
   - 一个**显式完整相对路径**的条目：`plugin-manager` → `root/.dsh-mobile/plugin-manager`，
     因为用户安装的插件不在 `$DSH_HOME` 下，扁平的「`$DSH_HOME` 下名字」模型表达不了。

   任何不在白名单内的名字（含 `../`、绝对路径、含 `/` 的项）一律拒绝。
   白名单条目同时用作 `preserve-<uuid>/` 下的条目名，因此**暂存名必须保持扁平**；
   访客路径由 `guestRelativePath(name)` 单独给出，测试会断言每条路径都落在
   两个声明的访客根（`root/.dsh` 与 `root/.dsh-mobile`）之下。
2. `promoteRuntime()` 在**备份旧根目录之前**把白名单项移出到
   `runtimeParent/preserve-<uuid>/`，提升完成后再移回新根目录的同一相对路径。
   安装与「切回上一版本」共用这一段提升核心，区别只是被提升的源目录不同
   （安装是 `staging-<uuid>/`，切回是 `retained/`）。
3. 回滚路径同样要还原：`rollbackPromotion()` 之后必须把已移出的项放回恢复出来的旧根目录，
   否则「回滚」本身就会造成数据丢失。
4. 回填时的冲突判定必须区分「空壳」与「有内容」，否则会误判：

   - 新根目录**不存在**该同名项 → 直接移入（正常路径）。
   - 新根目录存在一个**空目录** → 视为 rootfs 自带的空壳（镜像很可能预建空的
     `sessions/`、`plugins/` 目录），删除空壳后把用户数据移入。
     若不这样做，每次正常更新都会被判成冲突而失败。
   - 新根目录存在**非空目录或文件** → 判定为真冲突：保留用户数据不动、不覆盖也不删除，
     返回未回填清单并抛 `RUNTIME_PRESERVE_FAILED`；此时**不得删除 `backupRoot`**，
     以便用户排查或人工取回。
5. `recoverInterruptedPromotion()` 在存在遗留 `preserve-*` 目录时，
   不得按「当前与备份都有效」分支删除 `backupRoot`。
6. `resetWorkspace()` 属于用户显式清空运行时，可以一并清理 `preserve-*`。
7. 移动一律用 `Os.rename`（同一私有目录内，避免跨设备拷贝与半途中断）。
8. 迁移失败必须表现为**受控错误码**，不得静默降级。

## 版本保留与一键切回

运行时更新此前是「单向」的：安装成功后旧版本会被删掉，装错了只能重新下载。现在把上一版本留在
磁盘上，并提供「切换到上一版本 / 删除上一版本」两个动作。

1. **换了个名字存**：安装成功后不再删除 `previous*`（`backupRoot` / `backupManifest`），
   而是整体改名为 `retained`（`retainedRoot = runtimeParent/retained`、
   `retainedManifest = runtimeParent/retained-manifest.json`）。
   为什么必须换名字：`previous*` 在恢复逻辑里表示「提升正在进行」——
   `recoverInterruptedPromotion()` 看到它就会前滚或回滚。已完成的版本若留在那个名字下，
   下次启动会被当成中断的安装处理掉。
2. **只保留一份**：解压后的运行时约 778 MB（清单里的 `rootfs.extractedBytes`），
   所以上限就是「当前 + 上一版本」两份，不做 N 份并存。
   再次安装时先删掉旧的 `retained*`，再把 `previous*` 旋转过来；旋转失败**不算安装失败**
   （版本已经装好了），此时只清掉 `retained*`，把 `previous*` 留给下次启动的中断恢复。
3. **切回**：`RuntimeInstaller.switchToRetained()` 复用同一段提升核心
   `promoteRuntime(store.retainedRoot, store.retainedManifest)`：移出白名单用户数据 →
   `current` 改名为 `previous` → `retained` 提升为 `current` → 用户数据回填到新根目录，
   最后把刚离开的那一版旋转成 `retained`。因此可以来回切 A/B，而用户数据每次都跟着走。
4. **谁能做**：切换与删除都与安装共用 `installLock`。安装期间尝试切换会被拒绝
   （`INSTALL_IN_PROGRESS`）；运行环境正在跑时切换会被拒绝（`RUNTIME_BUSY`，与安装同一条判定）。
   删除只动 `retained*`，不碰正在使用的运行时，因此不要求停止运行环境。
5. **崩溃恢复**：`recoverInterruptedPromotion()` 末尾追加 `reconcileRetainedSlot()`——
   `retained*` 只有一半（有根目录没清单，或反过来）时直接删掉：半份副本无法被提升。
6. **界面**：设置首页 →「版本管理」一级页（从「运行与后台」里搬出来独立成页；设置首页搜索框输入
   `回退` / `版本` 也能直接定位）列出三槽（当前使用 / 上一版本 / 随安装包内置），
   每行显示版本号、dsh 版本与占用体积。运行中（`preparing` / `downloading` / `verifying` /
   `extracting` / `running` / `stopping`）禁用切换按钮并说明原因；磁盘上没有上一版本时
   两个按钮都不可用，并提示「安装一次新版本后才会保留」。
7. **dsh 版本口径只有一处**：`RuntimeVersionPolicy.DSH_VERSION`。运行时自检的回执、
   清单里的 `dshVersion` 字段、版本列表都过同一条规则，不匹配一律显示「读不到」，绝不回传原文。

## 远端版本列表（从发布页挑版本安装）

版本管理页新增「可从 GitHub 安装的版本」区块，让用户可以装发布页上的某一版运行时，而不只是
「内置的那一版」或「比当前更新的那一版」。

1. **不自动查询**：进入页面不发起请求，点「检查可用版本」才查。理由写进了代码注释——查一次要打
   GitHub API，未登录时限额很低，进页面就查很容易把限额耗光。
2. **只认带运行时清单的版本**：本次发布页里必须有 `runtime-manifest.json`，且该文件要过
   `RuntimeManifest.parse` 与 `requireHttpsUri(rejectPrivateHost = true)` 两道校验；
   `manifestSha256` 必须是 `sha256:` + 64 位小写十六进制，`manifestUrl` 必须落在本仓库
   `https://github.com/dphmoblie/deepseek-harness-android/releases/download/` 前缀下
   （`runtime/GitHubReleases.kt`）。其余 release 直接跳过，不参与列表。
3. **跳过与上抛分清楚**：只有「清单内容不合格」才跳过该 release；网络、HTTP、TLS 失败一律上抛。
   这条纪律直接决定界面文案：**「查不到可用版本」与「发布页上还没有带运行时清单的版本」是两句
   不同的话**，网络故障绝不能被说成「没有可用版本」。
4. **上限**：最多读 20 个 release（`MAX_RELEASES`），合并后最多 40 个条目（`MAX_ENTRIES`），
   新的在前；单个 url 上限 1024 字符（`MAX_URL_CHARS`）。
5. **不可装的行也要列出来**：缺 `manifestUrl` 或 `manifestSha256` 的条目只展示、不给安装按钮，
   行内说明「这个版本的清单没通过校验，只能查看、不能安装。」——比直接隐藏更好，用户能看出
   发布页上确实有这一版、只是不能装。
6. **安装走同一条路**：从列表安装与内置安装、上次更新共用 `RuntimeInstaller` 与同一把
   `installLock`，因此「保留白名单搬运 → 自动会话快照 → 下载 → 校验 → 切换」的次序完全一致。
   已安装的那一行显示「· 已安装」并禁用按钮。
7. **dsh 版本口径仍只有一处**：`RuntimeVersionPolicy.DSH_VERSION`。清单里没有 `dshVersion` 时
   显示「清单里没有 dsh 版本：安装后以运行环境页显示的为准。」，不回传原文。
8. **下载白名单收窄**：`runtime/RuntimeHttp.kt` 只保留 GitHub 发布页与清单地址，npm registry
   已从白名单删除——版本来源只剩发布页一处。

## 更新前自动会话快照

换镜像时 dsh 版本可能一起变，旧会话有可能读不出来。所以在**安装运行时之前**自动把会话目录
快照一份，版本管理页里有「会话备份」区块可以看、拍、恢复、删除。

1. **快照内容**：会话目录的字节副本。列表每行显示创建时间、文件数、占用字节、拍快照时的 dsh 版本
   与运行时版本（读不到分别显示「dsh 版本未读到」「运行时版本未读到」，绝不显示 `Invalid Date`）。
2. **上限与淘汰**：最多 3 份、合计 512 MiB，超出后**从最旧的一份开始淘汰**，被淘汰的 id 由原生层
   回传（`evictedIds`），界面照实说明「因超出保留上限，淘汰了 N 份最旧的备份」。
3. **恢复是合并回填**：同名文件不覆盖，只补缺失的文件。结果回传 `restoredFileCount` 与
   `skippedFileCount`，界面按有无跳过分两句提示。删除需要二次确认（第一次点只切成「确认删除」）。
4. **安装结果的四态**（`RuntimeInstallResult.autoSnapshot`）：`created`（带 `snapshotId`）、
   `skipped`（没有需要备份的会话数据，带原生 message）、`failed`（受控码 + message，
   **安装本身仍算成功**）、以及旧桥压根不回这个字段（此时不多说一句）。
5. **只在已经装过运行时时才提醒**：首次安装没有会话可丢，弹窗只会挡路。提醒正文明确两件事：
   开始前会自动备份一份；新镜像里的 dsh 版本可能与现在不同，读不出旧会话时可以用那份备份恢复。
6. **能说什么、不能说什么**：备份只解决「会话目录被换掉」，不解决 dsh 自身数据格式的变化。
   因此文案只承诺「多一份可恢复的副本」，不承诺「更新后旧会话一定能用」。

## 验收要点

- 单元测试覆盖 `RuntimePreservePolicy` 的白名单与拒绝路径（含 `../`、绝对路径、嵌套名）。
- 单元测试覆盖 `RuntimeVersionPolicy`（目标参数、按钮可用性、dsh 版本形态）与
  `RuntimeDshVersion`（读不到 / 非 JSON / 超限 / 版本号形态不符一律返回 null）。
- 真机验收：安装 v1 → 建一个对话 → 更新到 v2 → 会话与已装插件仍在。
- 真机验收：更新到 v2 后，设置页「运行时版本管理」里能看到「上一版本 v1」及其 dsh 版本；
  点「切换到上一版本」后当前版本变回 v1，会话/插件/工作区数据不变；再切一次能回到 v2。
- 真机验收：切换后重新打开 Harness，页面用的是新版本的入口（WebView 缓存键带运行时版本）。
- 真机验收：删除上一版本后 `retained/` 与 `retained-manifest.json` 都消失、按钮变为不可用，
  当前运行时的文件不受影响。
- 真机验收：更新过程中断（回滚路径）后，旧会话仍在。
- 真机验收：版本管理页点「检查可用版本」后能列出发布页上带清单的版本；
  断网时提示的是「查不到可用版本」而不是「发布页上还没有带运行时清单的版本」。
- 真机验收：从列表安装某一版 → 安装完成后「会话备份」里多出一条安装前拍的备份，
  恢复它能看到回填数与跳过数。
- 真机验收：应用自身更新（下载 → 校验 → 交给系统安装器）能走通；系统未允许安装未知来源时
  能给出「去系统设置允许安装」的入口。

## 相关但独立的待办

以下两项与运行时更新同属「存储边界」议题，但改动面独立，不并入本次修复：

- **访客可见目录收紧**：当前 `RuntimeLaunchResolver` 里有一条把 `/sdcard` 整体绑定进访客的
  可选绑定；应改为由用户选择多个目录（上限 8 个），分别挂到固定的访客路径
  （`/workspace`、`/mnt/<slug>`），并且只绑定被选中的目录，而不是整个 `/sdcard`。
  SAF 的目录树 URI 不是文件系统路径，需要先映射为真实路径并经用户确认。
- **存储权限 UI**：照片/视频权限的申请入口，以及 Android 11+ 的「所有文件访问」状态与设置页入口
  （低于 Android 11 隐藏该入口）。
